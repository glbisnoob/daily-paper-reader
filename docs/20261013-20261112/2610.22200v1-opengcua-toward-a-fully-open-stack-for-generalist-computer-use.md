## 摘要
计算机使用正迎来一个转折点：关注点正从仅 GUI 交互扩展到通过视觉与程序化接口在用户计算机上完成任务的系统。我们将通用计算机使用智能体（GCUA）定义为一类系统：模型在其中自主选择如何跨视觉与程序化接口进行观察、行动并组织其工作。然而，诸如 GPT-6 Astra 的计算机使用系统等前沿实现仍基本封闭，限制了对某设计的系统研究。我们提出 Open Generalist CUA（OpenGCUA），这是一个持续进行的项目，旨在与社区共同开发并开放 GCUA 的全栈技术。本报告介绍 OpenGCUA 的首个版本。代码执行是我们智能体设计的关键特性：它使中间结果能够决定后续操作，并使模型能够将其已有的编程能力直接应用于计算机交互。我们还提出从执行框架到模型的决策迁移，将选定的观察和任务状态决策从固定的框架规则转移到模型。在 OSWorld-v2 上，我们的完整配置提升了所有八个被评估模型的任务得分，包括 GPT-6 Astra 和 Claude Opus 5；相对于批处理式仅 GUI 执行，平均部分得分提高 +19.6 分，报告的单任务步骤数平均减少 53.0%。我们发布了实现与提示词、来自全部八个模型的评估轨迹，以及真机执行框架和跨设备 SDK 的初步版本。该执行框架应对基准测试未能完全覆盖的真机挑战，而 SDK 则提供跨计算机、移动设备和浏览器的通用编程接口。在我们的真机执行框架下，针对四个真实 macOS 任务，所选 Qwen3.8-Max 运行所报告使用的推理 token 数是 GPT-6 Astra 的 19.4 倍，突显了不同模型在真机执行效率上的显著差异。

## Abstract
Computer use has reached a turning point: the focus is expanding from GUI-only interaction to systems that complete tasks on users' computers through visual and programmatic interfaces. We define a generalist computer-use agent (GCUA) as a system in which the model chooses how to observe, act, and organize its work across visual and programmatic interfaces. Yet frontier implementations, such as GPT-6 Astra's computer-use system, remain largely closed, limiting systematic study of their design. We introduce Open Generalist CUA (OpenGCUA), an ongoing project to develop and open the full stack for GCUAs with the community. This report presents the first release of OpenGCUA. Code execution is a key feature of our agent design: it lets intermediate results determine subsequent operations and enables models to apply their existing programming capabilities directly to computer interaction. We also propose harness-to-model decision transfer, moving selected observations and task-state decisions from fixed harness rules to the model. On OSWorld-v2, our full configuration improves task scores across all eight evaluated models, including GPT-6 Astra and Claude Opus 5, raising mean partial score by +19.6 points and reducing reported steps per task by an average of 53.0% relative to batched GUI-only execution. We release our implementation and prompts, evaluation trajectories from all eight models, and preliminary versions of a real-device harness and a cross-device SDK. The harness addresses real-device challenges not fully captured by benchmarks, while the SDK provides a common programming interface across computers, mobiles and browsers. Across four real macOS tasks under our real-device harness, selected Qwen3.8-Max runs use 19.4 times as many reported reasoning tokens as GPT-6 Astra, highlighting substantial differences between models in real-device execution efficiency.

## 1. 核心问题与研究背景

- **领域转折**：计算机使用智能体（CUA）的研究焦点正从“仅 GUI 的截图—点击”扩展到“视觉交互 + 程序化访问”的混合系统。OpenAI 在 GPT-6 Astra 的文档中已建议用 PyAutoGUI/Playwright 编写短程序，而非主要依赖鼠标键盘工具；OSWorld-v2 上前沿智能体也更多通过代码、API 和文件操作完成任务。
- **概念缺口**：现有 GUI Agent、CLI Agent、多智能体混合系统、GUI+CLI 混合 Agent（如作者此前的 Qwen-UI-Agent）各自固定了部分决策，缺少一个统一视角来刻画“模型自主决定如何观察、行动、组织工作”的系统。
- **开放性问题**：前沿 GCUA 实现（如 GPT-6 Astra 的计算机使用系统）基本闭源，模型权重、完整提示、真机 harness、设备控制 SDK、执行轨迹均不可得，社区难以复现、比较不同设计，也难以研究设计选择对任务完成率与成本的影响。
- **项目目标**：提出 OpenGCUA，一个持续开放 GCUA 全栈的项目，覆盖模型、系统（真机 harness + 跨设备 SDK）、轨迹、效率与评测五个方面。本报告为首个版本，**不包含训练好的模型**。

## 2. 方法论

### 2.1 GCUA 的形式化定义

- 将 GCUA 定义为每步联合做出三个决策的策略 πθ：
  - **(q_t, p_t, m_{t+1}) ~ πθ(· | m_t, o_t)**
  - **观察什么**：q_t ⊆ Q = {screenshot, AX tree}，q_t = ∅ 表示不请求额外视图；CLI/API 输出自动返回。
  - **如何行动**：p_t 是程序，语句调用 A = A_GUI ∪ A_AX ∪ A_CLI ∪ A_API 中的原语，可含循环、分支、变量；单原语调用是最简程序。
  - **如何组织**：m_{t+1} 为更新后的工作状态（计划、进度记录、保留在上下文中的观察）。
- 下一步观察：**o_{t+1} = (e_t, {v_q(s_{t+1})}_{q∈q_t})**，即程序执行输出 e_t 与模型主动请求的视图。
- **四类接口**：GUI（像素坐标）、可访问性树（元素级、无需前台、不移动用户指针）、CLI（文件/数据/软件）、API（外部服务）。每类接口都同时提供观察与行动方式。
- **与已有工作的关系**：GUI Agent 固定 q_t≡{screenshot}、单 GUI 动作、harness 规则；CLI Agent 固定 q_t≡∅、仅 shell 程序；多智能体混合由编排器按子任务分配固定接口；Qwen-UI-Agent 固定每步截图、批量 GUI+CLI 动作序列、固定上下文规则。GCUA 逐项解除这三类约束，因此上述系统均为其特例。

### 2.2 代码执行（Code Execution）

- 模型每步输出一个 `<code>` 块，内含一个 Python 程序；harness 提取、语法检查后在计算机环境中执行。
- OSWorld-v2 配置提供 PyAutoGUI 与 `bash()`；真机 harness 额外提供 Playwright。
- 关键能力：**条件判断、循环、断言/验证**，使中间结果可在同一次模型调用内决定后续操作，无需为每个操作发起新调用。作者将“批量动作”视为“没有控制流的程序”，是过渡形态而非终点。
- 轨迹分析归纳出五类反复出现的代码执行模式：
  1. **跨接口组合**：GUI 点击与文件/应用状态检查交替；
  2. **循环式执行**：一次编写、按运行时目标重复（如遍历 7 个导航项并校验 DOM 状态）；
  3. **结果依赖执行**：程序内比较草稿文本后决定是否点击发送；
  4. **观察准备**：采集 25 个视角并拼成带编号的 contact sheet，供模型下一次视觉判断；
  5. **可执行验证**：断言预期修改发生，同时验证其余 64 个包条目未被改动。

### 2.3 Harness-to-Model 决策转移

- 核心思想：**机制留在 harness，决策交给模型**。harness 负责可靠执行接口调用、保存任务记录、管理上下文；模型决定何时观察、如何记录状态。
- 三个具体机制：
  - **按需观察（screenshot()）**：模型显式请求才在下一轮输入中附带新截图；环境仍每步截图，改变的是“模型收到什么”而非“环境记录什么”。
  - **任务状态台账（todo.update/todo.list）**：支持 pending、attempted、changed_unverified、claimed_verified、blocked 等状态，区分“已执行”与“已验证”；状态是模型自评，不是独立验证。
  - **动作意图（`<intent>`）**：执行前用一句话说明程序目的，便于真机用户理解，不参与 Python 执行。
- **Harness 管理的上下文**：滚动截图缓冲（分批移除旧图，减少对 prompt cache 的破坏）与 micro-compaction（用占位符替换旧工具输出）。这两项保留在 harness 侧。

### 2.4 真机与跨设备系统

- **真机五点挑战**：用户与智能体共享控制权；屏幕持续变化；用户请求在执行中演化；观察与控制需要显式目标（后台窗口/标签页）；任务起始于已有用户环境。
- **跨设备 SDK**：统一编程接口，所有操作绑定到显式资源（设备、应用、窗口、标签页）；`ui.ax` 提供结构化语义观察与元素操作，`ui.vision` 提供图像与坐标操作；观察捕获（`ui.ax.observe()`）与投递（`mu.emit`）分离；平台能力通过 `.android`/`.macos`/`.browser` 命名空间显式声明；`mu.files.copy` 支持跨设备文件转移。
- **真机 harness 五层架构**：Model（生成受保护的 Python 程序）→ Runtime（持久解释器、人在回路）→ Device SDK → Driver（原生机制、元素身份、投递策略）→ 真实应用与 OS。
- **干扰最小化策略**：优先元素级可访问性操作，其次窗口定向坐标输入，最后才前台输入；前台操作前需与用户协调。

## 3. 实验设计

### 3.1 基准与场景

- **主基准**：OSWorld-v2（v2.1）的 **82 任务离线子集**，排除 26 个需联网任务，保留本地 Web 应用与桌面任务。沿用 GPT-6 Astra 发布的评测协议。
- **指标**：部分分（0–100）、全任务成功率（归一化分数 > 0.999999）、每任务步数、每任务输出 token；消融中另报 cache 命中率；成本按公开 API 价格（含缓存折扣）估算。
- **真机场景**：4 个 macOS 任务——工作簿推理、PDF 申根签证表填写、受饮食约束的 Amazon 零食调研、巴黎双酒店比价；最多每任务每模型 3 次运行，报告 5 个配置的选定运行（run 1）。

### 3.2 对比方法

- **主对比**：GUI-only + 批量动作基线 vs. 完整 OpenGCUA（代码执行 + harness-to-model 决策转移），覆盖 8 个模型。
- **接口/执行消融**：单动作 GUI、批量 GUI、批量 GUI+CLI、代码执行四档，3 个模型（Qwen3.8-Max、DeepSeek-V4.1-Flash、GLM-5.3-Flash）。
- **GUI+CLI vs. GCUA**：4 个模型（另加 Claude Opus 5）。
- **Harness 机制消融**：以代码执行为基线，分别加入 screenshot、todo、intent、micro-compaction、滚动截图缓冲及全组合，2 个模型。
- **资源约束分析**：对 8 个模型施加统一货币预算上限与时间上限，绘制“得分—平均花费/时间”曲线。
- **真机案例研究**：GPT-6 Astra 与 Qwen3.8-Max 在相同 harness 下的低努力轨迹对比（观察目标选择、推理开销、任务级代码覆盖）。

### 3.3 公平性设计

- 同一 harness、同一提示、同一任务集；每任务保留“最新一次有评测结果的尝试”，而非最高分尝试。
- 跨模型汇总时每个模型等权：分数增益按点平均，相对资源下降先在模型内计算再平均。
- 真机实验明确声明为“刻画所评估配置”，而非建立通用模型排名。

## 4. 资源与算力

- **论文未报告任何训练算力**：本版本不包含训练模型，作者明确说明模型侧贡献是“用现有模型对智能体设计做实证验证”，而非新训练模型。
- 未提及 GPU 型号、数量、训练时长、参数量或分布式训练配置。
- 计算开销仅体现为**推理侧成本**：按各模型公开 API 价格与缓存折扣估算每任务美元成本；真机实验报告每任务估计成本（如 GPT-6 Astra 约 $18.29/任务，Qwen3.8-Max 约 $1.49/任务，Qwen3.8-Flash 约 $0.120/任务）。
- 时间测量受 API 带宽、限流、并发评测环境数、供应商排队、工具执行延迟影响，作者承认未跨模型控制，仅作探索性证据。

## 5. 实验数量与充分性

### 5.1 规模概览

- 主实验：8 模型 × 2 配置，共 16 组，82 任务。
- 执行方式消融：3 模型 × 4 配置 = 12 组。
- GUI+CLI vs. GCUA：4 模型 × 2 配置 = 8 组。
- Harness 机制消融：2 模型 × 7 配置 = 14 组（部分配置缺 cache 数据）。
- 资源约束曲线：8 模型 × 货币/时间两类约束。
- 真机：4 任务 × 最多 3 次运行 × 7 个模型配置，正文表格报告 5 个配置的选定运行；另有两组案例研究。

### 5.2 充分性评估

- **优点**：主实验覆盖 8 个前沿模型，且所有模型均获提升，方向一致性强；消融能分离“接口访问”与“执行控制”，设计有针对性；同时报告成功率、部分分、步数、token、cache、成本，维度较全。
- **不足**：
  - 消融多为 “selected runs”，未报告随机种子、方差、置信区间或显著性检验；
  - 真机仅 4 个任务、每模型 1 次选定运行，作者自认只能刻画配置而非排名；
  - 时间曲线因环境未受控而不可比，作者标注为探索性；
  - 离线子集排除联网任务，与真实网络环境存在差距；
  - 与闭源系统的比较只能是“把闭源模型当作被测模型”，无法比较其内部系统设计。

## 6. 主要结论与发现

- **GCUA 全面优于 GUI-only CUA**：8 个模型平均部分分从 45.3 升至 64.9（+19.6），每任务步数平均减少 53.0%，输出 token 平均减少 27.2%，全任务成功率亦全部提升；最强与最弱模型间的分数差距缩小一半以上。
- **代码执行的价值超出“有 shell 访问”**：在同样具备 GUI+CLI 接口的条件下，代码执行相对批量 GUI+CLI 平均提升 6.1 分、步数减少 14.8%；表 3 中 4 个模型提升 4.4–9.1 分。原因在于中间结果可在程序内驱动后续
