# CUA-Lite: An Open Platform for Computer Use Agents 

Zhanhui Zhou †, Weichen Zhang, Haoran Liu, Lingjie Chen Tianneng Shi, Kevin Lin, Zhengyuan Yang, Lijuan Wang, Dawn Song 

https://cua-lite.github.io 

# Abstract 

Open resources for computer use agents (CUAs) — environments, datasets, and models — remain scattered: without a standard, these resources cannot be integrated and scaled; additionally, evaluation, RL, and SFT cannot share one infrastructure. We present CUA-Lite , an open platform for developing CUAs, built around three standardized abstractions: (1) Unified environment interface , under which we integrate 12 benchmarks across desktop, browser, and mobile, plus lightweight VM-free sandboxes that replicate OSWorld’s desktop at much lower cost, providing over 30,000 verifiable tasks. (2) Unified supervised data format , into which we convert the major public CUA datasets, from GUI grounding and understanding to full rollouts, and record our fresh rollouts from frontier CUAs on these verifiable environments. (3) Model harnesses shared across evaluation, RL, and SFT , one per model and implemented for 14 model families. Each harness runs its model in these computer environments, producing the rollouts that evaluation and RL consume, or renders stored supervised data into the model’s own training format for SFT. We release reference scores across the integrated benchmarks, and show that RL and SFT through the same harness improve open-weight models. We release our dataset, code, and models, and the platform is open to contributions. 

# 1 Introduction 

Computer use agents (CUAs) operate desktop, browser, and mobile applications in com-puter environments. Developing CUAs requires environments with verifiable tasks, super-vised data, and models, each with a harness that runs the model in an environment. Open resources exist for all three: environments on desktop (Xie et al., 2024; Yuan et al., 2026; Bonatti et al., 2025; Li et al., 2025; Xie et al., 2025; Wang et al., 2026; Lv et al., 2026; Aggarwal et al., 2026), browser (Zhou et al., 2024; Koh et al., 2024; Liu et al., 2018; He et al., 2024; Bai et al., 2026), and mobile (Rawles et al., 2025; Xu et al., 2025a; Kong et al., 2026; Wu et al., 2026); supervised datasets, from GUI grounding labels to full rollouts (Deng et al., 2023; Xu et al., 2025b; Wang et al., 2025c; Mu et al., 2025); and models, from specialist CUAs (Qin et al., 2025; Wang et al., 2025c; Liu et al., 2026a; Xue et al., 2026) and vision–language models (VLMs) (Bai et al., 2025b;a) to API models with their own native computer use tools. However, these resources remain scattered: each environment has its own interface and runtime (e.g., a virtual machine (VM), a browser, a mobile emulator); each supervised dataset its own format; each model its own action space, prompt format, and rollout code. Without a standard, connecting models to environments means rewriting the same code: an action mapping, context management, and a rollout loop. Therefore, open resources cannot be integrated and scaled; additionally, evaluation, reinforcement learning (RL), and supervised finetuning (SFT) cannot share one infrastructure. 2.1 Environment Interface: Lite.Gym 

Lite.Gym exposes every integrated environment through one interface (Figure 2), a Gym-style loop (Towers et al., 2025) that standardizes one observation format across environments and one GUI action space per platform, plus optional extra tools per environment (Table 1). 

GUI actions as tool calls. CUA-Lite standardizes the GUI actions of each platform and exposes them through one tool per platform: click , type , and key through computer tool on desktop and browser; tap , swipe , and system_button through mobile tool on mobile (Table 1). The model’s harness maps its raw actions into that space (§2.3), so a model built for one action vocabulary runs on any integrated environment. Each tool call may carry a sequence of actions, so a model can plan several steps in one turn with action batching 

(Figure 2). A GUI action’s coordinates are normalized to [0, 1000 ] on every platform. 

Extra tools per environment. Beyond the GUI actions, an environment optionally exposes tools of its own: bash on Linux desktops, goto and back on browser, and open_app on mobile (Table 1). A model issues these tools alongside the platform’s GUI actions. 

Observations as tool results. A GUI action returns a screenshot, plus any text the environ-ment emits. An extra tool returns its own result, such as a shell command’s output.

2.1.2 VM-Free Desktop Sandboxes ( Lite.* )

Most existing desktop environments, such as OSWorld, are distributed as virtual machines. Each instance needs KVM, which shared and cloud hosts often do not expose, and carries a full guest OS, which makes it heavy to run and slow to boot. We propose VM-free desktop sandboxes ( Lite.* ), containerized Linux desktops that replicate OSWorld’s desktop at much lower cost. The official OSWorld VM ships as a disk image with no build recipe, so we reverse-engineer it. We recover the applications installed in the VM and their configu-ration, and rebuild the desktop from them as Dockerfile s. Fidelity. Lite.OSWorld yields evaluation scores close to OSWorld’s. (1) Lite.OSWorld adds two training splits to OSWorld’s 369 evaluation tasks: 1,722 tasks synthesized from templates and 707 perturbed from 256 of them (Appendix D). 

(2) Lite.ScaleCUA runs the 20,289 desktop tasks SCALECUA (Lv et al., 2026) synthe-sized on that same OSWorld desktop. 

(3) Lite.CUAGym runs the 10,910 desktop and browser tasks of CUA-Gym (Wang et al., 2026), across mock sites and real applications. 

(4) Lite.CUAWorld runs 2,479 tasks on the 41 professional applications of Gym-Anything (Aggarwal et al., 2026).

2.3 Model Harness Shared Across Evaluation, RL, and SFT 

A harness is the scaffolding that makes a model an agent. It turns each observation and the history into the model’s input, parses the output back into actions, and drives the loop. CUA-Lite has one harness per model, built around an adapter that converts between a Lite.Sample and the model’s own input and output. For SFT, the adapter renders a stored Lite.Sample into the model’s own format for training (§2.2). During a rollout for evaluation or RL, it renders the Lite.Sample as it grows and converts the model’s reply back into Lite.Gym actions. Inside the adapter, action_space maps the model’s raw actions to and from the standardized GUI actions (§2.1), and protocol manages the model’s context across turns. Modules are shared and inherited across models (Qwen3.5, Qwen3.8, and EvoCUA all build on Qwen3-VL’s), so a new harness implements only what differs. Harnesses currently exist for 14 model families.

4.1 SFT Setup. We SFT Qwen3.5-4B on GPT-5.5 rollouts collected from the verifiable training tasks (§2.2) that pass the verifier, and evaluate on held-out tasks. For desktop, we train on 5,000 Lite.Samples from Lite.ScaleCUA and evaluate on Lite.OSWorld’s 332 evaluation tasks (OSWorld’s 369, excluding the 29 infeasible tasks and the 8 that need a Google account). For browser, we train on about 2,000 Lite.Samples from WebGym and evaluate on 128 held-out WebVoyager tasks. For mobile, we train on about 1,000 Lite.Samples from MobileGym, whose 160 training tasks are templates that each generate many instances, and evaluate on its own 256 held-out tasks. We train Qwen3.5-4B with its official computer use harness (§2.3), with an image history of one screenshot (1920 × 1080 on desktop, 1280 × 720 on browser, 720 × 1600 on mobile) and the full text history. We evaluate every model three times at temperature 0 and report the mean success rate (Appendix G). 

Results. SFT on the GPT-5.5 rollouts raises Qwen3.5-4B from 22.6 to 44.8 on desktop, from 4.4 to 60.0 on browser, and from 14.6 to 26.8 on mobile (Table 4). As an ablation, we run SFT on these rollouts without their reasoning (§2.2), which costs 7.6, 11.3, and 5.4 points respectively, while Qwen3.5-4B’s own reasoning does not always help before SFT. 

Ablations. We also ablate two choices of the SFT setup: the teacher that provides the rollouts and the image history (Table G.1 gives the exact scores). 

(1) Teacher (Figure 6, left). We ablate the model whose rollouts Qwen3.5-4B is SFTed on, replacing GPT-5.5 with Qwen3.5-27B on desktop. GPT-5.5 is the stronger teacher, and most of its lead comes from reasoning . Without reasoning, Qwen3.5-27B’s rollouts train a model close to GPT-5.5’s, and adding its reasoning helps little. 

(2) Image history (Figure 6, right). We ablate how many of the most recent screenshots Qwen3.5-4B keeps in its context, one or four. The latest screenshot alone does about as well as four , both before and after SFT.

Results. GRPO further improves the SFTed Qwen3.5-4B on every platform (Figure 7). On held-out tasks, the evaluation score rises from 32.8 to 38.6 on desktop, the success rate from 60.0 to 72.8 on browser, and the shaped reward from 34.6 to 46.7 on mobile. 

Choosing training tasks. The obvious training tasks do not always suit RL. On desktop, before the runs in Figure 7, we tried GRPO on the official Lite.ScaleCUA RL split but found it did not raise the held-out score. We hypothesize that SFT on GPT-5.5’s Lite.ScaleCUA rollouts had already saturated the model on those tasks. The desktop runs in Figure 7 therefore use Lite.OSWorld’s synthesized LibreOffice tasks, one application suite so that a run fits on one node. On browser, training on live websites is prone to IP blocking, so we instead train on WebHarbor’s offline mirrors, using the WebVoyager tasks outside our held-out set. On mobile, MobileGym’s official training split is much easier than its evaluation split, so we draw our training and held-out tasks from it. 95 Limitations and Conclusion 

Limitations. CUA-Lite standardizes how environments, data, and models connect, but it also inherits their limitations. Open mobile environments with verifiable training tasks are scarce, so MobileGym is our only mobile training environment. WebVoyager runs on offline mirrors of its websites, so its scores do not measure the live sites. We do not fully audit the training verifiers, and a model judge scores some tasks in Lite.CUAGym and Lite.CUAWorld, so SFT data and RL rewards can include rollouts that did not solve their task. Our VM-free desktop sandboxes cover only Linux desktops, so Windows environments such as WindowsAgentArena still need a virtual machine, and mobile environments such as AndroidWorld still need an emulator. In §4, the desktop and mobile models are evaluated on the applications they train on, so their gains do not show transfer to unseen applications. Most previously reported scores come with no runnable evaluation script, so we do not claim to reproduce them and offer ours only as reference scores. Our harnesses implement only each model’s own GUI loop, not richer harnesses such as Codex and Claude Code. 

Conclusion. CUA-Lite gives computer use agent development one standard: an environ-ment interface, a supervised data format, and per-model harnesses shared across evaluation, RL, and SFT. On that standard we integrate 12 benchmarks and VM-free desktop sandboxes with over 30,000 verifiable tasks, convert the major public CUA datasets, and record fresh rollouts. CUA-Lite stays open to contributions, and every number in this paper ships with the command that produces it.

Environments for CUAs span desktop (Xie et al., 2024; Yuan et al., 2026; Bonatti et al., 2025; Li et al., 2025; Xie et al., 2025; Wang et al., 2026; Lv et al., 2026; Aggarwal et al., 2026), browser (Liu et al., 2018; Zhou et al., 2024; Koh et al., 2024; He et al., 2024; Bai et al., 2026), and mobile (Toyama et al., 2021; Rawles et al., 2025; Xu et al., 2025a; Kong et al., 2026; Wu et al., 2026); each defines its own action space and runtime, and most desktop benchmarks are distributed as virtual machines. Datasets range from GUI grounding and understanding labels to full rollouts, each in its own format (Deng et al., 2023; Lu et al., 2025; Xu et al., 2025b; Wang et al., 2025c; Liu et al., 2026a; Mu et al., 2025). Models range from specialist CUAs (Qin et al., 2025; Wang et al., 2025c; Liu et al., 2026a; Zhou et al., 2025; Xue et al., 2026; Awadallah et al., 2025; Venus Team et al., 2026) to VLMs (Bai et al., 2025b;a) and API models with native computer use tools, each with its own action space and prompt format (Wang et al., 2025a). Systems and infrastructure. OpenHands targets software engineering (Wang et al., 2025b), BrowserGym and AgentLab the evaluation of web agents (Le Sellier de Chezelles et al., 2025), and ClawGUI the training and deployment of mobile agents (Tang et al., 2026); AgentStudio is a toolkit of environments, annotation tools, and benchmarks for virtual agents (Zheng et al., 2025), and AgentBoard focuses on analytical evaluation (Ma et al., 2024). GEM and AgentGym-RL provide gym-style interfaces for text agents (Liu et al., 2026b; Xi et al., 2026); ComputerRL, SCALECUA, CUA-Gym, MobileGym, and WebGym scale environments or verified tasks for one platform (Lai et al., 2026; Lv et al., 2026; Wang et al., 2026; Wu et al., 2026; Bai et al., 2026); OpenEnv standardizes environment packaging (Meta PyTorch & Hugging Face, 2025). Each of these systems covers one platform, or one of the three abstractions. CUA-Lite provides all three across desktop, browser, and mobile, and one harness per model serves evaluation, RL, and SFT alike.

OS-World distributes its VM with 4 GB of guest memory and 4 cores, so we cap the Lite.OSWorld container at the same 4 GB and 4 cores for measurement. • Cold start : the wall time from gym.make to the first observation reset returns, which covers the boot, the task’s setup, and the first screenshot. Setup differs from task to task, so we alternate two os -domain tasks rather than repeat one, and both runtimes run that same pair, which leaves setup equal on the two sides. A container takes what it touches, and a VM holds the guest RAM its host must provide. • Idle CPU : the cgroup’s cumulative CPU time ( cpu.stat ’s usage_usec ) differenced across that same window and expressed as a share of one core, rather than a sampled rate, because one desktop repaint moves a sampled percentage by two orders of magnitude. • Disk : the image size, plus OSWorld’s qcow2 .

Training tasks. Lite.ScaleCUA, Lite.CUAGym, and Lite.CUAWorld inherit the task sets of their upstream releases, with the bugs we found fixed. Lite.OSWorld adds two training splits to OSWorld’s 369 evaluation tasks (Table D.2): • Synthesized (1,722 tasks): we generate each task from a template, and the templates of each application cover the operations of its OSWorld evaluation tasks. The tasks do not use OSWorld’s files. Most generate their own in the sandbox or copy in public ones (e.g., Wikimedia Commons photos and Project Gutenberg books), and the rest start from the application alone. Only the Thunderbird tasks reuse OSWorld’s mail profile. • Perturbed (707 tasks): we perturb 256 of OSWorld’s evaluation tasks, keeping each task’s files and setup and changing the request. Both splits mostly reuse OSWorld’s evaluator functions as verifiers, and we check that each task’s oracle solution scores 1. We train on the synthesized tasks (§4.2). The perturbed tasks start from the same state as evaluation tasks, so they are useful for debugging and analysis; we do not train on them and do not recommend it, as it would overfit to OSWorld. E.1 Format 

A Lite.Sample stores supervised data (a UI grounding label, UI question understanding, or a full rollout) in three fields: the images it refers to, the conversation, and the metadata that labels it (Figure E.1). Each message is tagged with its role (user, assistant, or tool), each content part with its kind (text, image, or action description), and the reasoning has its own reasoning_content field. Because every part is tagged, a harness can find a part by its type instead of parsing text. For example, it can drop the reasoning, keep only the most recent screenshots, or replace past steps with their action descriptions. Figure E.2 shows one Lite.Sample of each kind.              

> @dataclass
> class LiteSample :# one label, answer, or rollout images: list[Image] # what the messages refer to, deduplicated messages: list[LiteMessage] # user, assistant and tool turns metadata: LiteCUAMetadata
> class LiteCUAMetadata :dims: tuple[Platform, TaskType] # what it holds, and where it runs others: dict # provenance: the model, the rollout's reward Platform = "desktop" | "browser" | "mobile" TaskType = "grounding.action" | "grounding.point" | "grounding.bbox" | "understanding" | "use"
> class LiteUserMessage (TypedDict): # the instruction, and the observation content: list[TextContent | ImageContent]

23 G Training Details 

SFT. Every SFT run in §4.1 uses the same hyperparameters on every platform: two epochs over the training set, a global batch of 32 rollouts, and the Adam optimizer ( β1 = 0.9, 

β2 = 0.95, weight decay 0.1) with a learning rate of 5 × 10 −6, linear warmup over the first 10% of steps, and cosine decay to 10 −6. Unless an ablation varies them, runs keep one screenshot (1920 × 1080 on desktop, 1280 × 720 on browser, 720 × 1600 on mobile) and the full text history. The loss is averaged over the model’s output tokens. We evaluate the checkpoint after the second epoch three times at temperature 0 on the held-out tasks, and report the mean evaluation score. GRPO. Every GRPO run in §4.2 starts from the checkpoint SFTed on GPT-5.5 rollouts with reasoning and one screenshot, and uses the same hyperparameters on every platform: 16 training tasks per GRPO step, 8 rollouts per task at temperature 1, 8 gradient updates per GRPO step, clip ratios of 0.2 and 0.28, no KL penalty, and the Adam optimizer ( β1 = 0.9, 

β2 = 0.98, weight decay 0.1) with a constant learning rate of 10 −6. The platforms differ in training length, reward, and evaluation: • Desktop : 20 GRPO steps with 24 concurrent environments. The reward is the Lite.OSWorld verifier’s score, which gives partial credit on some tasks. Every two GRPO steps, we evaluate each held-out task four times at temperature 1. • Browser : 30 GRPO steps with 24 concurrent environments. The reward is 1 if WebVoy-ager’s GPT-4.1 judge accepts the rollout and 0 otherwise. Every five GRPO steps, we evaluate each held-out task once at temperature 0. • Mobile : 30 GRPO steps with 32 concurrent environments. The reward is 1 if the task succeeds, and otherwise half the fraction of its goal checks that pass. Every five GRPO steps, we evaluate each held-out task four times at temperature 1. A task family is the tasks of one app whose names share a prefix, at levels L1–L3; we drop L4, the hardest level, which takes 39% of the step budget but succeeds on only 4% of its tasks. 24
