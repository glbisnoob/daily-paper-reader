ABSTRACT 

Real desktop automation is neither purely visual nor purely programmatic. Agents must understand user-facing interfaces while efficiently manipulating files, scripts, and system state. However, native GUI/code coordination cannot be obtained by prompt-level tool composition. In our preliminary experiments, naively adding a code tool degrades a GUI agent, revealing that GUI/code routing must be internal-ized through training on high-quality hybrid data. We present OS-Helix, an end-to-end trained multimodal computer-using agent that unifies GUI actions and code execution in one action space. To construct the required supervision, we introduce application–artifact composition, pairing desktop applications with authentic file artifacts to instantiate executable Ubuntu states, and a decoupled instruction/eval-uator generation pipeline that produces environment-grounded tasks whose final states can be verified regardless of the solution modality. We cold-start the policy with SFT on filtered hybrid data and further improve it through online RL in live desktop environments. For RL, we propose Step-balanced GSPO, which aggre-gates importance weight by action step rather than raw assistant tokens to pre-vent long code actions from dominating heterogeneous-action optimization. On OSWorld-Verified, OS-Helix-27B and OS-Helix-35B-A3B achieve relative im-provements of 35.0% and 33.7% over their matched Qwen3.5 hybrid baselines, while OS-Helix-27B-RL further improves by 42.9% to reach 66.44% success. Ablations provide evidence consistent with contributions from learned GUI/code coordination, scalable verifiable supervision, and action step balanced optimiza-tion, while demonstrating cross-platform transfer on WindowsAgentArena. Our project homepage is at Ñ os-copilot.github.io/OS-Helix.

The rapid progress of vision-language models (VLMs) (Team, 2026; Wang et al., 2025b; Team et al., 2026a; Anthropic, 2025; Zeng et al., 2026; OpenAI, 2025; Bai et al., 2026; Zou et al., 2026) has accelerated the development of computer-using agents (CUAs), which aim to execute open-ended tasks in human-facing digital environments. Most existing CUAs formulate digital automation as graphical interaction, where agents perceive screenshots, reason over interface states, and act through mouse and keyboard operations. However, GUI-centric CUAs (Liu et al., 2026; Xue et al., 2026; Wang et al., 2026b; Zhang et al., 2026a; Luo et al., 2025; Cheng et al., 2024; Feizi et al., 2026) still face practical bottlenecks in realistic desktop workflows. Visual grounding can fail on small or ambiguous interface elements, and fine-grained interaction can make structured state manipulation cumbersome even with batched actions. A com-1arXiv:2610.22234v1 [cs.LG] 15 Oct 2026 plementary interface is programmatic control, through which command-line and code agents can inspect files, access system state, and execute compound operations directly through the shell (Yang et al., 2026e; 2024; Wang et al., 2025c). Yet code execution alone cannot fully address the long tail of desktop task scenarios that depends on visual layout, application-specific UI state, or software be-havior exposed only through the interface. As illustrated in Figure 1, these complementary strengths motivate a single agent that coordinates GUI and code, where GUI provides general visual access to arbitrary applications while code provides efficient and precise manipulation of programmatic state. Despite this complementarity, building a native hybrid GUI/code CUA remains an open problem. Simply attaching a code tool to a GUI model does not teach it when or why to use either modal-ity. In our preliminary experiments, as shown in Table 14, Qwen3-VL-32B-Instruct (Bai et al., 2025) achieves over ∼34% success on OSWorld-Verified (Xie et al., 2025) with GUI actions alone, but falls to roughly ∼32% when code execution is naively exposed. Prompt-level composition can therefore disrupt an existing GUI policy rather than create coordinated behavior, making it essential to internalize hybrid coordination capabilities into the model through training on high-quality hy-brid data. Several existing approaches have explored hybrid execution paradigms that combine GUI interaction with code-like actions. Framework-centric systems (Gonzalez-Pumariega et al., 2025; Hou et al., 2024; Yang et al., 2026a) rely on external harnesses to coordinate GUI, code, memory, and recovery; tool-call-based approaches (Jia et al., 2025; Yang et al., 2025b; Shi et al., 2026) ex-pose programmatic operations through predefined application-specific interfaces; and model-fusion approaches (Wang et al., 2025a; Qin et al., 2025) combine complementary capabilities through pre-defined designs. Although these systems expand the scope of hybrid computer use, they leave open how a single policy can learn the routing between the GUI and code actions through hybrid training. To address these challenges, we present OS-Helix, an end-to-end trained computer-using agent that unifies GUI interaction and code execution within a single policy. On the infrastructure side, we introduce application–artifact composition, which combines versioned applications with authentic artifacts to instantiate diverse and reproducible desktop states. An Ex-ploration Agent proposes instructions grounded in these states through brief exploration of the initialized environment, while an independent Evaluator Agent constructs task-specific, primarily rule-based evaluators. Together, this pipeline supports scalable synthesis, filtering, and collection of high-quality GUI/code trajectories for model training, thereby providing the data foundation neces-sary to internalize hybrid coordination capabilities into the model. On the training side, we first use filtered hybrid trajectories to internalize basic action semantics and modality routing, and then optimize the policy through online RL in executable desktop envi-ronments. In early RL experiments, we observe a steady increase in the proportion of code actions accompanied by a degradation in performance. We attribute this to the token-count asymmetry be-tween short GUI actions and substantially longer code actions, which causes the optimization signal to be dominated by code steps. To address this, we propose Step-balanced GSPO , which constructs the sample-level importance ratio over action steps rather than raw assistant-token counts, enabling more balanced optimization of the two modalities. These training components directly answer the open question of how a single policy can natively learn to coordinate GUI and code actions through hybrid training, yielding an agent that performs strongly and reliably across diverse desktop tasks. In summary, our contributions are: 1) We formulate native GUI/code hybrid computer use as an end-to-end policy-learning problem and show through controlled experiments that merely exposing a GUI policy to code execution fails to yield reliable routing, motivating the need to internalize coordination through hybrid training. 2) We introduce application–artifact composition and a decoupled instruction/evaluator synthesis pipeline to construct diverse, reproducible, executable desktop states and generate high-quality hy-brid data for internalizing GUI and code execution capabilities. 3) We propose Step-balanced GSPO for the agentic RL stage of native hybrid policy training, which prevents long code actions from dominating optimization, and enables a single policy to learn GUI and code coordination. 4) We will release the OS-Helix model family and research artifacts, including the desktop data-synthesis and RL environments, task and trajectory collection pipelines, approximately 9K generated 2instructions, 83K unfiltered SFT samples, and about 31K successful filtered SFT samples in the unified GUI/code action space. 

2 RELATED WORK 

Hybrid GUI/Code Computer-Using Agents. Traditional GUI-native agents learn screenshot-to-action policies over visual interface states (Qin et al., 2025; Wang et al., 2026b; Wu et al., 2025; Liu et al., 2026; Wang et al., 2025d), whereas command-line and coding agents operate over files, shells, and programmatic state (Anthropic, 2025; OpenClaw, 2026; Yang et al., 2026b; 2024). Their complementary strengths motivate hybrid computer use. Framework-centric systems (Gonzalez-Pumariega et al., 2025; Hou et al., 2024; Yang et al., 2026a) coordinate GUI, code, memory, and recovery through external harnesses, often using strong proprietary models. Their performance is coupled to costly inference and hand-engineered orchestration, making the model’s own hybrid coor-dination difficult to isolate. Tool-call-based approaches (Jia et al., 2025; Yang et al., 2025b; Shi et al., 2026) expose programmatic operations through predefined, application-specific interfaces, limiting coverage and transfer to available integrations and tool schemas. Some approaches integrate GUI, code, and other capabilities through model fusion (Wang et al., 2025a; Qin et al., 2025), relying on predefined fusion rather than coordination learned within a single policy. Qwen-UI-Agent (Zhou et al., 2026a) also explores training with mixed GUI and code-like action capabilities, demonstrating the practical potential of native hybrid agents. However, existing studies describe data construction, executable environments, supervision, and training configurations at different levels of granular-ity, making controlled reproduction and comparison of learned coordination mechanisms difficult. Our work complements by studying executable application–artifact state construction, decoupled instruction–evaluator synthesis, and more stable optimization for training a single GUI/code policy. 

Environment Scaling and Task Synthesis for Computer-Using Agents. Realistic long-horizon tasks and interactive environments are essential for training CUAs, yet manual task design and trajectory annotation are expensive and difficult to scale. This makes automated acquisition of high-quality instructions and demonstrations a central problem. One line of work crawls web tutorials and documentation and decomposes them into executable task instructions (Xu et al., 2025; Zhang et al., 2026a). Another line starts from the target environment itself and infers tasks from what the agent can observe or manipulate: Explorer (Pahuja et al., 2025) extracts and refines task in-tents from web entry pages, while OS-Genesis (Sun et al., 2025), GUI-ReWalk (Lin et al., 2025), TreeCUA (Jiang et al., 2026), and AUTO PLAY (Ramrakhya et al., 2026) synthesize tasks through exploratory interaction with the environment. These methods primarily scale task and trajectory synthesis, but they do not substantially scale the underlying interactive worlds, which constrains the diversity of behaviors learned by the agent. Unlike more constrained interaction domains such as web and mobile (Cao et al., 2026; Zhang et al., 2026c; Wu et al., 2026; Tang et al., 2026b; Cheng et al., 2026; Yan et al., 2026), PC environments, such as Ubuntu, Windows, and macOS, provide a natural substrate for scalable CUA training through system-level code execution, mature applica-tion ecosystems, persistent file systems, and package managers, enabling verifiable tasks grounded in concrete system state (Sun et al., 2026a; Fu et al., 2026). Recent work has begun to use vir-tual machines to expand desktop environments and synthesize tasks (Wang et al., 2026a; Lv et al., 2026; Huang et al., 2026), exploring different parts of desktop-state construction and task genera-tion. Table 6 summarizes the reported coverage of existing task-synthesis pipelines. Existing efforts differ in the extent to which they scale applications, authentic artifacts, executable initial states, and verifiable terminal conditions. Our pipeline integrates application–artifact composition, repro-ducible desktop-state construction, and environment-grounded instruction and evaluator synthesis into a unified framework for scalable, verifiable desktop-task generation. 

Training Paradigms for Computer-Using Agents. CUA training has broadly evolved from imitation-style supervised fine-tuning toward reinforcement learning in interactive environments. SFT-based systems learn action formats, visual grounding, and task execution from human demon-strations, synthetic trajectories, web tutorials, or teacher-model rollouts (Cheng et al., 2024; Qin et al., 2025; Wang et al., 2026b; Zhang et al., 2026a; Sun et al., 2025; Liu et al., 2026). Between SFT and online interaction, offline preference-optimization methods such as DPO (Gao et al., 2026) and offline GRPO (Yang et al., 2026c) improve policies from static preference data, but remain limited by the coverage of collected trajectories and cannot directly optimize recovery under envi-ronment feedback. 3 OS-H ELIX 

3.1 OVERVIEW 

An overview of the OS-Helix pipeline is shown in Figure 2. OS-Helix is built around a simple premise: a real computer-using agent should treat GUI interaction and code execution as two com-plementary ways of changing the same digital state. Rather than attaching a shell tool to a GUI model at inference time, we construct a unified pipeline in which environments, instructions, trajec-tories, and reinforcement signals are all designed for hybrid GUI/code execution. Formally, let q denote the user instruction, hi the history context before step i, and oi the current screen observation. The policy selects an action from a unified hybrid action space:

Each code action runs in a fresh process. Its stdout and stderr are appended to the current-turn context as a tool response for subsequent decision-making. 43.2 DATA INFRASTRUCTURE 

The scale of computer-using agent training is ultimately bounded by the diversity of executable states from which meaningful tasks can arise. This is particularly important on desktops, where workflows are shaped jointly by applications, user artifacts, and persistent local state. We view authentic artifacts as a natural axis for expanding this state space, with artifact types and file formats providing a direct link to the applications that can operate on them. Based on this principle, we construct diverse executable desktop environments and synthesize grounded, verifiable tasks from the resulting states. 3.2.1 APPLICATION –A RTIFACT COMPOSITION FOR DESKTOP ENVIRONMENTS 

Real-world desktop workflows are commonly grounded in existing artifacts that are read, edited, or transformed through applications. Thus, we factor scalable desktop-environment construction into two reusable components: applications with fixed versions, launch procedures, and diverse initializa-tion configurations, and artifacts carrying authentic content and persistent state. Their compatibility-aware composition produces executable desktop states from which realistic tasks can arise. To instantiate such states at scale, we organize artifacts and applications into an application–artifact compatibility graph , whose edges are determined by the artifact types and file formats that applica-tions can consume. The underlying application configuration records these supported input types, together with the version, launch commands, and initialization settings required for reproducible execution. For example, a .pptx artifact can be connected to LibreOffice Impress and WPS Pre-sentation directly, whose application configurations specify how each application is launched with the file and which application-specific initialization settings are required. The resulting states are instantiated on reproducible Ubuntu virtual machines for task synthesis and trajectory collection. 3.2.2 ENVIRONMENT -G ROUNDED TASK SYNTHESIS 

Given the diverse desktop environments constructed above, we next translate environment diversity into training-task diversity. Each synthesis episode first samples a target application and then selects compatible artifacts via the application–artifact compatibility graph , thereby instantiating a coherent and executable task context. Relying primarily on model priors tends to produce generic, repetitive instruction patterns and un-derutilize the state diversity of instantiated environments at scale. We therefore ground instruction generation in active exploration of the current environment. To avoid repeatedly covering familiar functionality, we maintain a global application memory that records functions previously exercised for each application and exposes this history during subsequent exploration, encouraging broader coverage over time. The Exploration Agent receives this memory together with application meta-data, exact file paths, launch configuration, tutorial, and initial screenshot, and performs a short non-destructive exploration restricted to opening, clicking, scrolling, and terminating. Based on the observed artifact content and application state, it proposes a realistic user instruction together with its initialization configuration and observable success conditions, without prescribing a GUI/code solution or revealing answer-critical information. To make synthesized tasks consistently verifiable, we adopt an everything-is-a-file abstraction in which terminal conditions are mapped, whenever possible, to inspectable file representations, and evaluator synthesis selects rule-based, VLM-based, or hybrid checks according to their observability. Verification specifies the desired terminal state without constraining how it is reached, allowing the same task to be completed through GUI interaction, code execution, or their combination. We decouple the instruction proposal from evaluator synthesis. Once an instruction proposal is ac-cepted, its instruction and success conditions are frozen and passed to an independent Evaluator Agent , which compiles the corresponding verification logic. Programmatically observable condi-tions are evaluated primarily with rule-based checks over VM files and command-line state, while visual conditions that cannot be reliably recovered programmatically are handled with VLM-based evaluation. Instructions and evaluators are validated separately in the pipeline. Instructions are checked for reachability, unambiguity, realism, and sufficient verification conditions, while evalua-tors must compile and assign zero reward to the initial state. Invalid evaluators are repaired when possible. Each validated instruction and evaluator then constitutes a task, after which semantically 5near-duplicate tasks are removed. Together, environment-grounded synthesis and file-backed verifi-cation produce a scalable pool of verifiable tasks shared by SFT trajectory collection and online RL. 3.3.1 SFT C OLD START 

Most open-source CUAs used as base models have previously been trained primarily for GUI-only interaction. They may possess visual understanding, coordinate grounding, and low-level control, but have not learned the new decision boundary created when code execution becomes an equally valid action. Merely adding a code tool expands the action space without supplying a routing prior for when to remain in the GUI, when to switch to code, and when to return to the interface for verifi-cation; it can even disrupt already learned GUI behavior. SFT therefore serves as a cold start in our pipeline: it establishes the action semantics of the unified tool schema and distills from teacher tra-jectories a coarse but usable GUI/code routing policy. We collect SFT trajectories on tasks produced by the data infrastructure described in Section 3.2, using Claude Sonnet 4.6 (Anthropic, 2026) as the teacher model with both Computer Use and Bash Tool enabled. The resulting trajectories are then postprocessed and normalized into the OS-Helix action schema. Each trajectory is scored by its eval-uator, using the teacher model itself when visual judgment is required, and the resulting score serves as the primary signal for rejection sampling. We further apply a filtering pipeline to remove mal-formed tool calls, schema-mismatched actions, and trajectories that fail evaluator or quality checks, yielding a set of high-quality SFT samples. Training hyperparameters and data-mixture details are provided in Appendix C.1. 3.3.2 AGENTIC RL WITH STEP -B ALANCED GSPO We first build a cross-node environment management system that monitors and manages over one hundred Ubuntu sandbox environments across multiple standalone machines. The system exposes a unified port to the training side and internally dispatches requests to the environments. We then perform online RL on carefully filtered generated tasks with rule-based evaluators only, further improving model performance. Each rollout interacts with a live desktop environment, and the paired evaluator score serves as the sole outcome reward signal. If an assistant turn contains an unparsable tool call or any other invalid action-format error, that assistant response is isolated as an invalid sample and assigned a reward of 0, even if the remaining trajectory could receive a positive evaluator score. We use three efficiency mechanisms to make online RL feasible under costly desktop interaction. First, we adopt an asynchronous RL pipeline that allows the rollout policy to lag behind the latest policy by at most one version, enabling environment interaction and policy optimization to run in parallel. Second, we maintain per-task success-rate estimates and bias sampling toward tasks near the current capability frontier, down-weighting tasks that are already too easy or remain too difficult. Third, we apply bounded sliding-window visual-context segmentation to control context length and sample growth. Rollouts are split into segments and each segment can contain multiple assistant actions that contribute to loss. We apply the same sliding-window segmentation logic during rollout inference to maintain consistency between training and inference. In our preliminary RL experiments, standard GSPO exhibited a systematic drift toward code-intensive behavior as shown in Figure 4. Specifically, as training progresses, the model increasingly favors code-related actions, ultimately resulting in a slight performance degradation relative to the initial SFT checkpoint. Within a mixed GUI/code training sample, a code action typically contains substantially more assistant tokens than a GUI click or keystroke. Standard GSPO averages token-level log-importance weights over all valid assistant tokens in the sample. Thus, even when a long code action constitutes only one of several GUI and code steps, it can dominate both the sample-level importance ratio and the clipping decision. This motivates an aggregation in which the weight assigned to each action step in the sample-level log-ratio is no longer determined by its token count. Step-balanced GSPO modifies only the aggregation of the sample-level ratio. Starting from the SFT policy, OS-Helix-27B-RL further raises the average success rate from 62.75% to 66.44%. The paired-bootstrap analysis of the aggregate difference is reported in Table 16. Why step balance matters. Panel (a) of Figure 4 uses the fraction of actions invoking code at each online RL update as a behavioral diagnostic. Under the same training setup, standard GSPO progressively drifts toward code-intensive behavior, whereas Step-balanced GSPO remains lower and more stable over the shared observed horizon. Panel (b) reports repeated-sampling coverage. Compared with the SFT policy, OS-Helix-27B-RL improves Pass@1 from 62.75% to 66.44% (+3.69 points) and Pass@3 from 70.88% to 76.44% (+5.56 points), with the latter supported by a paired-bootstrap confidence interval of 95% [2.24,8.97]. The larger gain under Pass@3 indicates that RL does more than strengthen a single preferred trajectory and increases the probability of discovering distinct successful trajectories across independent attempts.

The cross-corpus similarity to OSWorld is comparable to OSWorld’s internal-instruction similar-ity, indicating limited instruction-level overlap. Together with domain-removal ablation in Table 3, this provides complementary evidence against direct instruction overlap or reliance on data from the evaluated domains. Meanwhile, the synthesized corpus exhibits a higher but still broadly spread internal-similarity distribution, suggesting that it captures shared, transferable desktop-task structure rather than collapsing to a narrow instruction template family. 

6 CONCLUSION 

We present OS-Helix, a native hybrid computer-using agent trained end-to-end through scalable executable desktop task synthesis, hybrid SFT, and Step-balanced GSPO online RL, designed to na-tively coordinate heterogeneous GUI and code actions within a single policy. On OSWorld-Verified, 10 OS-Helix-27B and OS-Helix-35B-A3B achieve relative improvements of 35.0% and 33.7% over their matched Qwen3.5 hybrid baselines, while OS-Helix-27B-RL further improves by 42.9% to reach 66.44% success. OS-Helix-27B-RL also transfers to WindowsAgentArena with 63.87% suc-cess, surpassing GPT-5-based framework methods on both benchmarks. Ablations and behavioral analyses show that SFT provides the main gain, hybrid supervision outperforms GUI-only super-vision at a fixed scale, and learned routing improves both execution efficiency and task coverage beyond code access alone. Under matched RL settings, Step-balanced GSPO outperforms stan-dard GSPO and mitigates its drift toward code-intensive behavior, while RL increases Pass@3 from 70.88% to 76.44%, indicating broader discovery of successful trajectories across independent at-tempts. These findings establish native GUI/code coordination as a learnable hybrid paradigm and provide a reproducible foundation for further research on hybrid computer-using agents. 11 AI U SE STATEMENT

ETHICS STATEMENT 

This work does not involve human-subject studies or the collection of private data from real users. We study training methods for general-purpose computer-using agents, and conduct all trajectory collection, reinforcement learning, and evaluation in controlled, isolated Ubuntu virtual machines. The VMs use fixed application versions and a curated local file library, and are separated from per-sonal host files and credentials. This setup reduces the risk that exploratory actions during research inadvertently modify host state or access unauthorized resources. Although the experiments themselves present no substantial direct ethical risk, deploying agents with combined GUI interaction and code execution on real devices raises important safety and pri-vacy concerns. Such agents can continuously observe screen content, modify local files, and execute Python or Bash, and may therefore encounter personally identifiable information, confidential docu-ments, or authentication credentials. They may also be exposed to prompt injection through interface content or external files. Code actions further increase the potential impact of erroneous behavior or malicious workflows. The isolated experimental setting used in this work does not resolve these deployment-time risks. Real-world deployment should follow least-privilege and safety-by-design principles. These include granular permissions over applications, directories, networks, and code execution; explicit human confirmation before irreversible, credential-bearing, or otherwise high-impact operations; runtime policy checks, sandboxed execution, audit logs, and post-action verification; and data minimization and sanitization for screenshots, trajectories, and tool outputs. Users should retain the ability to define and revoke the agent’s authority, with sensitive applications such as banking, private commu-nication, and credential management inaccessible by default. Because general-purpose automation is inherently dual use, future CUA research should advance capabilities together with systematic red teaming, interpretable action auditing, and reliable human takeover mechanisms.

19 A LIMITATIONS AND FUTURE WORK 

OS-Helix is an initial step toward native GUI/code hybrid computer use, with remaining limitations centered primarily on computational and API resource constraints. First, desktop environments are difficult to scale comprehensively: even an application–artifact desk-top infrastructure spanning diverse applications cannot cover the full diversity of real user machines, private artifacts, application versions, and personalized configurations. Future work should further expand the application and artifact ecosystem and study broader randomization of system states and user configurations while preserving reproducibility. Second, automatic verification remains imperfect. Unlike software engineering tasks, where gold final states can be obtained deterministically, automated CUA task synthesis under limited resources cannot reliably capture ground-truth terminal states—tasks may therefore be subject to feasibility risks, and the resulting evaluators carry intrinsic brittleness. Concretely, rule-based evaluators re-liably cover many file-backed tasks but require careful construction and often depend on specific application versions or export formats; more fundamentally, even when an agent’s execution is se-mantically near-correct, inconsistent strictness in file-attribute checks can reduce the score to zero. Rubric-based partial scoring, adopted in several recent works including ours, partially alleviates this issue but does not resolve it entirely. VLM-based evaluators extend coverage to textual out-puts and visual outcomes, yet may miss fine-grained discrepancies; more critically, due to their inherent brittleness, existing RL engineering practice typically excludes VLM-based scoring from the reward signal altogether, concentrating construction effort on rule-based evaluators—which in turn constrains the types and diversity of tasks that can be incorporated into training. Future work should develop stronger evaluator-generation, repair, and validation pipelines, and systematically study cross-evaluator agreement as well as robustness to reward hacking. Third, our agentic RL experiments are subject to certain limitations imposed by available computa-tional resources. RL training was conducted only on the dense 27B model with relatively conserva-tive hyperparameter settings; the total number of training steps was likewise constrained, precluding a systematic investigation of the scaling behavior of agentic RL. For OS-Helix-35B-A3B, despite its strong performance in SFT experiments, the Mixture of Experts (MoE) architecture introduces non-trivial additional challenges in training-inference consistency and optimization stability dur-ing agentic RL, making it difficult to support this training pipeline reliably under current resource conditions. We regard a more thorough exploration of RL training dynamics and scaling laws, to-gether with a stable extension of Step-balanced GSPO to larger MoE computer-using agents, as an important direction for future work. Beyond scaling, we believe the community is now at an inflection point where recursive self-improvement (RSI) deserves serious consideration. As CUA models attain a meaningful level of general computer-use capability, the model itself can serve as its own teacher: rolling out interaction trajectories on existing tasks, providing the training signal for the next iteration, and progressively improving through this self-bootstrapping loop. Rather than relying solely on human demonstra-tion or externally curated data, such a paradigm allows the agent to continuously generate its own training trajectories with growing quality as capability improves and feed them back into subse-quent training rounds. We view this self-evolving, teacher-free training paradigm as one of the most promising long-term directions for advancing CUA agents. Finally, many existing desktop benchmarks were originally designed for GUI-only agents, with task design, reference solutions, and evaluation functions all implicitly centered on visual interaction paths. Although their tasks can often be completed with hybrid strategies, existing evaluators may not capture every valid GUI/code solution. Furthermore, using success rate as the sole metric is overly coarse: it neither distinguishes whether the agent selected the more efficient modality nor captures potential safety risks inherent to hybrid execution, such as unintended side effects of code execution or inadvertent system-level operations. A particularly promising complementary direction is the migration and adaptation of existing general-purpose agent benchmarks such as GDPval (Patwardhan et al., 2026) and Agents’ Last Exam (Sun et al., 2026b) into GUI environments. These benchmarks are inherently designed around authentic artifact manipulation and complex reasoning tasks, and thus naturally encompass diverse environment states and authentic artifacts. B.3 FINAL STATE MATERIALIZATION 

Our everything-is-a-file abstraction treats the file system as a common inspection interface rather than as a restriction on where a task state must originate. A terminal condition may initially reside in a downloaded web page, an in-memory application state, an unsaved layout, or a persistent user artifact. We attempt to materialize the relevant condition into a VM-resident file representation whenever this can preserve the semantics needed for evaluation: a web state may be downloaded or serialized locally, an in-memory result may be exported, and an answer may be written to a structured or plain-text file. This externalization separates the location of a state from its verifiable representation and allows heterogeneous desktop objectives to share a common evaluation interface. The materialization step is not uniformly lossless. Some conditions, such as exact document struc-ture, metadata, or serialized application state, admit faithful programmatic inspection; others depend on rendered layout, canvas appearance, transient UI state, or content for which serialization does not preserve the relevant evidence. Evaluator selection therefore reflects an observability trade-off: rule-based checks are used when a deterministic file or command representation captures the re-quired semantics, VLM-based checks are used when visual or otherwise non-serializable evidence is essential, and hybrid evaluators combine the two when they provide complementary evidence. B.4 INSTRUCTION AND EVALUATOR SYNTHESIS DETAILS 

The primary task-synthesis pipeline instantiates states through the application–artifact compatibility graph. The pipeline then follows a one-way information flow: application and artifact configura-tions determine the initialization context; the Exploration Agent produces a structured instruction proposal and textual success conditions; the independent Evaluator Agent compiles the frozen con-ditions into rule-based or visual checks; and each independently validated instruction-evaluator pair enters the task pool. 

Application-centered initialization. For each application, we record a canonical name, version, supported artifact types and file formats, launch commands, and initialization templates, and use these fields to build the application–artifact compatibility graph. Each synthesis episode first restores a controlled VM snapshot and samples a primary application, then selects zero or more compatible artifacts through the graph according to the application’s initialization templates. For every sampled pre-existing artifact, initialization creates a VM-resident, evaluator-only golden copy before task execution while leaving the original path as the active task target; this copy is bound to the task con-figuration and may serve as the expected reference in subsequent content or structural comparisons. The system then provides the Exploration Agent with application metadata, exact file paths, launch configuration, an application tutorial, global application memory, and an initial screenshot. The following partial PyCharm configuration illustrates how application metadata connects applica-tion initialization with artifact-library sampling. The version field fixes the application version assumed by task synthesis, trajectory collection, and evaluator implementation, while type declares the artifact or project types that the application can directly consume. The two entries in commands are alternative initialization templates: the first launches an empty application, and the second launches the application with a sampled artifact. The position-aligned values in random are normalized into initialization probabilities; hence [10, 90] assigns approximately 10% probability to an empty PyCharm launch and 90% to a file- or project-backed launch. When the second template is selected, the system randomly samples an absolute file path whose type is compatible with type from the artifact library and substitutes it for PATH before executing the command. The related app and related type fields retain compatibility relations among applications and artifact types for selecting conventional companion applications and for the graph-guided cross-application prototype. 23 This declarative configuration is what makes application scaling reproducible rather than a collection of ad hoc launch scripts. Adding an application requires specifying its version, launch procedures, supported artifact types, initialization probabilities, and optional relations to companion applica-tions. The compatibility graph then filters valid application–artifact pairings before an episode is instantiated in a fixed VM, allowing new applications and artifact types to expand the executable state space while preserving initialization and sampling semantics. Evaluator synthesis. Evaluator synthesis begins only after an instruction proposal has been ac-cepted and is performed by an independent Evaluator Agent in a separate context. Its inputs are the frozen instruction fields, initialization configuration, success criteria, and textual evaluation re-quirements. The Evaluator Agent may generate only the verification specification and cannot revise the instruction or proposal metadata. A rule-based evaluator comprises one or more self-contained Python judge functions. Each function declares its required imports locally, can run independently, accepts result and expected as inputs, and typically evaluates one well-defined subgoal. Either 24 input may be supplied by vm file as a VM-resident file or by vm command line as command-observable state. When initialization creates a local golden copy, expected may refer to it for content or structural comparison. When the target can be encoded directly in the rule, expected 

may be empty. Each judge accumulates a rubric-based score over fine-grained completion items with assigned weights. It returns a value in [0 , 1] , with zero for no satisfied items and one for complete satisfaction; if execution raises an exception, it returns the score accumulated before the exception. The evaluator relies only on VM-resident artifacts and deterministic rules, without ex-ternal or cloud-hosted golden assets, and checks the final artifact’s content, structure, formatting, metadata, or configuration state. When deterministic rules fully express the success conditions, the evaluator sets 

need rule judge=true without enabling visual judgment. When visual layout, canvas state, unparsable application-internal state, or dynamic web content is indispensable for verification, it may set need vlm judge=true . In this case, the VLM judge receives the agent’s execution trajectory as input, and vlm desc specifies the visual objects, attributes, and spatial relations to inspect in that trajectory. Rule-based and VLM-based judgments may both be used for task verification, but their scores are recorded separately. For a task with multiple rule judges, the rule-based score is the mean of the individual rule-judge scores, whereas the VLM-based score is produced independently by visual judgment. During SFT filtering, the two scores are thresholded separately, and a task is retained only when both its rule-based score and VLM-based score meet their respective thresholds (both 0.8). As described in Section 4.1, RL uses only tasks with rule-based evaluators to provide reward signals. This design avoids the brittleness and computational cost of VLM judgment and prevents the calibration mismatch that could arise from averaging the two score types directly. Although both scores lie in [0 , 1] , rule-based scores are derived from fine-grained, explicitly weighted completion items, whereas VLM scores generally reflect a coarser and more subjective judgment scale. The two scores therefore do not have interchangeable numerical semantics. Consequently, VLM judgment is used primarily to cover programmatic observability gaps during SFT-stage filtering. 

Instruction and evaluator filtering. Filtering first checks whether the JSON schema, getter ar-guments, and Python code can be parsed and compiled statically. The system then initializes the environment from the initialization configuration and executes the evaluator before any action. The initial-state score must be zero, as a nonzero score indicates reward leakage. An independent review model next scores instruction quality and evaluator quality separately. The former assesses whether the instruction is unambiguous, reachable, and realistic, while the latter assesses whether the eval-uator covers all success conditions, is sufficiently strict, and resists reward hacking. An instruction below the quality threshold is removed directly. If the instruction is valid but its evaluator fails an automated check or quality review, the system uses the previous evaluator and its failure information as revision context, regenerates the evaluator, and repeats the full validation and scoring procedure. The associated proposal is removed only after multiple repair attempts remain unsuccessful. After correctness filtering, we use embedding similarity to remove near-duplicate instructions gen-erated across batches, producing the task pool used for training stages. The RL task pool is then built by rolling out trajectories with the SFT-trained model on this pool and keeping tasks of moderate difficulty. 

Prototype cross-application extension. Beyond the application–system compositions in the pri-mary task pool, we implemented and began collecting a more structured form of cross-application task synthesis. The prototype uses the related app field in the application configurations to con-struct an application graph. Applications serve as nodes, while edges encode compositional relations induced by shared artifact types or file formats, convertible intermediate artifacts, or complementary workflows. This graph provides a structured prior for composing applications rather than treating all application combinations as equally plausible. For each task, the system first specifies a target number of applications, such as three, randomly samples a primary application, and then samples subsequent applications from its neighboring nodes. After each selection, the neighbors of the se-lected nodes are added to the candidate frontier, allowing the application set to expand along graph structure. To prevent the graph from overly constraining the composition space, each sampling step retains a small-probability jump mechanism that ignores graph connectivity and samples an applica-tion uniformly from the broader inventory. Artifact selection follows a corresponding compositional 25 procedure and may introduce zero or more related artifacts. This setting expands the exploration space and requires the Exploration Agent to additionally infer cross-application dependencies, in-cluding the execution order and the transfer of artifacts or intermediate results, before proposing a long-horizon instruction. We have already generated a small number of such prototype tasks and included them in the task pool. Their current scale is insufficient for a systematic evaluation of cross-application capabilities, so future work will expand the collection and study its effect on long-horizon execution across applications. E STEP -B ALANCED GSPO D ETAILS 

During reinforcement learning, a training sample may contain multiple assistant responses that con-tribute to the policy loss, with each response corresponding to one action step. The optimization unit of a training sample therefore need not coincide with an individual environment action step. In particular, the assistant span associated with a code action step is often substantially longer than that associated with a GUI step. The standard GSPO objective computes one sample-level importance ratio by aggregating token-level log-importance weights over all valid assistant tokens in the training sample (Zheng et al., 2025). Although this prevents a sample from receiving a larger sample-level weight solely because it contains more tokens, it does not equalize the contributions of different ac-tion steps within the same sample. As a result, a long code action can dominate both the sample-level ratio and the clipping decision even when it is only one of several actions in the training sample. This section formalizes the effect and derives a step-balanced aggregation for the GSPO ratio. Our goal is to preserve GSPO’s token-level importance weights and clipping structure while changing their sample-level aggregation to remove the deterministic dependence of an action step’s aggre-gate gradient coefficient on its token count. Recent work has also studied the granularity of im-portance ratios for LLM policy optimization, including sequence-level GSPO (Zheng et al., 2025), subsentence-level ratios (Yang et al., 2025a), cumulative token ratios (Zhang et al., 2026b), and hybrid token/sequence ratios (Min et al., 2026). These methods differ from our setting at the ob-jective level. SSPO assigns separate ratios to text fragments, but its published objective aggre-32 gates fragments with token-length normalization and does not use environment-action boundaries or action-type weights. CTPO and DHPO use token-level (or token/response-hybrid) objectives, while GSPO and GSPO-token use one response-level ratio. None of these objectives replaces token-count weights by normalized weights over labeled GUI/code action steps within a multi-action training sample.
