# Understanding Tool-Mediated Interaction Failures in Agentic GUI Software: An Empirical Study 

Yuchen Shao ∗† , Wenjing Liu ∗, Yuheng Huang ‡, Mengqian Xu ∗† , Ziqun Bao ∗, Long Yang ∗† ,Lei Ma ‡§ , Ting Su ∗, Chengcheng Wan ∗† ∗East China Normal University, Shanghai, China †Shanghai Innovation Institute, Shanghai, China 

‡University of Tokyo, Tokyo, Japan §University of Alberta, Edmonton, Canada 

Abstract —Large language model (LLM) agents increasingly complete tasks through live graphical user interfaces (GUIs). Because the model cannot directly operate the GUI, these systems often rely on tools to capture screenshots or UI trees, translate model outputs into GUI actions, and report whether the interface changed. We study failures where this tool-mediated interaction makes the agent’s view of the task diverge from the live GUI. We construct M ALVA , a defect library with 335 confirmed real-world failures from 40 open-source applications. These failures fall into 11 defect patterns rooted in state representation, state transition, and synchronization problems. They are widespread: 90% of the studied applications contain more than one defect type. They are also often silent: incorrectness appears in 86.6% of failures, including 119 cases that produce wrong behavior without a fail-stop signal. We operationalize this taxonomy with MALVA GUARD , a pre-deployment static contract checker that reaches 57.3% precision and 76.8% recall on an additional 20-application corpus. 

Index Terms —Interaction failure, LLM, empirical study 

I. I NTRODUCTION 

A. Motivation 

With the rapid advancement of large language models (LLMs), an increasing number of software systems pair an LLM agent with tools that observe and operate existing graphi-cal user interfaces (GUIs), including web browsers [1], desktop applications [2], [3], and mobile applications [4], without rely-ing solely on programmatic APIs [5]–[7]. This paper refers to these systems as agentic GUI software [8]–[10]. In the past 12 months, over 3,000 open-source applications have emerged on GitHub, along with around 30 commercial products launched by leading tech companies ( e.g. , Anthropic [11]). At runtime, tools in these systems often capture GUI state from screenshots or UI trees, and the LLM plans the next step. Tools then execute actions such as clicks or typing and report the resulting environment feedback back to the agent [12]. While promising, this tool-mediated process introduces a reliability problem: the agent’s view of the task can silently diverge from the live GUI [6]. Such divergence matters because these agents are mov-ing into real digital workflows, including enterprise dash-boards, customer-support portals, office productivity tools, online transactions, and mobile services [1], [2], [11]. In these settings, a tool misrouting a click can submit the wrong form, a stale screenshot can trigger redundant transactions, and

This failure is not isolated, developers of agentic GUI software face three reliability challenges: 

Challenge-1: Partial GUI observations. Developers often need agents to operate applications without programmable interfaces, relying instead on tools that read screenshots or UI trees [8], [15]. These tools expose only a slice of the live interface: elements may be obscured, off-screen, omitted from the UI tree, or visually present but not actionable. As a result, the agent may plan from an incomplete view of the target state. 

Challenge-2: Weak action boundaries. Developers expose large action spaces so agents can handle diverse tasks, but they rarely specify each tool’s operational boundary, including accepted parameters, required GUI preconditions, expected return format, or when to stop, retry, or escalate [16]. This leaves the tool loop unable to determine whether the next step arXiv:2610.31698v1 [cs.SE] 21 Oct 2026 Fig. 2: Tool-mediated workflow of agentic GUI software. is valid, leading to malformed calls, non-progressing retries, context overflow, or actions that target the wrong element. 

Challenge-3: Delayed tool feedback. LLM inference, GUI rendering, and tool execution run at different speeds [17]. After an action is executed, transient GUI changes, backend timeouts, or expired resource handles can cause reported tool status to diverge from the actual live interface state before the next observation begins. Despite extensive work on GUI automation and LLM agents, the tools that connect agents to live GUI environments have received little attention. Empirical work studied defects in traditional software [18], [19], ML-enabled systems [20]–[23], and LLM integrations [24], [25]. Traditional GUI automation treats automation code as test infrastructure, through scripted, model-based, and AI-assisted approaches [26]–[28], while GUI-agent studies evaluate task completion across web [5], [29], OS [6], and mobile [30] settings, and frameworks such as OpenClaw [3] propose architectural designs. Across all these lines, prior work either treats the tool layer as invisible infras-tructure or focuses on model and agent behavior, overlooking the tools that mediate between the agent and the environment. This paper fills this gap by systematically studying how such tools introduce failures in agentic GUI software. 

B. Contribution 

To understand how tools introduce failures when LLM agents operate live GUI environments, we conduct a sys-tematic study of 40 GitHub projects, based on their latest versions as of January 1 st , 2026 . These applications enable LLM agents to autonomously operate graphical interfaces across web, desktop, and mobile platforms. We manually collect around 2,000 issue reports and conduct extensive task execution to confirm 335 such failures. We find that such failures are widespread: 90% of the studied applications contain multiple defect types. The failures cause incorrect task results, infinite execution loops, wasted to-kens, and unexpected interruptions. As illustrated in Figure 2, they occur across four phases of the software loop: tools first observe and ground GUI state, the agent assembles context and selects the next tool call, tools then perform physical or API-backed actions, and tools finally report execution status and environment changes back to the agent. We identify 11 common defect patterns caused by state representation, state transition, and synchronization problems. We release M ALVA , a defect library containing all 335 con-firmed failures with their root causes and impacts. Based on the findings, we build M ALVA GUARD , a pre-deployment static contract checker for such failures in agentic GUI software. On an additional 20-application corpus, it achieves 57.3% precision and 76.8% recall. We hope this work can serve as a starting point for improving the reliability of agentic GUI software. II. B ACKGROUND 

A. Agentic GUI Software 

Agentic GUI software lets an LLM agent operate a live web, desktop, or mobile environment through a tool layer [6], [7], [31], [32]. Although this paper studies the full system, we refer to these applications as agents throughout for simplicity. The agent maintains State agent , which consists of the context window sent to the LLM together with memory, observations, action history, reasoning outputs, and selected tool calls. The environment has its own State env , covering the current GUI widgets, windows, focus, permissions, loading state, network conditions, and received tool-side effects. The tool layer is the bridge between the agent and the environment, and its tools fall into three roles. Observation tools collect GUI evidence for the agent, such as screenshots, UI trees, Document Object Model (DOM) [15] snapshots, OCR text, and element coordinates. Based on this evidence, the agent selects an action, which action tools then translate into backend effects such as clicks, typing, navigation, shell commands, browser API calls, mobile gestures, or ADB [33] commands, sometimes inside sandboxed browsers, desktops, or virtual machines [5], [6]. Feedback tools then close the loop by reporting execution status and visible effects back to the agent, including success signals, errors, timeouts, page loads, and target changes. 

B. Tool-Mediated Interaction Loop 

Given these components, agentic GUI software runs as a tool-mediated feedback loop [34], [35]. Formally, one cycle is defined as 

(State env ,t , State agent ,t ) Tt

−→ (State env ,t +1 , State agent ,t +1 )

where Tt denotes the tool-mediated transition across ob-servation, invocation, execution, and feedback. During this transition, tools may change the live GUI, append observations 2Fig. 3: Overview for constructing M ALVA defect library. or action results to the agent state, and update tool-local state such as caches, parsed snapshots, and backend handles. A later step therefore depends not only on the LLM output, but also on whether these tool states remain aligned with the live environment. Figure 2 splits the loop into four phases: P1 observes and grounds GUI state; P2 places relevant agent state into the context window and asks the LLM for the next action; P3 parses that output and executes the tool or backend operation; and P4 reports effects back to the agent. Reliable interaction therefore requires that observations reflect the current GUI, action parameters match valid targets, the GUI is ready before execution, and feedback confirms real progress. 

C. Interaction Failures 

When tools fail to keep State agent aligned with State env , the agent operates on a false view of the task. We define this mismatch as a tool-mediated interaction failure , or interaction failure for short. It covers hard failures such as crashes and exceptions, and soft failures where the loop stalls, repeats unproductive actions, or completes the wrong task [36], [37]. A defect occurs when a tool accepts or executes an invalid state without the necessary validation or effect check. III. S TUDY METHODOLOGY 

Since no prior work has systematically studied failures at the tool-mediated boundary in agentic GUI software, we construct MALVA , a defect library of confirmed failures, from scratch. As summarized in Figure 3, we follow four procedures, each described in detail below: 

A. Application Selection 

We select 40 open-source agentic GUI applications from GitHub, using their latest versions as of January 1 st , 2026 .We first use the GitHub Search API [38] to collect about 500 repositories of agentic GUI software using keywords that cover major platforms and agent types, such as “GUI agent”, “web agent”, “desktop agent”, “mobile agent”, and “computer use agent”. After removing duplicates and inactive forks, we keep repositories that meet three criteria: 1) the repository implements an executable agent loop for real-world tasks, not a toy demo or thin API wrapper; 2) the implementation contains concrete observation and action tools for GUI interaction; 3) the repository contains enough implementation and issue evidence to support defect analysis. C. Task Execution 

To collect evidence for candidate reports, we first inspect the issue status: 104 are closed issues, and 104 are open issues.  

> •

Closed issues : we examine discussions, linked pull re-quests, and commits to identify the failure scenario that developers acknowledged or fixed.  

> •

Open issues : we reproduce the failure directly when the required environment and credentials are available. Through this process, we derive 62 executable tasks from the open issue scenarios, since multiple issues often describe the same scenario. For each open issue, we identify the user goal, required environment state, and expected outcome. Each task specifies an initial state, an agent instruction, and a success oracle such as a UI change or system confirmation, instantiated under 14 environment-specific scenarios. The tasks span web, desktop, and mobile agents, with 35, 14, and 13 tasks respectively, and range from simple actions such as clicking or text entry to multi-step planning such as booking flights or configuring a system. To account for non-determinism, we run each of the 62 tasks 20 times with a 3-minute timeout per run [5], yielding 1,240 task runs. Each run involves multiple agent-environment interactions, and automated logging records visual evidence including screen recordings and DOM snapshots, agent traces including prompts and action logs, tool invocations and re-turn values, and environment feedback such as page loads and errors. In total, the dataset contains about 3,000 agent interactions. We conduct most experiments on Windows 11 to ensure a consistent graphical environment, using Linux virtual ma-chines for Linux-only applications. 

D. Defect Identification 

Using the evidence collected in the previous procedure, we manually assess each of the 208 candidates to verify whether the reported failure is real and reproducible:  

> •

Confirmed when multiple evidence sources converge on the same tool-layer mistake, such as linked fixes or commits for closed issues, and reproduction logs, tool traces, and before/after GUI states for open issues.  

> •

Excluded when the failure only appears in a few runs due to unstable environments, missing credentials, or unsupported setups. This yields 99 confirmed defects out of the 208 candidates, including 43 from open issues and 56 from closed issues. As a failure confirmed from one GitHub issue may not be unique to that application, we next perform cross-app expansion. For each of the 99 confirmed tool-layer mistakes, we exhaustively inspect all remaining 39 applications to check whether the same erroneous tool behavior arises at the same type of tool-environment interaction. When a matching case is found, we reproduce the corresponding failure and count each successful reproduction as a separate confirmed failure. This process yields 335 confirmed interaction failures in total. Finally, we label the confirmed failures through a separate iterative process. In each iteration, four authors discuss the identified failures and refine a list of patterns based on workflow phase, root cause, tool-layer mistake, and impact. Three authors independently categorize each failure into one of the defect patterns, label its impact, and cross-check their labels, reaching 95% initial agreement (Fleiss’ κ = 0 .95 ). A fourth author joins when disagreements remain and resolves them by revisiting the original evidence. The iterations stop when no new patterns emerge, and the labeling effort took about 7 person-months. IV. D EFECT PATTERN ANALYSIS 

A. Overview 

We classify 335 defects across 40 GitHub applications into 11 defect patterns, summarized in Table II. The taxonomy uses two axes to capture both where in the loop the failure occurs and what tool-layer contract is violated. The phase axis locates 4the earliest broken tool-layer boundary across P1 to P4. The root-cause axis records which contract is violated between the agent state, tool behavior, and live GUI state:  

> •

State Representation Failure (SRF, 26.3%) : Observa-tion or grounding tools build State agent from GUI evidence that is missing, wrong, stale, or incomplete, correspond-ing to Challenge-1.  

> •

State Transition Failure (STF, 55.5%) : The tool loop or executor advances the interaction even though the next step is invalid, unsupported, not ready, not progressing, or over budget, reflecting Challenge-2.  

> •

Synchronization Failure (SF, 18.2%) : Tool feedback or lifecycle management code updates State agent with a status that no longer matches State env or available resources, mirroring Challenge-3. The failures concentrate around recurring tool-layer con-tracts instead of isolated GUI glitches. As shown in Table II, Progress Check Failure, Tool Schema Mismatch, and Lifecycle Propagation Failure each appear in more than half of the studied applications at 65%, 63%, and 58% respectively, confirming that these defects are systemic weaknesses instead of application-specific bugs. At the failure level, these three patterns together with Context Budget Overflow account for 63.0% of confirmed failures, with P2 alone contributing 31.0% where the loop accepts the next step before checking progress, budget, or escalation conditions. This distribution further varies by observation tool type and execution environment, as shown in Figure 4. Agents that rely solely on screenshots or structural snapshots concentrate fail-ures in the phases tied to their grounding strategy: screenshot-based agents fail more in observation and execution, while structure-only agents fail more in P2 where DOM snapshots are mistaken for progress evidence. Desktop agents account for 56.1% of all confirmed failures and dominate in execution and resource-lifetime patterns, whereas mobile and web agents concentrate in P3 and P2 respectively, reflecting their distinct action interfaces and loop control patterns. The common mistake across all settings is treating model-visible state as if it already matched the live GUI: observations hide or perturb state, feedback tools report success before GUI changes, and tools promise more than the underlying execution layer can deliver. As a result, incorrectness appears in 86.6% of confirmed failures, including 119 that produce wrong behavior without a fail-stop signal.

2. Target Grounding Error. Grounding and targeting tools bind an intended target to the element, coordinate, box ID, or controllable region that the executor can safely operate. A wrong binding turns a valid target into an invalid or wrong locator before the action tool runs. The pattern appears in 38% of applications, averaging 2.60 cases each. The mismatch stems from rigid geometry rejections, coor-dinate drift between tool components, or semantic confusion over UI context. Figure 6 shows the web automation agent

3. State Exposure Gap. Observation and grounding tools need to expose the live GUI state that can affect the next action, not only the visible or currently serialized slice. Missing obstruction, focus ownership, scroll reachability, modal state, or freshness leaves State agent with only a partial view of State env . This pattern affects 18% of applications, with a median of 2 cases each. These gaps appear at several tool boundaries. At the window and focus boundary, as also seen in UI-TARS-desktop [13], the screenshot tool exposes the target visually but not the topmost click owner, so the action is delivered to the wrong window layer, as illustrated in Figure 1. The desktop automa-tion agent Clevrr-Computer [48] exposes a related gap: its 

get_screen_info() tool always reports 1920 x 1080 

to the vision model regardless of the actual display size, leaving the agent grounding targets against a stale window model instead of the active screen. At the viewport and scroll boundary, observation tools expose only the visible slice: the GPT-4V grounded web agent SeeAct [49] misses that a table column named “topics” is reachable through a horizontal scroll container, repeatedly concludes that no candidate matches the target, and stops. At the modal and loading boundary, observation tools keep reporting the underlying page while an unmodeled dialog or transient state hides the actionable UI. 

Finding-1: P1 accounts for 26.3% of failures: observation and grounding tools expose GUI evidence that is nonexistent, stale, or not tied to the same live target. Tools should validate evidence against the live GUI before passing it to the agent.

4. Progress Check Failure. Progress control depends on comparing consecutive tool outcomes and stopping, recover-ing, or changing strategy when repeated calls do not change observations, errors, or completion status. Without this guard, the loop treats another executable step as recovery and wastes steps or tokens on the same failed action. It affects 26 applications (65%), averaging 3.08 cases each. D. Phase 3: Execution Defects 

P3 materializes a model-selected action as a concrete tool invocation and backend side effect. This phase depends on parsers, adapters, and executors that preserve the action across schema normalization, parameter binding, and readiness val-idation. In each case, tools accept, translate, or execute an action without checking whether it is valid, correctly parame-terized, or safe to deliver to the current GUI or backend state, accounting for 82 of 335 failures. 

7. Tool Schema Mismatch. Tool invocation begins with parsers and registries normalizing model output into registered actions with expected fields and types. Unhandled wrappers, schema variants, or rigid parsing rules turn recoverable action descriptions into unparseable or unregistered tool calls. This is the most widespread pattern, affecting 63% of applications with a median of 2 cases each. 8. Parameter Semantics Error. Tool adapters sit between a parseable call and executor invocation, where defaults are bound, arguments are rewritten, and placeholders are resolved. A call can satisfy the tool schema yet still execute the wrong operation if this adapter step changes what its parameters mean. The pattern affects 25% of applications, averaging 1.70 cases per affected application. Parameter semantics shift in the adapter before the call reaches the executor. In autoMate , the scroll adapter silently replaces a requested 200-pixel scroll with a 500-pixel sys-tem value, causing the action to overshoot the target. When placeholders go unresolved, the effect is more sub-tle: the natural-language web automation agent actor-web-automation-agent [62] sends a parseable CAPTCHA action whose value remains <CAPTCHA_TEXT> , a marker that should instead become a structured execution error before the adapter forwards the call. Extra rewriting introduces a third variant: pywinassistant ’s query adapter expands a concise search query into irrelevant generated content, changing the semantics of the action before it reaches the executor. 

9. Missing Execution Preconditions. Execution tools sit at the boundary where a parsed call becomes a backend or GUI side effect. A call can be syntactically valid but still unsafe when the target resource or GUI state is not ready. Missing these readiness checks delivers shell, click, or type calls to missing resources or wrong GUI targets in 33% of applications, with a median of 2 cases per application. The failures arise from three sources: infrastructure un-readiness, planning order gaps, and input state staleness. Infrastructure unreadiness appears when backend resources are addressed before they exist: the computer-use application 

cua [63] calls get_vm() before provisioning or run_vm() 

finishes, missing a VM-readiness gate before later execu-tion tools address the backend resource. Input state staleness exposes a subtler form of the same missing check: the Llama-4-powered computer-use agent llama4-computer-use [64] sends a social-media query before activating the browser, AppAgent ’s text-entry tool types before activating a chat input field, and gemini-browser ’s browser-input tool reuses a stale search bar between queries. 

Finding-3: Execution tools in P3 (24.5%) accept malformed schemas, semantically invalid parameters, or actions with-out satisfied GUI preconditions. Tools should validate ac-tion schemas before invocation, reject unresolved parameter placeholders, and verify GUI and backend readiness before executing. 

E. Phase 4: Environment Feedback Defects 

P4 carries the effect of the previous tool action into the next loop iteration. Feedback tools report completion, expose up-dated observations, and maintain resource handles for sessions, windows, APIs, and OS tools. Across both patterns, feedback tools report success or propagate state before the live GUI or resource has actually reached a stable, usable condition, producing 61 of 335 failures. 

10. Temporal Feedback Mismatch. Feedback tools report progress before the next planning cycle [17], [65]. A tool that returns success or captures the page before the GUI reaches a stable, observable state leaves the next cycle planning from feedback that does not yet match State env . We observe this pattern in 8 applications (20%), averaging 1.38 cases each. Figure 11 shows cua returning success for key operations before the OS has finished rendering the UI update: the action tool dispatches the key event and receives an early acknowledgment, but the GUI render delay means the subse-quent observation still reflects the pre-action state. The timing contract also governs text input and DOM mutation: Clevrr-Computer [48] drops spaces during fast programmatic text entry, while UI-TARS-desktop ’s showWaterFlow injects ele-ments before document.head or document.body exists. In each case, the missing check is state stability before the next observation is captured. 

Fig. 12: Lifecycle propagation failure in desktop-agent [66] triggered by a misinterpreted ESC signal. 

11. Lifecycle Propagation Failure. Feedback tools carry lifecycle state for sessions, windows, pages, OS tools, and APIs. When disappearance, crashes, or incompatible return data are not propagated as recoverable structured errors, the agent keeps using stale handles or converts backend failure into ordinary continuation. This pattern affects 23 applications (58%), averaging 2.17 cases each. When a resource disappears without a structured error, the agent continues against a stale handle. Surf illustrates this path: during a flight-booking task, the system tries to extend the E2B sandbox only after it has already been destroyed, pro-ducing SandboxError: 404: Sandbox not found ;at that point, the desktop connection is gone and later tool calls cannot recover the task. Related cases treat a timed-out or black-screen sandbox as a recoverable UI state, so the agent keeps taking screenshots, refreshing, clicking, or sending keys against a dead environment. Lifecycle state can also be misrouted instead of lost. Fig-ure 12 shows the desktop automation agent desktop-agent [66] issuing pyautogui.press(’escape’) to close a failed Run dialog. The pynput listener tool intercepts this tool-generated key event and treats it as a user-stop signal, setting 

agent_running = false and terminating the run. The action tool had no way to mark its key event as internal, so the listener tool propagated it as a lifecycle stop without provenance. 

Finding-4: Although P4 is the smallest phase (18.2%), its failures are easy to overlook: feedback tools must verify GUI stability before reporting success and propagate resource lifecycle events as structured errors instead of ordinary continuation signals. V. S OLUTION : M ALVA GUARD 

Section IV shows that many runtime interaction failures stem from code-level anti-patterns: tool-layer operations are invoked, retried, or accepted without guards that align the agent state with the live environment. Findings 1–4 confirm that these missing guards appear systematically across all four phases. To detect them before execution, we implement MALVA GUARD , a pre-deployment static checker [67], [68]. As shown in Figure 13, M ALVA GUARD encodes the taxonomy as pattern-based static analysis rules. 8Fig. 13: Two-stage workflow of M ALVA GUARD .

A. Stage 1: Defect Detection 

Scope location. MALVA GUARD first identifies the scope to check. We define an interaction region as the local code or prompt span that contains a tool-environment interaction: in source code, it is the enclosing function or method; in project prompts or files without supported syntax trees, it is the matched line together with nearby lines. M ALVA GUARD 

searches source-code abstract syntax trees for operations that invoke models, read observations, handle actions, or update backend state, and identifies the corresponding interaction region for each match. M ALVA GUARD also checks helper calls (e.g. , parsing and execution) within the same code file. If the helper contains tool execution, parsing, or verification logic, MALVA GUARD checks that logic as part of the caller’s region. 

Contract verification. MALVA GUARD applies rule-based checks derived from the taxonomy. Each rule pairs a trigger pattern for a tool-environment interaction with a required guard: code or prompt evidence that bounds observations, con-strains loop progress, validates tool calls, or verifies feedback before State agent is updated from tool results. M ALVA GUARD 

searches for the guard within the interaction region; if absent, MALVA GUARD creates a missing-contract warning with the source location and missing guard. 

Defect grouping. MALVA GUARD generates a warning for each missing-contract location identified in the previous step. Within the same tool helper, adapter, or agent module, a single missing contract can trigger multiple warnings: the tool call, action parsing, retry logic, and feedback handling may all be flagged by the same checker rule because they share the same guard gap. M ALVA GUARD groups these co-located warnings into one defect only when they share the same checker rule and missing-contract type, recording one representative source line and keeping the remaining warnings as supporting evidence. Warnings from different checker rules are reported as separate defects even when they appear in the same component. 

B. Stage 2: Defect Attributing 

For each defect produced by Stage 1, M ALVA GUARD gen-erates a structured report and guard suggestion for developers. 

Defect report. For each defect, M ALVA GUARD records its location (file path, line number, and enclosing tool helper, adapter, or agent module), the missing contract ( e.g. , obser-vation bound, action validation, progress check, or feedback verification), the corresponding taxonomy defect pattern ( e.g. ,Context Budget Overflow, Tool Schema Mismatch), and the warning locations merged as supporting evidence.

C. Implementation 

MALVA GUARD supports Python, JavaScript, and Type-Script. It uses Python ast [69] and Tree-sitter frontends for source code [70] and line-based prompt matching. All experiments run on a cloud instance with 10 CPU cores, 100 GB system memory, 100 GB shared memory, an NVIDIA GeForce RTX 4090 GPU (48 GB VRAM, driver 550.163.01, CUDA 12.4), and Samsung NVMe SSD storage. 

D. Evaluation 

We evaluate M ALVA GUARD on a held-out corpus of 20 applications outside M ALVA , with no overlap with the original 40, following the same selection criteria as Section III. We manually build a defect oracle from issue, commit, and execu-tion evidence using the same validation process as Section III, yielding 112 real defects. M ALVA GUARD flags 497 missing-contract locations and groups them into 150 defects. Of these, 86 match oracle defects and 64 do not, yielding 57.3% precision. M ALVA GUARD misses 26 oracle defects, yielding 76.8% recall. Figure 14 breaks down the reported and missed defects by pattern. M ALVA GUARD achieves full recall on Tool Schema Mismatch, Parameter Semantics Error, Context Budget Over-flow, and Lifecycle Propagation Failure, where the missing guard is co-located with the triggering operation in the same local scope. Recall is lower for Progress Check Failure, Missing Execution Preconditions, and Target Grounding Error because their missing guards span multiple components or depend on cross-file conventions not visible in local source. Escalation Boundary Failure has zero reported cases because its instances are runtime security barriers, not guard omissions visible in local code. Both error types stem from the limits of local static analysis. False positives arise when a guard is hidden in framework wrappers, inherited callbacks, or runtime checks outside the local scope. They also arise when guard semantics span exception-handling and fallback paths. False negatives arise 9when defects depend on cross-file reasoning or framework-specific adapter semantics not visible in local code. These results reveal a broader code-quality risk: many applications still lack explicit code-level guards around tool use, leaving agent-environment interactions weakly protected regardless of whether a static checker is applied.

VI. T HREATS TO VALIDITY 

Internal Validity. Manual labels may contain bias or miss rare patterns despite multi-annotator confirmation. GitHub keyword filtering may miss unreported failures and issues described in non-technical terms. Reproduction may omit environment-specific factors that affect whether a failure man-ifests. M ALVA GUARD is a static checker and relies on local source and prompt evidence. It may miss contracts that become visible only at runtime or outside the local source scope. 

External Validity. Our findings may not generalize to all agentic GUI software. Windows/Linux behavior may differ on other platforms, and the common-use scenarios in Section III may miss specialized workflows in enterprise, accessibility, or hardware-control settings. Our open-source focus enables source-level confirmation from issues, commits, and execution logs, but may miss closed-source constraints or mitigations. VII. R ELATED WORK 

Empirical Studies and Defect Analysis. Prior works have studied defects across various software systems. One line of works studied defects in traditional software, including large-scale studies on code quality [18], learning-based name bug detection [19], and defect prediction surveys [72]. Another line of works studied ML-enabled software, building taxonomies of faults in deep learning systems [20], examining whether ML cloud APIs are used correctly [21], preventing their inte-gration failures at runtime [73], and automatically testing and fixing ML software when misbehavior is exposed [22]. The same theme extends to surveying ML testing landscapes [23]. Recent work further studies LLM and RAG integration de-fects in open-source software [24], bugs in LLM-generated code [74], and failure attribution in multi-agent systems to automatically identify which agent and step are responsible for task failures [25]. These works focus on code, model pipelines, API usage, or generated artifacts, but do not address failures that arise at the boundary between an LLM agent and a live GUI environment. This paper fills this gap by studying defects at this tool-mediated boundary and building M ALVA 

and M ALVA GUARD to support detection. 

LLM Agents and GUI Automation. LLM agents com-bine planning, memory, and tool use [34], [75]–[79]. Recent systems and benchmarks evaluate web navigation [5], [29], code generation [80], desktop/OS control [6], [81], and mobile automation [30], [82], while frameworks such as OpenClaw study GUI-agent architectures [3]. Several studies further ana-lyze capability and benchmark-level weaknesses such as local-ization bias, visual grounding, and unintended consequences in human-agent browsing [6], [83]–[88]. These works focus on whether an agent eventually completes a task, instead of how the tools that mediate between the agent and the environment fail to do so reliably. Our scope is the tool layer itself: how and why it fails to keep agent and environment states aligned. 

GUI Testing and Test Automation. Prior works have studied GUI testing through several approaches. One line of works explored target-application defects through record-and-replay or script-based automation [26], [89]–[91] and random or model-based exploration covering stochastic input gener-ation, state-machine-guided traversal, and use-case combina-tions [27], [92]–[100]. Another line of works applied AI/LLM-assisted methods guided by semantics, functionality, or natural language [101]–[107], including deep learning-based black-box approaches to Android app testing [28]. All of these works treat automation code as testing infrastructure and the target application as the subject of study. In agentic GUI software, however, the tool layer is part of the deployed system itself and participates in ordinary user tasks. This paper shifts the defect boundary to the tool layer itself, treating observation, action, and feedback tools as the primary subject of analysis instead of the vehicle for testing other software. VIII. C ONCLUSION 

Agentic GUI software uses observation, action, and feed-back tools to let LLM agents operate live interfaces. This paper analyzes 335 confirmed failures from 2,000 issues across 40 applications, identifying 11 defect patterns rooted in state representation, transition, and synchronization problems that degrade functionality, efficiency, and reliability across 90% of the studied applications. We release M ALVA , a defect library of confirmed failures with their root causes and impacts, and MALVA GUARD , a pre-deployment static contract checker that reaches 57.3% precision and 76.8% recall on an additional 20-application corpus. We hope this work can serve as a starting 10 point for improving the reliability of the tool layer in agentic GUI software. IX. D ATA AVAILABILITY
