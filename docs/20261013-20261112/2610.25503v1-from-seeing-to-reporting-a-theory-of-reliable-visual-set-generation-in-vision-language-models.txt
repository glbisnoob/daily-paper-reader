Abstract 

Vision-language models (VLMs) are asked to report what they see: to count objects, box them, parse a screen or pick a click target (GUI grounding). We argue that reporting is part of the visual task, not merely its formatting. In a dense scene with 173 shapes, GPT-6.1 lists 173 records that match every shape, yet the counts it states in the same response sum to 188. From Seeing to Reporting (FSR) is a theory of vi-sual reporting and a set of inference-time proce-dures that improve the reports of frozen VLMs. It models reporting as a chain from responses to decoded records, constructed sets and task answers, linked by task-compatible matching. The chain gives exact relations for deleting records, averaging their coordinates and switch-ing readouts, and it splits the error of one an-swer chosen among several calls into miss-ing candidates, lost representatives and wrong choices. These relations guide procedures for counting, detection, document layout, screen parsing and GUI grounding that use the task specification and a shipped configuration, with-out requiring labels from the target task. On 50 dense synthetic scenes, a one-call reporting-and-decoding protocol cuts per-type count error by 85.2% for GPT-6.1 and 98.8% for Claude Sonnet 5.5. On 600 ScreenSpot-Pro items, a GUI-grounding tier that combines three models lowers the miss rate from 13.67% for GPT-6.1’s two-stage zoom to 9.33%, against 12.67% for three such zooms combined by a cluster vote at about the same cost. A plain vote over the same three models misses 12.33%: the other mod-els supply the candidates, and selecting among them turns those candidates into fewer misses. We release the protocols, the stored responses and the analysis code.

A typical answer has two parts. The first is a list : one entry per object, each giving a class name and a location (a point or a box). We call each entry a record . The second, when it is requested, is a stated count : the numbers the model writes for how many objects of each class it found. Code can also count the records in the list; we call that the list count . The two counts should agree. Often they do not. Sonnet 5.5 wrote an exact list in 39 scenes (after mapping its word “diamond” to the class “square”), and its stated counts were wrong in all 39. The response contains a correct enumeration; the model’s own summary of that enumeration is not faithful to it. Visual set reports are becoming the interface be-tween perception models and the systems that use them: inventory counts, document layout, screen parsing for computer-use agents, click targets. What we do. We describe reporting as a chain with four objects (Figure 2): a response , the raw text of one call to a model; the records decoded from it; a set of records built from one or more responses, for example by keeping only records that two calls agree on; and the task answer read from that set, such as a count per class or a click point. Three quantities connect the chain to every loss we study: the maximum number of records that can be paired one-to-one with true objects un-der the task’s matching rule, the number of records that are scored, and the rule that reads the answer. They give exact relations for what each operation does. Deleting unconfirmed records lowers the er-ror exactly when the deletion loses fewer than one match per two scored records removed (with equal costs of the two error types), whichever model or view supplied the confirmation. Averaging the co-ordinates of agreeing records is a separate effect that can help or hurt. The chain takes reports as they come: from one call on the whole image, or from several views produced by an existing view planner such as tiling or zoom, whose merging and cross-view confirmation are constructions like any other. Alongside these relations we state a be-havioural model, kept separate from them: each object has a persistent tendency to be reported or missed, partly shared across models. This analysis of what a model reports complements analyses of what a single call can see (Shi et al., 2026). 

Seeing and reporting. The title names the two things the chain separates. What a set of calls has seen is its coverage : the correct records or candi-dates present anywhere in the responses, in any field, view or model. What is reported is a selec-tion from that coverage: which field is read, which records are kept, which point is output. The repairs in this paper add coverage, improve the selection, or, by averaging coordinates, move the records that are kept; on a fixed set of calls an operation helps exactly when, on what it changes, the errors it re-pairs outweigh the correct outputs it breaks, at the exchange rate the loss sets (Section 4). Reading the list instead of the stated count, and deleting unconfirmed records, change only the selection. Three problems, kept apart. Practice often treats three problems as one. Detecting that a report is wrong can be done without labels, from disagree-ment between reports (Proposition 6). Judging 

which of several reports or configurations is more accurate cannot in general be certified from out-puts alone, because two scenes can produce the same outputs (Proposition 11); it needs labels, on the task itself or on related sources from which a configuration is carried over (Section 7.9). Repair-ing a report works when the needed information is already available: in another field of the same response, in another view of the image, or in an-other model’s report. A method that detects errors well need not judge well, and one that judges well need not repair. A model asked at run time to score or compare candidate answers, as in our GUI-grounding tier, is one more source of evidence for a repair, not a certificate. The paper is organized around this distinction. 

Three answers. Do vision-language models report what they see? Not reliably, and the gap is visible within one response: in dense scenes GPT-6.1 and Sonnet 5.5 often write an exact list while the counts they state in the same response are wrong. Will better models make the repairs unnecessary? Some failures are already absent on our tasks: on our synthetic counting scenes, the average coordinate offset is about 1% of the matching tolerance, and Gemini 3.8’s default reasoning setting removes most of its broken lists. The gap between list and stated count, and object-level errors that repeat across calls, remain in the newest models we tested. More calls of the same model, or a different source of evidence? For counts, clicks and error detection, a different source helped more: another field of the same response, the original pixels of a smaller crop, or a different model. Repeating the same call helps mainly by removing false records that do not repeat. 

What we find. Measured against common reme-dies on the same stored calls (Section 7.1) and, for clicks, on 600 further items (Section 7.7), the shipped defaults do better than these remedies in most comparisons, and the theory’s quantities say where and why. 3• Repair the readout. On dense synthetic scenes with five classes, counting the list in-stead of reading the stated count cuts per-type count error by 71% to 84% in the same re-sponses of GPT-6.1 and Sonnet 5.5, and the full list-first protocol cuts it by 85.2% and 98.8% at the cost of one call, where self-consistency over three calls gains at most 23%. On one-class photographs, and on aerial and document images where the lists themselves miss objects, the protocol’s change is small and not significant for these two models; Gem-ini 3.8 needs its default setting, at which far fewer of its lists break (flagged lists 90% to 12%) (Sections 7.2 and 7.3). • Repair the set. When a partner call confirms the records of a base call, the change in set er-ror splits exactly into deleting the records the partner does not report and averaging the coor-dinates of those it does. Deletion helps when the marginal matching rate p1 of the deleted records is below 1/2; the task family’s default decides correctly in 85% of draws over 54 base/partner pairs, and five labelled images cut the loss from a wrong decision from 0.43 to 0.17 errors per image. Confirmation is a default for set error on over-reporting fami-lies only; for F1 the default is a single call (Sections 7.4 and 7.9). • Repair the view. Two-stage zoom cuts the miss rate by 65% for Gemini 3.8 and 41% for Sonnet 5.5 (not significant for GPT-6.1), where a three-click vote or zooming only on disagreement gains at most 13%. Confirming a whole-image report with four crop reports cuts set error by up to 45.5% and hurts where 

p1 > 1/2 (Section 7.5). • Detect. A second, cheaper model catches 61% of GPT-6.1’s misses and a second call of the same model 17%, at the price of flagging more items (Section 7.6). • Repair a click by choosing among models. 

The miss rate of one answer chosen among several calls splits exactly into three terms: no correct candidate, no correct cluster represen-tative, a wrong choice among representatives. FSR’s GUI-grounding tier, built on this split, misses 9.33% of 600 ScreenSpot-Pro targets, against 13.67% for GPT-6.1’s two-stage zoom, 12.67% for three such zooms at about the same cost, and 12.33% for a plain vote over the same three models’ points; against a crop-first baseline the difference, −2.17 points, has an interval that reaches zero (Section 7.7). • Judge. With the truth, choosing the best set among three calls of one model would remove 45% of set error; selectors fitted with labels reach 16%. Defaults chosen on other sources transfer: three-call unanimity improves set er-ror significantly in 9 of 15 over-reporting cells and significantly worsens none, and a single-call configuration chosen on three detection sources raises macro F1 on the fourth from 42.1 to 49.1 (Sections 7.8 and 7.9). 

Contributions. Our contribution is a common task-loss model for visual reporting, procedures that act on its stages, and experiments that separate what information is available from the quality of the answer finally delivered. The model covers multi-record outputs and the single-record case of click grounding. Its exact relations do not prescribe one universal interface; they say what each operation can change and what must be measured to decide whether the change is useful. 1. A common theory of reporting operations and task quality. A chain from response to records, set and answer, in which task-compatible matching, scored record counts and the readout express the losses for counts, boxes, screen elements and clicks; exact rela-tions for deletion, coordinate averaging and readout; conditions, stated as inequalities on confirmation rates, under which repetition, a new view or a second model helps, with a behavioural model of persistent errors; a con-strained oracle for any declared family of can-didate sets; an exact split of the error of one answer chosen among several calls, with the effect of adding a source and of switching an answer; and an impossibility result for certi-fying a report from outputs alone (Sections 3 and 4). 2. Executable procedures for recovering, con-structing and selecting visual records. A de-fault pipeline that dispatches by task and bud-get, and a several-model GUI-grounding tier, in which every input is named (task specifi-cation, shipped configuration, computed from 4the outputs, or optional labels), together with the revisions of the model that led to them (Section 5). 3. Mechanism-resolving evidence and afixed-protocol evaluation of complete task outputs. Measurements on 67,364 calls to five proprietary models and one open-weight model that attribute gains and failures to single operations, and a 600-item click evaluation of the complete tier. All responses, the labels whose licences allow redistribution, a script that rebuilds the others from the official downloads, and the code that regenerates every table and figure are at

2 Related Work 

Counting and set reporting by VLMs. Count-ing is a long-standing weak spot of vision-language models (Paiss et al., 2023; Rahmanzadehgervi et al., 2024), and recent work locates part of the failure after perception: count information can be present in internal representations yet misaligned with the emitted number (El-Shangiti et al., 2026), and a visual counting bottleneck has been isolated in the model pipeline (Pang et al., 2026). Training-free fixes divide the image and count per region (Qharabagh et al., 2026), in the spirit of sliced in-ference for small-object detection (Akyon et al., 2022). Point-and-count supervision (Deitke et al., 2025) and sequence-style detection (Chen et al., 2022; Li et al., 2025a) make the list itself the out-put. Program-based visual reasoning counts by running code over the items a model finds (Gupta and Kembhavi, 2023; Surís et al., 2023); we show that the same code readout repairs the counts a sin-gle model writes about its own list. We work with frozen API models and observe the same gap from the outside: the information is in the model’s own list in the same response, so the fix is a readout rule rather than a probe or a training signal. We also extend the analysis from counts to boxes, screen elements and clicks, where the loss is a matching between sets. 

Views: zoom, tiles and resolution. Zooming in improves fine-grained perception (Wu and Xie, 2024; Shen et al., 2024; Zhang et al., 2025) and GUI grounding (Jiang et al., 2025; Tang et al., 2026), and region-level consistency can be used at test time (Du et al., 2026). GUI-Lens lets a single general-purpose model crop from coarse to fine, with OCR and detector anchors and a verifi-cation step (Fu et al., 2026); Section 7.7 compares our GUI-grounding tier with a simplified crop-first baseline in its style and shows that the two err on different items. A companion study analyses when zooming in is safe for small objects (Shi et al., 2026). Uncertainty-driven zoom on open 7B mod-els found that zooming every item can hurt (Tang et al., 2026); on frontier API models we find two-stage zoom on every item, in the style of ReGround (Li et al., 2025b), not significantly different (GPT-6.1) or better (Sonnet 5.5, Gemini 3.8), and cheaper than zooming only on disagreement. The two ob-servations are compatible: whether zoom hurts de-pends on whether the crop cuts the target and on the relative cost of the second call (Section 7.5). 

Visual scaffolds. Overlaid marks and coordinate grids are a popular way to help models localize (Yang et al., 2023; Lei et al., 2025). An overlay adds no Shannon information to the sent image and can only change how the model uses it (Shi et al., 2026); we observe two such changes in cur-rent models (fewer omitted class fields for Gemini 3.8, more uses of a class name outside the vocabu-lary for Sonnet 5.5) and no coordinate correction, because on synthetic counting scenes their system-atic coordinate offset is about 1% of the matching tolerance. 

Self-consistency, self-correction and cross-model agreement. Sampling several answers and voting improves reasoning (Wang et al., 2023), but mod-els often fail to correct themselves (Huang et al., 2024; Madaan et al., 2023; Liao et al., 2025), and their errors can be self-consistent and hard to de-tect (Tan et al., 2025; Bhat and Yamasaki, 2026). Disagreement between different models comple-ments self-consistency for uncertainty estimation (Hamidieh et al., 2026), and multi-VLM agreement has been used to verify OCR (Zhang et al., 2026); we use disagreement among three frontier models’ clicks as an alarm and choose among their points with a scoring model (Section 5.1); test-time scal-ing can also separate perception from reasoning (Avogaro et al., 2026). In set tasks these effects have a precise form: confirmation changes the set error by an exact identity, and whether a partner helps depends on its confirmation rates for the base model’s true and false records, not on its overall quality (Proposition 5). 5Ensembles, fusion and selective prediction. 

Weighted box fusion averages coordinates of matched detections (Solovyev et al., 2021), and de-tection ensembles combine models by affirmative, consensus or unanimous voting (Casado-García and Heras, 2020); our three-call unanimity is the unanimous strategy applied to repeated calls, and we show that its effect splits into a selection term and an averaging term, the latter of either sign un-der threshold matching. Error decompositions for detection split error into classification, localization, duplicate and background parts (Bolya et al., 2020; Oksuz et al., 2018); our split is instead by operation, so that each term belongs to one decision. Classi-cal models for aggregating judges assume errors that are independent given the truth (Dawid and Skene, 1979; Grofman et al., 1983), which object-level persistence violates. Work on ensemble diver-sity measures how correlated the members’ errors are (Kuncheva and Whitaker, 2003), and deep en-sembles obtain diversity by training members in-dependently (Lakshminarayanan et al., 2017); our members are repeated calls of fixed models, and we measure how strongly their errors on the same object are shared. Our alarms are evaluated as risk-coverage curves, as in selective classification (Geifman and El-Yaniv, 2017). The matroid struc-ture of matching rank (Edmonds and Fulkerson, 1965) and the assignment algorithm (Kuhn, 1955) underlie our identities and oracle, and one-to-one matching between predicted and true sets is also the loss of set-prediction detectors (Carion et al., 2020). 

What is known and what is new in the theory. 

Several of our relations specialise known results to record sets. The deletion threshold is the cost-sensitive decision threshold (Elkan, 2001); its F1 form matches the result that the F1-optimal thresh-old is half the optimal F1 (Lipton et al., 2014); diminishing coverage is the submodularity of cov-erage (Nemhauser et al., 1978); the certification bound is a two-point argument (Tsybakov, 2009); and the propensity model is related to labeler-expertise models (Whitehill et al., 2009). The three propositions on choosing one answer among sev-eral calls are elementary: a partition of the miss event, the chain rule, and the law of total proba-bility. The quantity F is the miss counterpart of pass@ k-style coverage of a candidate set; what the propositions add is the bookkeeping with represen-tatives fixed before any choice, which makes the three terms measurable on stored calls (Section 7.7). The set-reporting setting adds three things. First, a deleted record can lose fewer matches than it held, because a remaining record may take over its target, so the threshold concerns the marginal matching rate p1 rather than precision, and p1 estimated on five labelled images, with the task family’s default as the starting point, predicts the effect of deletion on other images. Second, a selector and an oracle can be compared fairly only within the same feasi-ble family, which the constrained oracle provides. Third, a view can confirm or reject only the records it contains, which restricts cross-view confirmation to each view’s field. The chain itself is the unifying contribution: the same three quantities, matching size, scored record count and readout, carry these results across counts, boxes, screen elements and clicks. 

Benchmarks. We use SKU-110K (Goldman et al., 2019), DOTA (Xia et al., 2018), Do-cLayNet (Pfitzmann et al., 2022), FSC-147 (Ranjan et al., 2021), PixMo-Count (Deitke et al., 2025), ScreenSpot-Pro (Li et al., 2025b), ScreenSpot-v2 (a corrected release of ScreenSpot; Cheng et al., 2024), GroundCUA (Feizi et al., 2026) and Screen-Parse (Gurbuz et al., 2026), together with a syn-thetic counting probe whose labels are exact.

3.5 Output contract and status 

The decoder reports four status layers for every call. They are distinct, and passing a lower layer never implies a higher one. L1 transport : the call returned, and its finish reason (stop, length) is recorded. L2 outer syntax : the whole response parses as the requested JSON object after stripping a code fence. L3 record validity : which records were recovered (strict parse, or a declared salvage of individual objects when the whole response does not parse), which of them are valid under the task contract, and four list-level degeneracy flags (Sec-tion 5). L4 task completeness : whether S contains every target. L1 to L3 are checked by code; L4 cannot in general be checked without labels (Sec-tion 4.5). The procedures return S, ˆy and σ for every input, never drop a call from cost or denomi-nator accounting, and report the strict-JSON failure rate, so the share of salvaged responses is visible.

4 Theory 

One principle runs through the results on opera-tions. A library of calls fixes what can be reported, its coverage; a rule applied to the library decides what is reported, its selection. On a fixed library, an operation lowers the loss exactly when, on the records or items it changes, the errors it repairs out-weigh the correct outputs it breaks, at the exchange rate the loss sets. Section 4.1 states the exact re-lations for record sets: deleting records, averag-ing their coordinates, and reading a different field of one response. Section 4.2 gives a behavioural model of how models report objects across repeated calls, views and models, which says when a part-ner adds coverage; unlike the relations, it is an as-sumption to be checked. Section 4.3 bounds what selection over a fixed library can reach. Section 4.4 treats a single answer chosen among several calls: the three places where a miss can arise, the cov-erage an added source brings, and the net effect of switching an answer, which is the principle’s form for clicks. Section 4.5 states what outputs alone cannot certify. Table 3 lists, for each result the method uses, the quantity it measures, the deci-sion it makes and where it is checked. 4.2 Behaviour under repetition, changed views and changed models Joint reporting law. Fix a complete interface η:model, prompt, schema, setting, cap and view. A call with interface η reports a true object o with probability qo,η , and a candidate false object f (a location where false records tend to appear) with probability qf,η . Given these propensities, repeated calls with the same η are independent. This joint law, with q free to depend on every part of η, is the behavioural model; the consequences below use only it, together with conditional independence given the propensities for calls with different in-terfaces wherever that is stated, and not the ex-planatory logit parametrization (object, model and view terms) of Appendix A.1. A reported record contributes to the loss only through the matching: emitting a record near o, producing a match, and adding a match that no other record already pro-vides are different events. Three consequences are used in the paper. Per-sistence : for fixed η, the probability of missing o

in all K calls is (1 − qo,η )K , and averaged over ob-jects it is E[(1 − qo,η )K ], which tends to the share of objects with q = 0 . The decay is slow when q is small for some objects, so at a fixed budget many misses repeat. Diminishing coverage : for calls that are exchangeable given the image, the expected number of targets matched by the union of K calls is concave in K; this follows from the submodu-larity of coverage (Nemhauser et al., 1978) and of matching rank (Lemma 1). The statement concerns raw coverage, not the loss of a constructed set: re-peated calls can still remove false records that do not repeat. For example, with 20 true records that are always reported and 80 candidate false records reported independently with probability 0.2, one call has expected E = 16 and three-call unanim-ity has expected E = 0 .64 . The argu-ment is the two-point method of minimax lower bounds (Tsybakov, 2009); methods that estimate accuracy from the agreement of several classifiers without labels (Platanios et al., 2014) rely on as-sumptions, such as weakly dependent errors, that rule such pairs out. Kϑ (with equal priors, the best probability of nam-ing the right world is (1 + TV) /2), and no test is reliable uniformly over admissible classes in which 

ϑ can be arbitrarily small. The practical reading: agreement alone does not certify correctness. This does not prevent running a default procedure, or-dering interfaces under explicit assumptions tested on other data, as the companion paper does for decomposition (Shi et al., 2026), or operating a configuration chosen on source data without new labels. 

Corollary 1 (Sign of a count gap) . Suppose that, for a given report S, some admissible world has 

|S| > n , and that the admissible worlds are closed under adding any number of targets that no inter-face reports and that do not change the rest of the output. (This differs from the sign of a recall gain between two interfaces, which assumptions such as monotonicity in tokens per object can fix.) 

Without further information, neither deleting un-confirmed records nor keeping them dominates for a count objective. Our count procedure keeps them, a conservative choice whose quality we evaluate empirically.

Step 4: views. For clicks we use a re-grounding strategy in the style of the ReGround method that Li et al. (2025b) evaluate. The first call gives a point on the whole screenshot. A crop one third of the screenshot’s width and height, centred on that point and shifted to stay inside the image, is sent at native pixels, and the second call gives the point in the crop. If the second call gives no point, the first point is kept; if the first call gives no point, there is nothing to zoom on and the answer is no point, which counts as a miss. Using agreement to decide when to zoom costs more and is not more accurate (Section 7.5). For sets and counts, the pipeline does not plan views itself: it works on whatever reports it is given. By default it sends the whole image. When a view planner is configured, for example a tiling scheme or the companion paper’s safe decom-position, which places every target wholly inside some view, with neighbouring views overlapping by one object and no view having fewer tokens per object than the whole image, and cannot lower expected recall under that paper’s monotonicity as-sumptions (Shi et al., 2026), each view is one call, its records are mapped to image coordinates, and Step 5 merges them. We computed the apparent size of every annotated object in the whole-image calls on SCP-dense, DocLayNet, DOTA and SKU-110K, using the input geometry measured in the companion paper and its released calibration data (32-pixel tokens for GPT-6.1, 28-pixel tokens for Sonnet 5.5, a fixed grid of about 1,090 tokens for Gemini 3.8). The median object spans 0.62 to 1.43 16 tokens across its shorter side (the companion paper measures size as the square root of the area, which is never smaller). Below that paper’s design value of S⋆ = 1 .5 fall 55% to 79% of objects on the three detection sources and every shape on SCP-dense; yet GPT-6.1 and Sonnet 5.5 write nearly exact lists on SCP-dense. The companion paper likewise finds that these model families reach half recall at well under one token per object side. A fixed threshold would decompose images whose whole-image report is already complete, so when to call a planner is a property of the model and the task that the configuration supplies. These sizes come from the annotations and inform only this de-sign choice; the pipeline reads no annotation at run time. Section 7.5 reports how the pipeline handles reports from four crops, and how our own tiling arm, which did not meet the safe condition, fared on large objects. 

Step 5: construction. The construction is chosen per loss (Table 4). Records of different calls are associated without labels (Table 2): boxes of the same class with IoU ≥ 0.5, screen elements at IoU 

≥ 0.5 without class, and points of the same class within the task’s tolerance. On over-reporting task families and set error, three calls are made and a record is kept only if all three report it, with its co-ordinates averaged over the three. Everywhere else a single call is delivered without deletion. Over-or under-reporting is a property of the task family, shipped with the configuration from our evaluation; the user does not supply it. Coordinate averaging is on by default because its contribution is positive in 37 of 54 base/partner pairs and negative in 13 (Sec-tion 7.4); the deletion-only variant is in the menu. Reports of several views are first merged into one report: the union of their records, where a record is dropped if it is associated with a record already kept from another view (a duplicate in an overlap). When reports from different views confirm one an-other, a view can confirm or reject only records that lie wholly inside it; a record that no partner view contains is kept (Section 4.2). A call that still has no readable answer after recovery counts as an empty report, so three-call unanimity keeps nothing on that image; this is the construction we evaluated, and dropping such a call from the support count is in the menu. 

Step 6: readout. The answer is read from the final set. For counts it is the list count of S,the number of records of each class. When the list behind S carries a degeneracy flag and the response stated counts, the answer falls back to the stated count d, and the status says so ( count_from_statement ); a flagged list without stated counts keeps the list count and its flag. With several views, each response states counts for its own crop, and overlapping views would count shared objects twice; stated counts are therefore never combined across views, and a flagged merged list keeps the list count, with the status saying that no stated count was used. The fallback changes only the count: S itself is not re-paired, so the count and the set each carry their own status. The flags, not the readout gap, trig-ger the fallback, because a gap shows that the two readouts disagree without saying which is right (Proposition 4). 

A second model [config] , optional. When a sec-ond model is configured, its default role is the alarm of Step 8: its answer is compared with the user’s, and items where they disagree by more than a threshold are flagged. The disagreement dis τ is the summed per-class difference of the two answers for counts, the number of records not associated across the two answers for sets (Table 2), and the distance between the two points as a share of the longer image side for clicks, where a missing point always raises the alarm. The partner is fixed by a rule (GPT-6.1 and Sonnet 5.5: Gemini 3.8; Gemini 3.8: Sonnet 5.5), which picks the cheapest other model per click call (Appendix D), and the thresh-old δ is a point the user picks on the risk-coverage curve (Section 7.6; shipped default 1.5%). Using the second model to confirm records is a menu op-tion, chosen with labels or a shipped family-level ranking rather than as a zero-label default, because it is worse only in cells where the user’s own model is the strongest (Section 7.9). 

Step 7: optional labels [labels] . Labels are never required. With fewer than three labelled images the pipeline keeps the shipped default and reports the labelled error. With three or more, it switches to another configuration from the menu only if that configuration’s mean advantage over the labelled images, paired by image, minus one standard error is positive. Section 7.4 evaluates this rule for the decision to delete unconfirmed records. With 5 to 10 labelled images it may also fit the record gate, a logistic selector on output features (Section 7.8). The repository implements Steps 1 to 6 and 8 of Algo-rithm 1 for counts, sets and single-model clicks, including merging views and cross-view confirma-tion, as a single entry point ( fsr_pipeline/ )whose branches read only the task specification, the shipped configuration and the responses a client re-turns; the label rule of Step 7 is a function in the same module, and the record gate is fitted by the analysis code of Section 7.8. Algorithm 2 runs as a separate function ( gui/code/decision.py ), and the per-model F1 configuration is a key of the shipped configuration file evaluated by the analy-sis of Section 7.9; neither is a branch of this entry point. A replay client serves the stored responses of this paper instead of calling a model. A request for which nothing was stored, such as a follow-up that was never sent, returns “unavailable”, and the pipeline continues on its documented branch. Run on raw responses, the entry point reproduces the component analyses: the count errors of Sec-tions 7.2 and 7.3, the click hit rates after two-stage zoom of Section 7.5, and, with recovery switched off, the set error of the shipped construction in all 18 transfer cells to within 0.07 per image, a dif-ference that comes from the 0.1-pixel coordinate rounding of the component analysis. Follow-ups were stored for a sample of flagged detection calls. In the 18 set cells, 171 image runs had at least one flagged call; a stored follow-up cleared the flag in 24 of them, and replaying these changes set error by at most 0.55 per image in any cell. No follow-ups were stored for the count experi-ments, where 51 runs were flagged, so their re-sults are those of the first call. Synthetic bound-ary cases go through the same code, and each pro-duces an answer, a readout branch and a status: an empty or unreadable response, truncated JSON, a list without stated counts, a degenerate list with and without stated counts, two transport failures in a row, one unreadable call among three, and a click with no first point or no point in the crop. The replay output is released with the analysis outputs (pipeline_replay.json ). 

5.1 GUI grounding: clicks from several models 

Algorithm 1 delivers one model’s two-stage zoom point. When the per-item budget covers the planned worst case of a second tier, the pipeline offers one built on the three sources of a miss (Proposition 8); 18 its mean cost is about 3.2 times that of one zoom. Its run-time inputs are the image, the instruction and the budget; it reads no target label and does not abstain. The models, their settings, the distance 

δ, the scorer and the number of compared clusters come from the shipped configuration [config] .Algorithm 2 gives the steps, organised by Propo-sition 8. Generation enlarges the candidate menu, which is the only way to lower F ; Section 7.7 mea-sures the rescue rate of each source on the others’ misses (Proposition 9). The representative step fixes which member of each cluster can be output, and the comparison chooses among representatives, so these two steps divide the remaining misses be-tween L and W . The comparison runs only on items with an alarm, where the measured miss rate of the scorer’s choice is highest (Sections 4.4 and 7.7); items whose candidates form one cluster keep that cluster’s representative. The scorer’s hit score is used only to rank. The registry makes the point that is scored, drawn, compared and returned the same point: every step refers to a candidate by its identifier, and the code asserts that the coordinates drawn for the scorer equal those returned. If a call fails, the procedure continues with the remain-ing candidates. It returns no point only when no candidate is available; a missing point counts as a miss, and every returned point is scored by the hit-in-target rule. The budget selects among planned call schedules before inference: the tier runs only if the budget covers its planned worst case of 15 calls at per-call output caps of 16,384 tokens at the lowest setting and 32,768 at the default. Techni-cal retries are outside this bound, and the per-item costs we report are realized averages over all at-tempts, retries included. The rules are implemented as one deterministic function over stored or live responses ( gui/code/decision.py in the re-lease), with request builders for each step; with the evaluation script, run on the stored responses, it regenerates the results of Section 7.7. 

5.2 Revising the model from failed predictions 

The theory was built by iteration, and the iteration is part of the method. A model is stated, a conse-quence is derived and tested, and when a prediction fails we record three things: which assumption failed and how we know; how the revised assump-tion was checked directly; and what new conse-quence the revision predicts, and whether it holds. 6 Experimental Setup 

Models and settings. The main experiments use three API models: GPT-6.1 (OpenAI), Claude Son-net 5.5 (Anthropic) and Gemini 3.8 Flash (Google), written Sonnet 5.5 and Gemini 3.8. Pilots and the controlled-scene experiments also use GPT-5.6 and Opus 5.5, and an open-weight model, Qwen3-VL-235B, is tested in the pilots and on the readout tasks. Each call uses either the lowest reasoning setting the API offers or the default setting. Setting labels do not match behaviour, and we report what was measured (Appendix C). Three facts matter for interpretation. First, the default setting also doubled the output cap (16,384 to 32,768 tokens); three runs separate the two: the Gemini 3.8 runs of Section 7.3, a 90-call 16k control on the de-tection sources, and a 16k control on controlled scenes. Second, Sonnet 5.5’s reasoning share at its default setting varies by task: 0% to 23% of calls in the reasoning experiment (dense scenes, FSC-147, screens) and 0% to 90% across detec-tion cells; we attribute a Sonnet result to reason-ing only where most of its calls reasoned. Rea-soning tokens are read from the usage fields of every call after the pilots (Qwen3-VL is an in-struct model and reports none); the two pilots logged no thinking tokens for the Claude mod-els. Third, Gemini 3.8 at its lowest setting still reasoned on click and point outputs (about 99% of GUI click calls), so its click results at the lowest setting include reasoning. GPT-6.1’s lowest setting is reasoning_effort=low , and most of its calls carry some reasoning tokens. Images sent to Sonnet 5.5 were resized to at most 1,568 pixels on the long side and 1.15 megapixels (by our code, or in the detection experiment by the provider), and images sent to the other models to at most 2,048 pixels; for Sonnet 5.5 this is below the 2,576-pixel long edge measured for it in the companion paper (Shi et al., 2026).

7 Results 

The results follow the three problems of Section 1: a comparison with common practice (Section 7.1), repairing reports (Sections 7.2 to 7.5), detecting errors (Section 7.6), repairing a click by choosing among several models (Section 7.7), and judging which report or configuration is more accurate (Sec-tions 7.8 and 7.9). Each table caption states the operation, the comparator, the loss and any label 21 use. 

7.1 Against common practice 

The comparisons in this subsection use the stored calls of the earlier experiments; the 600-item click evaluation is in Section 7.7. Table 7 compares the defaults of Section 5 with the remedies practitioners use most, on the same stored calls. The pattern follows the three prob-lems. Self-consistency repeats the same source of evidence, so its gains are small: the median of three stated counts helps GPT-6.1 by 23% and the other two models by about 1%, at three times the cost, and a vote of three clicks changes the miss rate by 

−4.5% to +2 .5% . Uncertainty-gated zoom, which zooms only when two clicks of the same model disagree, inherits the same weakness, because per-sistent errors rarely produce disagreement; it gains 13% for Gemini 3.8 and nothing significant for the other two. The remedies that change the in-formation win: reading the list cuts dense-count error by 85% and 99% for about the cost of one call, and zooming every item cuts the miss rate by 45% and 65% for less than a three-click vote. For set error, three-call unanimity with averaged coor-dinates improves 9 of the 15 over-reporting cells (median −9.6% ), against −2.9% for majority vote and −3.7% for box fusion, and it beats box fusion directly in 11 of the 15 cells and is not significantly worse in any. For detecting missed clicks at the same distance threshold, a second model catches 1.9 to 3.5 times the share of errors that a second call of the same model catches, while flagging more items (Section 7.6). 

7.2 Repair the readout: read the list, not the number Same response, two answers. Figure 3 shows one response in full. When a list-first response has both a list and stated counts, the list length misses the true total by 0.04 objects on average for GPT-6.1 and 0.02 for Sonnet 5.5, while the stated totals miss by 7.78 and 10.48 (Table 8, last row). Read-ing per-type counts from the list (the list count) instead of the stated counts in the same response cuts per-type count error by 75.6% (GPT-6.1) and 77.7% (Sonnet 5.5) under a count-first prompt, and by 84.2% and 70.7% under the list-first prompt. Generation is held fixed in these comparisons, so the gain is a readout effect: the model’s list carries information that its own summary loses. 

The gap grows with the length of a multi-type list. Figure 4 (values in Table B.1) repeats the same-response comparison on four datasets. On PixMo (6 objects per image, one class) and FSC-147 (43.8 objects, one class), the stated total tracks the list for GPT-6.1 and Sonnet 5.5 and the differ-ence is not significant. On SCP (47.6 objects, five classes) the list count is better by 44% for GPT-6.1 and by 98.5% for Sonnet 5.5, whose stated per-type counts are 65 times as far from the truth as its list. On SCP-dense (164.3 objects) both models gain 76% to 78%. The gap therefore appears when the stated count must summarize a long list across several classes. 

Aliases and protocol. In list-first responses, Son-net 5.5 wrote 258 “diamond” records across 50 im-ages although the format listed the allowed names. The declared alias map, applied to the same list, takes its error from 5.42 to 0.42 ( −92 .3% ). The prompt alone does not do this: the map is part of the task, and the decoder applies it. Holding the mapped readout fixed, list-first lists are better than count-first lists by 39.4% for GPT-6.1 and 92.3% for Sonnet 5.5. The complete protocol, compared with the stated count of a count-first response, cuts error by 85.2% [−89 .1, −80 .3] for GPT-6.1 and 98.8% [−99 .5, −98 .1] for Sonnet 5.5. For Gem-ini 3.8 at its lowest setting the change is +15 .6% [−5.3, 39 .4] , not significant: the degeneracy check routes 40 of its 50 responses to the stated count. These are effects of the reporting and decoding protocol. The same-response and same-list com-parisons isolate the readout and the alias map; the full protocol also changes how the list is generated. 

Aerial and document images with several classes.

7.3 Repair the readout when the list degenerates 

Gemini 3.8 at its lowest setting writes long lists in which most records lack a valid class and some co-ordinates repeat, so the list count is far worse than its stated count ( +182 .5% in the same response; Figure 4). The four-part degeneracy check of Sec-tion 5 flags 45 of its 50 dense-scene lists. For 40 of them the readout falls back to the stated count; the other 5 have no stated count and keep the list count with a status flag. On the GPT-6.1 and Sonnet 5.5 list-first responses it flags none. For Gemini 3.8, degeneration depends mainly on the reasoning setting. At the same 16k output cap, Gemini 3.8’s default setting reduces flagged lists from 90% to 12% and the readout error from 52.80 to 24.52 ( −53 .6% [ −72 .4, −29 .5] ; Table 10). Dou-bling the cap to 32k gives a point estimate of 15.44, a further change that is not significant. Even then, Gemini 3.8’s dense-count error is about ten times GPT-6.1’s, and none of its 50 counts is exact. Strict JSON parsing fails for 70% to 78% of Gemini 3.8 responses at every setting, so the declared record salvage of Section 3.5 is a necessary part of the decoder, and its share is reported. On the list-first responses of the readout ex-periment, applying the same check to existing re-sponses recovers 68% (SCP) and 58% (SCP-dense) of Gemini 3.8’s error relative to reading its list, and 42% relative to the stated count on FSC-147. For Sonnet 5.5, whose lists are not degenerate, the cost of the check reaches +23% on SCP and +13% 

on SCP-dense (not significant; intervals [0 , 57] 

and [0 , 26] ). On the open model Qwen3-VL, with thresholds unchanged, it lowers SCP-dense error by 7% [−13 , −1] relative to the stated count. Gemini 3.8’s missing class fields follow a pattern: a record is more likely to omit its type when the previous record has the same type, and a row-by-row scan that interleaves types cuts its count error by 60%, while grouping by type makes it worse. 

7.4 Repair the set: delete below the threshold, keep geometry separate Deletion and geometry, measured separately. 

Table 11 (per-pair values in Table B.2) splits the effect of confirming a base call with a partner call into the selection term of Proposition 1 and the ge-ometry term of Proposition 3, for 54 base/partner pairs on six sources. Both identities hold exactly on every image, so the selection term of a pair has the sign of 1 − 2p1 by construction (Figure 5a). What the data add is where p1 lies: 0.00 to 0.39 on SKU-110K and 0.05 to 0.22 on DOTA, where dele-tion removes 4 to 68 errors per image, against 0.39 to 0.90 on FSC-147. On FSC-147, where models under-report, p1 is 0.39 to 0.90 and deletion hurts in 7 of 9 pairs, which is why counting families keep a single call. Coordinate averaging is positive in 37 pairs and negative in 13. In two pairs it reverses the sign of the deletion-only result: DocLayNet with GPT-6.1 confirmed by Sonnet 5.5 (selection +0 .80 ,geometry −1.10 per image) and GroundCUA with Sonnet 5.5 confirmed by itself (selection −0.87 ,geometry +1 .20 ). These are the two pairs in which an earlier check of the threshold on intersections with averaged coordinates failed; separating the terms accounts for both. 

The threshold from a few labels. The useful question is whether p1 measured on a handful of labelled images predicts what deletion will do on other images. For each pair we drew 5 labelled images 200 times, estimated p1 on them, and pre-dicted from Proposition 2 whether deleting uncon-firmed records lowers set error on the other 55 im-ages of the pair. The prediction is right in 83% of draws (80% with 3 labelled images, 87% with 10), and the loss against the better decision on the other images is 0.33 errors per image (0.48 and 0.15). The shipped family default alone, which deletes on over-reporting families and keeps on FSC-147 without any label, is right in 85% of draws with a loss of 0.43. The label rule of Step 7 combines the two: it starts from the family default and switches only if the labelled images favour the other deci-sion by more than one standard error. Reports from a view planner. In the crop calls of the Review experiment (Table 6) the pipeline receives, for each image, a whole-image report and four reports from four native-resolution crops (6% overlap, one call per crop), on 30 Ground-CUA screens and 30 SKU-110K images, scored at IoU ≥ 0.5 without class. Merging the four crop reports alone lowers set error relative to one whole-image call for GPT-6.1 on screens ( −19 .4% [−27 .5, −10 .6] ) and for Sonnet 5.5 on SKU-110K (−64 .0% [ −70 .6, −56 .6] ), raises it for Sonnet 5.5 on screens ( +44 .9% ) and for Gemini 3.8 on SKU-110K ( +24 .7% ), and is not significant in the other two cells. Confirming the whole-image report with the merged crops under the shipped rule, in which a crop confirms or rejects only the records it contains wholly, lowers set error in 4 of 6 cells: GPT-6.1 ( −22 .8% ) and Gemini 3.8 ( −20 .3% ) on screens, and GPT-6.1 ( −45 .5% ) and Sonnet 5.5 (−36 .6% ) on SKU-110K. In these 4 cells it is also better than confirmation by a second whole-image call ( −11 .8% to −22 .6% ), and better than the shipped three-call unanimity in 3 of them ( −8.0% 

to −20 .2% ; Gemini 3.8 on screens −4.7% , not sig-nificant), at the price of five calls instead of three. In the other two cells it raises set error: Sonnet 5.5 on screens ( +12 .9% ) and Gemini 3.8 on SKU-110K ( +37 .9% ). The threshold of Proposition 2 accounts for both groups. Among the whole-image records that the crops do not confirm, the share matched to a true object ( p1) is 0.03 to 0.24 in the four cells where confirmation helps, and 0.62 and 0.76 in the two where it hurts, as the identity requires. The plain rule, in which every record needs confirmation, differs from the shipped rule by at most 4 percentage points, because with a 6% overlap few records lie wholly inside no crop. 

Grids and coordinates. On SCP, the systematic coordinate offset of current models is at most 0.3 pixels, with slope 1.000 and spread 0.9 to 1.5 pixels, against a matching tolerance of 30 pixels. A grid, ticks or cell labels therefore have no coordinate error to correct: in every arm, localization changes by at most 0.23 pixels, and at the lowest setting they do not significantly change detection for GPT-6.1 and Sonnet 5.5. For Gemini 3.8 at its lowest setting, a grid lowers set error by 3.5 per image by reducing records that omit their class, and a row-by-row scan lowers it by 11.5; at its default setting the grid makes detection and localization slightly worse. “No overlay” is therefore the shipped de-fault, chosen from these measurements; the theory does not forbid an overlay from helping a model whose list format it changes. Markers also make Sonnet 5.5 write “diamond” more often ( +0 .3 per image). An overlay adds no Shannon information 28 and can only change how the model uses its input (Shi et al., 2026); the two changes we saw are of that kind. 

Wording, instructions and review. “Do not miss any” wording, compared with a symmetric instruction not to miss or invent, has no measurable effect on SCP for any of the three models. Asking the model to localize each item relative to struc-tures in the image has no significant effect, because current models have almost no location misses on these scenes. Same-view self-review, in which the model edits its own draft, confirms true and false records at nearly the same rate ( h+ ≈ h−) and has no net gain on screen parsing; on FSC-147 it gave significant gains for 2 of 3 models, which we do not explain. Pairwise comparators that ask a model which of two reports is right judge whether some-thing is an object rather than whether the box is pre-cise, and are not used. Reasoning is not uniformly helpful: on 20 GroundCUA screens, GPT-6.1’s default setting raises set error by 18.7 per screen 

[5 .8, 34 .3] , through 16.3 additional false records and no fewer misses. 

7.6 Detect errors: they persist, so ask someone else Persistence. Object-level errors repeat across calls. Intraclass correlations of reporting across repeated calls are 0.60 to 0.98 for true objects and 0.23 to 0.93 for false reports. On the detection sources, a binomial model with a common report-ing probability is rejected in all 12 dataset and model cells, while a beta-binomial model fits. The share of misses that recur in every repeated call is 0.76 to 0.99 on the detection sources and 0.73 to 0.94 on the screen sources. In clicks, 64% to 83% of a model’s errors are repeated by a second call of the same model within the agreement tolerance. 

A second model is a better alarm. Persistence means that a second call of the same model rarely disagrees with the first where the first is wrong. A second model shares only part of the propensity. With the partner set by a fixed rule as the cheapest other model, the share of errors in which both calls agree on the same wrong point falls from 83% to 39% for GPT-6.1, from 64% to 29% for Sonnet 5.5, and from 73% to 48% for Gemini 3.8. In the risk-coverage analysis (Figure 6), at δ = 1 .5% , the same-model alarm catches 17% of GPT-6.1’s er-rors (4 of 23) and the cross-model alarm catches 61% (14 of 23); for Sonnet 5.5 the shares are 36% and 71% (Table 12). The cross-model alarm sets more items aside, and Figure 6 shows the trade-off: where the two curves overlap, its miss rate at matched acceptance coverage is lower by 0.5 to 2.7 points (point estimates on 260 items, without intervals; for GPT-6.1 at 93.1% acceptance cov-erage it catches 9 of the 23 errors against 6 for the same-model alarm), and for GPT-6.1 and Son-net 5.5 it reaches operating points with a miss rate of 3% to 4%, below the lowest same-model val-ues (7.0% and 10.5%). After two-stage zoom the same pattern holds, so the advantage comes from the second model and not from zoom alone. We zoomed each model’s second click as well (772 calls), so that both alarms compare zoomed points. At δ = 1 .5% a second zoomed call of the same model catches 40% to 50% of the remaining er-rors, and the partner’s zoomed point catches 68% to 78%, with miss rates of 2.6% to 3.6% on the 85% to 88% of items acted on (Table 12). The same-model alarm again acts on more items (93% to 94%); where the two curves overlap, the cross-model miss rate at matched acceptance coverage is lower by 0 to 1.5 points.

7.8 Judge: selection has room left, but labels do not close it Selection among a model’s own outputs. 

Choosing the best feasible set from a model’s own three calls would remove 45.2% of set error rela-tive to one call (median over 12 cells; Table 14), and 72% to 74% for GPT-6.1 on SKU-110K and DOTA. The constrained oracle differs from the un-restricted value on 25 of 720 images and has the same median. Record gates on output features, fit-ted with labels and evaluated by cross-fitting, reach 15.6% (logistic) and 14.6% (boosted trees); fitted on 10 labelled images they reach 13.2%. The more flexible selector does not help under cross-fitting, and its in-sample value (36.5%) is overfit. The em-pirical gap, median 26.1 points, combines informa-tion absent from the output features with selector and estimation shortfall (Proposition 7); our results bound it but do not apportion it. It measures the distance between the tested selectors and the best set in a fixed library of three calls, so it does not bound what adding calls or changing the library could gain. Within the operations we compared, the larger gains came from changing the informa-tion, a different view, model or readout, rather than from selecting among a model’s own outputs. 

7.9 Judge: defaults that transfer 

Table 15 (full values in Table B.4) evaluates con-struction transfer on stored reports: for each source, the construction that does best on the other five sources is applied to the stored calls of the sixth, so it is never chosen on the source it is evaluated on. Table 4 shows where the final defaults follow these transferred constructions and where they differ. For set error, the best same-model construction on the other five sources is three-call unanimity with av-eraged coordinates on every evaluated source. It lowers set error significantly in 9 of the 15 over-reporting cells and raises it significantly in none; on FSC-147, the under-reporting family, it is worse in 2 of 3 cells, consistent with Proposition 2 and Corollary 1. For F1, the transferred same-model construction is better in 2 cells, worse in 4 and not significant in 12, so the default is a single call. Three calls cost three times one call. From logged token usage at list prices, unanimity costs $0.029 to $0.21 per image for GPT-6.1 across the five over-reporting sources, $0.032 to $0.13 for Sonnet 5.5 and $0.011 to $0.058 for Gemini 3.8.

8 Discussion 

What a practitioner can take away. Table 17 lists each component of the method with when to use it, its measured effect, where it does not help, and its cost; Table 4 gives the shipped settings and Appendix D the prompts. Three quantities decide most choices at run time: the degeneracy flags de-cide which count to read; agreement between two calls of one model measures stability, not correct-ness, so high agreement means another such call adds little; and the family default, or p1 estimated on a few labelled images, decides whether to delete unconfirmed records. 

Why the gains come from changing information. 

The theory and the measurements point the same way. Object-level persistence means that repeated calls of one model share most of their errors. In our comparisons, votes over the same outputs gained at most 23% for counts and 4.5% for clicks, and even a perfect selector over three calls can only choose among the records those calls contain. The largest gains we measured came from operations that change what is available: reading a different field of the same response, looking at a different view, or asking a model with a different model-specific component. Where those operations fail, the failures have the predicted form: deletion hurts when p1 > 1/2, tiling can lose objects that no tile contains whole, and a partner hurts when its additional loss of true matches outweighs its addi-tional rejection of false records, with the effect of averaged coordinates counted separately. 

Where click accuracy can still come from. Of the tier’s 56 remaining misses on the 600 click items, 43 have no correct candidate and 13 are lost in representation or choice (Proposition 8). A better rule over the same candidates can act only on the 13. The 43 need a source with a high rescue rate ϕ

on exactly those items, and its gain must survive representation and choice: of the crop-first source’s 7 rescues, 3 did (Section 7.7). On items where the models agree, any further action must meet the break-rate condition of Proposition 10. 36 What future models should change. The mea-surements point to properties that model builders can target directly. A model’s stated summary should be computed from its own enumeration: GPT-6.1 and Sonnet 5.5 already list almost exactly the right number of objects, and their stated counts lose that information. Long lists should not de-grade with position; Gemini 3.8 at its lowest set-ting drops class fields more often when consecu-tive records share a class; an order that interleaves classes lowers its count error and grouping by class raises it (Section 7.3). Class vocabularies given in the prompt should be respected, since Sonnet 5.5 still wrote “diamond” 258 times when the for-mat named the allowed classes. Finally, errors that persist across calls limit what a fixed budget of resampling can repair; diversity across calls, or cal-ibrated uncertainty at the object level, could make the cheaper same-model alarm as useful as a sec-ond model. 

Scope of the results. The theory’s guarantees hold under their stated conditions. The iden-tities of Section 4.1 hold for any outputs and any fixed choice of maximum matching. Propo-sition 5 assumes deletion-only confirmation, no match takeover, and no ignore region or none of the base report’s false records inside one; outside these conditions the exact identity of Proposition 1 replaces it. The disagreement floor is a bound for point tasks and for boxes at IoU thresholds above 0.5; the click alarm is empirical and is evaluated by risk and acceptance coverage. Proposition 11 con-cerns model classes that admit scenes with identical or nearly identical output laws; when an object is reported with probability at most ϑ per call, K calls separate the two scenes by at most Kϑ in total vari-ation. The readout repair applies where a readout gap exists: on our dense synthetic scenes the gap is most of the error, while on aerial and document images it is a small part of it for GPT-6.1 and Son-net 5.5. Section 6 states how the reasoning setting and the output cap were separated. All results are for the model versions listed in Appendix C, at a total cost of about $758; we release every response and the analysis code, so the reported identities and tables can be reproduced without new model calls, while evaluating a new model version requires its own responses, analysed the same way. 

Broader impact. More accurate and auditable visual reports can make inventory, document and screen-automation systems more reliable, and an explicit status and alarm make failures visible in-stead of silent. The same techniques could make automated agents act with more confidence; our pipeline always returns a status and never claims certification without labels. 

9 Conclusion 

Reporting is part of the visual task, not merely its formatting. When vision-language models re-port sets of objects, part of their error is in the report rather than in the seeing. FSR treats report-ing as a chain from responses to records, sets and readouts, which makes that error analysable. The chain gives exact identities for what each operation does, a behavioural model of persistent errors, and a proof that outputs alone cannot certify correct-ness when two scenes produce the same outputs. It also separates three problems. Repair works where the information is already present: read the count from the model’s list of records, not from the numbers it states, unless the list has degenerated; delete unconfirmed records only below the cost threshold; change the report structure, its decoding (declared aliases applied in code), the view or the model, rather than restating the same request more insistently. Error detection benefits most from a different source of evidence; on our click tasks a second model provided it better than a second call. For one click, the error splits exactly into missing candidates, lost representatives and wrong choices, which tells where to spend calls: FSR’s GUI-grounding tier, which adds two other models’ candidates and compares them only where they dis-agree, lowered the miss rate on 600 ScreenSpot-Pro items to 9.33%, against 13.67% for one model’s zoom and 12.33% for a plain vote over the same three models; against a crop-first baseline the differ-ence was not significant. Judging between reports needs labels or a configuration transferred from other data; three-call unanimity, chosen on five sources, improved set error on most over-reporting cells of the sixth and did not significantly worsen it in any of them, while for F1 a single call remained the default, with an interface and setting per model on the detection sources. A.1 Explanatory parametrization and views 

To describe how propensities vary with the model and the view when the rest of the interface is held fixed, that is, for calls that share the prompt, schema, setting and cap, we use the explanatory parametrization 

logit qo,η = ao + bo,m (η) + γv(η)(o),

P 

> m

bo,m = 0 , γv0 (o) = 0 ,

where v0 is the whole image, ao is common to all models (how hard the object is), bo,m is specific to model m, and γv(o) is the change from the whole image to view v, which depends on the apparent size of o in v. All three terms may differ between prompts, schemas, settings and caps; a comparison that changes one of these compares two such parametrizations, not two terms of one. The form is related to item-response and labeler-expertise models, in which an item’s difficulty and a rater’s ability combine on the logit scale (Whitehill et al., 2009) (there as a product, here additively, as in Rasch-type models); here the items are objects and the raters are models and views. The two constraints are conventions that make the parts well defined: centering separates the shared part from the model-specific one, and the reference view separates both from the view effect. We do not estimate the parts; the parametrization motivates the predictions of Section 4.2, each of which is tested directly. A view can raise how often objects are reported while the misses of the two calls stay as correlated, or become more so. For a true object drawn at random from the image, let A and A′ indicate that two calls with the same interface report it and B that a call on another view does, with means μA = μA′ and μB ,the calls being conditionally independent given the propensities. Then 

P (A = 0 , B = 1) − P (A = 0 , A ′ = 1) = (1 − μA)( μB − μA)+ Cov( A, A ′) − Cov( A, B ) : 

the first term is the gain in how often objects are reported, the second the gain in complementarity. For example, with two equally likely kinds of object reported with probability 0.2 and 0.4 on the whole image, a view that adds log 2 to every logit gives 1/3 and 4/7: the mean rises from 0.30 to 0.45 and the covariance with the first call rises from 0.0100 to 0.0119, yet the probability that the first call misses an object and the second reports it is 0.305 for the new view against 0.200 for a repeated call: the gain in how often objects are reported (0.107) more than offsets a small loss of complementarity (0.002).

D Protocol Details 

List-first prompt. The full-protocol readout runs used the following system prompt for GPT-6.1 and Gemini 3.8 (native 0 to 1000 frame); the user message was “List every geometric shape in this image with its center, then counts by type. Respond with JSON only.” 

You are a precise visual counting and localization assistant. Given an image containing geometric shapes, identify every shape. Report coordinates on a 0-1000 grid: x = 0 is the left edge and x = 1000 the right edge of the image, y = 0 is the top edge and y = 1000 the bottom edge. Use integers. List the shapes in reading order: scan the image row by row from top to bottom, and within a row from left to right. The "type" value must be exactly one of: circle, triangle, square, star, pentagon. A square rotated by any angle is still a "square"; do not use any other type name. Respond with ONLY a JSON object (no markdown, no commentary) in this format: {"shapes": [{"type": "circle", "x": 402, "y": 311}, ...], "counts_by_type": {"circle": 5, "triangle": 3, "square": 0, "star": 2, "pentagon": 4}} Shape types to recognize: circle, triangle, square, star, pentagon. Locate every shape carefully. Count systematically; do not miss any and do not invent shapes that are not there. 

49 Write the full shapes list first; after it, give counts_by_type for the shapes you listed. 

For Sonnet 5.5 the coordinate paragraph reads “The image is 1024x1024 pixels. Report coordinates as integer pixel positions in this image, where (0,0) is the top-left corner.” The count-first prompts of the readout experiment ask for counts_by_type before the list; all prompts are released with the responses. 

Decoder. The decoder strips a code fence and parses the whole response as JSON (L2). If that fails, it recovers each balanced {...} object that has the record fields (declared salvage) and reads 

counts_by_type if present, with its class names mapped by the same alias map (the pure-readout comparisons of Table 8 compare stated and list counts with neither mapped). Coordinates are mapped from the model’s frame to image pixels. Classes are lower-cased and mapped by the declared alias map; for SCP, {diamond, rhombus, rotated square} 7 → square. Records whose class is outside the vocabulary after mapping stay in the audit collection Zall , are excluded from the delivered collection Z that set scores evaluate, and are counted by the first degeneracy flag; Table 10 adds a sensitivity that keeps them and scores them as unmatched. On the detection sources, records with a label outside the vocabulary or a box outside the image are likewise kept in the audit collection, excluded from delivery and counted as invalid (Table 2). 

Degeneracy flags. A list is flagged if any of the following holds: more than 10% of records lack a valid class; the list length is outside [0 .5, 1.5] times the stated total; more than 10% of records repeat a rounded coordinate pair already in the list; or the finish reason is “length”. The same thresholds are used for every model, including the open model. 

Scoring and clustering. Scoring uses the compatibility relation of each task in Table 2: for example, points of equal class within 30 pixels on SCP and 20 pixels on SCP-dense, detection boxes of equal class at IoU ≥ 0.75 , screen elements at IoU ≥ 0.5 without class, and clicks inside the target box. Maximum matchings are computed with a linear assignment on the 0/1 compatibility matrix (Kuhn, 1955). Clusters across calls use the association rule of Table 2 (boxes: equal class and IoU ≥ 0.5, also on the detection sources where scoring uses 0.75), with a maximum-cardinality, then maximum-overlap assignment against cluster representatives, and the averaged record is the coordinate mean of members. 

Constructions. Same-model: inter2 (two calls, intersection), union2 , unan3 and maj3 (three calls, unanimity or majority), union3 ; each with averaged ( _fus ) or base-record ( _del ) coordinates. Cross-model: x2_inter and x2_union with a named partner, x3_unan and x3_maj over the three models (one call each), x3_union . The leave-one-source-out default for an evaluated source is the construction with the best mean relative change over the other five sources, computed separately for each loss and pool. 

Alarms. For clicks, the same-model alarm compares two unzoomed calls of one model; the cross-model alarm compares one unzoomed call of the user’s model with one of the partner; after zoom, the same-model alarm compares the model’s zoomed first click with its zoomed second click, and the cross-model alarm compares the zoomed first clicks of the two models. An item is set aside in the risk-coverage analysis when the two points are farther apart than δ times the longer image side. The partner is set by a fixed rule, the cheapest other model per click call (GPT-6.1 and Sonnet 5.5: Gemini 3.8; Gemini 3.8: Sonnet 5.5). 

Clicks from several models. Candidates are the two-stage zoom points of Step 4, mapped to the original screenshot. A candidate’s identifier is the first 16 hexadecimal digits of the SHA-256 of the item, model, setting, parent call and coordinates. The scorer’s score request shows a native crop of one fifth of the screenshot’s width and height around the candidate, with a marker at the point, the instruction and the platform, and asks for a verdict and the probability that a click at the marker hits the intended element; it never names the model that produced the candidate. A missing or unreadable score counts as −1 for ranking. The comparison request shows the downscaled screenshot with both representatives marked by their identifiers and a native crop around each, asks which candidate satisfies the instruction (element, 50 text, state, relation and whether the exact point lies inside the element), and allows “undecided”; it forbids proposing a new point. Each pair is sent in both orders, and the code asserts that the points drawn equal the representatives’ coordinates. Ranking keys, ties and failures follow Algorithm 2: a failed first click leaves that model without a candidate, a failed zoom keeps the first click, a failed comparison gives no win. 

The 600 click items and baselines. The 600 items were sampled from the ScreenSpot-Pro annotations not among the 200 ScreenSpot-Pro items of the GUI experiment, in proportion to each application file and, within it, to each pair of group and element type, with a fixed seed; they share no screenshot with those items. A first batch of 100 seeded items, part of the 600, was run through every arm to check costs and transport only; its calls are among the 13,126. The three-call baseline runs three independent default-setting zooms of GPT-6.1, clusters the three points with the same δ, and returns the earliest point of the largest cluster (ties: the cluster with the earliest point). The crop-first baseline uses GPT-6.1 at its default setting: the first call must return a region of the downscaled screenshot, the second sees that region at native resolution with 8% padding and may return a smaller region or a click, and a third call, if needed, must click; an unreadable reply falls back to the centre of the last region. It follows the coarse-to-fine cropping of GUI-Lens (Fu et al., 2026) without its OCR and detector anchors or verification step, with our own prompts. Paired intervals resample screenshots (4,000 draws, seed 20261014); McNemar tests are exact. 

Configuration transfer on the detection sources. The menu contains the four single-call configurations run on every image of the four detection sources (first repetition): list or regions interface, each at the lowest and the default setting. In the regions interface the model returns one row per region of a fixed coordinate registry, with a status of empty, found or unknown, and reports each object in the region that contains its centre; in the list interface it returns one list for the whole image in registry scan order. For each model and evaluated source, F1 picks the configuration with the highest mean of per-source mean F1 on the other three sources, and set error the one with the lowest mean relative change against the list interface at the lowest setting; ties keep the earlier configuration in the order list-lowest, regions-lowest, list-default, regions-default. Intervals are paired bootstrap intervals over the images of the evaluated source.
