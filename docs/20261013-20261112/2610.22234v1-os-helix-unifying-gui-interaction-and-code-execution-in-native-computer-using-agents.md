## 摘要
真实的桌面自动化既非纯粹视觉式，也非纯粹编程式。智能体必须理解面向用户的界面，同时高效操作文件、脚本和系统状态。然而，原生的 GUI/代码协同无法通过提示词层面的工具组合获得。在我们的初步实验中，简单加入代码工具反而会降低 GUI 智能体性能，这表明 GUI/代码路由必须通过对高质量混合数据的训练来内化。我们提出 OS-Helix，一个端到端训练的多模态计算机使用智能体，在单一动作空间中统一 GUI 动作与代码执行。为构建所需监督，我们引入应用—产物组合（application-artifact composition），将桌面应用与真实文件产物配对以实例化可执行的 Ubuntu 状态，并提出解耦的指令/评估器生成流水线，生成以环境为依托、无论求解模态如何均可验证最终状态的任务。我们通过对过滤后的混合数据进行 SFT 对策略进行冷启动，并在真实桌面环境中通过在线 RL 进一步提升。针对 RL，我们提出 Step-balanced GSPO，其按动作步而非原始助手 token 聚合重要性权重，以防止长代码动作主导异构动作优化。在 OSWorld-Verified 上，OS-Helix-27B 和 OS-Helix-35B-A3B 相较于各自匹配的 Qwen3.5 混合基线分别取得 35.0% 和 33.7% 的相对提升，而 OS-Helix-27B-RL 进一步提升 42.9%，达到 66.44% 的成功率。消融实验提供的证据与学习到的 GUI/代码协同、可扩展可验证监督以及动作步平衡优化的贡献相一致，同时在 WindowsAgentArena 上展示了跨平台迁移能力。项目主页为 https://os-copilot.github.io/OS-Helix/。

## Abstract
Real desktop automation is neither purely visual nor purely programmatic. Agents must understand user-facing interfaces while efficiently manipulating files, scripts, and system state. However, native GUI/code coordination cannot be obtained by prompt-level tool composition. In our preliminary experiments, naively adding a code tool degrades a GUI agent, revealing that GUI/code routing must be internalized through training on high-quality hybrid data. We present OS-Helix, an end-to-end trained multimodal computer-using agent that unifies GUI actions and code execution in one action space. To construct the required supervision, we introduce application-artifact composition, pairing desktop applications with authentic file artifacts to instantiate executable Ubuntu states, and a decoupled instruction/evaluator generation pipeline that produces environment-grounded tasks whose final states can be verified regardless of the solution modality. We cold-start the policy with SFT on filtered hybrid data and further improve it through online RL in live desktop environments. For RL, we propose Step-balanced GSPO, which aggregates importance weight by action step rather than raw assistant tokens to prevent long code actions from dominating heterogeneous-action optimization. On OSWorld-Verified, OS-Helix-27B and OS-Helix-35B-A3B achieve relative improvements of 35.0% and 33.7% over their matched Qwen3.5 hybrid baselines, while OS-Helix-27B-RL further improves by 42.9% to reach 66.44% success. Ablations provide evidence consistent with contributions from learned GUI/code coordination, scalable verifiable supervision, and action step balanced optimization, while demonstrating cross-platform transfer on WindowsAgentArena. Our project homepage is at https://os-copilot.github.io/OS-Helix/.

## 1. 核心问题与研究动机

- **背景**：真实桌面自动化既不是纯视觉任务，也不是纯编程任务。GUI 智能体（截图→鼠标/键盘）具备通用视觉访问能力，但在小目标/歧义元素上易定位失败，且对结构化状态操作繁琐；代码/命令行智能体可高效检查文件、访问系统状态、执行复合操作，但无法覆盖依赖视觉布局、应用专有 UI 状态或仅通过界面暴露的软件行为的长尾场景。
- **核心问题**：如何让**单一策略**原生地协调 GUI 动作与代码执行，而不是在推理时把 shell 工具"贴"到 GUI 模型上。
- **关键实证动机**：作者初步实验发现，Qwen3-VL-32B-Instruct 仅用 GUI 动作在 OSWorld-Verified 上约 34% 成功率，**朴素暴露代码执行后反而降到约 32%**。说明提示词层面的工具组合会破坏已有 GUI 策略，而非产生协同；GUI/代码的"路由"必须通过对高质量混合数据的训练内化。
- **对现有工作的定位**：框架中心方案（外部 harness 编排 GUI/代码/记忆/恢复）性能耦合于昂贵推理与手工编排，难以隔离模型自身的协同能力；工具调用方案依赖预定义的应用专用接口，覆盖与迁移受限；模型融合方案依赖预设融合而非单策略内学习。因此"单一策略如何通过混合训练学会 GUI/代码路由"仍是开放问题。

## 2. 方法论

### 2.1 统一混合动作空间
- 策略形式：`a_i ~ π_θ(· | q, h_i, o_i)`，`a_i ∈ A_hybrid = A_GUI ∪ A_meta ∪ A_code`。
  - `A_GUI`：点击、输入、滚动、拖拽、按键等；`A_meta`：`wait`、`terminate` 等回合级元动作；`A_code`：直接执行 Python 或 Bash。
- 每个代码动作在**新进程**中执行，其 stdout/stderr 作为工具响应追加到当前轮上下文，供后续决策使用。SFT、RL、测试共用同一套工具 schema。

### 2.2 数据基础设施：应用—产物组合
- **核心思想**：把桌面环境构造分解为两个可复用组件——固定版本/启动流程/初始化配置的**应用**，与携带真实内容与持久状态的**产物（artifact）**；二者通过**应用—产物兼容图**组合，边的依据是应用可消费的文件类型/格式。
- 应用配置为声明式记录：版本、支持的产物类型、启动命令模板（如"空启动"与"带文件启动"）、初始化概率（如 `[10, 90]`）、相关应用与相关类型。新增应用只需补配置，即可在固定 VM 快照上复现实例化，避免 ad-hoc 启动脚本。
- 规模：45 个应用（44 个桌面应用 + 1 个 OS 应用），覆盖 9 大功能类别（办公文档、编程/数据库、图形/CAD、音视频/3D、科学工程、Web 通信、个人事务等）与 21 类文件格式；产物来自公开语料/数据集（docx、pptx、xlsx、pdf、tex、blend、dxf、代码项目等）。

### 2.3 环境依托的任务合成（解耦指令/评估器）
- **探索式指令生成**：每个合成回合先恢复受控 VM 快照、采样主应用与兼容产物，并为每个预置产物创建"仅评估器可见"的 golden copy（原始路径作为任务目标）。Exploration Agent 获得应用元数据、精确路径、启动配置、教程、**全局应用记忆**（记录各应用已覆盖的功能，避免重复）与初始截图，仅允许 `open/click/scroll/done` 的**非破坏性短探索**（禁用键盘与自由文本输入），据此提出真实用户指令、初始化配置与可观测成功条件；指令不预设 GUI 或代码解法，也不泄露答案关键值（精确值只写入隐藏的成功/评估字段）。
- **一切皆文件抽象**：尽可能把终止条件物化为 VM 内可检查的文件表示（下载网页、导出内存状态、写出结构化/纯文本结果），从而把"状态所在位置"与"可验证表示"分离。
- **评估器合成**：指令被接受后**冻结**，交给独立上下文的 Evaluator Agent，仅生成验证规范、不得改写指令。规则评估器由若干自包含 Python `judge` 函数组成，输入可为 `vm_file` / `vm_command_line` / `empty`，按带权子项累积 rubric 分数并返回 [0,1]；仅在视觉/不可序列化证据不可或缺时才启用 VLM judge，二者分数**分开记录、分别阈值化**（SFT 过滤时均需 ≥0.8）。
- **过滤与校验**：静态可解析/可编译检查 → 初始状态执行评估器必须为 0 分（防奖励泄漏）→ 独立 review 模型分别给指令质量与评估器质量打分（覆盖性、严格性、抗 reward hacking）→ 失败评估器带失败信息重生成并重跑全流程 → 嵌入相似度去重。RL 任务池只用**规则评估器**任务，并通过 SFT 模型 rollout 保留中等难度任务。
- **规模数据**：过滤前生成 8,880 条指令；任务级评估器构成为规则 78.52%、VLM 12.45%、二者兼用 9.02%；桌面 SFT 样本池 83,701 条（来自 5,416 个任务的轨迹），其中正确样本 37.13%、失败样本 20.28%、无效样本（工具格式/schema 7.04%、内容质量 27.11%、其他 8.43%）；成功过滤样本约 31K，含 40,729 个工具动作（左键 36.98%、代码 15.86%、等待 12.41%、按键 10.67%、输入 8.72%、终止 8.25% 等）。

### 2.4 SFT 冷启动
- 目的：建立统一工具 schema 的动作语义，并从教师轨迹中蒸馏**粗粒度但可用**的 GUI/代码路由先验；作者强调"仅扩大动作空间不提供路由先验，甚至会破坏已学 GUI 行为"。
- 教师模型：Claude Sonnet 4.6（同时开启 Computer Use 与 Bash Tool）；轨迹后处理归一化到 OS-Helix schema，按评估器打分（需视觉判断时用教师模型本身）做拒绝采样，再过滤畸形工具调用、schema 不匹配与质量不合格轨迹。
- 数据混合：约 31K 过滤后桌面样本 + 40K 通用多模态样本（GUI 理解、代码、数学、OCR、图表、对话），约 1:1。

### 2.5 在线 Agentic RL 与 Step-balanced GSPO
- **工程**：跨节点环境管理系统监控 100+ 个 Ubuntu 沙箱，对外暴露统一端口并内部调度；异步 RL 流水线允许 rollout 策略最多滞后一个版本；按任务成功率 EMA 做**前沿采样**（高斯核 `w_i = exp(-(p̂_i-μ)²/2σ²)`，μ=0.5、σ=0.25，p̂ 初值 0.5、α=0.9）；**有界滑窗视觉上下文**（保留 5–10 张截图，超过 10 张则存段、丢最旧 5 张、保留最新 5 张，仅窗口内助手响应计入 loss）。
- **奖励**：仅使用配对环境评估器分数（[0,1]），无辅助格式奖励或手工步级奖励；若某助手回复含不可解析工具调用/越界动作，则该回复被隔离为无效样本并赋 0 奖励，即使整条轨迹最终可得正分。
- **问题诊断**：标准 GSPO 在混合样本中按**token 数**聚合样本级重要性比，长代码动作（含推理、工具包装、代码内容 token）会主导样本级比率与裁剪决策。初步 RL 实验中观察到代码动作比例持续上升、性能相对 SFT 略有退化。
