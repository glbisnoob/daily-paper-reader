ABSTRACT 

Reinforcement learning for computer-use agents increasingly relies on proactive re-ward agents that interact with the post-execution GUI environment to verify what recorded screenshots cannot reveal. The reliability of such verification hinges on two coupled decisions: what to check and when to stop. Existing methods leave these decisions to prompted foundation models. However, neither scaling up the model nor providing few-shot examples reliably improves verification: prompted Judges ranging from 4B to GPT-5.4 all plateau at 68 %– 70 % macro-average agree-ment. This is because the value of a check depends on the environment rather than the task alone, and becomes apparent only through execution. Learning from execution is itself constrained, as the Actor’s terminal state cannot be faithfully replicated during training, allowing only one verification attempt per state. We introduce VERICUA, a proactive reward agent that learns its verification strat-egy from these single attempts. A trainable JUDGE decides what to check and when to stop, while a frozen PROBE executes the checks in the live environment. Online reinforcement learning optimizes the JUDGE for both verdict correctness and efficient PROBE use, with returns normalized across terminal states. Trained only on OSWorld and evaluated without further training on MobileWorld and WebArena-Verified, VERICUA achieves the highest reward agreement across all three benchmarks and lies on the agreement–cost Pareto frontier among proactive verifiers. It surpasses few-shot GPT-5.4 by 5.36 points with 47 .6%– 59 .8% fewer PROBE tokens, and even a 1B VERICUA exceeds every prompted Judge. As the reward for Actor RL, it raises task success by 3.21 points overall and 5.40 points on held-out multi-application tasks. These results identify the verification strat-egy, not verifier scale, as the key to reliable GUI rewards. Code is available at 

https://github.com/Jeffjeno/VeriCUA .

1 INTRODUCTION 

Training computer-use agents (CUAs) with reinforcement learning requires reliable rewards for task completion (Lv et al., 2026; Lai et al., 2026; Wang et al., 2026). Rule-based rewards are precise but brittle and difficult to scale (Xie et al., 2024; El Hattami et al., 2025; Kong et al., 2026), while passive model-based rewards are more flexible but can only verify what is exposed in the available observations (Qi et al., 2025; Bai et al., 2024; Wang et al., 2025; Yang et al., 2025). Decisive evi-dence, such as the contents of a saved file or other hidden application state, may therefore remain unobserved (Cai et al., 2025). Proactive verification addresses this limitation by interacting with the post-execution environment to acquire the missing evidence before issuing a verdict (Dai et al., 2026; Cui et al., 2026; Shi et al., 2026). Because such verification is performed for every training rollout, it must be not only accurate but also efficient enough to avoid invoking an expensive model for each reward.

Reliability depends on the verifica-tion strategy, which consists of two coupled decisions the task leaves open: what to check and when to stop . For a task that requires notes on every slide, one slide without notes already establishes fail-ure (Figure 1(b)). The prompted verifier in Figure 1(a) instead requests a slide-by-slide comparison and keeps scrolling without reaching a verdict. Scale does not fix this. Under the same verification loop, prompted Judges from a 4B model to GPT-5.4 all reach 68 %– 70 % macro-average agreement, and few-shot examples add at most 0.6 points (Table 1). Our key observation is that a check’s value is revealed by executing it, not by reading the task . A prompted Judge sees the task and the recorded screenshots, which show what a plausible check looks like but not what evidence it will return. That depends on where the evidence resides, the state the Actor left, and what the PROBE can reach. When to stop depends on how often screenshot-only verdicts turn out to be correct. The strategy must therefore be learned by executing verification and comparing its verdicts with true outcomes. Learning from execution, however, faces a single-attempt constraint : each Actor terminal state admits only one verification attempt, which rules out within-state rollout comparisons. An Actor starts from a resettable initial state, so RL can compare several rollouts from the same state (Shao et al., 2024). A GUI verifier starts from the Actor’s terminal state, the product of one stochastic execution. Re-execution may not reproduce it, identical screenshots can hide different application state, and probing itself changes it. We introduce VERICUA, a proactive GUI reward agent that learns its verification strategy under this constraint. A trainable JUDGE decides what to check and when to stop, and a frozen GUI PROBE executes the checks. Freezing the PROBE ties outcome differences to the JUDGE and lets the PROBE be swapped without retraining. We initialize the JUDGE with outcome-filtered teacher traces and then train it with online RL on complete attempts graded by executable outcomes, so each check is credited by the evidence it actually yields. The reward also depends on whether the PROBE was used, which lets a single attempt signal whether stopping was right. Returns are normalized across terminal states in each batch (Hu et al., 2025), so no environment forking is required. We evaluate VERICUA on OSWorld (Xie et al., 2024), MobileWorld (Kong et al., 2026), and WebArena-Verified (El Hattami et al., 2025). First, strategy matters more than scale. VERICUA surpasses few-shot GPT-5.4 by 5.36 macro-average points with 47 .6%– 59 .8% fewer PROBE tokens and lies on the agreement–cost Pareto frontier (Figure 4). Even VERICUA-1B outperforms prompted GPT-5.4 (OpenAI, 2026) and its teacher Kimi-K2.6 (Kimi, 2026). Second, the learned strategy transfers. Trained only on OSWorld, the JUDGE achieves the highest agreement on unseen mobile and web environments. Third, better rewards train better agents. 2 METHOD 

2.1 OVERVIEW As shown in Figure 2, VERICUA verifies the Actor’s task outcome using its execution history and live terminal environment. It consists of a trainable JUDGE and a frozen GUI PROBE. The JUDGE initially formulates task-success checks and marks each as satisfied, violated, or unresolved based on the available evidence. If the evidence supports a success or failure verdict, verification terminates. Otherwise, subject to the probing budget, the PROBE gathers evidence for the unresolved checks and returns status updates with supporting observations. Subsequent JUDGE calls retain the checks from the previous round and update their statuses using the returned evidence. By specifying what the PROBE inspects and deciding whether to request further interaction, the JUDGE determines the evidence acquired and hence the verdict. We train it on complete verification at-tempts, one per Actor terminal state, with a reward on verdict correctness and PROBE use (Sections 2.3 and 2.4). 2.2 THE JUDGE-PROBE VERIFICATION LOOP Consider an Actor policy πθ attempting task x in a live GUI environment E and terminating at time 

T with trajectory τ = ( o0, a 0, . . . , a T −1, o T ), where ot and at denote GUI observations and actions. The JUDGE receives x and an input representation ψ(τ ) containing the Actor’s action history and its most recent screenshots (Appendix I). When the JUDGE requests additional evidence, the frozen PROBE interacts with the live terminal environment to inspect unresolved task conditions and returns status updates with supporting observations. Each round therefore involves the two decisions that make up the verification strategy: whether the current evidence supports a terminal verdict and, if not, which checks to send to the PROBE.

A correctness-only reward scores a correct verdict reached directly the same as one reached after probing. Because each terminal state admits a single attempt, there is no sibling attempt to reveal whether probing was needed, so the reward itself must carry that signal. Let ˆYi denote the final JUDGE verdict and Yi the executable outcome recorded before PROBE inter-action. We set pi = 1 if the verification attempt invokes the PROBE at least once, and pi = 0 

otherwise, so the probing term of the reward reflects the JUDGE’s stopping decision rather than the frozen PROBE’s execution length. The terminal reward is ri = R( ˆYi, Y i, p i).Correct verdicts receive higher rewards when reached without probing, encouraging reliable judg-ments from existing evidence. Incorrect verdicts receive larger penalties when issued without prob-ing, discouraging premature judgments. Unresolved or invalid outputs receive the lowest reward, discouraging attempts that exhaust the probing budget without reaching a terminal verdict. The ex-act reward schedule is given in Appendix G. We use this terminal reward to jointly train check formulation and stop-or-probe decisions over veri-fication attempts. The reward preferences teach the JUDGE to stop once the evidence suffices, while the shared return trains check formulation through its effect on the evidence collected and the verdict. We next describe how we collect verification trajectories and optimize the JUDGE. 2.4 ONLINE OPTIMIZATION OF THE JUDGE 

Initialization. Before online optimization, we initialize the JUDGE by supervised fine-tuning on teacher verification trajectories whose final verdicts match the executable outcomes. These traces provide examples of structured check generation and verdict prediction, so that each attempt during online RL is a complete, well-formed verification. The PROBE remains frozen. 

Sampling verification trajectories. We run the JUDGE from the live terminal environment of each Actor rollout and execute its PROBE requests to obtain the evidence. Each completed verification attempt receives the terminal reward defined in Section 2.3. Unlike an Actor’s resettable initial state, this terminal environment is produced by one stochastic execution: replaying the Actor need not re-produce it, transient state such as unsaved edits and modal dialogs cannot be confirmed from screen-shots, and PROBE actions further alter it. We therefore collect one verification trajectory per Actor terminal environment, without environment forking or same-state verifier rollout groups.

3.1 EXPERIMENTAL SETUP 

Benchmarks. We evaluate on the OSWorld (Xie et al., 2024) tasks that require neither net-work access nor Google Drive, the GUI-only subset of MobileWorld (Kong et al., 2026), and WebArena-Verified Hard (El Hattami et al., 2025), using 414 , 100 , and 100 trajectories, respectively. These cover successful executions and diverse failures from five Actors: EvoCUA-32B (Xue et al., 2026), Qwen3.8-27B (Qwen Team, 2026), Holo3.1-35B-A3B (H Company, 2026), Qwen3-VL-4B-Thinking (Bai et al., 2025), and Gemini 3.7 Flash (Google DeepMind, 2026). Each trajectory in-cludes the action–observation history, the clean task snapshot from which its terminal environment can be re-executed, and an executable outcome label hidden from all verifiers. 

Training data. We train the JUDGE only on OSWorld and keep it frozen thereafter, so MobileWorld and WebArena-Verified test zero-shot transfer. Each environment uses one frozen PROBE shared by all VERICUA variants. We denote trained Judges by size: VERICUA-4B (Qwen3-VL-4B-Thinking), VERICUA-2B (Qwen3-VL-2B-Thinking), and VERICUA-1B (MiniCPM-V-4.6-Thinking (Yu et al., 2026; Yao et al., 2024)). SFT uses Kimi-K2.6 verification traces and online RL uses newly collected OSWorld trajectories, all disjoint from evaluation (Appendix G). 

Baselines. Unless noted, all baselines use Qwen3-VL-4B-Thinking, and existing methods follow their published observation and prompting configurations (Appendix D). (i) Passive verifiers: Dis-tRL (Wang et al., 2025), DigiRL (Bai et al., 2024), and ZeroGUI (Yang et al., 2025). (ii) Prompted proactive verifiers: VAGEN (Cui et al., 2026) and prompted VERICUA, which shares trained VER-ICUA’s JUDGE–PROBE architecture, prompts, and budget of at most K=2 PROBE rounds but uses an off-the-shelf Judge. We also evaluate prompted VERICUA with the backbones of VERICUA-2B and VERICUA-1B, and with the frontier models Kimi-K2.6 and GPT-5.4, both also tested few-shot. 

Evaluation protocol. Both evaluations use the executable task evaluator as ground truth and ag-gregate four independent runs (Appendix A). Verifier evaluation: We keep only Actor trajectories whose outcome is stable across six re-executions from the clean task snapshot (Appendix D). 4 RELATED WORK 

Reward signals for computer-use agents. Task-completion rewards for computer-use agents can be obtained from executable evaluators or model-based judgments. Executable evaluators derive outcome labels from application or backend state (Xie et al., 2024; Kong et al., 2026; El Hattami et al., 2025), relying on task-specific checking logic. Environment synthesis automates the construction of verifiable tasks by generating resettable tasks together with executable evaluators (Cao et al., 2026; Zhang et al., 2026b). Model-based evaluators assess recorded observations and action histories using prompted or trained judges (Bai et al., 2024; Wang et al., 2025; Qi et al., 2025; Yang et al., 2025; Xia et al., 2025), while rubric and milestone-based critics further structure this assessment (Rosset et al., 2026; Li et al., 2026). However, since recorded observations obscure uncaptured state, verifiers must acquire additional evidence through active interaction with the environment. 

Interactive verification and evidence acquisition. Recent work incorporates evidence acquisition into both post-execution verification and task execution. Post-execution verifiers continue from the Actor’s terminal environment and inspect state before issuing a verdict (Dai et al., 2026; Cui et al., 2026; Shi et al., 2026). Other approaches integrate evidence collection, completeness checking, or recovery into the acting policy (Cai et al., 2025; Han et al., 2026). Text-reasoning verifiers can be 9Preprint trained with RL by replicating a problem to compare verification attempts (Zhang et al., 2026a); we study the post-execution GUI setting, where each state yields a single verification attempt. 

5 CONCLUSION 

We introduced VERICUA, a proactive GUI reward agent that learns what to check and when to stop. Prompted verifiers benefit little from larger models or few-shot examples because a check’s value is revealed only through environment interaction. With only one verification attempt per Actor terminal state during training, VERICUA learns this strategy by comparing outcomes across states. Across desktop, mobile, and web, it reaches the agreement–cost Pareto frontier, enables a 1B Judge to surpass prompted frontier models, and improves downstream policy RL. These results identify verification strategy, rather than model scale, as the key to reliable and affordable GUI reward supervision.

D EVALUATION DETAILS 

We use fixed inference settings for each component during reward evaluation. The JUDGE uses a sampling temperature of 1.0. The frozen PROBE uses a sampling temperature of 0.0, a maximum output length of 8192 tokens per API request, and at most 15 interaction steps per probing round. The maximum number of probing rounds follows the main experimental setup (Section 3.1). 

Trajectory screening and cost accounting. We re-execute each Actor trajectory six times from the clean task snapshot and retain it only when all six re-executions yield the same executable outcome and the mean pHash similarity over their final three screenshots exceeds 0.95 . Verifier trials then run in separate fresh re-executions. In cost accounting, trials that never call the PROBE count as zero tokens, and image tokens follow Qwen-VL accounting. VAGEN has no separate Probe, so its full active loop is billed. We measure cost in PROBE tokens because this is the cost the verification strategy controls. The JUDGE decides which checks the PROBE executes and when probing stops. Within each benchmark, every prompted and trained VERICUA JUDGE drives the same frozen PROBE, so these tokens are counted on one model with one tokenizer. JUDGE tokens are not comparable in the same way. Tokenizers differ across backbones, closed models such as GPT-5.4 report reasoning only as provider-side counts, and per-token prices differ by orders of magnitude between a locally served 1B– 4B model and a proprietary API. Counting JUDGE cost would therefore only widen the advantage of VERICUA over proprietary JUDGE models. The JUDGE is paired with an environment-specific frozen PROBE. Within each benchmark, prompted and trained VERICUA use the same PROBE configuration, so any difference between them comes from the learned verification policy. F IMPLEMENTATION DETAILS 

Training implementation. We implement cold-start Judge SFT using LLaMA-Factory. The Qwen3-VL-4B Judge is fine-tuned on eight GPUs with DeepSpeed ZeRO-3. Online RL uses Slime with Megatron Core for parameter updates and SGLang for rollout generation. For online Judge RL, we allocate eight NVIDIA A800-SXM4 GPUs (80 GB each) to parameter updates and eight addi-tional GPUs to rollout generation. Parameter updates use eight-way tensor parallelism, and rollout generation uses single-GPU engines. Training uses BF16 precision. Objectives and hyperparameters are given in Appendices E and G. 

Inference implementation. We also run JUDGE and PROBE inference on Huawei Ascend 910B3 accelerators. The eight-NPU configuration comprises three PROBE instances using two NPUs each and two JUDGE instances using one NPU each. Inference uses BF16 precision with vLLM 0.18.0 and vLLM-Ascend 0.18.0, running on CANN 9.0.0, PyTorch 2.9.0, and torch-npu 2.9.0.post2. Model inference and GUI execution run in separate processes and communicate through API requests. Model choices and decoding settings are given in Appendix D. 

Desktop environments. The Ascend-based desktop evaluation uses 16 independent x86 Ubuntu 22.04.3 virtual machines at a resolution of 1920 × 1080 , each with four virtual CPUs and 4 GiB of memory. The virtual machines run under QEMU 8.2.10 with TCG emulation on ARM64 hosts. Environment initialization, trajectory re-execution, and verifier isolation follow the protocol in Ap-pendix D.
