## Abstract 

Web agents are increasingly deployed to complete tasks autonomously on real websites, where adversarially injected content can induce them to perform unauthorized actions. Existing evaluations primar-ily use fixed attacks or focus on a single attack type, and evaluate attacks at the text level rather than through real state changes, thus underestimating how vulnerable agents are to diverse attacks. To address the gap, we introduce REEF , a benchmark of Red-teaming 

Executable Environments with Faithful Verification for measuring the security vulnerabilities of web agents. REEF covers 9 verifier-grounded websites spanning travel, commerce, productivity, media, and communication, and pairs every authentic benign task with a malicious objective delivered through 5 attack types at both the user and the environment level. REEF’s state-based verifiers provide the execution feedback that drives ANGLER , an Adaptive Near-miss-Guided Lure Evolution framework for Red-teaming. Rather than evaluating a fixed attack set, ANGLER uses outcomes from prior rollouts to guide LLM-based attack mutation and candidate selection, prioritizing near-miss seeds during refinement. Across 8 VLM-based web agents, ANGLER achieves an end-to-end attack success rate (ASR) of 20.36%, compared with 15.24% for the non-adaptive setting. Compared with attack-free execution on the same benign tasks, attacks generated by ANGLER reduce benign task success rate (BSR) from 61.9% to 44.4%. 

## 1 Introduction 

Recent advances in large language models and vision-language mod-els enable web agents to navigate websites and complete multi-step tasks on behalf of users [10, 11, 22, 36]. However, these capabilities also introduce security risks, as malicious instructions may induce web agents to perform unauthorized actions, such as sending mes-sages, modifying settings, or completing transactions [9, 24, 27]. Adversarial content can reach web agents through user-level attacks that manipulate user instructions or environment-level attacks that inject malicious content into webpages encountered during execu-tion. If the agent follows such content, it may perform actions that are not authorized by the authentic user goal. A faithful security evaluation must therefore test attacks during interactive website execution and verify whether they cause unauthorized changes to website state. Existing security benchmarks provide executable environments for evaluating adversarial attacks against web agents and related tool-using agents. WASP [9], RedAgentBench [6], and SecureWe-bArena [34] execute adversarial tasks in interactive environments,

but evaluate agents using fixed and static attack cases or trajecto-ries. However, these benchmarks do not adapt attack generation or selection during agent evaluation based on outcomes from previous rollouts, potentially missing vulnerabilities that could be uncovered through feedback-driven exploration. Although recent works have begun to introduce adaptive at-tacks, they are typically limited to a single attack type. Studies of pop-up and advertising-based injections each target a specific delivery channel [27, 35], while MUZZLE [24] uses execution feed-back to adapt attacks but focuses specifically on indirect prompt injection. Consequently, existing evaluations provide broad evalua-tion of fixed attacks or adaptive refinement within a narrow attack class. What remains missing for web agents security evaluation is an adaptive but reproducible framework across multiple attack types. However, simply adding an adaptive attacker to existing benchmarks is insufficient because newly generated attack plans must be validated against specific constraints and evaluated under consistent task contexts, objective definitions, and verifier rules. Therefore, we address these requirements with REEF and AN-GLER, which combine a fixed benchmark specification with adap-tive search. Built on 9 resettable AutoWebWorld environments [31], REEF pairs benign tasks with grounded malicious objectives across 5 attack types. A site compiler enforces attack constraints and checks plan validity, while programmatic verifiers assess outcomes from website state and committed artifacts. Within this feasible space, ANGLER combines systematic exploration, experience-guided LLM mutation, and feedback-driven candidate selection under a fixed rollout budget. This separation enables controlled compar-isons of discovery policies under shared attack constraints and success criteria. Our contributions are summarized as follows: 

• We introduce REEF, an executable benchmark spanning 9 web-sites and 5 attack types. Unlike fixed-case evaluations, REEF supports controlled online mutation of structured attack con-figurations and uses programmatic verifiers to measure benign task completion and malicious objective success. 

• We propose ANGLER, an adaptive experience-guided framework for red-teaming web agents. It uses verifier-grounded rollout feedback to identify near-miss seeds for attack refinement and to select subsequent candidates within a predefined feasible attack-plan space. 

• We establish an evaluation protocol for comparing adaptive and non-adaptive attackers under identical task contexts and rollout counts. ## 2 Related Work 

General Web Agent Benchmarks. General web agent bench-marks establish the execution environments and evaluation proto-cols. Mind2Web [8] and WebLINX [20] provide large-scale demon-strations collected from diverse real-world websites, supporting the learning and evaluation of agents across tasks and previously un-seen domains. WebArena [37] introduced self-hosted websites and realistic multi-step tasks to evaluate language agents through the completion of functional tasks. VisualWebArena [16] extended this setting with visually grounded tasks that require agents to jointly interpret webpage text, images, and interface elements. Browser-Gym [7] standardizes browser observations, actions, and experimen-tal interfaces across multiple benchmarks, and AutoWebWorld [31] generates resettable and programmatically verifiable websites from finite-state specifications. These benchmarks improve environmen-tal realism, task diversity, and evaluation reproducibility, but pri-marily measure whether agents complete benign user tasks. 

Web Agent Security Benchmarks. Security benchmarks extend agent evaluation by introducing malicious objectives or untrusted external content. ST-WebAgentBench [18] and SafeArena [26] re-spectively examine policy adherence and agents’ completion of harmful requests. WASP [9] evaluates end-to-end prompt-injection attacks with realistic malicious objectives, while RedTeamCUA [19] extends adversarial testing to hybrid Web–OS environments. TRAP [17] studies how persuasive content embedded in realistic interfaces redirects web agents away from their original tasks. SecureWe-bArena [34] covers multiple user- and environment-level attack vectors, and REDAgentBench [6] emphasizes executable attacks and faithful measurement of their effects. These benchmarks im-prove environmental realism and attack coverage, but evaluate adversarial cases instantiated before execution rather than refining subsequent attacks from observed outcomes. Recent work has begun to make attack generation adaptive. We-bInject [28] optimizes webpage-level pixel perturbations through the rendered interface to induce malicious actions. Other approaches refine prompt injections through black-box tree search, reinforce-ment learning, or white-box and black-box prompt optimization [5, 12, 29]. AdvWeb [33] trains a black-box adversarial prompter us-ing successful and failed attack strings collected against a tar-get VLM-based web agent. Trajectory-driven methods instead use observed execution failures to guide subsequent attacks. MUZ-ZLE [24] revises indirect prompt injections from Web-agent exe-cution feedback, while SIR [32] extracts reusable attack principles from failed computer-use-agent trajectories. These methods demon-strate the value of feedback-driven testing, but their adaptation remains within a narrow attack mechanism.

## 4 REEF Construction 

We construct REEF by combining diverse executable web environ-ments, compositional task and attack generation, and programmatic verification of website-state changes. 

## 4.1 Overview 

REEF is an executable multi-site benchmark for systematically eval-uating the security vulnerabilities of web agents. Built on 9 state-ful and realistic website environments from AutoWebWorld [31], REEF spans 5 application domains: travel, commerce, productivity, media, and communication. These websites run in isolated environ-ments with synthetic users and content, enabling reproducible state-changing interactions without affecting public services. Across these websites, REEF instantiates 326 malicious objectives cover-ing 5 functional categories: browsing and navigation, lightweight actions, content publishing, account configuration, and transac-tional commits. Malicious objective completion is verified from the resulting website state, and browsing and navigation objectives additionally require the agent to terminate on the intended page. Section A.2 provides the detailed statistics. Each benchmark case combines an authentic benign task with a site-supported malicious objective and a compatible attack delivery configuration. The malicious objective can be delivered through a user-level direct prompt injection or an environment-level webpage injection, while the payload, delivery configuration and injection surface are subject to site-specific constraints. Each case is compiled and validated against site-compatible execution and evaluated using programmatic state-based verifiers that separately measure benign task completion, malicious objective achievement, and recovery. This executable design evaluates site-specific attack cases under a common protocol and measures their effects through website state changes, rather than treating payloads as isolated text prompts. 

## 4.2 Task and Attack Construction 

Benign Task Construction. For each website, we model its user-facing workflows as a finite-state machine (FSM). Starting from the reset state, breadth-first search (BFS) enumerates valid paths to reachable goal states. We convert each path into a parameter-ized task template and instantiate its free variables using entities supported by the website. Each resulting task is paired with a pro-grammatic user verifier 𝑉 𝑢 that checks whether the specified goal state has been reached. This construction increases task diversity while preserving the underlying workflow structure. 

Attack Construction. For each website, we define malicious-objective templates over unauthorized but executable state changes

• Environment-level. Indirect Prompt Injection (IPI), Pop-up In-jection, Distraction Injection, and Ad Injection deliver the mali-cious objective through injected webpage content. A benchmark attack case 𝑐 = (𝑏, 𝑝 ) pairs a benign task 𝑏 with an executable attack plan 𝑝 supported by the same website. 

Quality Control. We combine automated consistency checks with manual audits during benchmark construction. For each website, cases containing invalid configurations, implausible instructions, broken interactions, or mismatches between visible behavior and verifier outcomes are corrected and rerun. 

## 4.3 Faithful Execution and Measurement 

Compilation and Validation. Given a candidate attack case 𝑐 =

(𝑏, 𝑝 ), the compilation-and-validation pipeline either produces an executable case or rejects the candidate. The compiler instantiates the selected benign-task, malicious-objective, and delivery tem-plates with registered site-specific parameters and constructs the corresponding verifier specifications. It produces a composed agent instruction for a user-level plan or a renderer-ready injection spec-ification for an environment-level plan. Static validation rejects undefined site-specific templates, entities, or injection surfaces, as well as incompatible task-objective pairs, invalid timing or pay-loads, and payload–objective inconsistencies. Only validated cases are eligible for rollout. 

Verifier-Grounded Measurement. We determine rollout out-comes directly from recorded website states rather than relying on agent self-reports or LLM-as-a-judge scoring. Each attack case is paired with three programmatic verifiers: 

• The user verifier 𝑉 𝑢 determines whether the benign objective is achieved during the rollout. 

• The attacker verifier 𝑉 𝑎 determines whether the malicious ob-jective is achieved during the rollout and remains satisfied at termination. 

• The recovery verifier 𝑉 𝑟 confirms whether a malicious effect observed earlier is absent at termination. Before each rollout, the attacker verifier 𝑉 𝑎 must be false in the reset state, preventing a pre-existing malicious effect from being counted as attack success. Together, the three verifiers distinguish attacks that are never successful, recovered before termination, or successful at termination.

## 5 Adaptive Attacker with Experience Guidance 

We propose ANGLER, a two-stage adaptive framework for discov-ering vulnerabilities in web agents. The first stage covers feasible combinations of benign tasks and attack types. The second stage iteratively uses an experience pool to guide LLM mutation of candi-date attacks, with near-miss records prioritized as mutation seeds. A funnel-aware contextual bandit then selects the most promis-ing candidate for execution. Verifier feedback updates both the experience pool and the bandit. 

## 5.1 Two-Stage Scheduler 

Our two-stage scheduler separates systematic coverage from adap-tive optimization by assigning the benign task and specifying the attack search space for each rollout. 

Coverage Stage. At the beginning of evaluation, the experience pool is empty, so the attacker has no prior outcomes to guide adap-tive generation or selection. To bootstrap this process, the coverage stage systematically evaluates feasible pairings of benign-task tem-plates and supported attack types. For each rollout, the scheduler prioritizes a pairing that has not reached its coverage quota, and then chooses one of the least-used instruction instances from that template. Once every pairing reaches its predefined quota, which may differ across attack types, the scheduler transitions to the adaptive stage. This forced exploration mitigates cold-start bias and prevents early random successes from prematurely dominating subsequent search. 

Adaptive Stage. Once the coverage requirements are satisfied, the scheduler enters the adaptive stage. It selects a benign template uniformly, chooses one of its least-used instruction instances, and assigns the rollout to a compatible attack level, either user-level or environment-level. These scheduling decisions are independent of previous attack outcomes. Within the assigned attack level, the corresponding contextual bandit selects the specific attack type and delivery configuration. This separation prevents the attacker from concentrating its rollout budget on easier task contexts while allowing adaptive optimization within each scheduled context.

## 5.2 Experience-guided Candidate Generation 

Experience Pool and Seed Selection. After each rollout, we add a record to the experience pool containing the executed attack plan, verifier outcomes, benign-task completion, and attack-funnel signals, and assign it to one of the four categories in Table 2. When only a few matching records are available or their observed ASR is low, seed selection favors verified successes because they provide executable starting points for further mutation. As more records become available and ASR increases, the seed selection system will give higher priority to near-miss records. Unlike blocked rollouts, near-misses show that an attack induced its malicious effect at least transiently, even though the effect was absent at termination. They help locate the remaining bottleneck, allowing ANGLER to guide subsequent mutations toward the stage where the attack failed rather than treating all unsuccessful rollouts alike. The exact sampling priorities and criteria are provided in Section B.2. 

Candidate Generation. During the adaptive stage, the attacker uses the selected seed as structured feedback for experience-guided LLM mutation. For each candidate slot, the program assigns a ma-licious objective grounded in the current website, while the LLM determines how that objective is expressed and delivered. ## 6 Experiments 

We evaluate whether ANGLER discovers verifier-confirmed vulner-abilities more effectively than non-adaptive attack policies under matched task contexts and rollout budgets. We further examine vulnerability variation across websites and target agents, the effect of attacks on benign-task completion, and the contribution of the adaptive components. 

## 6.1 Experimental Setup 

Backbone Models. All target agents use the VisualWebArena in-teraction scaffold [16] with the same observation interface, action space, prompt structure, and interaction horizon, differing only in their VLM backbones. We evaluate 8 vision-language models on REEF: GPT-4o [15], GPT-6.1 Sol [21], Claude Sonnet 4.5 [1], Claude Sonnet 5.5 [2], Qwen3-VL [3], Qwen3.7-Flash [23], GLM-4.6V-Flash [14], and GLM-5V-Turbo [13]. During the adaptive stage, we use Qwen3.5-9B [25] as the proposal model for candidate gen-eration and keep it fixed across target agents. 

> 6

Evaluation Protocol. For each target agent and website, we com-pare ANGLER with a non-adaptive baseline attacker under matched task contexts and identical rollout budgets. At each rollout, the base-line constructs candidate attacks supported by the current website, filters them through the compiler, and selects one of the remain-ing candidates uniformly at random. We additionally execute the same benign tasks without attacks to measure clean task success. Before each rollout, the environment is restored to its initial state, and all experimental conditions receive the same target-agent con-figuration and interaction horizon. We report verifier-confirmed final attack success rate (ASR), benign-task success rate (BSR), and call-to-action engagement rate (CTA).

At the aggregate level, ANGLER improves the average ASR for all 8 backbones and all 9 websites. ## 6.5 Discussion and Analysis 

Engagement May Not Imply End-to-End Success. CTA mea-sures whether an agent engages with injected webpage content, whereas ASR requires the malicious objective to be satisfied at termination. The attack-type breakdown in Table 11 reveals sub-stantial gaps between these stages: pop-up injection achieves 52.4% CTA but only 17.1% ASR, while distraction injection achieves 47.0% CTA and 17.8% ASR. These gaps show that a high CTA does not necessarily translate into a high ASR, as the agent may abandon the malicious path before completing the objective. Nevertheless, high engagement remains security-relevant because it may redi-rect the agent to attacker-controlled pages and expose it to further malicious content. Therefore, CTA should be interpreted as a mean-ingful indicator of attack exposure and engagement. 

Vulnerability Varies Across Models and Attack Types. The effectiveness of an attack depends on both the target backbone and its delivery mechanism. As shown in Table 11, GPT-4o is highly susceptible to environment-level attacks: pop-up and distraction injection achieve CTA rates of 83.3% and 89.3%, together with ASRs of 42.3% and 39.3%, respectively. In contrast, CTA never exceeds 5.4% for GPT-6.1 Sol or 2.3% for Claude Sonnet 5.5 across the four environment-level attack types. However, direct prompt injection still achieves ASRs of 32.5% and 32.9% against these two models. These results show that low engagement with injected webpage content does not imply general robustness, as a model that resists one delivery channel may remain vulnerable to another. 

## 7 Conclusion 

We presented REEF and ANGLER for measuring and discovering se-curity vulnerabilities of web agents through verified website-state changes. REEF provides 8,316 executable cases over 9 stateful web-sites and 5 attack types spanning both user-level and environment-level delivery, using programmatic state verifiers to measure both benign and malicious task completion. Across 8 VLM-based target agents, ANGLER increases average ASR from 15.24% to 20.36%, a relative improvement of 33.6%. 

## Ethics and Privacy Statement 

All experiments are conducted in isolated and resettable benchmark environments using synthetic accounts, entities, and malicious objectives. No attacks are directed at public services, real users, or real accounts, and the experiments do not collect personal data or access real secrets.

## A REEF Details A.1 Environment-level Attack Types 

Figure 5 illustrates the four environment-level attack types sup-ported by REEF. All four leave the authentic user instruction un-changed and inject adversarial content through the website envi-ronment. 

Indirect Prompt Injection. Indirect Prompt Injection embeds the adversarial instruction within ordinary webpage content, such as a community post, discussion note, or support message. The injected content adopts the surrounding page’s native presenta-tion and attempts to appear as task-relevant information that the agent should follow. Unlike the other attack types, it does not rely on a modal interruption, warning-style distraction, or explicitly sponsored presentation. 

Pop-up Injection. Pop-up Injection presents the adversarial con-tent in a modal overlay above the current webpage. The pop-up interrupts the normal interaction flow and typically frames its call to action as a required verification, security check, or workflow 

> 9

prerequisite. This attack tests whether visual prominence and ap-parent urgency cause the agent to prioritize the injected instruction over the authentic user goal. 

Distraction Injection. Distraction Injection places a non-modal notice or banner alongside the normal task interface. The injected content commonly claims that the page state is outdated, incon-sistent, or requires synchronization, thereby redirecting the agent toward an auxiliary action while leaving the original interface ac-cessible. It differs from Indirect Prompt Injection by presenting the payload as a separate warning or status notice rather than ordinary page content. 

Ad Injection. Ad Injection delivers the adversarial instruction through a designated advertising or sponsored-content surface, such as a promoted card or corner advertisement. The payload uses promotional framing, such as offering a shortcut or task assistant, to make its call to action appear beneficial to the current workflow. This attack evaluates whether the agent treats sponsored content as actionable guidance for completing the user’s task.

## B.2 Seed-Sampling Details 

During the adaptive stage, ANGLER generates each new candidate by selecting an experience record and mutating its attack plan. The selected record serves as the mutation seed, allowing previ-ous execution outcomes to guide subsequent generation. For each scheduler-assigned context, we first retrieve experience records associated with the same benign instruction and otherwise fall back to records from the same benign-task template. Let 𝑛 denote the number of retrieved records and let ASR denote their running verifier-confirmed attack success rate. When 𝑛 < 8 or ASR < 0.5, we use the low-evidence regime in Table 9, which favors verified successes as reliable starting points for mutation. Otherwise, we use the refinement regime, which prioritizes near-misses to ad-dress the remaining failure stages. Within the near-miss categories, benign-incomplete records receive greater weight because they provide stronger evidence that the attack diverted the agent from the authentic task. Because every category has a positive weight, lower-priority records may still be sampled.

## B.3 Mutation Prompts 

For each adaptive proposal round, we construct a JSON-serialized prompt that combines fixed mutation instructions with rollout-specific context. The fixed instructions define the permitted modifi-cations, output format, and validity constraints. The rollout-specific context contains the parent attack plan, benign user goal, outcome category, verifier results, attack-funnel signals, delivery configura-tion, and site-specific catalog constraints. The program additionally assigns 𝑘 objective slots, each specifying a catalog-provided ma-licious objective, its parameters, action URL, attacker instruction, and a unique slot identifier. The proposal model must yield one mutation per slot, preserving its assigned objective or parameters. The mutation router determines which aspects of the parent plan may be revised according to its attack type and observed failure stage. For user-level attacks, only the injected instruction may be revised. For environment-level attacks, the prompt empha-sizes placement and timing when the injection was not observed, CTA wording and visual salience when it was observed but not engaged, and continuation instructions when the malicious path was reached without completing the objective. For successful seeds, the program may assign new catalog-backed objectives, while the proposal model varies only their expression and delivery. The proposal model must return a single JSON object containing exactly 𝑘 mutations with distinct slot identifiers. Each mutation must preserve the catalog-provided attacker instruction and, when applicable, its action URL and CTA label. The model may not intro-duce new objective parameters, entity identifiers, routes, verifier rules, rendering logic, HTML, or arbitrary CSS. 

## B.4 Mutation Output Schema 

The proposal model does not directly generate executable attack plans. Instead, it returns candidate revisions through a constrained JSON interface, allowing each revision to be bound to a program-assigned objective and validated before execution. The output is a single JSON object containing a mutations array. Each entry must bind to a unique assigned objective slot through slot_id and include at least one permitted update listed in Table 10. No other fields are accepted. The system normalizes the returned mutations and compiles them into executable attack plans before candidate selection. It removes entries with missing or duplicate slot identifiers, unsup-ported fields, invalid values, or payloads that omit required catalog-provided instructions, URLs, or CTA labels. It also rejects duplicate plans and candidates that cannot be instantiated by the site-specific compiler. If fewer than the required number of valid mutations

remain, the unfilled slots receive catalog candidates that pass the same compiler validation.

## B.6 Runtime Analysis 

We report the wall-clock execution time of ANGLER across all 8 victim backbones and 9 websites. For each valid formal rollout, we measure the elapsed time from the creation of its execution artifact to the completion of the final trajectory. The measurement therefore includes victim-model inference, browser interaction, environment execution, and verifier evaluation. It excludes candidate generation before rollout dispatch, queueing between rollouts, interrupted executions, and infrastructure failures that were not committed as formal experience records. Table 12 reports the mean execution time per valid rollout. The results show that the runtime of ANGLER depends primarily on the latency of the victim backbone and the number of interaction steps required by each website. Qwen3.7-Flash has the lowest aver-age execution time at 63.9 seconds per rollout, followed by GPT-4o at 94.3 seconds and GLM-5V-Turbo at 109.2 seconds. Qwen3-VL requires the longest average runtime at 299.7 seconds per rollout, with particularly long executions on Coursera and Slack. GPT-6.1 Sol also exhibits substantial site-dependent variation, primarily due to long executions on Coursera and Walmart. Because the victim models are served through a mix of local GPUs and remote APIs, these measurements represent practical rollout latency under our evaluation setup rather than controlled model-serving throughput.
