## 摘要
计算机使用智能体正日益承担从日常桌面操作到长时程专业工作流的各类任务。然而，以屏幕截图和鼠标键盘操作为中心的接口可能引入人类交互先验，要求反复进行屏幕解读，同时使计算机的语义与程序化能力未被充分暴露。我们主张应暴露这些能力，并让模型选择与组合它们。我们提出混合计算机使用（Hybrid Computer Use, HCU），这是一种面向通用智能体的统一接口，融合三个互补通道：通过代码和命令行工具进行的程序化交互、通过可访问性（accessibility, AX）进行的语义交互，以及通过图形用户界面（GUI）进行的视觉交互。我们的 HCU 支持高效的 AX 交互，并在通道切换期间防止基于过期状态的动作。一个补充性的 HCU 技能引导智能体选择并协调各通道，以有效使用该统一接口。我们设计的 AX 工具返回紧凑的观测，批量执行动作，并以 AX 差异（AX diffs）报告其效果，因此模型所需的往返次数更少。在 OSWorld 2.0 上，HCU 在对比系统中取得了最高的 Partial 和 Binary 分数。通过分析智能体轨迹，我们发现所有被评估的模型在使用 HCU 时均有提升，但它们在各个通道上的工作分配方式不同，并且在效率和任务成功率上均持续优于对比基线，这凸显了允许灵活选择与组合通道的统一计算机使用接口的价值。

## Abstract
Computer-use agents increasingly tackle tasks ranging from everyday desktop activities to long-horizon professional workflows. Yet interfaces centered on screenshots and mouse-and-keyboard actions can impose a human-interaction prior, requiring repeated screen interpretation while leaving the computer's semantic and programmatic capabilities underexposed. We argue for exposing these capabilities and letting models choose and combine them. We introduce Hybrid Computer Use (HCU), a unified interface for general agents that combines three complementary channels: programmatic interaction through code and command-line tools, semantic interaction through accessibility (AX), and visual interaction through graphical user interfaces (GUI). Our HCU supports efficient AX interaction and guards against stale-state actions during channel switching. A supplementary HCU skill guides agents in selecting and coordinating channels to use the unified interface effectively. Our designed AX tools return compact observations, execute actions in batches, and report their effects as AX diffs, so the model needs fewer round trips. On OSWorld 2.0, HCU achieves the highest Partial and Binary scores among the compared systems. Analyzing agent trajectories, we find that all evaluated models improve with HCU yet allocate work across the channels differently and consistently outperform compared baselines in terms of both efficiency and task success, highlighting the value of unified computer-use interfaces that allow flexible channel selection and combination.

## 1. 核心问题与研究动机

- **背景**：计算机使用智能体（computer-use agents）已从 OSWorld 1.0 的日常桌面任务扩展到 OSWorld 2.0 的长时程、专业软件工作流，任务步骤多、跨度长，因此**交互效率**与任务成功率同等重要。
- **核心问题**：现有接口大多模仿人类操作方式——看截图、定位控件、点击鼠标或敲键盘。这种“人类交互先验”带来三重代价：
  - 智能体需要反复解读屏幕，精确定位坐标，即使应用已通过无障碍接口暴露了控件身份与取值；
  - 本可直接用代码处理的数据，被迫用重复的点击拖拽完成；
  - 计算机已有的**语义能力（AX）**与**程序化能力（代码/CLI）**被严重低估。
- **整体含义**：作者主张不应由接口固定“计算机该怎么用”，而应把程序化、语义、视觉三类互补通道同时暴露给通用智能体，**由模型自主选择与组合**；这呼应“苦涩的教训”——强人类化接口可能限制越来越强的模型的能力发挥。
- **与已有工作的差异**：ALE、WeaveBench 的 GUI-as-Tool 只组合程序化+视觉；UFO2、Tactile、CUA Driver 涉及 AX，但或偏向专用多智能体系统、或以保留用户桌面为优先；HCU 在通用智能体内统一三通道，并补齐 AX 的批量执行、等待步骤、后置反馈与跨通道守卫。

## 2. 方法论

### 2.1 核心思想

- 在智能体既有的“观察–行动”循环内，通过 **MCP** 增加两个桌面工具（AX 与 GUI），与智能体自带的代码/Shell/文件工具并列，形成三通道：
  - **程序化**：代码、命令行、文件操作；
  - **语义（AX）**：读取应用无障碍树，执行“引用寻址”的动作；
  - **视觉（GUI）**：全桌面截图、缩放、鼠标键盘输入。
- **不引入规划器、子智能体或额外循环**，通道选择完全由模型决定；观察与执行可跨通道（如截图观察 + AX 执行），因此同一接口可挂接到不同 agent harness。

### 2.2 AX 通道的三项关键设计

1. **紧凑视图 + 稳定目标引用**
   - 服务端保留完整 AX 记录，向模型展示经过投影的紧凑视图：去除空结构包裹、合并相邻无引用文本、去重关系标签、保留同名控件消歧上下文、表格单元格值随名称展示、重复兄弟节点按预算汇总。
   - **引用在压缩前绑定**（`aN` 应用、`wN` 窗口、`rN` 元素），因此视图裁剪不影响引用所指元素；被省略的目标可通过 `find` 或限定 `scope`/`root` 的观察取回。
   - 实测投影使视图 token 减少：Chrome −44.1%（1817→1016）、Audacity −14.1%、Obsidian −12.6%，且 100% 保留已发出的引用；对比 OSWorld 2.0 原生 XML，同一 Obsidian 窗口从 30,526 token 降至 1,237 token。
2. **批量动作 + 等待步骤**
   - 一次 `act` 调用可在同一逻辑窗口内顺序执行最多 64 个动作与 `wait` 步骤；`wait` 不发送输入，可等待窗口出现、查询匹配、引用元素达到指定 value/state/text、目标消失（`gone`）或 UI “变化后稳定”（`settle`）；置于末尾即成为终态校验。
   - 任一步失败、等待超时或窗口连续性丢失即中止批次，并报告停止位置与执行证据，避免盲目重放。
3. **后置反馈（AX diff）**
   - 默认返回逐目标 `effect` 摘要、`windows` 行（打开/关闭/聚焦）以及相对上一次有效快照的结构化 AX diff，模型无需额外观察即可继续。
   - 严格区分“已知未送达”“输入可能已发出但效果未知”，避免把输入投递误当作已验证的效果；失败时返回公开错误码（如 `invalid_argument`、`stale_ref`、`gui_frame_stale`、`wait_timeout`、`window_changed`、`effect_unknown`）与修正提示。

### 2.3 跨通道动作守卫（Algorithm 1 文字流程）

- 输入：一个带目标的 AX 批次或 GUI 坐标批次 A，以及最后一张截图 F。
- 对 A 中每个动作 a 依序处理：
  - **若为 AX 动作**：在执行前用 `LiveTarget(ref)` 解析引用，核对元素身份与动作特定前置条件；若缺失、歧义、被替换或条件不满足 → 拒绝且**不发送任何输入**，也**不重定向**到同名元素，返回新证据或请求重新观察。
  - **若为 GUI 坐标动作**：检查当前桌面边界、可见顶层窗口、堆叠顺序、活动窗口及目标点所在窗口布局是否与截图 F 所绑定的“布局租约”一致；不一致则以 `gui_frame_stale` 阻断并返回新截图。
  - 通过则执行。
- 守卫检查的是**实时状态**，无论此前是哪个通道改变了桌面；若处于“可能有排队 OS 请求仍会触发”的不确定状态，则直接停止桌面自动化，不重放批次。
- 状态维护规则：GUI 变更会使 AX 工作快照、隐藏元素缓存、find 游标失效，但保留引用注册表与已交付的 diff 快照；AX 的 `full`/`screenshot` 观察会成为当前 GUI 帧并登记布局租约。

### 2.4 配套技能（Skill）

- 从开发轨迹中的高频错误提炼，分三部分：
  1. **通道能力**：各通道能提供什么观察、有何局限；
  2. **高效交互**：如何使用引用、批量动作配等待、直接依据返回反馈继续；
  3. **验证与恢复**：区分“输入送达 / 局部 UI 变化 / 任务结果”，以及过期引用、调用错误、证据不足时的恢复方式。
- 不含任何任务特定解法；仅通过工具 schema + 技能文本约束调用契约。效果：畸形参数被拒比例从 17.37% 降至 1.36%，同一工具反复换参重试的任务运行比例从 44.69% 降至 0.37%。

### 2.5 系统实现

- 一个进程拥有一个桌面会话：`computer-use mcp` stdio 服务或后台守护进程；共享 Go 服务负责校验、AX 快照与引用注册、find 游标、diff 快照、GUI 布局租约；平台 provider 以私有协议实现取树与原生输入。
- 原生后端：Linux（Python + AT-SPI/X11）、macOS（Swift + AXUIElement/CoreGraphics/ScreenCaptureKit/SkyLight）、Windows（C# + UIA3/Win32），构建时选择。
- 评测版与发布版差异：批内检查统一为有序 `wait`、`apps` 取代 `observation_target`、批次上限 32→64、结果首行为带公开错误码的 JSON 证据行，并新增 GUI `zoom`、AX `select`、`settle` 等待、逐目标效果报告与 Linux 逐目标点布局检查。
