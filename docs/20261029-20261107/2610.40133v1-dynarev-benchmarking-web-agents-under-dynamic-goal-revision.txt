# DYNA REV : Benchmarking Web Agents under Dynamic Goal Revision 

## Shiqi Zhang 1,2, Guochen Zhou 1, Zesheng Wei 1, Hai Zhao 2, Zhisong Zhang 11City University of Hong Kong 2Shanghai Jiao Tong University 

## szhang2879-c@my.cityu.edu.hk , zhisong.zhang@cityu.edu.hk 

## Abstract 

Web agents are typically evaluated with goals fully specified before execution and fixed there-after, whereas real users often revise their re-quirements during interaction. To study such interactions, we introduce D YNA REV , a bench-mark of 181 tasks to evaluate web agents un-der dynamic goal revision . DYNA REV uses semantic milestones to deliver revisions at task-defined stages, covers additive revisions, un-conditional overrides, and runtime-conditioned overrides, and evaluates correctness, respon-siveness, and efficiency through trajectory-grounded evaluation. Five-model evaluations show that agents often satisfy only part of the task requirements, with performance varying across task sources, revision types, and mod-els. Further analyses reveal varied milestone timing, mixed effects of dynamic delivery, and contrasting revision-handling outcomes, with gains from instruction rewriting while preserv-ing browser state and losses from browser re-sets. D YNA REV provides a testbed for study-ing how web agents adapt to evolving user goals. The code and data are available at 

https://github.com/zsq259/DynaRev .

They support a wide range of practical tasks such as infor-mation seeking, online shopping, travel planning, and service navigation. However, most web-agent tasks assume that the user’s goal is fully specified before execution and remains fixed throughout the interaction (Deng et al., 2023; Zhou et al., 2024; Koh et al., 2024; He et al., 2024; Xue et al., 2025; Gou et al., 2025). Real-world user goals are often more dynamic. For example, a user may first ask an agent to find a flight from Los Angeles to Boston, then add “Avoid overnight flights” after viewing the candidates, re-vise this preference to “If daytime flights cost more than $150 extra, overnight flights are acceptable,” and later request nonstop flights only. Such in-teractions are not merely a fixed instruction split across multiple turns: later instructions may add new constraints, override previously active ones, or introduce requirements that apply conditionally based on the web state observed during execution. We refer to this setting as dynamic goal revision .Recent work has begun to recognize goal adaptation as an important agent capability. AgentChangeBench (Rana et al., 2025) studies goal shifts in conversational tool-using agents, DeskCraft (Wang et al., 2026) considers interrup-1arXiv:2610.40133v1 [cs.AI] 29 Oct 2026 tions and corrections in desktop workflows, and In-terruptBench (Zou et al., 2026) evaluates additions, revisions, and retractions in long-horizon web navi-gation. However, three gaps remain in web settings. First, revisions are often injected based on rela-tive trajectory progress rather than task-semantic progress, so agents following different paths may receive the same revision at different task stages. Second, existing settings largely omit conditional revisions whose applicability depends on the web state. Finally, evaluations mainly assess task-level success and recovery cost, with limited analysis of revision-level constraint satisfaction, post-revision responsiveness, and cost–quality trade-offs. To address these gaps, we introduce D YNA REV ,a benchmark for evaluating web agents under dy-namic goal revisions. DynaRev uses semantic mile-stones , task-defined stages of the current goal, to trigger revisions independently of the execution path, and covers additive, unconditional-override, and conditional-override revisions, with condi-tional branches resolved from the web state. We develop a revision-aware, trajectory-grounded eval-uation framework that assesses answer correctness, revision responsiveness, and cost-aware efficiency. We construct 181 dynamic tasks from Online-Mind2Web (Xue et al., 2025) and Mind2Web 2 (Gou et al., 2025), and evaluate five models. Agents often satisfy only part of the task requirements, with performance varying across task sources, revision types, and models. Further analyses reveal substantial variation in milestone timing and mixed effects of dynamic delivery, while instruction rewriting with preserved browser state improves quality and efficiency and browser resets degrade performance. These results reveal behaviors missed by static evaluation. Our contributions are threefold: (i) We formu-late dynamic goal revision for web agents and in-troduce semantic milestone-based revision deliv-ery. (ii) We construct D YNA REV , covering additive revisions, unconditional overrides, and runtime-conditioned overrides. (iii) We develop a revision-aware, trajectory-grounded evaluation assessing correctness, responsiveness, and efficiency. 

## 2 Related Work 

GUI Agents and Web Agents. GUI agents inter-act with graphical interfaces through actions such as clicking, typing, and scrolling to complete user tasks (Zhang et al., 2024; Nguyen et al., 2025). web agents instantiate this setting in browser en-vironments, where agents can also use structured page representations such as HTML and accessibil-ity trees. Representative systems such as SeeAct (Zheng et al., 2024) and WebVoyager (He et al., 2024) demonstrate LLM-based agents operating on real websites. We focus on web agents as the evaluation setting in this work, while dynamic goal revision is relevant to GUI agents more broadly. 

Web Agent Evaluation Benchmarks. The eval-uation of web-agents has progressed from offline action prediction to interactive and real-world ex-ecution. Mind2Web (Deng et al., 2023) evalu-ates agents against human interaction trajectories, while WebArena (Zhou et al., 2024) and Visu-alWebArena (Koh et al., 2024) provide interac-tive sandbox environments with functional eval-uation. WorkArena (Drouin et al., 2024) and WorkArena++ (Boisvert et al., 2024) extend eval-uation to enterprise workflows and compositional tasks. WebVoyager (He et al., 2024) extends evalu-ation to live websites, and more recent benchmarks such as Online-Mind2Web (Xue et al., 2025) and Mind2Web 2 (Gou et al., 2025) further improve task realism and outcome verification. Despite these differences, their tasks generally specify the complete user objective before execution and keep it unchanged throughout the interaction. 

Multi-turn Interaction and Dynamic Goal Re-vision. Multi-turn interaction has been studied in both web and general agent settings. MT-Mind2Web (Deng et al., 2024) evaluates context-dependent sequential instructions, while We-bLINX (Lu et al., 2024) studies real-world web-site navigation through multi-turn dialogue. More recent work directly considers evolving goals: AgentChangeBench (Rana et al., 2025) studies goal shifts in conversational tool-using agents, Intent-Flux (Zhang et al., 2026) evaluates intent drift un-der superseded and withdrawn requirements, while COMPASS (Qin et al., 2026) and RECAP (Mitra et al., 2026) consider evolving constraints and in-tent in multi-turn interactions. Related settings have emerged for GUI agents, including ReInAgent (Jia et al., 2025), DeskCraft (Wang et al., 2026), and most closely, InterruptBench (Zou et al., 2026), which evalu-ates user additions, revisions, and retractions dur-ing long-horizon web navigation. ## 3 Problem Formulation 

We formalize web-agent interaction under dynamic goal revisions. Throughout this section, consider a user who initially asks an agent to “Find me a daytime flight from New York to Los Angeles,” and may revise the request during execution. 

3.1 Web Agent Interaction 

We consider a web agent interacting with a browser environment over multiple steps. At step t, the agent receives observation st and produces action 

at. A trajectory up to state st is represented as 

τt = ( s0, a 0, s 1, a 1, . . . , s t), (1) 

which records the preceding state-action sequence and ends with the latest observed state. 

3.2 Dynamic Goal Revision 

A dynamic goal revision task is defined as 

T = ( I0, {(Mk , I k )}nk=1 ) , (2) 

where I0 is the initial instruction, each Ik (k ≥ 1)is a revision delivered during execution to update the previously specified goal, and n is the num-ber of revisions. Each instruction specifies one or more task constraints, and revisions update which constraints are active. A central challenge is deciding when a revision should be introduced. Triggering at a fixed step or at a fixed relative position along an execution tra-jectory can expose different agents to the same revision at substantially different stages of task progress, since successful web trajectories may vary considerably in both length and structure. We therefore define each milestone Mk as an in-evitable semantic stage of the goal that has already been specified before revision Ik. Importantly, a milestone is derived from the previously specified goal rather than from the revision that will follow it. Any successful execution of the current goal should eventually reach this stage, regardless of the concrete sequence of UI actions used to get there. In the running example, a milestone can be “The initial search for daytime flights from New York to Los Angeles has been completed and the search results have been observed.” A later require-ment such as “Only consider nonstop flights” is introduced after this stage is reached. A trigger ϕ(Mk, s t) ∈ {0, 1} determines whether Mk is reached at state st. If ϕ(Mk, s t) = 1, revision Ik is delivered before the next step. 

3.3 Revision Types 

Using the same flight request, we consider three forms of revision. An additive revision introduces a new constraint while preserving previously active constraints, e.g., “Only consider nonstop flights.” An unconditional override replaces a previously active constraint with a new one, e.g., “Actually, choose an overnight flight instead.” A conditional override replaces a previously active constraint with an alternative only when a specified runtime condition is satisfied, e.g., “If daytime flights cost more than $150 extra, overnight flights are accept-3able.” In a conditional override, the agent must determine the applicable branch and corresponding active constraints from the web state, rather than receiving them from the revision. 

## 4 Benchmark Construction 

We construct dynamic goal revision tasks by trans-forming static goals into sequences of instructions and revisions with explicit constraint bindings, con-structing semantic milestones for revision delivery, and validating task quality and interaction natural-ness. Construction details are in Appendix A. 

4.1 Static-to-Dynamic Task Transformation 

We first decompose the original task goal into atomic constraints, each describing an indepen-dently verifiable requirement. These constraints provide the basic units for revision construction and evaluation. We then construct an initial instruc-tion I0 that is sufficiently specific to form a natural and executable request, while leaving part of the original goal to be introduced during execution. The remaining constraints are organized into a sequence of revisions according to a natural inter-action order. Closely related constraints may be introduced together rather than mechanically sepa-rated into different turns. For override revisions, a previously active constraint is replaced or relaxed; conditional overrides additionally associate the re-placement with a runtime condition that can be ver-ified from the web environment. Each constraint is finally bound to the revision that introduces or modifies it, providing an explicit correspondence between goal evolution and evaluation units. 

4.2 Milestone Construction 

For each revision Ik, we construct its milestone Mk

from the cumulative goal specified by I0, . . . , I k−1.The milestone describes a completed semantic stage that can be identified from the web state, while avoiding specific UI actions, reference-trajectory states, or information from the upcoming revision. We also avoid requiring a particular result configuration; for example, completing a search can constitute a milestone even when no matching candidates are returned. 

4.3 Quality Control 

Generated tasks are checked for both structural validity and interaction naturalness. The initial in-struction must express a coherent executable goal, while subsequent revisions must introduce mean-ingful changes rather than artificial fragments of the original instruction. Milestones must describe semantic stages implied by preceding goals and remain independent of a particular reference trajec-tory or future revision. For conditional overrides, the triggering condition must be observable from the runtime environment. We additionally verify the consistency between revisions and their asso-ciated constraints. Tasks that fail these checks are regenerated or excluded from the benchmark. 

## 5 Revision-Aware Evaluation 

We evaluate agent executions through constraint verification and post-revision behavioral assess-ment, with metrics covering answer correctness, revision responsiveness, and cost-aware efficiency. Implementation details are in Appendix C. 

5.1 Constraint Verification 

Following the Agent-as-a-Judge paradigm (Zhuge et al., 2025; Gou et al., 2025), we evaluate each constraint using the agent’s final response and in-teraction trajectory. Constraints associated with undelivered revisions are counted as unsatisfied. For conditional overrides, we determine the active branch and evaluate the corresponding constraints. Each constraint is decomposed into indepen-dently verifiable claims. According to the required evidence, we classify them into two types: sim-ple claims can be verified directly from the agent’s final response, whereas page claims require sup-porting evidence from web states in the interaction trajectory. A constraint is satisfied only if all of its claims are verified. For task i, we denote the resulting judgment for constraint c by zi,c ∈ { 0, 1}.

5.2 Post-Revision Behavioral Assessment 

Final outcomes alone do not indicate whether an agent actually responds to a revision. For each delivered revision Ii,k , we therefore examine the subsequent local action window and use an LLM judge to determine whether the agent’s behavior is consistent with the revised intent. We denote this binary judgment by Ri,k ∈ { 0, 1}.

The baseline retains the original instructions, interaction history, and browser state, corresponding to direct continuation from the current execution. ## 8 Conclusion 

We introduced D YNA REV , a benchmark to as-sess web agents under dynamic goal revisions, featuring semantic milestone triggers, runtime-conditioned overrides, and fine-grained evaluation of correctness, responsiveness, and efficiency. Ex-periments with five models show that immediate adaptation does not ensure final constraint satisfac-tion. Further analyses reveal timing mismatches between fixed-position and milestone-based revi-sions, while instruction rewriting while preserving browser state improves task quality and efficiency. 8Our benchmark provides a foundation for studying web agents’ ability to handle evolving user goals. 

## Limitations 

We acknowledge the limitations of this work. (i) Our benchmark is constructed from static web tasks and may not capture the full diversity of real-world goal changes. (ii) Milestone triggering and evalua-tion rely on imperfect LLM-based semantic judg-ments. (iii) Semantic milestones assume that mean-ingful intermediate task stages can be identified, which may be harder for tasks with highly diverse successful trajectories.

## A Benchmark Construction Details 

This section provides additional details for the static-to-dynamic task transformation described in Section 4. The construction procedure follows five stages: constraint decomposition, initial instruction construction, revision and milestone organization, quality control, and constraint binding. 10 A.1 Constraint Decomposition 

We first decompose each source task into a set of atomic constraints. Each constraint describes a single independently verifiable requirement and is designed to avoid semantic overlap with the others. The resulting constraints serve as the shared units for subsequent revision construction and evalua-tion. Tasks with too few constraints to support mean-ingful multi-round decomposition are excluded at this stage. This prevents the construction procedure from producing artificial revisions by fragmenting a goal that is naturally expressed in a single turn. 

A.2 Initial Instruction Construction 

The atomic constraints are separated according to whether they are necessary for forming a natural ini-tial request. We refer to constraints that are needed to specify a coherent and executable starting goal as required constraints, while constraints that can be naturally introduced later are treated as later 

constraints. The initial instruction I0 contains the required 

constraints. If these constraints alone leave the target underspecified, a small number of later con-straints may also be included to make the request sufficiently clear. The objective is to keep I0 exe-cutable without prematurely exposing requirements that can naturally arise during subsequent interac-tion. Before constructing the initial instruction, we also check whether the target website is accessi-ble. Tasks affected by persistent access failures, ab-normal redirections, or similar issues that prevent meaningful execution are excluded from further construction. 

A.3 Revision and Milestone Organization Revision organization. The remaining con-straints are organized into a sequence of revisions according to a natural interaction order. Closely re-lated constraints may be introduced together when they would normally be expressed in the same user turn, rather than being mechanically separated to increase the number of revisions. Additive revi-sions directly introduce previously unspecified re-quirements while preserving the constraints that are already active. 

Milestone construction. Each revision Ik is paired with a semantic milestone Mk that deter-mines when it is delivered. The milestone is de-rived only from the cumulative goal specified by 

I0, . . . , I k−1, rather than from the upcoming revi-sion Ik. We describe milestones as completed se-mantic stages of the currently specified task rather than particular UI actions or reference-trajectory states. The milestone description also avoids unneces-sarily requiring a specific result configuration. For example, completing a search stage can constitute a milestone even if the search returns no match-ing candidates. This distinction prevents milestone triggering from depending on incidental properties of the current web state rather than on task progress itself. 

Eligible override constraints. For tasks contain-ing override revisions, we distinguish between core 

and preference constraints. Core constraints define the fundamental task object or objective, such as the target product category, search subject, or desti-nation. Preference constraints describe attributes that users may naturally revise during execution, such as color, price range, rating, or ranking prefer-ence. Override revisions are constructed only from 

preference constraints. 

Unconditional overrides. The construction of an unconditional override is separated into replace-ment planning and timeline organization. We first select an eligible preference constraint and choose an alternative value from the same semantic di-mension. Replacement candidates are primarily collected from values observed in the source tasks; when the available candidates are insufficient, addi-tional alternatives in the same semantic dimension are generated and reviewed for consistency with the task context. The selected original preference and its replace-ment are then incorporated into the multi-round timeline. The original preference is introduced be-fore the override, while the later revision explicitly replaces it with the new requirement. Separating replacement selection from timeline generation re-duces interference between deciding what should change and deciding when and how that change should be expressed. 

Conditional overrides. Conditional overrides re-tain the original preference as the default require-ment and activate an alternative only when a speci-fied runtime condition is satisfied. The condition must be observable from the web environment dur-ing execution and should introduce an additional 11 environment-state judgment rather than reducing to a direct restatement of the preference replacement itself. We consider two types of conditions. Numerical-threshold conditions are defined over observable quantities such as price differences, rating dif-ferences, or distance, and activate the alternative branch when the relevant value crosses a specified threshold. Existence conditions depend on whether a particular type of option is available, such as whether an item is in stock or whether a direct flight exists. For conditional-override construction, the se-lected replacement pair is combined with a con-dition appropriate to the task context and constraint dimension, and the resulting branch structure is then incorporated into the multi-round timeline. 

A.4 Quality Control 

Generated tasks are reviewed for both structural validity and interaction naturalness. The initial in-struction must specify a coherent executable goal, while subsequent revisions must introduce mean-ingful changes rather than artificial fragments of the source instruction. Milestones must describe se-mantic stages implied by previously specified goals, remain independent of the upcoming revision, and avoid dependence on a particular sequence of UI operations. For conditional overrides, the runtime condition must be observable from the web environment and the alternative branch must remain meaningful in the underlying task context. We also check the consistency of the revision sequence and the con-straints that it is intended to introduce or modify. When an instance fails these checks, the rele-vant construction stage is regenerated. Tasks that remain invalid after the prescribed retries are ex-cluded from the final benchmark. 

A.5 Constraint Binding 

After a task passes quality control, each atomic con-straint is bound to the instruction that introduces or modifies it. This correspondence records the prove-nance of each evaluation requirement and allows the evaluation pipeline to distinguish constraints associated with different stages of goal evolution. Constraint binding is performed as a separate post-processing stage rather than jointly with revi-sion generation. Generating revisions and bindings simultaneously may encourage artificially regular partitions in which each revision is constructed merely to correspond to a convenient subset of constraints. Separating the two stages allows revi-sion construction to prioritize natural interaction structure while preserving an explicit instruction– constraint correspondence for later evaluation. 

## B Execution Details 

B.1 Interaction Context 

At each step, the agent receives the accumulated user instructions, the complete action history, and web observations from the interaction trajectory. To control context growth, we retain the full web ob-servations for only the five most recent interaction steps. Earlier observations are replaced with a fixed placeholder, while their corresponding actions re-main in the context. Thus, the complete instruction and action histories are preserved throughout execu-tion, while detailed web-state history is maintained within a fixed recent window. 

B.2 Revision Delivery and Termination 

Revisions are delivered when their corresponding semantic milestones are reached. If the agent de-clares completion while revisions remain pending and execution budget remains, the completion is intercepted, the next pending revision is delivered, and execution continues. A run terminates when the agent calls done af-ter all revisions have been delivered, or when the maximum execution step limit is reached. 

B.3 Environment Configuration 

All agents are executed through BrowserGym with Playwright-controlled headless Chromium. Obser-vations use the viewport-restricted AXTree repre-sentation. The same execution configuration, in-cluding the context-management strategy, is ap-plied to all evaluated agents. 

## C Evaluation Details 

This section provides implementation details omit-ted from Section 5, focusing on claim construction, trajectory evidence retrieval, and post-revision be-havioral assessment. 

C.1 Claim Construction and Verification 

For each constraint to be evaluated, the claim gen-erator receives the constraint, the agent’s final re-sponse, and the task context, and produces one or more independently verifiable claims together with their verification types. For constraints containing 12 relative-time expressions, we additionally provide the task execution date to resolve the temporal ref-erence. Claim decomposition is used when a single con-straint requires multiple verification instances. For example, if a constraint requires every returned ho-tel to provide free breakfast, the evaluator generates a separate claim for each returned hotel. This al-lows each hotel to be verified independently while preserving the original constraint as a single task requirement. Claims of type simple are verified directly from the agent’s final response, whereas page claims are passed to the trajectory evidence retrieval proce-dure described below. 

C.2 Trajectory Evidence Retrieval 

For each page claim, we first identify the subject whose property or web evidence must be verified. We then inspect the final recorded web state. If it already provides sufficient evidence, the claim is verified directly from this state. Otherwise, we search the trajectory beginning from the delivery of the instruction to which the constraint is bound. The claim subject is used as an anchor for lightweight lexical matching over subsequent web states, producing a small set of candidate states. Only these candidates are passed to the page verifier. A lexical match is used only for candidate re-trieval and is not itself treated as evidence. Can-didate states are examined in trajectory order, and the first state judged to provide sufficient evidence is used to verify the claim. If no retrieved state pro-vides sufficient evidence, the page claim is treated as unverified. 

C.3 Post-Revision Behavioral Assessment 

For each delivered revision, we examine at most the next three agent actions, stopping earlier if an-other revision is delivered or the task terminates. The resulting action window is evaluated by the behavioral judge to determine whether the agent responds consistently with the revised intent.

System 

You judge whether a GUI agent’s actions in a short window (1-3 steps) responded to a specific user instruction that was just injected. The instruction is one of a sequence of corrections the user gave the agent during execution. Decide TWO things, independently: 1. wra ∈ {0, 1} 

34 wra=1 — at least one action in the window concretely advances the new instruction’s intent (issuing a relevant search, navigating to a relevant page, filtering / refining results to match the new constraint, opening a candidate that satisfies the new requirement, etc.). wra=0 — none of the actions clearly serve the new instruction.
