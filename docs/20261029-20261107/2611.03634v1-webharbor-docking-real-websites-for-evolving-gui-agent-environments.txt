ABSTRACT
GUI web agents require realistic and interactive environments that remain sta-
ble during both evaluation and training. Live website evaluation suffers from
changing content, access restrictions, and limited coverage of authenticated work-
flows, while existing synthetic environments for training often lack functional
depth and visual fidelity. We propose WebHarbor, a suite of 153 executable and
dockerized website environments that faithfully reconstruct the visual interfaces,
content, and functional workflows of real-world web services under deterministic
control. We build WebHarbor through task-driven human-agent collaboration,
where environments evolve as new tasks expand their functional scope, coding
agents implement the required changes, and human contributors audit visual fi-
delity, functional correctness, and task validity. The resulting suite comprises 3,518
tasks spanning multi-step and post-authentication workflows, where existing works
often fail to cover. Beyond reliable evaluation, WebHarbor provides high-fidelity
synthetic web environments for cost-efficient reinforcement learning (RL). We
demonstrate that a Qwen 4B-level GUI agent trained with RL in WebHarbor gen-
eralizes to unseen tasks and performs competitively with leading open-source GUI
web agents across four benchmarks. The code and data are publicly available at
https://github.com/aiming-lab/WebHarbor.

INTRODUCTION
Web agents powered by large language models (LLMs) with multimodal capability interpret rendered
webpages and complete tasks through browser interactions (Deng et al., 2023; He et al., 2024; Zheng
et al., 2024; Qin et al., 2025). Their progress depends on environments that support reliable evaluation
and training. Evaluation requires stable and reproducible outcomes, while reinforcement learning
(RL) additionally requires executable state transitions and repeatable resets (Qi et al., 2025; Bai
et al., 2024; Wei et al., 2025; Lai et al., 2025). Live websites offer realistic interfaces, but changing
content, bot detection, and regional restrictions undermine experimental control. Moreover, live-web
benchmarks rarely cover authenticated workflows, despite their importance to many everyday user
requests (He et al., 2024; Xue et al., 2025). In our experiments, about 38% of Online-Mind2Web
tasks were blocked by bot detection, and 22% of WebVoyager tasks were outdated due to website
changes. These failures introduce uncontrolled variation into evaluation and prevent agents from
learning the many workflows hidden behind authentication.
An alternative should combine realistic visual observations, functional interactions, and persistent
authenticated state with offline execution and reliable resets. Achieving this balance is challenging:
commercial websites encompass extensive content and functionality, making complete reconstruction
impractical, while visually similar replicas may lack correct search, account management, booking,
or transaction logic. Even apparently functional environments may expose shortcuts, omit plausible
alternative actions, or leak answers through their interfaces, undermining task validity. The goal
is to match both what agents observe and how websites respond to their actions, while ensuring
reproducibility and practical utility for both evaluation and RL.
Human crafted benchmarks such as WebArena and VisualWebArena offer reproducible applications
but cover very few websites (Zhou et al., 2024; Koh et al., 2024). Manually reconstructing real
websites can improve fidelity, but requires substantial effort and remains difficult to scale. Recent

To address this gap, we introduce WebHarbor, a suite of 153 executable website environments drawn
from the website spaces covered by WebVoyager and Online-Mind2Web. WebHarbor uses task-
conditioned construction: target tasks specify the pages, data, and interaction workflows that each
environment must support, providing a tractable scope for reconstructing large web content. Coding
agents then implement the frontend, backend, database, and visual content through a standardized set
of environment-construction skills. Human contributors inspect the rendered websites, execute the
target workflows, and revise failures in visual fidelity, functional correctness, data realism, and task
validity, where fix implementations are done by coding agents. This human-agent process produces
Dockerized environments that run without access to the target services, reset to controlled initial states,
and support both public information-seeking tasks and in-depth workflows behind authentication. The
final resource contains 3,518 tasks covering information retrieval, account management, bookings,
and transactions, and can be used as a stable benchmark or as an executable training environment.
In summary, our contributions are threefold.
(1) We introduce WebHarbor, a suite of 153 controllable web environments and 3,518 tasks with
authenticated workflows and persistent state changes largely absent from live-web benchmarks.
(2) We develop a human-agent collaborative construction pipeline that combines task-conditioned
website implementation by coding agents with iterative human auditing of visual fidelity, func-
tional correctness, and task validity until approval.
(3) Experiments across three web agent benchmarks demonstrate that a Qwen 4B agent trained
with RL in WebHarbor generalizes to unseen tasks and achieves performance competitive with
leading open-source web agents on live web benchmarks.

RELATED WORK
GUI Web Agents
Web agents have evolved from systems that operate on HTML or accessibility
representations (Zheng et al., 2024; He et al., 2024) to multimodal agents that integrate webpage
understanding, reasoning and planning, action grounding, and sequential decision-making to execute
user instructions (Gur et al., 2024; Koh et al., 2025; Putta et al., 2024). While prior work has
largely focused on learning from demonstrations (Hong et al., 2024; Cheng et al., 2024; Xu et al.,
2024; Qin et al., 2025; Wang et al., 2025), recent approaches such as WebRL, WebAgent-R1, and
OpenWebRL, further optimize agent policies through reinforcement learning based on environment
interactions (Qi et al., 2025; Wei et al., 2025; Yang et al., 2026). These approaches motivate the
need for environments that provide realistic visual observations, executable state transitions, and
reproducible initial conditions. WebHarbor provides such an infrastructure for efficient training and
reliable evaluation of GUI web agents across diverse website interfaces.
Web Agent Benchmarks
Existing benchmarks trade off website coverage, interaction depth, and
experimental control. MiniWoB++ and WebShop provide controlled settings for browser interaction
and shopping (Liu et al., 2018; Yao et al., 2023), while Mind2Web expands website coverage but
relies on cached snapshots that limit interactive exploration (Deng et al., 2023). Live-web bench-
marks such as WebVoyager, Online-Mind2Web, and DeepShop offer realistic interactions across
diverse websites (He et al., 2024; Xue et al., 2025; Lyu et al., 2025). Online-Mind2Web, even with
periodic task updates, however, it remains vulnerable to website changes, bot detection, CAPTCHA,
and network or geographic restrictions, while offering limited coverage of authenticated and state-
changing workflows. In contrast, self-hosted benchmarks such as WebArena, VisualWebArena, and
WorkArena support complex interactions under controlled settings (Zhou et al., 2024; Koh et al.,
2024; Drouin et al., 2024). However, their limited website coverage, heavyweight deployments, and
costly environment resets complicate repeated evaluation and online RL training. REAL provides de-
terministic replicas of 11 real websites with persistent state changes, but starts from pre-authenticated
states (Garg et al., 2025). WebHarbor bridges these trade-offs with 153 image-rich and executable
websites and 3,518 tasks, covering both information seeking and authenticated and state-changing
workflows. Its lightweight SQLite-backed architecture enables fast resets, facilitating reproducible
evaluation and scalable online RL training across many websites.

Recent work scales web agent training through environment and
task synthesis. WebArena-Infinity and InfiniteWeb synthesize functional browser environments from
documentation, specifications, and visual references (Zhou, 2026; Zhang et al., 2026). AutoWebWorld,

WEBHARBOR
Given a target website and a set of relevant tasks, WebHarbor reconstructs an executable local
environment that preserves task-relevant interfaces, content, and state transitions. We call this process
docking: replacing live dependencies with local assets, seeded state, and controlled resets while re-
taining recognizable visual and functional behavior. Figure 2 illustrates the iterative workflow. Target
tasks define the reconstruction scope, coding agents use reusable skills to implement the frontend,
backend, database, and visual content, and human contributors audit the resulting environments.
Human feedback guides coding agents in repairing visual and functional defects. As new tasks reveal
missing functionality or shortcuts, the same process expands and refines the environments while
maintaining deterministic execution and reliable resets.
3.1
TASK-DRIVEN DOCKING
Reconstructing an entire commercial website is impractical, given the significant scale of services
such as Amazon’s product catalog or YouTube’s video library. Instead, we adopt a task-driven
reconstruction process that scopes each environment to the functionality and content required by its
target tasks. Each task specifies entry and terminal pages, observable entities and attributes, required
browser actions, and persistent state changes. These requirements define the task-relevant support
surface: the pages, routes, image content, and data needed for realistic interactions.
We begin with WebVoyager’s 15 websites and 643 tasks (He et al., 2024), whose live-web evalu-
ation has become less reliable due to website changes. We then extend coverage to all websites
in Online-Mind2Web (Xue et al., 2025), but exclude its original tasks, which primarily focus on
information seeking rather than authenticated and state-changing workflows. For these websites,
human contributors identify core functional areas, and an LLM expands them into candidate work-

flows using its knowledge of common web services. Human contributors then review and refine
these tasks for functional coverage, feasibility, and interaction depth. The resulting tasks cover
account management, bookings, purchases, saved items, and other persistent operations. Task-driven
scoping also facilitates visual and functional fidelity by explicitly defining the observations and
state transitions that must be reproduced. Beyond task completion, environments preserve natural
navigation paths and surrounding content, including plausible alternatives and near-miss items that
prevent trivial shortcuts. This approach bounds reconstruction effort while retaining the interaction
complexity needed for evaluation and training. The full list of 153 websites is provided in Tables 19
and 20 in the Appendix. Synthesis prompts are provided in Appendix B.
3.2
SKILL-DRIVEN SYNTHESIS AND EVOLUTION
Task-driven docking defines what an environment should support, while skill-driven synthesis and
evolution transform these requirements into an executable offline website. For each website, the
coding agent first explores the target service through a rendered browser, recording its task-relevant
page hierarchy, navigation paths, URL patterns, interactive controls, and visual appearance. The
rendered DOM and resolved asset URLs provide references for reconstructing client-rendered
pages and lazy-loaded content. Guided by these observations and reusable construction skills (see
Appendix B), the coding agent builds a self-contained web application backed by SQLite and bundled
with local visual assets. These assets are either downloaded from the target website or replaced with
visually similar alternatives obtained from public sources. The initial reconstruction is then refined
through repeated execution of target tasks. For each task, the coding agent interacts with the rendered
interface and identifies the first unsupported observation or state transition. Missing pages prompt
the creation of new routes and views, incomplete workflows require additional form handlers and
persistent state updates, and insufficient content motivates new database records and task-relevant
alternatives. After each revision, the environment is reset to its seeded state, and the complete
workflow is executed again. This iterative process allows increasingly diverse and challenging tasks
to expand and refine the environment until all target workflows can be completed end to end through
the visible interface with the intended persistent state changes.
3.3
HUMAN-IN-THE-LOOP ITERATIVE REFINEMENT
Automated synthesis provides weak quality control for visual fidelity, long-horizon behavior, and
task validity. Coding agents may complete target workflows while leaving surrounding interfaces
visually inaccurate, functionally shallow, or artificially easy. In our pilot study of 26 websites, 13
environments exhibited visual or asset defects (e.g., images mismatched with descriptions), and 14
had broken or shallow interactions (e.g., unresponsive buttons). Such issues are often overlooked
by coding agents during long-horizon environment construction but are readily identified by human
reviewers. Figure 1 illustrates how fully automated reconstructions may capture coarse website
layouts while simplifying functionality or omitting important visual content.
To improve the environment quality, we introduce human-in-the-loop auditing and iterative collab-
oration. Specifically, We organize human participation into two roles. Contributors specify target
websites and high-level functional requirements and guide coding agents during construction. Desig-
nated reviewers then compare reconstructed environments against the target websites and execute
each task end to end, checking task feasibility, intended interaction sequences, and visual and func-
tional fidelity. Reviewers translate identified defects into actionable requests for coding agents and
re-evaluate affected workflows until approval. On average, each environment undergoes 2–3 review
rounds, each taking 1–2 hours. Reviewers also develop task-specific verifiers and judging rubrics that
define the grading criteria for LLM-as-a-Judge (Zheng et al., 2023) or agent-as-a-Judge (Zhuge et al.,
2024). All contributors and reviewers are community volunteers included in the author list.

3.5
DATASET ANALYSIS
We analyze WebHarbor along four dimensions. (1) Effective community collaboration: As shown
in Table 3, 57 members across 26 affiliations collaboratively developed 153 website environments in
five months. Substantial code contributions, cross-role participation, and iterative reviews demonstrate
the feasibility of scaling environment construction through coordinated community effort. (2) Broad
and deep task coverage: Figure 4 demonstrates that WebHarbor achieves both broad semantic
diversity and substantial interaction depth, rather than relying on repetitive information-seeking
tasks. Under a size-controlled comparison, WebHarbor exhibits the lowest median nearest-neighbor
similarity (0.58 versus 0.66–0.76), with its least-similar half covering approximately 91% of websites.
The dashed cross-set curve shows a median nearest-task similarity of only 0.39 to Online-Mind2Web,
indicating minimal task overlap and mitigating the risk of data leakage. Moreover, Table 2 presents
that the suite includes 448 transaction/booking tasks, with 31.8% requiring authentication, 35.6%
modifying persistent state, and 53.7% involving cross-page reasoning, which remain largely absent
from existing live-web and synthetic benchmarks. (3) Rich environment implementations: Table 4
compares WebHarbor to existing synthetic environment suites. WebHarbor leads the compared
suites in total and per-environment pages, images, asset size, and source lines, with an average of 37.3
pages, 1,319.9 images, 104.8 MiB of image assets, and 6,610.6 source lines of code per environment.

4.1
EXPERIMENT SETUP
RL training & Baseline
We use OpenWebRL-4B (Yang et al., 2026) as our main baseline because
it is a SOTA open-source agent trained through online RL on live websites. The synthetic environ-
ment suites WebArena-Infinity, AutoWebWorld, and CUA-Gym do not release trained checkpoints.
OpenWebRL is trained on 2,102 WebGym tasks across 704 live websites (Bai et al., 2026). Our
mirror-trained policy starts from the same SFT checkpoint, OpenWebRL-4B-SFT, and reuses the
same multimodal multi-turn GRPO (MM-GRPO) objective and ReAct-style GUI harness. At each
turn, the policy observes the current state screenshot, textual action feedback, and full interaction his-
tory, and acts through browser tools (e.g., MOUSE_CLICK). For WebHarbor training, each instance
runs in an isolated and deterministically seeded sandbox through Orchard interface (Peng et al., 2026).

Benchmarks
We evaluate generalization on four
benchmarks. Online-Mind2Web contains 300 realis-
tic tasks across 100+ live websites and provides broad
coverage of sites and user domains (Xue et al., 2025).
WebVoyager comprises 643 tasks on 15 popular live
websites (He et al., 2024). WebArena contains com-
plex tasks in reproducible self-hosted websites (Zhou
et al., 2024), where we use a subset of 226 tasks
adopted by Sun et al. (2025) and Wang et al. (2026b).
To test authenticated workflows, WebArena-NL dis-
ables automatic login and provides the account cre-
dentials in the task description. We also evaluate on the WebHarbor test set, which is free from
live-web disruptions and covers diverse websites.
Evaluation Protocol
Following the evaluation protocol of OpenWebRL, we use a 1280×1000
viewport and decode with temperature 0.6, top-p 0.95, and top-k 20. Each task receives a fresh
browser context and a 30-step budget except for WebArena, which uses a 50-step budget. Online-
Mind2Web uses an o4-mini AgentTrek judge (Xu et al., 2025; Xue et al., 2025). WebVoyager
and DeepShop use benchmark-specific GPT-4.1 judges checking both the screenshots and the final
answers. WebArena uses official programmatic state validators. For WebHarbor benchmark, we use
the verifier to inspect state changes and the final answer.

CONCLUSION
We introduce WebHarbor, a comprehensive suite of 153 executable website environments and 3,518
tasks that bring real-world web interactions into controllable offline settings. Through task-driven
docking and human-agent collaboration, these environments continuously evolve to support richer
functionality while preserving visual fidelity and task validity. The resulting suite offers broad
website coverage, image-rich interfaces, and complex authenticated workflows, with lightweight state
resets enabling reliable evaluation and efficient RL training. Our held-out test set further provides a
stable benchmark for assessing GUI web agent capabilities often overlooked by existing benchmarks.
Furthermore, we demonstrate that a Qwen 4B agent trained entirely in WebHarbor generalizes
effectively to unseen tasks and achieves competitive performance against leading open-source web
agents across four benchmarks. We believe WebHarbor can facilitate reproducible evaluation,
scalable RL training, and sustained community-driven evolution of GUI web agent environments.
LIMITATIONS
As an environment suite for GUI web agents, WebHarbor has several limitations.
(1) WebHarbor imitates target website rather than equaling it, and our claims are bounded
by the proposed tasks and fidelity auditing by human reviewers. Client-heavy behavior
(interactive maps, real-time tickers) is approximated or replaced with static surrogates.
(2) Despite judge consistency checks for the test set of WebHarbor, scripted verifiers and
model-based judges may overlook valid alternative solutions or subtle failures. This common
limitation of web agent evaluation calls for more robust evaluation protocols in future work.
(3) To validate the training value of our synthesized offline environments, we mainly compare
with OpenWebRL (Yang et al., 2026) which is a SOTA open-source agent trained through
online RL on live websites. We do not systematically explore alternative supervised fine-
tuning (SFT) data, general-purpose harnesses such as OpenCode (anomalyco, 2025) and
CLI-based agents, or other RL algorithms. Due to computational constraints, we train only
one 4B model and leave generalization across model families and scales to future work.
ETHICS STATEMENT
WebHarbor is developed to support open research on GUI web agent evaluation and training. Envi-
ronment construction involves referencing real websites and obtaining visual assets from original
services or publicly available alternatives. We acknowledge that website designs, trademarks, and
visual assets may be subject to third-party rights. Our environments are intended for research and
benchmarking rather than commercial replication of the original services. Researchers reusing or

redistributing these materials should respect applicable licenses and intellectual property rights. By
reconstructing websites as self-contained environments, WebHarbor enables agents to practice com-
plex interactions without repeatedly accessing or modifying live services. Authenticated workflows,
account management, bookings, and transactions operate within controlled local states, reducing risks
associated with experiments on live websites. However, synthetic environments cannot fully capture
the diversity and dynamics of real websites, including evolving content, personalized interfaces,
access restrictions, and external dependencies. Strong performance in WebHarbor does not guarantee

require additional validation and appropriate safeguards. We hope that accessible and reproducible
environments will support more transparent and responsible research on GUI web agents.

B
SYNTHESIS PROMPTS
WebHarbor synthesizes each environment from observations of the target website and a task specifi-
cation. Website observations define the page hierarchy, navigation, visual design, content structure,
and interaction patterns. Tasks define the routes, records, account state, and state transitions required
for evaluation. The synthesis process uses both sources to produce one executable environment.
Stage 1 reconstructs the interface, backend, data model, authentication flows, and initial seed state.
Stage 2 defines tasks that cover the website’s main functions and include multi-step workflows.
Stage 3 executes every task and adds any missing routes, data, forms, or state transitions. Stage 4
removes answer leakage, adds near-miss alternatives, expands result sets, and checks cross-field
consistency. Stage 5 finalizes the deterministic seed database and validates reset behavior.
Table 10 presents the Stage 1 prompt for reconstructing the target interface, backend, assets, authenti-
cation flows, and deterministic seed state. Table 11 gives the Stage 2 prompt for defining executable
task contracts with broad functional coverage, calibrated difficulty, and grounded answers. Table 12
details the Stage 3 execution loop that identifies missing routes, data, forms, and state transitions
and then replays each repaired workflow. Table 13 specifies the Stage 4 checks for answer leakage,
near-miss distractors, catalog breadth, and cross-field consistency. Table 14 provides the Stage 5
prompt for idempotent seeding, benchmark account state, asset pinning, and reset verification. Each
prompt also states its procedure, constraints, required checks, and output artifacts.

Stage 4: Environment hardening
Skill: harden-env
Objective.
Audit every executable task along four dimensions:
answer
de-leaking, near-miss distractors, catalog breadth, and cross-field
consistency.
The environment must preserve task feasibility while
preventing an agent from succeeding through a visible answer, a single
obvious result, or inconsistent data.
A. De-leak answers.
Search with the task’s natural query and inspect
the rendered DOM and screenshot before opening any detail page.
Remove constraint values from item names, answer text from snippets,
precomputed comparisons, visible list counts, question-shaped headings,
pinned answer callouts, and algorithm-revealing labels.
Check all
known leak patterns, including fuzzy search that floods an answer
bucket, a sort order that places the target first, and a pre-curated
lookup table that reproduces the task wording.
Move required evidence
into consistent specs, descriptions, histories, or detail views.
B. Add near misses.
For each task, retain 1-3 full matches and add at
least five plausible items that match the category but fail exactly
one constraint, such as price, size, color, date, brand, location,
availability, or required feature.
Keep the full-match density at or
below 50%.
The alternatives must look realistic and support
meaningful comparison; do not add arbitrary noise.
C. Broaden the catalog.
Require each natural query to return at least
six items from multiple relevant subcategories.
Expand thin category
pages and search indexes with real-looking entities, useful metadata,
and aligned images.
Preserve the target site’s hierarchy so broader
coverage increases decision complexity without changing the intended
answer.
D. Enforce consistency.
Treat structured specifications as the source
of truth.
Whenever a field changes, regenerate every dependent
description, feature bullet, tag, variant option, availability label,
and displayed summary.
Confirm that listing cards, detail pages,
account records, and transaction history agree.
Keep constraint
values out of names unless the real site uses them as product
identity.
Per-task verification.
Use Playwright to run the natural query,
capture the results, search the rendered DOM for the answer, count
full matches and near misses, verify result diversity, click the
correct detail page through the interface, and compare all related
fields.
Record pass/fail evidence for all four dimensions.
Static
template review and HTTP probes do not replace this check.
Final invariants.
Rebuild after every data change, reset the site,
and confirm byte equality between runtime and seed databases.
Re-run
authenticated and state-changing workflows, inspect desktop and narrow
viewports, and verify that all required images decode.
Finish with
zero answer leaks, at least five near misses per task, broad search
results, consistent fields, and unchanged task solvability.

Stop only after the
local code and pinned assets reproduce the accepted environment
deterministically.

E
RL TRAINING IMPLEMENTATION DETAILS
We use the established OpenWebRL framework (Yang et al., 2026) to evaluate WebHarbor as an
RL training substrate. The released live-web-trained reference policy and our mirror-trained policy
use the same OpenWebRL-4B-SFT initialization, multimodal multi-turn GRPO objective, browser-
agent interface, and GPT-4.1 reward definition. The WebHarbor adaptation replaces the live task
pool and browser backend with WebHarbor tasks executed in deterministic mirror sandboxes. This
design isolates the training signal of the mirrors from any change in policy optimization.
E.1
BROWSER AGENT HARNESS
At each turn, the policy receives the current screenshot, active URL, viewport and tab metadata,
textual feedback from the previous action, and the complete reasoning and tool-call history. Only the
current screenshot remains in the multimodal context. Textual history preserves earlier observations
and action outcomes. Table 21 lists the 13 browser tools shared by live-web and mirror rollouts. The
harness may execute several tool calls from one response before returning the next observation.

E.2
TASK VERIFICATION AND AGENT JUDGE
Each episode executes one task in an isolated image for its website. At startup, the image copies the
frozen seed into a fresh live database and stores a root-only initial snapshot before the agent begins.
The harness records the action–observation trajectory, final answer, termination state, browser state,
and timestamped screenshots. Root-owned evidence separately preserves the site-access log and the
initial and post-episode database states. The verifier assembles these records after the agent phase so
that grading uses the observed interaction and protected environment state.
The reviewer authors a task-specific verifier and a natural-language rubric as two forms of the grading
contract. The verifier produces the official binary outcome. Depending on the task, it checks required
answer facts, task-relevant visited routes, the relevant final browser state, and the exact database delta
between the initial and final snapshots. Mutation checks require the requested additions, updates,

The deterministic verifier runs first. The Agent Judge then runs in the same sandbox before it is
released and audits the completed trial. It receives the task instruction, reviewer-authored rubric,
complete normalized trajectory, final answer, and screenshots. It may also inspect the verifier
code and recorded verdict, pristine seed database, live final database, and site code. It returns
agent_success, agent_failed, or task_error, together with a confidence score, a con-
cise explanation, verified hard facts, and a verifier-disagreement flag. The task_error label is
reserved for a concrete environment defect that makes the task impossible, never for an agent mistake.
The Judge verdict is an audit signal and cannot alter the verifier result. A missing or malformed
Judge output is recorded as a Judge error while the verifier result remains unchanged. The two signals
therefore cover different requirements: the verifier provides a reproducible final-outcome check,
while the Agent Judge can assess semantic equivalence and sequence-dependent rubric items from
the trajectory. Both remain separate from the optimized OpenWebRL reward described below.
E.3
TRAINING CONFIGURATION
Training starts from the released OpenWebRL SFT checkpoint and applies MM-GRPO to groups
of five trajectories per task. A trajectory-level reward is converted to a group-relative advantage for
every assistant turn, and groups with identical rewards are removed by dynamic sampling. The reward
is OpenWebRL’s format gate followed by a GPT-4.1 success judgment over the final answer, action
history, and recent screenshots. The task-specific WebHarbor verifier serves only as a diagnostic
metric. Table 22 lists the full rollout, optimization, and reward settings.
