Abstract 

Existing Graphical User Interface (GUI) benchmarks predom-inantly rely on precise and stateless user instructions. In every-day usage, however, instructions are often vague and history-dependent : users omit the exact details of their past operations because they no longer remember them, leaving the agent to recover the missing context from long and noisy interaction histories. To bridge this evaluation gap, we introduce MemU-Bench , a mobile benchmark of 118 vague tasks grounded in 29 long-horizon user trajectories, where agents must distill raw interaction streams into memory and retrieve the miss-ing context on demand, with task outcomes verified against serialized application databases. Alongside Success Rate, we incorporate Interaction Efficiency (IE) and Success weighted by Path Length (SPL) to expose agents that succeed by ex-haustively searching across different applications rather than by genuinely recalling the history. Evaluations show that with-out user history, state-of-the-art systems struggle under such ambiguity: the best-performing Gemini-3.1-Pro achieves an SPL of only 16.4%, and end-to-end GUI agents fall below 5%. To address this, we further propose AppMem , a training-free framework that distills user history into a structured, app-centric memory bank, tracks interrupted intents across appli-cation switches, and selectively retrieves relevant memories via target-app inference. AppMem raises the SPL of GPT-5.5 from 15.7% to 66.9% ( +51.2% ), outperforms a naive sum-mary baseline by 9.3%, and delivers consistent gains across evaluated backbones. 

1 Introduction 

Graphical User Interface (GUI) agents built on Multimodal Large Language Models (Wang et al. 2024b; Bai et al. 2025b,a) are rapidly evolving into general-purpose digital assistants that translate natural language instructions into ex-ecutable action sequences on real devices (Tang et al. 2025; Hu et al. 2025a; Cheng et al. 2024; Lin et al. 2025; Qin et al. 2025; Lu et al. 2026a, 2025; Tang et al. 2026a). Existing benchmarks almost exclusively evaluate GUI agents under precise, self-contained instructions (Rawles et al. 2023, 2025; Xie et al. 2024). Everyday usage rarely looks like this. Since users seldom remember the exact details of their past interactions, they tend to issue vague, history-dependent commands such as “modify the meeting time”, which cannot be resolved unless the agent knows which meet-ing was created, when, and in which application (Figure 1). It comprises 118 vague tasks grounded in 29 long-horizon user trajecto-ries that cover more than 30 applications, with 100 to 800 steps per trajectory. Tasks are stratified by history length into 71 Level-1 and 47 Level-2 tasks to assess memory scalabil-ity. Each task follows a three-phase protocol: the agent first builds a memory bank from the raw history, then retrieves key information for the vague instruction, and finally executes the task online. Outcomes are verified programmatically against serialized application databases , complemented by an LLM judge for open-ended text. Besides Success Rate (SR), we incorporate Interaction Efficiency (IE) and Success weighted by Path Length (SPL) (Anderson et al. 2018), which penalize agents that reach the goal by wandering across ap-plications instead of recalling the relevant context. Evaluations on MemU-Bench expose a consistent weak-ness of current systems. Without access to user history, the best-performing model, Gemini-3.1-Pro, attains an SPL of only 16.4%, and end-to-end GUI agents remain below 5%. Their trajectories degenerate into aimless exploration across applications, which inflates interaction cost even when the task eventually succeeds. Long-term memory is thus not an optional extension but a prerequisite for handling vague instructions in realistic settings. Guided by these observations, we propose AppMem, a training-free framework that equips GUI agents with long-term user memory. During daily usage, AppMem summa-rizes the interaction stream through a sliding window into 

app-centric memory entries and tracks the status of each in-tent, so that events interrupted by application switching are merged into coherent threads instead of fragmented records. Upon receiving a vague instruction, it infers the target appli-cations, retrieves only their associated entries, and iterates until the collected information is sufficient for execution. On MemU-Bench, AppMem raises the SPL of GPT-5.5 from 15.7% to 66.9% ( +51.2% ), outperforming the naive sum-mary baseline by 9.3%, and generalizes across backbones (e.g., improving the SR of MAI-UI-8B by 16.9%). We summarize our main contributions below: 

• We present MemU-Bench , a mobile benchmark of 118 vague tasks over 29 long-horizon trajectories that evalu-ates whether GUI agents can recover missing context from 

long, noisy, and interleaved user histories, with database-level verification and efficiency-aware metrics. 

• We systematically evaluate closed-source models, open-source models, and end-to-end GUI agents on MemU-Bench, showing that all of them fail under vague instruc-tions without history and that naive summarization helps general models far more than GUI-specialized agents. 

• We develop AppMem , a training-free memory frame-work combining intent-continuation memory generation with app-guided retrieval , improving SPL by up to 51.2% and delivering consistent gains across evaluated models. 

2 Related Work 

2.1 GUI Agents and Memory Mechanisms 

GUI agents have evolved from script-based automa-tion (Zhou et al. 2024; Wang et al. 2024a) to Multimodal Large Language Model agents that execute closed-loop ac-tions directly from pixels (Qin et al. 2025; Wang et al. 2025). These agents, however, assume stateless and precise instruc-tions (Zhou et al. 2025; Xu et al. 2026, 2025a; Yan et al. 2025; Gu et al. 2025; Cao et al. 2026): each task is an iso-lated episode, and prior user activity is discarded. Memory offers a natural remedy and has been studied extensively for LLM agents, which consolidate long dialogue or task histo-ries into retrievable structures (Chhikara et al. 2025; Zhang et al. 2026b; Hu et al. 2025b; Zhang et al. 2025; Tang et al. 2026b). These systems, however, operate on textual interac-tions whose semantics are explicit, whereas GUI histories are streams of screenshots and low-level actions with in-tents fragmented across applications. Existing GUI memory modules sidestep this difficulty by memorizing only tran-sient states within a single task execution (Lu et al. 2026b; Jin, Wang, and Zhang 2026; Zhang et al. 2026a; Zeng et al. 2026; Wang et al. 2026). AppMem instead maintains a per-sistent, app-centric memory across user’s interaction stream.

3.2 Dataset Construction 

Trajectory Sketches and Task Syntheses. We first man-ually design vague tasks together with intent-level trajectory sketches. Each sketch outlines a sequence of high-level user intents for a long-horizon session (e.g., ordering food, then casual gaming) without prescribing specific applications or operation paths. The information required to resolve the final vague task is embedded into the interaction process itself. Operators are therefore free to vary applications and execu-tion paths, which increases trajectory diversity. Synchronous Trajectory Collection and Granular Log-ging. Guided by the sketches, operators interact with an Android Virtual Device emulator to simulate daily phone usage. Rather than following deterministic paths, they intro-duce realistic noise such as accidental touches and redundant app switching. Sessions are fragmented across multi-hour spans with long inactive gaps, mirroring how people actu-ally use their phones. A background script concurrently cap-tures screenshots and atomic actions at 0.3-second intervals, preserving the complete raw interaction log. 

Data Processing and State Serialization. Consecutive identical screenshots are filtered out, yielding clean, action-interleaved logs. Upon trajectory completion, the emulator state is frozen and serialized: we record the system time and pull the runtime databases (e.g., SQLite files) of all involved applications. Restoring these snapshots before testing repro-duces the exact device state left by the operator, so every effect of the historical interaction (a sent message, a modi-fied event) exists in the backend and can be verified against ground-truth records. The resulting benchmark contains 29 user trajectories and 118 tasks: 71 Level-1 (L1) tasks with shorter histories (fewer than 400 screenshots) and 47 Level-2 (L2) tasks embedded in longer flows (more than 700 screenshots). As shown in Figure 3, tasks span 5 major application categories, and tra-jectories cover more than 30 applications, with up to 179 ap-plication switches within a single trajectory. 3.3 Evaluation Strategies 

Task success is verified by a cascade of checks, applied in order of decreasing determinism. 

Rule-based Verification. For tasks with deterministic ob-jectives and no open-ended text, we extract the raw backend records from the application’s database and verify success conditions programmatically. 

LLM-as-Judge. For tasks involving open-ended text (e.g., messages), deterministic fields such as timestamps are rule-checked, and only the free-text fields are forwarded to an LLM judge for semantic comparison. For a minority of tasks where the database is inaccessible, a VLM evaluates the out-come from screenshots and actions. Restricting the judge to short text fields keeps context small and decisions consistent.

4 AppMem 

AppMem targets the two capabilities: consolidating frag-mented intents scattered across applications, and retrieving precisely under vague instructions. As illustrated in Figure 4, it slides a fixed-size window over the historical log to build a persistent, app-centric memory bank, and answers vague instructions through app-guided retrieval .

4.2 App-guided Retrieval 

Upon receiving a vague instruction ˜I, the agent retrieves the missing context from the memory bank M in four steps. 

Application Inference. Let A denote the set of distinct applications appearing in M. Based on ˜I, the agent infers a subset of relevant applications A∗ ⊆ A .

Memory Retrieval. Once the target applications A∗ are identified, AppMem filters the global memory bank to form an app-specific sub-bank M∗, narrowing the search space: 

M∗ = {mi ∈ M | app i ∈ A ∗}

Information Filtering. Given M∗ and ˜I, the agent distills the retrieved entries into the key information κ:

κ = ffilter (M∗, ˜I)

where ffilter denotes the synthesis function executed by the GUI agent to extract the task-relevant information. 

Sufficiency Verification. Finally, the agent assesses whether κ suffices to execute ˜I. If so, retrieval terminates, execution begins. Otherwise, the explored applications are removed from the candidate set ( A ← A \ A ∗), and the pro-cess returns to Application Inference, for up to K iterations. 

5 Experiments 

5.1 Experimental Setup 

We evaluate three categories of models on MemU-Bench: (1) closed-source models (OpenAI 2026; Anthropic 2026; DeepMind 2026); (2) open-source models (Alibaba 2026; Bai et al. 2025a); and (3) end-to-end GUI agents (Xu et al. 2026; Gu et al. 2025; Zhou et al. 2025). Each model is tested under two baseline settings: Vanilla , which receives no user history, and Summary , which applies the same sliding win-dow W to iteratively summarize user behaviors and retrieves key information directly from the summary. All memory and summary operations are performed by the evaluated model itself, without assistance from external models. We set the sliding window size W = 10 and the maximum retrieval iterations K = 3 . Given the cost of processing long-horizon trajectories, each model is evaluated in a single complete run with temperature 0. More implementation details are pro-vided in the supplementary materials.

Effectiveness and Generalizability of AppMem. App-Mem improves evaluated backbones, whereas Summary only helps models with strong long-context ability (Table 2). With Summary, general models gain substantially (Qwen3.5-397B-A17B: 35.6% SR), but end-to-end GUI agents barely move (+1.7% SR): their GUI-specific tuning appears to com-promise long-text processing as the history accumulates. Efficiency. The efficiency metric reveals an even sharper contrast. Vanilla agents that do succeed still wander (e.g., IE of 0.65 for Gemini-3.1-Pro), and naive summarization can further lower efficiency on weaker backbones, as their limited long-context capability hinders extracting and retaining key information from lengthy historical trajectories (e.g., GUI-Owl-1.5-8B’s IE drops from 0.67 to 0.30). AppMem instead improves IE across models, up to 0.91 for GPT-5.5, showing that its compact, targeted memory lets agents act with near-human step economy rather than by brute-force exploration. 

5.3 Ablation Study 

We ablate the components of AppMem on Qwen3.5-397B-A17B (Table 3). Removing Ongoing Intent Continuation (OIC) lowers SPL by 4.7% and nearly doubles the memory size (from 8.8K to 15.3K tokens), confirming that stitching interrupted intents produces memory that is both more com-plete and more compact. 5.4 In-depth Analysis 

Error analysis. Retrieval, not navigation, is the dominant bottleneck. We manually classify the Summary baseline’s outcomes along two axes: whether the retrieved information contains the missing context, and whether online execution succeeds (Figure 5a). Most tasks (57.6%) fail due to insuffi-cient information, while only 6.8% fail despite having it. The remaining cases split into 24.6% that succeed with sufficient information and 11.0% that succeed despite insufficient in-formation by exploiting on-screen clues at execution time. We provide a failure case in the supplementary materials. 

Performance of end-to-end GUI Agents under clear in-structions. End-to-end agents execute well but cannot use history: their failure is a memory problem, not an execu-tion problem. We additionally evaluate them under explicit instructions that require no history processing (Figure 5b). The same agents that fail under vague instructions perform far better here, with a gap of 55.1% for MAI-UI-8B. Their GUI training provides solid execution ability; what they lack is the capacity to summarize and exploit long user histories.

6 Conclusion 

We introduced MemU-Bench, a mobile GUI benchmark of vague, history-dependent instructions on which state-of-the-art GUI agents fail without user history. Our training-free framework AppMem consolidates histories into app-centric memory entries and retrieves them through app-guided infer-ence, improving both success rate and efficiency across eval-uated backbones. More broadly, our results position memory, not execution ability, as the primary bottleneck for long-horizon GUI agents and a key direction for future work. A User Historical Trajectories

H Evaluation Reliability 

Our evaluation protocol consists of two stages: rule-based verification and LLM-as-Judge. Specifically, 44.9% of the tasks are evaluated solely through rule-based verification, while the remaining 55.1% require the LLM-as-Judge to assess open-ended textual outputs. For all LLM-based eval-uations, the temperature is set to 0 to ensure deterministic inference and reproducible decisions. To validate the accuracy of the evaluation protocol, we manually verify the success status of all tasks that require the LLM-as-Judge for Qwen3.5-397B-A17B, and compare the results with those produced by our evaluation protocol. Compared with manual evaluation, our evaluation protocol achieves an accuracy of over 95%, demonstrating that it pro-vides an accurate and reliable assessment of task success. 

I Implementation Details 

We set the sliding window size to W = 10 (images resized to 672 × 1492 ) and the maximum retrieval rounds K = 3 .End-to-end GUI agents and Qwen3-VL-8B are evaluated in an end-to-end manner. For other models, We employ the SeeAct-V (Gou et al. 2025) framework, where they act as planners to generate textual actions that are grounded into coordinates by Qwen3-VL-32B-Instruct. Finally, Qwen3.5-35B-A3B serves as the LLM-judge for evaluation. The local evaluation pipeline and agent framework are executed on a workstation equipped with an Apple M4 Pro chip and 24GB of unified memory, running macOS. GUI environments are managed via ADB within Android Studio. Models are in-voked through standard OpenAI-compatible API interfaces. The temperature is set to 0 to ensure deterministic inference and reproducibility. To validate the stability of this evaluation protocol, we repeat the evaluation of Qwen3.5-397B-A17B three times under identical settings and observe negligible performance variation across runs (the SR of each run devi-ates by less than 1.7% from the mean SR), confirming the low empirical variance of the evaluation protocol. Therefore, a single deterministic run provides a reliable estimate of model performance for benchmarking purposes while substantially reducing API evaluation cost.
