ABSTRACT
Graphical user interface (GUI) agents can improve decision-making with world-
model foresight, provided that predicted states accurately reflect post-action in-
terfaces. Existing state representations fail to jointly capture interface layout,
UI semantics, and explicit locations. We introduce Typed Spatial Markdown
(TSM), a Markdown-style textual state representation for desktop web interfaces.
TSM serializes block-level and atomic-level UI elements according to their spa-
tial relationships, jointly encoding their types, visual semantics, explicit locations,
optional control states, and hierarchical membership. To train a screenshot-to-
TSM renderer, we construct AtomBlock-WebUI, a dataset with precise anno-
tations at both granularities. By injecting element-type labels into HTML and
directly extracting bounding boxes after rendering, we avoid annotation errors
caused by post-hoc inference from webpage structures. Building on TSM, we
propose MKD2World, a desktop web world model trained in two stages for
current-state description and action-conditioned next-state prediction. During in-
ference, the web agent queries MKD2World as needed and performs a “digest”
step, in which it interprets each predicted state and extracts task-relevant evidence
for selecting the best action. Experiments show that MKD2World-9B achieves
an EleF1 score of 26.50 on the out-of-domain test set, outperforming GPT-5.6-
Sol(14.98) by 11.52 points. Across Online-Mind2Web tasks, MKD2World-9B
improves the success rate of the Qwen3.5-35B web agent from 22.94% to 37.61%,
achieving competitive performance among leading open-source GUI world mod-
els. Code is available at https://github.com/OmniAI-Lab-CUHKSZ/
MKD2World.

INTRODUCTION
With the development of vision-language models (VLMs), graphical user interface (GUI) agents
have become capable of completing interactive tasks in real-world scenarios (Cao et al., 2026a; Hu
et al., 2026; Zhou et al., 2026). At each decision step, an agent generates an executable action based
on the task objective, current interface, and historical information. However, without sufficient un-
derstanding of webpage dynamics—including the functions of user interface (UI) controls and the
logic of interface transitions—it may generate ineffective actions that increase interaction costs or
cause irreversible errors, such as accidentally deleting important data or leaking private informa-
tion (Shen et al., 2026b; Liu et al., 2026). Action-conditioned world models offer a promising way
to anticipate future interface states before execution, helping agents assess whether candidate actions
advance the task while reducing risky real interactions (Mei et al., 2026; Gu et al., 2025).
The usefulness of such foresight depends on what state a world model predicts. Figure 1 compares
representative GUI state representations and highlights the desired trade-off: preserving a complete,
structured interface state without incurring the cost of pixel-level reconstruction. We argue that, to
distinguish the consequences of candidate actions, a predicted state should preserve a complete yet
structured account of the post-action interface, including both the elements that change and the sur-
rounding context needed to interpret those changes—their semantics, locations, control states, and

structural relations. At the same time, it should avoid the cost and instability of reconstructing every
visual detail of a webpage. Existing GUI world models represent states as free-form descriptions
of interface changes, structured interface representations such as the Accessibility Tree (AXTree)
and Document Object Model (DOM) (Zuo et al., 2026), HTML rendered into webpages (Koh et al.,
2026), or images generated directly by image generation models (Guan et al., 2026). Free-form
text concisely conveys major changes but loses layout structure and substantial information from the
next interface. Common AXTree and DOM serializations preserve parts of the interface structure,
yet often omit explicit element locations and have incomplete visual semantics (Wu et al., 2023).
Other structured textual representations retain some layout and locations, but support limited ele-
ment types and omit UI control states, complete visual semantics, or interface block structure (Cao
et al., 2026b). HTML-rendered images may omit actual images or deviate from the real layout,
whereas pure image-generation approaches are costly and often distort fine-grained text (Zheng
et al., 2026; Luo et al., 2025). Thus, these representations do not adequately balance preserving a
complete, structured interface state with avoiding the burden of full visual reconstruction. This limits
the completeness of the interface information available to a world model and, in turn, to downstream
agent reasoning.
To address this bottleneck, we introduce Typed Spatial Markdown (TSM), a structured and spa-
tially grounded state representation for desktop Web interfaces. TSM organizes rendered Web UIs
into block-level and atomic-level elements according to their spatial relationships. Each entry en-
codes its type, visual semantics, bounding box, optional control state, and hierarchical membership,
jointly capturing what an element is, where it appears, what it conveys, and how it is organized.
Markdown provides a readable hierarchical serialization of this structured state. By retaining the in-
terface information needed to compare action-induced changes without reconstructing the full pixel-
level interface, TSM provides a compact and directly comparable state space for action-conditioned
world modeling and downstream agent reasoning.
Learning this state space from screenshots requires reliable UI element types and locations. Ex-
isting desktop Web UI datasets often extract them from the DOM or AXTree through rule-based
parsing (Wu et al., 2023; Gurbuz et al., 2026). However, HTML structures are highly heterogeneous
across webpages: tags and class names are typically tied to page styling and interactions, while
role attributes are often incomplete, making unified and reliable semantic annotations difficult to
obtain (Gou et al., 2025). Post-hoc DOM parsing can therefore assign types to visually invisible ele-
ments or yield misaligned bounding boxes; visual models may likewise localize elements away from
their actual positions (Fu et al., 2026). To reduce ambiguities introduced by such post-hoc semantic
inference, we construct AtomBlock-WebUI. A VLM generates HTML with reference to real web-
page layouts and explicitly injects predefined UI element types. After rendering, we directly extract
the coordinates of the corresponding typed DOM nodes. This pipeline provides visually aligned
type and location supervision for the dual-granularity UI detector in our TSM renderer.
Building on TSM and AtomBlock-WebUI, we introduce MKD2World, an action-conditioned desk-
top Web world model that predicts future TSM states from screenshots and candidate actions.
MKD2World first learns to reconstruct the current interface in the TSM state space, and then learns

action-conditioned state transitions with transition-aware objectives that emphasize the elements
changed by an action. At inference time, it simulates a next TSM state for each candidate action.
We further train the GUI agent to understand TSM and design a digest-based inference strategy,
through which the agent interprets predicted typed, spatial, and stateful changes to select the action
that best advances the user objective. The main contributions of this work are as follows:
• Typed Spatial Markdown (TSM). We propose TSM, a structured and spatially grounded Web
UI state representation that encodes UI semantics, explicit spatial information, control states, and
hierarchical structures, together with a screenshot-to-TSM renderer.
• AtomBlock-WebUI Dataset. We construct a 9.7k-scale desktop Web UI annotation dataset using
a pre-injected automated annotation pipeline, providing element types and bounding boxes for
both block-level and atomic-level UI elements to train the dual-granularity UI detector in the
screenshot-to-TSM renderer.
• MKD2World: A TSM World Model for Web Agents. We propose MKD2World, an action-
conditioned desktop Web world model that predicts future TSM states from screenshots and can-
didate actions. MKD2World uses a two-stage training scheme with transition-aware objectives,
and supports uncertainty-triggered, digest-based action selection by TSM-aware Web agents.
• Comprehensive Evaluation and Online Validation. We propose EleF1 to evaluate TSM predic-
tion accuracy, and demonstrate strong out-of-domain prediction and consistent decision-making
gains on Online-Mind2Web and VisualWebArena.

RELATED WORK
2.1
WEB UI UNDERSTANDING AND DATASETS
Existing datasets obtain UI annotations either from webpage structure metadata or directly from
screenshots. Structure-derived datasets—including WebUI (Wu et al., 2023), SeeClick (Cheng et al.,
2024), and PixelWeb (Yang et al., 2025)—scale efficiently by leveraging AXTree or DOM informa-
tion, but their labels depend on heterogeneous HTML, DOM, or accessibility conventions and often
require page-specific heuristics to obtain unified semantic types and visually aligned boundaries.
Screenshot-based methods such as OmniParser (Lu et al., 2024) and ScreenAI (Baechler et al.,
2024) avoid dependence on webpage structure but can suffer from category ambiguity, coordinate
offsets, or errors inherited from individual recognition components; high-quality manually anno-
tated datasets (Nayak et al., 2025; Dicu et al., 2025) are limited in scale. AtomBlock-WebUI differs
from both lines by injecting a predefined semantic taxonomy into webpage HTML before rendering
and extracting bounding boxes from the corresponding rendered nodes, providing visually aligned,
dual-granularity (block-level and atomic-level) supervision for screenshot-to-TSM rendering.
2.2
GUI WORLD MODELS AND STATE REPRESENTATIONS
GUI world models support either inference-time action selection (Mei et al., 2026; Gu et al., 2025)
or training-trajectory synthesis (Xiao et al., 2026; Zuo et al., 2026). Across both settings, the choice
of state representation fundamentally determines which interface information can be predicted, com-
pared, and used for action selection (Figure 1). Existing state spaces include: (1) free-form change
descriptions (Chae et al., 2025; Gu et al., 2025; Shen et al., 2026a), which are compact but lack ex-
plicit spatial layouts and hierarchical structure; (2) structured text or AXTree representations (Cao
et al., 2026b; Zuo et al., 2026; Xiao et al., 2026), which preserve partial structure but do not con-
sistently expose element locations, visually grounded types, and control states in a unified form;
(3) executable HTML code (Zheng et al., 2026; Koh et al., 2026), which can retain page structure but
whose rendered outputs may deviate from the target layout or content; and (4) future images (Guan
et al., 2026; Luo et al., 2025), which retain rich visual information but incur high generation cost
and are unreliable for fine-grained text and small elements. These representations typically trade
off spatial and hierarchical fidelity against prediction cost and visual grounding. TSM targets this
gap by representing visible UI states as typed, spatially explicit, hierarchically organized elements
with control states and visual semantics, remaining efficient for action-conditioned prediction and
downstream candidate-action comparison. AtomBlock-WebUI provides visually aligned supervi-
sion for rendering screenshots into this state space, while MKD2World models action-conditioned
transitions within it for Web-agent reasoning. Detailed discussion refer to Appendix D.

3.2
TYPED SPATIAL MARKDOWN REPRESENTATION
Typed Spatial Markdown Definition.
We represent a TSM state as Mt = (Bt, Et, ρt), where
Bt and Et are the sets of block-level and atomic-level elements, respectively, and ρt denotes the
hierarchical membership relations among UI elements. We define 6 block-level types and 8 atomic-
level types. A block-level element is written as b = (τ b, p), and an atomic-level element as e =
(u, c, τ e, p). Here, u denotes the optional control state, c denotes visible text or visual semantics,
and τ denotes the semantic type. The bounding box is defined as p = (x, y, w, h), representing
the center coordinates, width, and height of a UI element, with values normalized to [0, 999]. More
details are provided in Appendix E.
AtomBlock-WebUI Construction.
As shown in Figure 2, we first deduplicate the webpage
screenshots in Multimodal-Mind2Web (Zheng et al., 2024) using fingerprint-based filtering. We
then use the screenshots as layout reference and employ Qwen3.6-Plus to generate HTML with ex-
plicit yolo-* labels and image descriptions. We retrieve semantically matched images from the
CC3M (Sharma et al., 2018) image–text dataset and inject the image into HTML. Finally, we use
Playwright to drive Chromium and render full-page screenshots. The annotation program directly
retrieves the yolo-* DOM nodes to obtain bounding boxes. Figure 3 compares AtomBlock-WebUI
with existing Web UI datasets in annotation source, viewport controllability, viewport element den-
sity, and category balance. We evaluate annotation quality against existing datasets in Section 4.
More details are provided in Appendix C.

Screenshot-to-TSM Renderer.
Given a webpage screenshot, the renderer converts it into TSM
using a YOLO26 (Jocher et al., 2026) UI detector trained on AtomBlock-WebUI, PP-OCRv6 (Zhang
et al., 2026), and Qwen3.5-0.8B. It first uses the UI detector to identify element types and coordi-
nates and PP-OCRv6 to recognize text, then binds the recognized text to the corresponding elements.
Some regions are cropped and passed to Qwen3.5-0.8B for visual semantics. Finally, the renderer
constructs a UI Element Tree with containment relationships and sorts the elements according to
their spatial relationships to obtain the TSM representation. Details are in Appendix E.2.

3.4
WORLD MODEL ENHANCED WEB AGENT
At each decision step, the web agent first generates a candidate action set At = {(ak, ik)}K
k=1,
where ak is a candidate action and ik is its intent. The web agent decides whether to invoke the
world model based on its confidence. For each candidate action, MKD2World takes the current
screenshot It and the candidate action ak as input and predicts the interface state ˆSk. The web agent
compresses each prediction into a structured digest dk = Digest(It, ak, ik, ˆSk), which includes a
textual description of the main changes, their consistency with the action intent, their effectiveness
in advancing the task, and evidence from ˆSk. Finally, the web agent aggregates all digests dk and
selects the best action to execute. In addition, we conduct TSM-aware training for the web agent,
training it to describe interface states in TSM and improve interaction ability with MKD2World.

EXPERIMENTS
In this section, we first evaluate the annotation quality of AtomBlock-WebUI. We then assess the
prediction accuracy of MKD2World. Finally, we enhance web agents with MKD2World and evalu-
ate their performance on GUI tasks.
4.1
ATOMBLOCK-WEBUI EVALUATION
Comparison Datasets.
We compare AtomBlock-WebUI with four desktop Web UI annotation
datasets: ScreenParse-v2, WebUI-CHI23, WebUI-COCO, and UI-Elements.
We first dedupli-
cate each dataset.
For ScreenParse-v2 and WebUI-CHI23, we randomly sample 1,000 view-
port pages from their training sets. WebUI-COCO and UI-Elements use all 618 and 508 pages.
AtomBlock-WebUI uses the same set of 1,000 full webpages and reports two evaluation settings:
AtomBlock-Top evaluates only the top 16:9 viewport of each page, while AtomBlock-Full
averages the evaluation results over all viewports of the same page. Each dataset uses its native
viewport resolution and retains only desktop viewports, predominantly 1920 × 1080.
Evaluation.
Each dataset is annotated under its own category taxonomy. We use GPT-5.6-Sol
with low thinking effort to evaluate annotation quality. Given the original screenshot, the annotated
screenshot, and script-computed statistics comprising drawable-box count in the current viewport,
distinct-category count, occupied cells in a 4 × 4 grid of annotation centers, and HSV color en-
tropy of the original image, the evaluator scores four dimensions: object validity assesses whether
recognizable UI elements appear inside the boxes; boundary alignment assesses whether element
boundaries align with the annotation boxes; label semantics assesses whether annotated categories
are compatible with the element semantics; page complexity is judged from the original image alone
and reflects how richly structured the interface is. We randomly sample 20 pages from each dataset
and score them with humans to validate the GPT judge against human ratings. Raters score inde-
pendently with the same prompt, blinded to dataset identity and GPT scores (Appendix I; Table 1).
Annotation Quality.
AtomBlock-Top leads the VLM judge by 2.53 / 2.26 / 2.69 points on bound-
ary alignment, label semantics, and page complexity, and also ranks top under human evaluation
with object validity and the best complexity. AtomBlock-Full stays close, leading human boundary
alignment and label semantics, with only a mild drop in complexity on full pages.
Community Adoption.
AtomBlock-WebUI is released on Hugging Face and has accrued over 7K
downloads; it also ranked Top-5 on the Hugging Face dataset trending leaderboard. These signals
suggest that the dataset addresses a clear community need for well-annotated Web UI resources.

Datasets and Metrics.
We extract interface transitions from WebChain and MolmoWeb-
HumanTrajs. After quality filtering, domain-based splitting, TSM rendering, and focus annotation,
we obtain a 100k Current-State reconstruction training set and a 31k Next-State prediction train-
ing set. We reserve 500 validation transitions for model selection and result analysis, and evaluate
all models on in-domain (ID) and out-of-domain (OOD) test sets. Each test set contains 1,000
transitions across five action categories: click, text/key, scroll, navigation, and other, with 200 tran-

4.3
MKD2WORLD ENHANCED WEB AGENT
Datasets and Metrics.
We evaluate the effectiveness of MKD2World in improving web agent
performance on Online-Mind2Web (Xue et al., 2025; Deng et al., 2023) and VisualWebArena (Koh
et al., 2024). Online-Mind2Web contains 300 real-time website tasks. After removing unavailable
tasks and tasks heavily affected by network instability, we select 109 relatively stable tasks as our
test set, including 25 Easy, 48 Medium, and 36 Hard tasks (see Appendix H). The interaction tra-
jectories are reviewed by GPT-5.6-Sol under a unified criterion to determine whether each task is
successfully completed. The judge receives the task instruction, the full trajectory of screenshots in
temporal order, the action history, the agent’s final answer, and runtime error logs. An early stop by
the web agent does not count as success. We set success = 1 only when the screenshots and action
records show that all task requirements are completed; ambiguous, incomplete evidence, or termi-
nation at the 50-step budget yields 0. Additionally, we use 233 tasks from VisualWebArena as a
supplementary benchmark to further evaluate the generalization ability of MKD2World. Success on
VisualWebArena is determined by the benchmark’s official checkers rather than trajectory quality.
After the agent stops, the checkers inspect the final page and the last submitted answer and return a
binary score under rules.
Model Settings.
We enhance four web agents with MKD2World: Qwen3.5-35B-A3B, Qwen3.5-
9B, GUI-Owl-1.5-8B (Xu et al., 2026), and deepseek-v4.1-flash. We use WMA, WebDreamer,
Qwen-AgentWorld, and WebWorld as world model baselines. When comparing different world
models, we hold the agent fixed to Qwen3.5-35B-A3B on Online-Mind2Web and to Qwen3.5-9B
on VisualWebArena. All web agents follow the same policy: the input is the current screenshot, the
action history, and the task goal; the output is only one action type with normalized coordinates.
With world-model support, a web agent may emit one or more candidate actions according to its
confidence. We set the context length to 32K tokens, the output length to 5K tokens, and thinking
effort to medium. We cap each episode at 50 steps and stop after 4 consecutive repeated actions.
All world models make predictions under their official prompting strategies. We cap world-model
outputs at 6K tokens, disable thinking mode, and set temperature to 0. For MKD2World, we further
fine-tune all web agents except DeepSeek-V4.1-Flash for TSM awareness, using a 50K subset of the
Current-State reconstruction training set at a learning rate of 2×10−6; all other settings match those
used to train MKD2World for Current-State reconstruction in the previous subsection. We further
add a digest step in which the web agent consolidates the MKD2World’s predictions before acting.
This adaptation strengthens collaboration between the web agent and MKD2World.

the Base agent across most backbones on both benchmarks. Specifically, on Online-Mind2Web with
Qwen3.5-35B, MKD2World reaches 37.61%, improving over the Base agent by 14.67 points and

5
CONCLUSION
In this paper, we presented TSM, a complete structured interface state, and constructed viewport-
controllable AtomBlock-WebUI with balanced types and precise boxes. We further introduced
MKD2World and proposed digest and TSM-awareness to strengthen WebAgent–MKD2World col-
laboration. Empirically, MKD2World outperforms GPT-5.6-Sol on prediction accuracy and boosts
Qwen3.5-35B by +14.67% on Online-Mind2Web. Despite the improvements, due to the complexity
and frequent updates of web interfaces, MKD2World cannot achieve pixel-level aligned prediction.
Our current setting targets static pages; it does not yet perform temporal understanding of audio,
video, or animation, nor predict audiovisual changes over the next time interval.

ATOMBLOCK-WEBUI CONSTRUCTION AND STATISTICS
We perform fingerprint-based near-duplicate filtering on screenshots from Multimodal-Mind2Web.
Each image is converted to grayscale, resized to 17 × 16 with Lanczos interpolation, and encoded
as a 256-bit difference hash (dHash) by comparing adjacent pixels in each row. Screenshots whose
hashes have Hamming distance dH(hi, hj) = popcount(hi ⊕hj) ≤5 are connected in a graph;
each connected component keeps one randomly selected image. Subsequently, we use the filtered
screenshots as layout references and generate HTML with Qwen3.6-Plus. We require the model to
cover 8 atomic and 6 block types, inject yolo-* category labels and vary color schemes for visual
diversity. Each image node is an <img> tag with a data-caption attribute. We next inject
CC3M images into pages. For each <img> node, we encode its data-caption with MiniLM-
L6-v2 and retrieve the top-50 candidates via FAISS. We then re-rank by aspect-ratio mismatch with
the target region and randomly pick one of the top-5. The chosen image is resized to the node and
written back to the HTML. We render pages with Playwright-driven Chromium and collect bound-
ing boxes from nodes tagged with yolo-* labels. We retain the original image-injected HTML,
so each page can be re-rendered under different viewports while producing consistent annotations.
AtomBlock-WebUI comprises 9,683 full-page screenshots and 1,321,234 type–bounding box an-
notations, split into 6,906, 1,388, and 1,389 pages for training, validation, and testing. Table 6
summarizes AtomBlock-WebUI’s category distribution: 8 atomic categories account for 1,195,520
instances(90.49%), and 6 block categories for 125,714(9.51%).

D.2
GUI WORLD MODELS AND STATE REPRESENTATIONS
GUI world models follow two broad paradigms. For inference-time decision enhancement, a world
model predicts the next interface state conditioned on each candidate action, and a value model
scores the predictions to select the best action (Mei et al., 2026; Gu et al., 2025). For training data
synthesis, agents interact with world models over multiple steps to produce interaction trajectories
that are then used for agent training (Xiao et al., 2026; Fang et al., 2025; Zuo et al., 2026). Across
both settings, the choice of state representation fundamentally determines which interface infor-
mation can be predicted, compared, and used for action selection. Figure 1 summarizes the central
trade-off among representative GUI state representations: preserving rich, structured interface infor-
mation while avoiding the cost and instability of pixel-level reconstruction. 1. Free-form textual
change descriptions. WMA (Chae et al., 2025), WebDreamer (Gu et al., 2025), and WAC (Shen
et al., 2026a) describe post-action interface changes as free-form natural-language text. This rep-
resentation is compact and easy for language models to generate, but typically does not explicitly
encode element-level spatial layouts, does not provide a structured, comparable state, and makes
it difficult to evaluate prediction accuracy or directly compare candidate outcomes. 2. Structured
textual and accessibility representations. MobileDreamer (Cao et al., 2026b) uses structured text

Prior work has studied UI understanding datasets, GUI element grounding, and action-conditioned
world modeling, but these lines have not jointly provided a state space that is spatially explicit,
hierarchically structured, and efficient to predict. TSM fills this gap by serializing complete UI
states into typed spatial elements. AtomBlock-WebUI supplies aligned supervision for rendering
screenshots into this state space, and MKD2World models action-conditioned transitions within it.

E.2
TSM RENDERER DETAILS
The screenshot renderer converts a webpage screenshot into a TSM state using a YOLO26 detector
trained on AtomBlock-WebUI, PP-OCRv6, and Qwen3.5-0.8B. A child block is contained in a
parent if its center lies inside the parent and the parent covers more than 85% of its area. The block
priorities are 0 for Navigation, Sidebar, and Footer, 1 for Form and Table, and 2 for
Section (lower is high priority). So generic Section do not override function-specific blocks.
For each atomic element, we first take blocks that contain its center; otherwise those covering at least
50% of its area. Among candidates, we keep the smallest block with the highest priority; unmatched
elements stay at the TSM top level. Qwen3.5-0.8B describes images and icons, and judges states of
checkboxes, radios, and selects. For checkboxes and radios, we enlarge the crop to capture the same
line. For selects, we extend the crop downward and treat the dropdown as open if options appear.

G.2
FOCUS ANNOTATION
Focus annotations exist only for changed transitions. Given states St and St+1, we mark add
and update elements in St+1 and record their spans to compute the Base–Focus Element Loss.
Directly comparing St and St+1 may confuse rendering noise or minor positional shifts with actual
changes. We therefore match elements between the two TSM states. For each element, we parse
20


content, type, state, and bbox, and record its span in the TSM string. For text-input actions, we first
match the element at the action location. If multiple nearby elements share a similar shift, we keep
them matched. We then match elements with aligned semantics and bboxes, then those with aligned
semantics but shifted bboxes. Unmatched elements are labeled add only if they pass a reliability
filter. A matched element is update if any of content, state, or bbox changes reliably.

## Input

- ‘supported_unified_actions‘: allowed action types.
- The attached image is the current viewport screenshot.
## Candidate policy
- Return one direct-execution candidate at confidence 8-10.
- Return two or three complementary candidates at confidence 0-7,
including exploratory actions for unfamiliar interfaces.
- Set ‘confidence‘ to an integer from 0 to 10 indicating confidence
that the candidate is the correct next action.
## Action contract
- Express coordinates on a ‘0..999‘ grid relative to the screenshot.
- Choose action types from ‘supported_unified_actions‘.
- Ground coordinate actions in visible screenshot evidence.
- Use ‘type_text‘ for a focused input; use a click candidate to
establish focus.
26


- Use ‘finish‘ when the screenshot or action history shows task
completion.

‘clear‘, and ‘enter‘ are optional.
- ‘scroll‘: ‘{"type":"scroll","delta_x":0,"delta_y":500}‘ with integer
deltas in ‘[-999,999]‘; positive ‘delta_y‘ scrolls down.
- ‘key_press‘: ‘{"type":"key_press","key":"Enter"}‘.
- ‘hotkey‘: ‘{"type":"hotkey","keys":["ctrl","l"]}‘.
- ‘navigate‘: ‘{"type":"navigate","url":"https://..."}‘ with an
absolute HTTP(S) URL.
- ‘go_back‘, ‘go_forward‘, ‘refresh‘, ‘wait‘: ‘{"type":"..."}‘.
- ‘select_option‘:
‘{"type":"select_option","coordinate":[x,y],"option_text":"..."}‘.
- ‘drag‘:
‘{"type":"drag","from_coordinate":[x1,y1],"to_coordinate":[x2,y2]}‘.
- ‘clear‘: ‘{"type":"clear"}‘ or ‘{"type":"clear","coordinate":[x,y]}‘.
