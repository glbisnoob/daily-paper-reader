## Abstract 

Mobile GUI agents can carry out tasks across apps, yet most run on a separate computer that drives a phone over the Android De-bug Bridge (ADB), out of reach of ordinary users and of the apps through which most people reach Web services. We present Coati ,a source-available agent that users install as an Android app. Its runtime on the phone, the host, records what a model alone can-not see: the effect of each action at its target, result screens across apps, and the progress of repeated steps. VerifyLoop checks action outcomes and completion claims against host evidence and reports a completion it cannot audit as unverified. AppMemory builds per-app procedural memory from observations that the interface supports and reuses it on later visits. A routed fast executor lets a lightweight selection model take simple, confident steps and lets the host repeat loops of simple steps that the large model plans once. On all 116 AndroidWorld tasks, with Gemini 3.8 Flash as every agent’s backbone, Coati succeeds on 86.5% of the tasks over three trials, ahead of the strongest open-source agent Artemis (77.6% with the same accessibility-only access, 76.5% even when allowed ADB) and far ahead of FinalRun and Midscene (about 59%), and Verify-Loop cuts false completion claims by about a third at comparable success. In everyday use, the fast executor cuts the median time of phone tasks by 39% at comparable success and runs three of four loop tasks 2.8–5.4 × faster with 6–9 × fewer model tokens, while AppMemory shortens a repeated deep route in an unfamiliar app from 18.5 steps to 6–7. On an Android 16 phone, routed execution completes all 27 benchmark runs with 76% fewer Reasoning calls on the critical path. Host evidence, not model self-assessment, makes an installable agent reliable and fast.

## 1 Introduction 

Multimodal large language models can now operate graphical user interfaces (GUIs) directly: they read a screenshot or an interface tree and act through taps, swipes and text entry [13, 22, 41]. On mobile devices this matters more than anywhere else, because most applications expose no programmable interface and their layouts change across versions, languages and device states [25, 26]. People also access many Web services through mobile applications. A mobile GUI agent intended for everyday use should therefore run directly on the phone and operate these applications. However, most mobile GUI agents run on a separate computer that drives the phone over the Android Debug Bridge (ADB) [2, 25]. The computer sends actions to the phone and receives observations in return. For ordinary users, installing and operating such a sys-tem can be difficult. More importantly, the agent can understand the phone only through the information returned by the bridge. Therefore, it may miss fine-grained changes after an action, making it difficult to determine whether the action succeeded and whether the task actually reached its target state [15, 32, 39]. These limi-tations suggest a more direct and promising deployment model: an agent installed directly on the phone. Because its runtime and the interface it operates reside on the same device, the agent can observe the interface state and action outcomes in real time. It can also maintain records of cross-application results and the progress of repeated actions. Running an agent directly on the phone also imposes practical requirements. Each step should avoid unnecessary waiting and model calls. Since users may not continuously monitor the screen, a task reported as complete must actually reach the requested state. Repeated tasks should not require the agent to rediscover the same route each time. Existing mobile GUI agents do not fully satisfy these requirements. They typically ask a large model to make de-cisions step by step, rely on the model to judge whether a task is complete, and treat repeated actions as separate model decisions. These choices can increase latency and token costs, while making execution failures more difficult to detect [16, 29, 31]. agent must therefore use local evidence not only to execute actions, but also to verify their outcomes, assess task completion, and retain useful experience. This calls for a different execution principle: the model may propose an action, but the runtime on the phone should determine what actually happened from evidence recorded by the host [15, 32, 39]. We present Coati , a source-available Android agent that users in-stall as an app. Coati is designed to address the reliability, execution-efficiency, and repeated-use challenges of installable mobile agents. Its core principle is host-grounded execution : the model proposes an action, while evidence recorded by the host—the information col-lected by Coati’s runtime on the phone—determines the outcome. We implement this principle with three mechanisms. (1)Veri-fyLoop checks each action against the interface changes it causes and audits completion claims using the result screens of the appli-cations involved and the progress of delegated loops. When the available evidence is insufficient, it reports the task as unverified rather than complete. (2)AppMemory stores interface observa-tions as per-application guidance only when they are supported by the interface and the task passes the completion audit. It then retrieves this guidance during later visits. (3)Routed fast execu-tor reduces the cost of model calls. A lightweight typed selector handles simple, confident actions from host-built candidates, while the Reasoning model handles uncertain steps, application switches, and text entry under a user-selectable speed–accuracy mode. For repeated simple actions, the Reasoning model plans the loop once, and the host executes it item by item while recording the handled items. Together, these mechanisms use the same host evidence to improve execution efficiency and constrain what the agent can claim and remember. We compare Coati with the strongest open-source agents on all 116 AndroidWorld tasks. All agents use Gemini 3.8 Flash as the backbone model and run on the same device with the same task instances and execution protocol. Coati achieves an average task success rate of 86.5% across three trials, ahead of the strongest open-source agent Artemis (77.6% with the same accessibility-only access, and 76.5% even when allowed ADB), and far ahead of FinalRun and Midscene (about 59%). At comparable success rates, VerifyLoop reduces false completion claims by about one third (Section 4.2– 4.3). Beyond AndroidWorld, whose tasks are short first visits, we evaluate execution efficiency and repeated use in everyday settings. Compared with a per-step Reasoning configuration, the routed fast executor reduces the median execution time of phone tasks by 39% at comparable success. It also makes three of four loop tasks 2.8–5.4 × faster while reducing model token usage by 6–9 ×. For repeated deep navigation in an unfamiliar application, AppMemory reduces the average execution length from 18.5 steps to 6–7 steps (Section 4.4–4.5). Overall, Coati unifies action verification, execution acceleration, and experience reuse within a single host-evidence loop. Our eval-uation examines these mechanisms from four perspectives: bench-mark capability, completion reliability, everyday execution speed, and repeated use. The results show that improving the reliability and efficiency of an installable mobile agent depends not only on the model itself, but also on whether the host can continuously record and use evidence from actual execution. Our contributions are: 

• A host-grounded execution framework for mobile GUI agents. The framework uses host evidence, rather than model self-assessment, to decide if an action succeeded, if a task was completed, and what is worth remembering. 

• Three core mechanisms. We design and implement VerifyLoop, AppMemory, and a routed fast executor with loop delegation, and integrate them into an installable Android application. The source code is available for noncommercial use. 

• An evaluation that distinguishes benchmark capability from everyday use. We conduct three trials on all 116 Android-World tasks with the same backbone model, comparing against the strongest open-source agent Artemis as well as FinalRun and Midscene, and use everyday tasks, simple action loops, and repeated deep-navigation tasks to evaluate the practical contri-bution of each mechanism. 

## 2 Related Work 2.1 Mobile GUI Agents and Their Deployment 

Mobile GUI automation began with scripts and demonstrations, such as Appium’s selectors [2]. Multimodal models turned it into general-purpose agents: SeeClick [4], Aria-UI [36] and UI-TARS [24] improve grounding, while AndroidGen [14], Mobile-Agent [29, 30] and Mobile-Agent-v3 [37] combine screenshots, interface informa-tion and history for multi-step tasks; pure-vision parsers such as OmniParser [20] and accessibility-based agents [6] cover comple-mentary screens. AndroidWorld [25] provides the standard dynamic benchmark. Training-based work scales environments, data and reinforcement learning: MobileRL [34] trains with online agentic reinforcement learning, and OpenMobile-2 [35] trains on more than 110 apps with generated trajectories and app-native tools. Such work raises a single model’s capability but still calls that model at every step and does not accumulate application knowledge in use; Coati’s routing and AppMemory act at run time and are comple-mentary to it. Nearly all of these agents drive the phone from a separate computer and ask a large model for every step. Coati runs on the phone, and the evidence it records there is what its decisions rest on. 

## 2.2 Verification, Reflection and Experience 

Mobile-Agent-v2 [29] and MobileUse [16] use reflection to detect and recover from erroneous actions; VeriSafe Agent [15] and V-Droid [6] verify candidate actions before execution, and Backtrack-Agent [32] and VeriGUI [39] study error recovery. These verifiers ask a model to judge the model’s own progress. VerifyLoop decides with host evidence wherever it exists (pixel and text changes at the target, result screens across apps, loop progress) and uses a model only to read that evidence. For experience, AutoDroid [31], AppAgent [18, 38], GUI-explorer [33], LLM-Explorer [40] and App-Cards [17] build application knowledge from exploration, documen-tation or trajectories; AppMemory determines which observations from real tasks are reusable and retains only those supported by the interface. 

## 2.3 Fast and Slow Decision Making 

Dual-process designs pair a fast policy with a slower deliberate one [19], and model cascades and routers send easy queries to Coati: Host-Grounded Execution for Installable Mobile GUI Agents Conference’17, July 2017, Washington, DC, USA 

cheaper models [3, 23]. These approaches typically use query diffi-culty, model confidence, or expected cost to decide when additional reasoning is necessary. In GUI agents, however, the difficulty of a step also depends on the current interface state: a simple tap, a text-entry action, an application switch, and an irreversible com-mit may require different levels of deliberation even within the same task. Existing routing methods generally select a model for a request, while leaving target resolution, action execution, and post-action verification to the same reasoning pipeline. Coati routes at the level of GUI steps: the fast route selects among candidates the host can execute exactly instead of generating actions, routing follows host-observable state (verification outcomes, exploration, pending commits), and repetitive work is delegated as a loop that the host executes and tracks, rather than as a sequence of model decisions.

## 3.2 Coati Overview 

Figure 1 presents the architecture. At each step, Coati captures the screen and accessibility tree, and hybrid perception produces a parsed screen. The router selects either the fast selector or the Reasoning route. VerifyLoop checks each action and feeds its verdict to the next decision, while AppMemory retrieves advisory entries and learns only from accepted tasks. Both routes share capture, safety handling, completion auditing and task state. Coati is an Android application whose accessibility service reads the interface and performs actions. An optional overlay shows progress and lets the user pause or stop the task. Permission and installation dialogs remain under user control. 

## 3.3 Hybrid Perception 

Coati first uses the accessibility tree when it contains enough la-belled, visible and actionable nodes. Each node becomes an element with text, type, bounds, supported operations and state, while con-tainers inherit useful labels from their descendants. For custom canvases, games and WebViews without semantics, a Fast model parses the screenshot into a compact positional array of regions and elements with normalized coordinates, text, function, operations and state; this keeps a parse around one to two thousand output tokens. On-device GPU OCR is restricted to unlabelled, non-image nodes to recover painted widgets embedded in otherwise native screens. OCR may add or snap text and the system rejects a parse that describes another image, but it never overwrites model text. Detailed parse-level measurements appear in Appendix A. 

## 3.4 Routed Execution 

Candidates and background planning. The host builds a finite candidate set from the parsed screen: operations on actionable elements, scrolling, back, app return or launch, waiting, completion and escalation. Each candidate carries the element text, type, state and exploration annotations, and the host executes it at the element bounds, so the fast route never generates coordinates. The selector receives the goal, background sub-goals and hints, retrieved manual entries, recent history, candidates and evidence about the previous action. One request chooses the next candidate, judges the previous effect and, when needed, supplies a typing value, so a healthy step costs one round trip. The Reasoning model plans at task start and on each new page, returning sub-goals, hints, required text and optional AppMemory observations. Escalation. The router uses the Reasoning route when the selec-tor requests it, fast actions repeatedly fail or exploration remains uncertain, a commit is reached before the task state is complete, the completion audit rejects a claim, perception or selection is un-available, or the step leaves the current app or enters text. It passes the reason and recent fast history to the Reasoning model, then resumes the fast route unless repeated escalations make reasoning the default for the remainder of the task. 

Speed–accuracy modes. Whether a fast choice is trusted de-pends on its confidence and on whether the selector is exploring or goal-directed. Coati exposes the thresholds as a user setting with three modes: Fast executes every goal-directed choice and explorations above 0.4 on the fast route and also types text there; Balanced, the default, raises the exploration threshold to 0.6 and sends text entry to the Reasoning route; Accurate runs only goal-directed choices with confidence of at least 0.8 on the fast route. 

Loop delegation. For repeated actions over list items, the Rea-soning model plans the per-item operation, optional count, stop condition and scope once. The host then resolves the control on the first item, applies it to subsequent matching items without a model call per item, and records an item only when verification shows a target change. It scrolls when no unhandled match is visible and stops at the count, condition, list end or a bounded no-progress limit. The loop record—action, handled items, stop reason and list coverage—becomes host evidence, so a task over every matching item is not accepted when the loop did not reach the list end. 

Pre-commit gate. Because the selector treats background guid-ance as a hint, it may commit a form whose values are not all set, for example submitting an order with two copies when the task asks for three. Undoing a commit costs several steps and an audit rejection. Before tapping a button, item or card whose label denotes a commit (submit, save, send, export, confirm, pay, and their equivalents), Coati asks the Fast model once whether the screenshot shows every value the task requires; if not, the step is escalated with the missing value named. Tabs and switches are excluded, and a failed check never blocks the action. Commits are rare, so the gate costs about one Fast call per task.

## 4 Evaluation 

We ask four questions, one per claim: RQ1 (capability): with the same backbone model, how does Coati compare with open-source agents on AndroidWorld? RQ2 (reliability): does host-grounded verification keep Coati from claiming success it has not achieved? 

RQ3 (speed in everyday use): does the routed fast executor make everyday tasks and loops of simple steps faster and cheaper without losing success? RQ4 (repeated use): does AppMemory shorten tasks that users repeat? 

## 4.1 Setup 

AndroidWorld. AndroidWorld [25] has 116 parameterized tasks across 20 applications (61 easy, 36 medium, 19 hard), each with an official step budget and an evaluator that inspects the resulting app state rather than the agent’s claim. Every agent runs in the same Android 13 emulator (Pixel 6 profile) with Gemini 3.8 Flash through Google’s API as its backbone, on the same task instances (seed 30), budgets and official evaluators. A harness starts each task, waits for the agent, submits the answer of information tasks and calls the evaluator; the emulator is cold-restarted every ten episodes. Coati runs in its per-step configuration (C2: the Reasoning route on every step, VerifyLoop on) for three trials; the ablation C1 turns VerifyLoop off. The open-source agents Artemis [10], FinalRun [8] and Midscene.js [21] run with their released code through the same harness, with their model calls redirected to the same backbone; Artemis is run both in its accessibility-only (GUI) mode, matching Coati’s access, and, for one trial, with the ADB access its release expects, while Midscene’s default thinking level is rejected by the API, so we use the lowest accepted level. Episodes in which the environment failed before the agent acted are excluded and rerun under the same rule for every agent (Appendix B). We report the success rate (SR, partial scores as given by the evaluators), pass 3

(tasks solved in all three trials), the false-completion rate (declared completions that the evaluator judged failed), and time and model tokens per episode. These agents report far higher success in their own evaluations (around 90% on this benchmark), and two deliberate choices ac-count for the gap here, neither of them the backbone model. First, every agent is held to AndroidWorld’s official per-task step budget (about ten steps for a simple task), whereas the opponents’ released configurations plan up to roughly 120 steps; under the official bud-get most of their failures here are step-limit cut-offs rather than wrong decisions. ## 4.3 Reliability: Grounded Completion (RQ2) 

Table 4 isolates VerifyLoop. Without it, 9 of Coati’s 112 declared completions were false (8.0%) and nothing caught them. ## 4.5 Repeated Use: AppMemory (RQ4) 

Table 6 shows three independent learning sessions on a deep route in an app the model has never seen. Without memory, every run explores: 18.5 steps and 190 s at the median. In each session the first run explores and the manual learns the route from it; every later run goes there directly, in 6–7 steps and a median of 77 s, 2.5 ×

faster, with all nine later runs successful. The effect is specific to unfamiliar apps: on a familiar stock app the model already knows the route, and memory neither helps nor hurts. The manual also survived an app update that moved the entry points (version 2 of the fixture replaces two bottom tabs with a hub page): after learning on version 1, runs on version 2 took 6 steps against 13–15 without memory. The effect carries over to routed execution on the phone of RQ3: from an empty manual, the first deep-route run explored for 22 steps (222 s), and the next two took 5 steps (23 s and 21 s) against 34.3 steps and 295 s without memory, with no Reasoning call on the critical path; all four runs, including a task on the same route, succeeded. On the fast route most steps involve no model call that could describe the page; three changes made learning reliable there: observation-only calls while the background advisor is busy, a per-task observation budget that keeps the latest observations, where the route that worked is, rather than the first, and a stricter page identity for learning (visible-text Jaccard ≥ 0.9, not 0 .6), so that sibling pages sharing their bars are described separately. 

## 5 Lessons from Deployment 

Deploying the agent as an Android app exposed failure modes that affect both success and speed. Accessibility-based agents are likely to encounter the same issues. The agent’s own overlay hides the app. 

Android marks every node under a touchable window as invisible to the user; a tree read while Coati’s overlay was touchable kept 2 of 63 nodes, so the fast route saw an almost empty screen. Reading the tree while the overlay passes touches restored 62 of 63. Injected taps are not always taps. Accessibility gestures carry no touch source, and some list views ignore them; Coati falls back to the node’s click action when a list item’s tap leaves the screen unchanged. Presses of 50 ms or longer were dropped by one app right after launch, so taps last 20 ms, and swipes are kept out of the system gesture areas, where they trigger navigation. State must survive power loss. Task state written without a file sync was empty after a cold restart; writes now sync before an atomic rename. Measurement interferes. Using uiautomator to check results suspends the agent’s accessibility service; checks read state through the agent instead. 

Coordinate spaces and thinking budgets. Mixing pixel bounds with normalized coordinates in one prompt made the model copy pixel values, and output limits that include thinking tokens truncated answers; both were fixed in the prompt and request settings. 

## 6 Discussion and Limitations 

Scope and generalization. AndroidWorld evaluates first-time task completion, but not routine execution time, repeated use, or the reliability of completion claims. These aspects are evaluated sepa-rately in RQ3 and RQ4. Routing is less effective during first-time exploration, especially on deep routes, whereas AppMemory re-duces this cost on later visits. Our main experiments use emulators, Coati: Host-Grounded Execution for Installable Mobile GUI Agents Conference’17, July 2017, Washington, DC, USA 

one backbone model, two released fixture apps, and a limited num-ber of runs; the results also depend on server-side model latency. The phone results in Appendix D provide an additional check on current consumer hardware, but broader evaluations across devices, models and task sets remain future work. 

Hardware and privacy. GPU-assisted OCR requires a usable Vulkan GPU. Without one, Coati falls back to the accessibility tree and vision parsing, and the OCR models also increase the appli-cation size. Screenshots and page descriptions are sent to model providers. Although AppMemory stores only sanitized, interface-supported facts, neither mechanism prevents sensitive data from leaving the device; deployments should therefore use trusted model endpoints. 

Deployment and platform policy. Coati operates other applica-tions through Android’s Accessibility Service, whose autonomous use is restricted by current Google Play policy [9, 11]. We therefore distribute Coati as source code for direct installation rather than through Google Play. The proposed verification, memory and rout-ing mechanisms are independent of the action-injection layer and could transfer to sanctioned system interfaces. In the current de-sign, permission and installation dialogs remain under user control, actions are visible on screen, and users can pause or stop a task at any time.

## A Perception Details 

On-device GPU OCR.. Coati runs PP-OCRv5 mobile [5, 7] through NCNN with Vulkan [27] on the device GPU. Devices without a us-able Vulkan GPU run without OCR: a CPU implementation took 1.5–6 s per screen on an entry-level device, too slow to help a step. On a recent phone GPU, a complete OCR pass takes 40–85 ms per screen in the runs of Appendix D; on an entry-level Mali-G52, detection takes about 0.2 s and recognition about 90 ms per line, and batching horizontally adjacent lines into one recognition pass reduces total time by 25–35% at unchanged accuracy (an 84-line screen from 7.8 s to 5.9 s, a 21-line screen from 2.0 s to 1.5 s). Recog-nition skips labelled nodes, the status bar and the soft keyboard, and on native screens reads only unlabelled, non-image nodes. Models load asynchronously at service start, and on tree-less screens OCR runs in parallel with the vision parse and may delay a step by at most one second. 

Conservative OCR repair. A first repair strategy that replaced model text with OCR text improved parses overall but degraded elements the model had right: OCR misreads small text, icon glyphs and thumbnails. Coati’s final repair never overwrites model text. It keeps only confident lines (confidence ≥ 0.8 with at least two alphanumeric characters, or confident single-digit counters), ap-pends confident lines the parse missed, fills elements that have no text, snaps text-like elements only to lines with the same content, and moves an element only when the match is unique. Section A.1 shows that this strategy improves every metric without degrading any element. 

Parse agreement. If fewer than 30% of a vision parse’s texts are confirmed by OCR on the same screenshot, the parse describes a different image and is requested again. We observed such parses through a third-party model relay that mixed up responses be-tween requests; the check discards them before they cause actions, although it cannot prevent the screenshot from having been sent. 

Parse-level perception benchmark. Fourteen device screen-shots (four native, three custom canvas, three Flutter, two from a video app, two from a streaming client), 28 vision parses, with ground-truth element texts and positions from the accessibility tree or layout constants. We report the share of ground-truth elements found, the share with exactly correct text, the share whose parsed tap point falls inside the true element, and the number of elements that a repair made worse.

## B Evaluation Protocol 

Harness. All agents run through one harness that instantiates AndroidWorld tasks from the official registry (seed 30), applies the official step budgets, records every attempt in a per-emulator ledger, cold restarts the emulator every ten attempts, and scores with the official evaluators. The harness refuses to resume an experiment whose identity (task instance, parameters, sources and model con-figuration) differs from the stored one, so every reported episode ran under one configuration. 

Environment failures and resumption. An episode is excluded and rerun, for every agent alike, only when the environment failed before the agent could act: AndroidWorld’s own task setup raised an error (for example a missing tool or an uninitialized database), the agent’s driver did not start, or no model response arrived at all. One task, MarkorCreateFolder, names its folder after the current time to the second, so its instance can never match a stored one when a run resumes; its stored episode is rerun on every resumption, again for every agent. Archived episodes are kept with the results. We release the harness, its settings and every per-run result.

## C Tasks 

Everyday tasks. Loops of simple steps. Car Market is an offline marketplace fixture with 40 listings. In its repeat mode every row shows the listing ID, a Sold badge on six listings, and Favorite, Compare and Hide controls; a Refresh control drops one listing’s price on the fifth refresh. R1: add the first 10 listings to favorites. R2: add six given listing IDs to the compare list. R3: hide every listing marked Sold. R4: refresh until the price of a named listing drops below $40,000 and report it. The fixture persists its state, which the checker reads after each run.

## D Routed Execution on a Phone 

On-device benchmark. To measure routed execution on cur-rent consumer hardware, we built a benchmark of nine tasks on a OnePlus phone running Android 16 (1272 ×2772 portrait). The tasks cover interface types that stress different components (Ta-ble 9): native pages reached through several menus (L1), search with text entry across pages (L2), a setting that depends on an-other page (L3), a custom-drawn canvas with no accessibility tree (W1) and with text entry (W2), a native form with painted step-per and toggle widgets (O1), a system permission dialog shown by another process (P1), and two Flutter apps: a finance app with login and tab navigation (G1) and settings (G2). Each task has an automatic check of the resulting app state. Both configurations use Gemini 3.8 Flash as Reasoning and Fast model through the official API; the fast route’s selector is Jev (version jev-1.13.0), a “System One” model that answers structured questions with typed, confidence-scored decisions [28]. Per-step Reasoning is Coati with every step on the Reasoning route (VerifyLoop enabled); Routed en-ables the fast route in Fast mode, hybrid perception and GPU OCR. Each task runs three times per configuration, both configurations in every round, with app knowledge off. Task time is the duration the agent logs from task start to accepted completion. Model latency in the test environment fluctuated, so absolute times are longer than in the emulator experiments and vary between rounds; both configurations are affected alike.

## D.3 Case Study: A Commit Stopped by the Pre-commit Gate 

Task O1 asks to choose an item in a native order form, set a painted stepper to three copies, turn on a painted toggle, fill two native text fields, and submit; hybrid perception merges a vision parse for the painted widgets into the tree. In one routed phone run, the selector left the stepper at two copies, completed the rest of the form and chose Submit order . Before the tap, the pre-commit gate asked the Fast model whether the screen satisfied the task and received “Copies is set to 2 instead of 3”. The escalated Reasoning step tapped “+” once more, its verification confirmed three copies, and the order was submitted with the requested values. Without the gate, only the completion audit could have caught the wrong order, after the fact.
