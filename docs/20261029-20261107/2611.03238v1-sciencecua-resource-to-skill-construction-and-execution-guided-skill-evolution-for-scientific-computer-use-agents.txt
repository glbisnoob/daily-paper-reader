Abstract
Computer-use agents for scientific software require application-specific expertise. Much of this expertise is
already documented in human-authored software manuals and web pages, making them readily available
resources for improving agents’ operational capabilities. However, turning these resources into executable,
reusable skills remains challenging due to mismatches between documented and deployed software versions and
differences in scope between documentation coverage and task requirements. To address these challenges, we
introduce ScienceCUA, a two-stage framework combining resource-to-skill construction with execution-guided
skill evolution. First, ScienceCUA identifies tasks supported by the software from its documentation, infers
operational trajectories, and generalizes them into reusable Skills. Command catalogs, syntax constraints, and
shortcuts are organized separately as References for on-demand lookup. Then, ScienceCUA uses execution
feedback to drive skill self-evolution by contrasting successful and failed trajectories for the same task,
identifying deficiencies, revising existing skills or adding new ones, and updating the skill library only after
repeated validation in real environments. To enable reliable evaluation without benchmark noise or task
leakage, we introduce two improved benchmarks. ScienceBoard-Verified provides an audited and corrected
basis for measuring task performance, while ScienceBoard-VE separates skill evolution from final testing
through disjoint evolution and test tasks and further supports native-agent evaluation. Experiments show
that the initial Skills and References improve average task success rate by up to 7.23 percentage points
over the base model, while skill self-evolution increases the total gain over the baseline to as much as 17.12
percentage points. ScienceCUA turns software documentation into an evolving set of executable skills and
queryable references, offering a practical way for general-purpose agents to use scientific software reliably
and at scale.

Introduction
Computer-use agents (CUAs) built on foundation models can now execute multi-step tasks through
graphical and command-line interfaces (Qin et al., 2025; Sager et al., 2026; Xie et al., 2024). Most
existing benchmarks, including WebArena, OSWorld, and Windows Agent Arena, focus on general-
purpose web, office, and desktop tasks, while scientific software has received comparatively less
attention (Xie et al., 2024; Zhou et al., 2024; Bonatti et al., 2024; Sun et al., 2026). Scientific
software is widely used for experiments, simulations, and data analysis, but operating these tools
often requires application-specific workflows, commands, syntax, and parameter constraints (Sun
et al., 2026; Ai et al., 2026). To complete scientific-software tasks, agents must use software-specific
knowledge to select appropriate operations and organize them into effective workflows (Shao et al.,
2026).
We study this problem using ScienceBoard (Sun et al., 2026), which evaluates CUAs on six
scientific applications. Figure 2(a) shows that each application provides user manuals or official
tutorials containing application-specific knowledge. However, Figure 2(d) shows that directly placing
these resources in the model context yields only limited gains in task success while substantially
increasing execution time. Figure 2(b) illustrates that human-authored documentation mixes
operational instructions with conceptual explanations and other narrative content. A particular
task, however, typically depends on only a small fraction of the available information, as shown in
Figure 2(c). The central question is how to extract task-relevant information from these human-
oriented resources and organize it as structured knowledge that the model can use effectively.
Prior work has constructed reusable skills from human-created resources for content creation,
gaming, software operation, and related applications (Fan et al., 2026; Che et al., 2026; Jiang et al.,
2026; Shen et al., 2026). For scientific software, these resources must supply two kinds of knowledge
with different lifetimes: procedural guidance for a specific task, and shared software knowledge
queried on demand. We therefore introduce ScienceCUA, which extracts task-oriented procedural
knowledge and cross-task shared software knowledge from raw software resources, organizes them as
2


Skills and References, respectively, and combines them on demand during execution.
However, the initial Skills and References constructed from raw resources have inherent limitations.
First, the available PDF or HTML resources may not match the version of the software deployed in
the execution environment, since perfectly matched resources are not always available. Second, for
some applications, the resource coverage is broader than the range of tasks being evaluated, while
the task scope is unknown during construction. The resulting knowledge library therefore contains
many entries that are irrelevant to the evaluation tasks, reducing the density of useful information.
Third, some task requirements may fall outside the coverage of the resources themselves.
To address these limitations, ScienceCUA drives the continual evolution of Skills and References
through execution feedback. Prior work has used task feedback and execution trajectories to build
reflective memory, optimize external skills, or adapt agent behavior (Shinn et al., 2023; Zhao et al.,
2024; Ni et al., 2026; Liu et al., 2026; Yang et al., 2026; Chen et al., 2026; Zhang et al., 2026; Sun
et al., 2025). In contrast, ScienceCUA improves a scientific-software knowledge library initialized
from software resources, using historical failure trajectories to guide subsequent exploration and
help agents avoid repeating failed paths or continuing to follow potentially erroneous Skills and
References; when knowledge is insufficient, it revisits the original resources to retrieve and construct
task-relevant Skills or References. Combined with on-demand composition, this design both helps
agents bypass ineffective paths caused by version mismatch and, where the original resources support
it, supplements omitted or overly general knowledge in the initial library, thereby reducing the
mismatch between the resources and the actual tasks. Candidate updates are added only after
independent validation in the target environment.
To support reliable evaluation, we audit and repair ScienceBoard to create ScienceBoard-Verified.
We also add a set of tasks that do not overlap with the final test tasks, use them exclusively for skill
evolution, and combine the audited benchmark and the new tasks into ScienceBoard-VE; in addition,
we extend the evaluation framework to support native agents. Across six scientific applications, the
initial Skills and References improve the average task success rate over the base model by up to
7.23 percentage points. Execution-guided skill evolution increases the total gain over the baseline to
as much as 17.12 percentage points. Our contributions are:
1. Resource-to-skill construction for scientific software. We present a method for con-
structing a knowledge library from raw software resources. It organizes task-oriented procedural
knowledge as Skills and cross-task shared software knowledge as References, and supports
their on-demand composition during execution.
2. Execution-feedback-driven skill evolution. We use failure trajectories to guide exploration
and help agents avoid repeatedly following erroneous Skills or References. When knowledge
is missing or an existing entry is inapplicable, the system supplements or revises Skills and
References from the original resources and updates the knowledge library only after validation
in the target environment.
3. Reliable evaluation of skill construction and evolution. We audit and repair Science-
Board to create ScienceBoard-Verified, add skill-evolution tasks disjoint from the final test set
to form ScienceBoard-VE, and extend evaluation to native agents.
2
Related Work
Resource-to-Skill Learning.
Automatically constructing reusable agent knowledge from external
resources is a relatively recent research direction. MMG2Skill Che et al. (2026) converts public guides
3


into editable Skills, but assumes that tasks are paired with relevant guides in advance and does not
realize an end-to-end pipeline for constructing Skills directly from raw resources. VisualSkill Jiang
et al. (2026) leverages document images to support GUI element identification and state verification.
However, some HTML documentation contains no images and thus provides no additional visual
evidence; even when screenshots are available, their interfaces may differ from the current software
version, potentially introducing misleading visual cues. SkillFoundry Shen et al. (2026) supports
workflow generation for concrete scientific tasks, but focuses on domain capability coverage and
task workflows rather than on systematically organizing reusable knowledge for a given scientific
software package. Overall, existing methods differ in their resource formats, task assumptions,
and construction objectives, but systematic investigation is still lacking into how to automatically
discover tasks from raw scientific-software resources and organize cross-task reusable knowledge
without pre-specified task–resource pairs.
Self-Evolving Skills and Experience-Driven Agent Adaptation.
Skill self-evolution improves
reusable agent knowledge from execution experience without modifying model parameters. Early
work such as Reflexion Shinn et al. (2023) used verbal feedback to improve subsequent behavior,
and SEAgent Sun et al. (2025) extended this experience-driven paradigm to computer-use agents.
Later work made such experience explicit and reusable as skills. EvoSkill Alzubi et al. (2026)
creates or revises skills from failure feedback and selects candidates through validation, while
Trace2Skill Ni et al. (2026) distills trajectory-local lessons into transferable skill catalogs. As skill
updates become central, subsequent studies increasingly focus on their reliability. SkillOpt Yang
et al. (2026) constrains the scope of skill edits and accepts only validation-improving updates, while
SkillCAT Chen et al. (2026) contrasts successful and failed trajectories for the same task and uses
task replay before merging candidate edits. Most prior methods start from execution experience or an
existing skill library. ScienceCUA instead initializes its library from scientific-software documentation
and addresses version and task-coverage mismatch through failure-history-guided exploration and
source-grounded additions or revisions.

Method
3.1
Resource-to-Skill Construction
ScienceCUA first transforms software documentation into an initial library of reusable Skills and
queryable References, and then evolves this library using execution feedback from a disjoint set of
evolution tasks.
Decoupling Skills and References
Given PDF/HTML software documentation D, we construct an initial library L0 = (S0, R0), where
Skills S0 encode reusable task-level operational procedures and References R0 organize cross-
task shared knowledge, such as commands, syntax, and parameter constraints. For example,
KAlgebra’s 2D and 3D plotting workflows form separate Skills, while syntax for square roots and
exponentiation is stored in a Reference (Figure 4). During execution, the agent selects a Skill for
the required workflow and consults References as needed to incorporate software knowledge into its
actions.

Construction Pipeline
We represent a Skill as s = (ns, ds, as, ps, bs), where ns is its name, ds is its capability description,
as specifies its applicability, ps lists its preconditions, and bs contains its procedural body, including
the steps needed to accomplish the goal. We represent a Reference as r = (nr, dr, cr), where nr is
its name, dr describes its purpose, and cr contains the concrete lookup content. Construction first
organizes the documentation into a shared evidence corpus. From this corpus, one branch extracts
References, while the other discovers Tasks, infers trajectories, and induces Skills.
Traceable evidence organization.
To support all downstream stages and reduce hallucinations,
we organize documentation into traceable evidence. A parser uses authored headings and navigation
to structure text and visual content while retaining source locations. An agent refines this organization
without rewriting the content. Every downstream Reference, Task, and inferred action or observation
must be grounded in this evidence.
Reference extraction.
To make shared software knowledge accessible during execution, the
Reference branch turns relevant evidence into focused lookup entries. A program first extracts and
deduplicates candidate lookup content from the documentation, including command tables, syntax
constraints, and shortcut descriptions. An agent reviews the remaining candidates to decide what
to retain and how to group them, preserving documented syntax, parameters, and examples.
Task discovery, trajectory inference, and Skill induction.
To ground reusable Skills in
concrete operational requirements, the other branch proceeds from goals to trajectories before
induction. An agent first discovers source-supported user goals without benchmark task input. For
each Task, it infers ordered actions and expected observations, retaining documented controls. These
trajectories make the required operations explicit before related procedures are grouped into a
coherent Skill, helping preserve actionable detail during abstraction. After induction, we check
whether the operational capability expressed by each trajectory is included in a Skill and explicitly
record any exclusions.

3.2
Execution-Guided Skill Self-Evolution
Differences between documented and deployed software versions, together with gaps between resource
coverage and task requirements, can leave the initial library misaligned with the target environment
or incomplete for its tasks. ScienceCUA therefore keeps the execution model fixed and continually
evolves Skills and References through two mechanisms: failure-history-guided exploration and
source-grounded knowledge addition.
Evolution setting and overall workflow.
As described in Section 4.2, ScienceBoard-VE
contains an evolution set E = Expanded \ Verified and a held-out test set V = Verified, where
E ∩V = ∅. Evolution uses E, while V remains unseen until final evaluation. Given the initial library
L0 = (S0, R0), ScienceCUA processes each task q ∈E independently and maintains its history Hq.
Histories and provisional updates are not shared across tasks.
Each task uses two types of execution. Task exploration attempts the task with the frozen
initial library, together with any prior failure records available, to search for a feasible path and
collect environmental feedback. Candidate validation temporarily loads one modified or newly
added Skill or Reference and reruns the task to test whether that candidate can independently
support successful execution.
Each task begins with task exploration. A first-exploration success requires no update and exits
the evolution process. After a failure, the system either makes no change, revises existing knowledge,
or adds source-supported knowledge according to its diagnosis. Any modified or newly added Skill
or Reference undergoes candidate validation. A successful candidate enters the candidate pool P.
A failed candidate and its validation trajectory enter Hq to guide the next task exploration. If
a later exploration succeeds with the help of failure history, the system contrasts it with earlier
failures, derives a revision candidate when needed, and validates it. Each task contributes at most
one validated candidate to P. These candidates are then consolidated into Lfinal, merged targets
undergo regression certification, and the library is frozen for evaluation. Further details are provided
in Appendix I.

4.1
ScienceBoard-Verified
We substantively revise 37 tasks and remove one
additional task, yielding 168 executable tasks reserved for final evaluation. We organize the revisions
and supporting repairs into four categories: (1) Instruction Ambiguity, which covers 15 revised
tasks with unclear goals or omitted completion requirements; (2) Task & Answer Errors, which
covers 12 revised tasks involving incorrect task statements, reference answers, or expected evaluator
results; (3) Evaluator Bias, which covers 10 revised tasks in which unnecessary restrictions
exclude valid execution paths, output representations, or output locations; and (4) Environment
Repairs, which covers application prompts, response handling, runtime and initialization settings,
and unavailable external dependencies. The fourth category includes shared evaluation-environment
repairs and the removed task; these do not add to the 37 revised tasks. Appendix G details all 37
task revisions, the task removal rationale, and the associated evaluation-environment repairs.
4.2
Expanding the Benchmark for Skill Self-Evolution
To separate skill improvement from final evaluation, we add 108 tasks that do not overlap with
the verified test set: 20 each for KAlgebra, Celestia, GRASS GIS, ChimeraX, and Lean 4, and 8
for TeXstudio. These tasks are used exclusively for skill self-evolution, while the 168 tasks in
ScienceBoard-Verified remain unseen during skill construction and evolution and are used only
for final evaluation. The resulting ScienceBoard-VE contains 276 executable tasks in total. The
evolution tasks use the same types of software operations as the test tasks but differ in their specific
targets or requirements, allowing execution experience to transfer without reusing the test tasks
themselves. See Appendix H for details.
4.3
Native-Agent Evaluation
The original ScienceBoard evaluates models through a unified API-based interaction loop. We extend
it to support native evaluation of Codex and Grok Build, keeping tasks, software environments,
and evaluators unchanged. In both settings, ScienceBoard supplies screenshots and accessibility
trees, executes the returned action code or control instructions, and evaluates task outcomes. In the
model-based setting, each API request includes the system prompt, task instruction, screenshots
and accessibility trees from the three most recent steps together with the model-generated actions
for those steps, and the current screenshot and accessibility tree. For ScienceCUA, we implement
two-stage resource routing through progressive disclosure. Before execution, the evaluated model
selects relevant Skills and References from their names and descriptions based on the task instruction.
The selected entries are then loaded in full into the system prompt and included in every subsequent
execution request. In the native-agent setting, each task uses a separate persistent session, to which
the outer evaluation framework appends only the current screenshot and accessibility tree at each
step. The native harness maintains the task history and compacts context as needed. Skills and
References are registered as independently loadable native resources, which the agent selects and
reads during execution. Each turn concludes with one ScienceBoard action block for the evaluation
framework to execute. To prevent agents from obtaining additional reference material through web
search, we disable web search for native agents. To preserve task independence, conversation history
and runtime context are maintained separately for each task and are not shared between tasks.

5
Experiments
Experimental setup.
We evaluate ScienceCUA on ScienceBoard-Verified. Model-based evaluation
uses Qwen-3.8 Max, GLM-5.2, Grok-4.6, and GPT-5.5. Native-agent evaluation uses Grok Build
with Grok-4.6 and Codex with GPT-5.5. The two settings follow the respective interaction and
resource access protocols described in Section 4.3. In model-based ScienceCUA evaluation, at most
three Skill and Reference entries are selected in total before each task. In native-agent evaluation,
the agent autonomously selects and reads resources during execution, with no limit on the number of
Skill and Reference entries it can access. We report task success rates for each of the six applications
and use their unweighted mean as the overall performance metric.
Model-based evaluation compares ScienceCUA with Vanilla, direct document injection, RAG,
VisualSkill, and SkillFoundry. Native-agent evaluation compares Vanilla, VisualSkill, SkillFoundry,
and ScienceCUA. ScienceCUA and VisualSkill use the same documentation inputs. SkillFoundry
does not support direct documentation input and instead automatically searches for and collects
online resources based on the name and version of the software installed in the execution environment.
Implementation details are provided in Appendix B for direct injection, Appendix C for RAG,
Appendix D for SkillFoundry, and Appendix E for VisualSkill.
Skill self-evolution uses the 108 additional tasks in ScienceBoard-VE. After evolution, the
knowledge library is frozen and evaluated on ScienceBoard-Verified without access to evolution
trajectories or histories.

5.2
RQ2: Do Skills and References make complementary contributions to task success?

procedural guidance and cross-task shared lookup knowledge to task success. Skills organize complete
operational procedures around specific goals, while References provide shared knowledge that is not
tied to any single procedure, including syntax constraints, parameter rules, command and function
catalogs, and keyboard shortcuts. The two resource types have no one-to-one correspondence that
permits direct, equivalent merging. We therefore do not use a forced merger of the two resource types
as an information-matched control for knowledge organization, and instead use resource ablations
to evaluate the value of providing each knowledge type individually and both jointly.

5.3
RQ3: Can self-evolution mitigate the limitations of Resource-to-Skill construction?
The initial library may lack task-relevant knowledge or contain instructions incompatible with the
deployed software version. We use Grok-4.6 (xhigh) and GPT-5.5 (xhigh) to compare the initial
library, Full ScienceCUA, two ablated variants, Trace2Skill (Ni et al., 2026), and SkillCAT (Chen
et al., 2026), examining whether execution-guided self-evolution improves performance on unseen
tasks. The −Knowledge addition variant only revises existing entries without adding new Skills
or References. The −Failure history variant withholds prior exploration and candidate-validation
records from subsequent exploration, leaving the other mechanisms unchanged. Within each model
setting, all evolution variants use the same initial library, evolution tasks, software environments,
and runtime configurations. Detailed ScienceCUA settings are provided in Appendix I.
Table 3 shows that self-evolution improves the average success rate from 44.70% to 54.59%
for Grok-4.6 and from 57.16% to 65.81% for GPT-5.5, yielding gains of 9.89 and 8.65 percentage
points, respectively. Full ScienceCUA also outperforms Trace2Skill and SkillCAT, which achieve
average success rates of 46.44% and 53.02% with Grok-4.6, and 60.46% and 63.74% with GPT-5.5,
respectively. These results indicate that knowledge improvements obtained during evolution transfer
to final test tasks not used during evolution.
Removing either knowledge addition or failure history reduces average success rates, but the
dominant source of improvement varies by application. KAlgebra and Celestia are particularly
sensitive to failure history: removing it reduces success by 9.68 percentage points for KAlgebra under
both models, and by 9.09 and 6.06 points for Celestia under Grok-4.6 and GPT-5.5, respectively.

6
Conclusion
We present ScienceCUA, a two-stage framework for computer-use agents operating scientific software.
The first stage extracts source-grounded operational knowledge from software documentation,
distilling task-level workflows into executable Skills and organizing commands, syntax, and parameter
constraints as queryable References. The second stage refines Skills and References using execution
feedback from the target software environment. We also construct the audited ScienceBoard-Verified
and add evolution tasks disjoint from the test set to form ScienceBoard-VE, supporting knowledge
evolution and native-agent evaluation. Experiments across six scientific applications show that the
initial Skills and References improve average task success by up to 7.23 percentage points over the
baseline in model-based evaluation. Knowledge self-evolution increases the total gain to as much
as 17.12 percentage points. These results suggest that human-authored software resources can be
transformed into executable, verifiable operational knowledge that continually improves through
environmental feedback, enhancing general-purpose agents’ ability to use scientific software. By
maintaining Skills and References outside the model parameters, ScienceCUA offers a practical path
for agents to adapt to changes in scientific software environments and task requirements without
retraining the model.

Discussion and Implications
Niche and private software are priority settings for our approach.
Knowledge of niche,
private, or self-developed software may be underrepresented during general models’ pre-training
and post-training, leaving gaps in their understanding of specific functions, workflows, and usage
constraints. Extracting knowledge from documentation therefore has the potential to yield larger
performance gains for such software. Execution feedback can then guide revisions and additions
that adapt this knowledge to the deployed environment and task requirements. For widely used
software whose operational knowledge is well covered during training, models may already know
much of the documented material, leaving less room for improvement through external knowledge.
Knowledge organization should reflect software and task requirements.
Scientific software
requires both operational workflows and precise parameter constraints, syntax rules, and command
and function catalogs. These details are often shared across tasks and consulted only when a
step requires them. ScienceCUA therefore organizes goal-oriented procedural knowledge as Skills
and shared lookup knowledge as References, allowing agents to follow workflows while accessing
specific rules and details on demand. Other software and scenarios may require different forms
of knowledge organization. Applying our approach to these settings can retain the process of
constructing knowledge from resources and improving it through execution, while adapting knowledge
organization to the target setting. Such adaptation could include exploring code-based or visual
representations, whose effectiveness we have not systematically compared within the same framework.
Base model capabilities affect the value of external knowledge augmentation.
Recent
frontier models, such as GPT-6 Astra, demonstrate stronger computer-use capabilities. As models
become able to complete more scientific-software tasks on their own, the additional gains from
ScienceCUA’s self-evolved Skills and References may diminish, a pattern observed in our supple-
mentary experiments (Appendix P). Similar effects may arise in other CUA settings: when a base
model already possesses the relevant operational knowledge, the room for improvement from Skills
may shrink; if their guidance is outdated, inapplicable to the task, or imposes unnecessary con-
straints on execution paths, it may even interfere with the model’s own judgment and lead to worse
performance than the base model without Skills. The value of external knowledge therefore needs to
be evaluated in relation to the base model’s capabilities and the specific task. Practical deployment
must also balance task performance against inference cost. In budget-constrained settings that call
for lower-cost models, constructing and continually improving external knowledge from software
resources retains practical value. Moreover, the software covered by ScienceBoard has publicly
available documentation, and models may already have learned some of this operational knowledge.
For niche, private, or self-developed software whose knowledge is underrepresented during model
training, external knowledge may still fill capability gaps and yield larger gains. This expectation
warrants further empirical validation.

PDF normalization.
PDF text is extracted with PyMuPDF from the embedded text layer. OCR
is disabled and raster images are not indexed. Repeated headers and footers are removed. We infer
a hierarchy from chapter, section, appendix, and numbered headings and retain page ranges as
source locators. When a reliable semantic heading is unavailable, the corresponding page is kept as
a page-level document rather than discarded. This yields 81 semantic sections and 7 page fallbacks
for KAlgebra. The Celestia guide is retained as 48 page-level documents because its layout does not
provide sufficiently reliable semantic section boundaries.
HTML acquisition and freezing.
Each HTML corpus begins at a fixed official documentation
root. URLs are canonicalized and restricted to the documentation scope. The reachable in-scope link
queue is traversed to exhaustion, with no page-count limit, and every successful response is frozen
with its requested URL, final URL, acquisition time, raw HTML hash, outgoing links, and local file

HTML normalization.
For every retained page, the extractor selects the main, article, or body
content and removes scripts, styles, templates, and navigation chrome. It segments the remaining
content at h1–h6 boundaries. Paragraphs, lists, tables, and preformatted code are preserved in
reading order, with code represented as fenced blocks. Exact duplicate pages are removed by content
hash. Raw HTML and normalized Markdown-compatible text are both retained for audit, but only
normalized text is indexed. This procedure is deterministic and uses no language model.
C.2
Structure-Preserving Chunking
Chunk boundaries are computed with the tokenizer of BAAI/bge-m3. Each indexable text is prefixed
with its document title and complete section breadcrumb. The target length is 700 tokens and the
hard maximum, including this prefix, is 1,000 tokens. Text that exceeds the limit is split preferentially
at paragraph, line, or sentence boundaries with an 80-token overlap between consecutive pieces.
Chunks never cross documents or semantic sections. Exact duplicates are removed using the SHA-256
hash of the complete index text. Near-duplicate removal is not applied. The counts in Table 6 are
post-deduplication, and no resulting chunk exceeds the hard limit.
C.3
Hybrid Retrieval and Reranking
Retrieval is performed independently for each application. The query is exactly the stripped task
instruction. The software name is used only to select the corresponding corpus and is not appended
to the query. Cross-application retrieval is disabled.
We retrieve 30 candidates with BM25 and 30 with a dense encoder. BM25 uses k1 = 1.2, b = 0.75,
binary query term frequency, and a Unicode-aware tokenizer that preserves compound identifiers.
Dense retrieval uses BAAI/bge-m3 with a maximum input length of 1,024 tokens, CLS pooling,
and L2-normalized embeddings. Encoding uses FP16 on CUDA with batch size 2. The resulting
1,024-dimensional vectors are stored in FP32. Similarity is exact cosine similarity, implemented as a
dot product over normalized vectors, without approximate-nearest-neighbor search.
The two ranked lists are combined by equal-weight reciprocal rank fusion (RRF):

F.2
Deterministic Validation and Control
All Agent outputs are validated by Python before entering a downstream stage. A textual citation
must contain a quote that exactly matches the corresponding Evidence text; a visual claim must
reference an authorized and inspected image artifact. Citations cannot point to nonexistent or
out-of-scope Evidence, and downstream objects can reference only upstream identifiers present in
the current frozen snapshot.
Stage-specific validation additionally checks schema constraints, duplicate candidates, field
lengths, step ordering, and cross-object consistency. For Trajectories, Python verifies that the
submitted task_id matches the dispatched Task, that exactly one acceptable trajectory is returned,
23


that step ordinals are consecutive, and that linked References exist and satisfy the reference_guided
dependency rules. For Skills, Python validates Task/Trajectory/Reference relations, step structure,
exact citations, and the coverage protocol over every dispatched Trajectory.
Pipeline state changes only through structured submission tools. Ordinary natural-language
replies do not commit business results. Key stages freeze immutable CorpusSnapshot and Knowl-
edgeSnapshot objects so that downstream child sessions read stable inputs. Attempt/Receipt
bookkeeping, idempotent retry, recovery, and storage details are implementation mechanisms and
are documented in the released code rather than expanded here.

Task Construction and Deduplication
We construct 108 additional tasks across the six scientific applications for skill self-evolution. These
tasks use the same types of software operations as the test tasks to support the transfer of operational
experience, while varying the target objects, task parameters, or specific requirements to form
distinct tasks. We manually compare each additional task against the ScienceBoard-Verified tasks,
examining its goal, initial state, required output, and evaluation criteria to confirm that it does not
duplicate a test task. Researchers in the corresponding scientific domains who are familiar with the
respective software manually review and execute all additional tasks to verify that their requirements
are clear, their reference answers or target states are correct, and they can be completed in the
specified software environments.
I
Execution-Guided Skill Self-Evolution: Additional Details
This appendix specifies the execution protocol used in Section 3.2. Evolution uses only E =
Expanded\Verified and the original resources D. For new-knowledge creation, D is accessed through
bounded live browsing that starts from the configured official documentation root for the current
application and follows only in-scope links discovered from fetched official pages. It does not use a
search engine, BM25 retrieval, a saved Resource-to-Skill snapshot, or model knowledge as source
evidence. The execution model is fixed, and V = Verified is reserved for final evaluation.
I.1
Frozen Initial Library and Per-Task State
All evolution tasks start from the same frozen initial library L0 = (S0, R0). A task never installs a
provisional update into the library used by another task. Instead, it maintains a private execution
history and may contribute at most one independently validated candidate to a global candidate
pool P. Candidates are consolidated only after all tasks terminate.
For each task q, its first task exploration selects a fixed routed set Fq of Skills and References
from L0. Later task explorations use the same routed names and initial versions, even after the task
has produced a failed candidate. This separates behavioral exploration from candidate installation:
rejected knowledge remains evidence, not active guidance.
Each candidate contains one complete target entry relative to L0. A candidate produced after
a failed exploration may revise one entry in Fq or add one Skill or Reference supported by D. A
candidate distilled after a later successful exploration may only revise one existing routed entry. A
rejected candidate is never used as the textual base of a later candidate.
I.2
Complete Execution History and Input Separation
Each task has an indexed history archive. For every task exploration and candidate validation, the
archive records the task instruction, execution type, exact execution-time prompt, raw action–
observation trajectory, evaluator outcome, routed Skill and Reference names, their complete
execution-time contents and version hashes, and every screenshot mapped to its trajectory step.
When applicable, it also records the diagnosis and the complete candidate entry used in validation.
Screenshots are interpreted as pre-action observations: the effect of an action is checked in the
following screenshot.
The first task exploration receives no history. Every later task exploration receives all earlier task
explorations and candidate validations for that task, including their exact prompts, raw trajectories,
diagnoses, candidates, outcomes, and screenshots. The records are explicitly labeled so that the
29


agent can distinguish exploration from validation, identify which knowledge version was loaded,
and map each screenshot to its execution and step. All historical screenshots are placed in the first
model turn and marked as evidence; the final live screenshot remains the state on which the agent
must act. The prompt instructs the agent to inspect the complete history, avoid repeating failed
action sequences, and not follow initial Skills or References mechanically when current GUI evidence
suggests a version mismatch.
Diagnosis and knowledge writing receive the task, loaded entries, exact prompt, raw trajectory,
evaluator result, and complete screenshot sequence. The analysis agent must inspect every screenshot
before submitting its result. Candidate validation is deliberately separated: it receives no exploration
history, successful trajectory, diagnosis, or candidate rationale. This prevents the validation agent
from succeeding through transient trajectory memory rather than through the proposed external
knowledge.

A task exploration that succeeds at i > 1 may have relied on failure history unavailable at deployment.

I.5
Candidate Consolidation and Final Evaluation
After every evolution task terminates, accepted candidates are grouped by target Skill or Reference.
Revisions are grouped by the identity of their original entry. For additions, a conservative Grok

semantic-deduplication pass groups candidates only when they have the same knowledge type and
express the same reusable capability at substantially the same granularity, scope, and intended use;
Skills and References are never grouped together, and uncertain candidates remain separate. Each
group adopts the title of one independently validated member rather than inventing a new title.
If this auxiliary grouping call is technically unavailable or violates its structured-output contract,
the pipeline fails open to exact type-and-title grouping, thereby avoiding an unsupported merge.
Different targets are consolidated independently and are never mixed merely because they came
from the same task.
If a target has exactly one accepted candidate, that already validated candidate is adopted
directly without another task execution. If a target has multiple candidates, the consolidation model
receives every accepted candidate and either the target’s complete initial content for a revision or
an explicit new-entry baseline for an addition. It then produces one complete entry that preserves
the independently validated, non-conflicting improvements of all candidates. The merged text is not
allowed to discard a candidate-specific capability merely to simplify the entry.
Because merging can change individually validated content, a multi-candidate consolidation must
pass regression certification. Let Qg contain all tasks that contributed candidates to consolidated
target g. The same consolidated content and hash are installed for every replay, and each q ∈Qg is
executed from its standard initial environment in a fresh, history-free session with its first-exploration
routing fixed. The initial full replay over Qg does not consume the reflection budget.
If every replay succeeds, the target is certified. Otherwise, a reflection agent receives the initial
entry, all accepted candidates, the current consolidation, and every regression prompt, raw trajectory,
evaluator outcome, and screenshot. It chooses between two actions:
1. Revise. If the consolidated content caused or contributed to any failure, a complete replacement
is regenerated from the initial entry and all accepted candidates rather than edited cumulatively
from the failed consolidation. Previously passed results are invalidated, and all tasks in Qg
are replayed.
2. Keep. The current consolidation may be retained only when every current failure is attributable
to grounding and the content itself requires no change. Passed tasks remain certified, and only
the failed tasks are replayed.
Each reflection followed by its required replay consumes one of at most Mconsolidation cycles.
Infrastructure or API failures are handled separately and are not treated as task failures. If
certification still fails after the allowance is exhausted, target g is rejected: a revised target retains
its initial version, while an uncertified addition is omitted. After all target groups are resolved,
Lfinal = Consolidate(L0, P) is frozen and evaluated on V with standard initial environments, fresh
sessions, normal routing, and no evolution history. No additional global regression is performed.

Why broad resource coverage leaves a task-relevant gap.
The GRASS GIS Reference

concentrated in a much smaller part of this space, primarily the Graphical User Interface (including

downstream task distribution is known, so its initial construction aims to cover the software broadly.
This coverage-oriented strategy can produce Skills and References for material that benchmark tasks
rarely use, while leaving frequently needed leaf-level knowledge too general to execute. The d.vect
command illustrates this mismatch: the initial Display catalog identifies the command but does not
provide the syntax and parameter combinations needed by the recurring vector-styling tasks.
The manual spans twelve major sections; task demand is concentrated in a subset. The d.vect command is documented under
Display.

parameters. These failures motivate adding knowledge at the module level rather than writing a

Research Setting and Baseline Reproduction Constraints of
Resource2Skill
O.1
Research Setting and Knowledge Objectives
Resource2Skill and ScienceCUA both investigate how to transform human-created resources into
reusable skills, but they differ in their research settings and knowledge objectives.
Resource2Skill primarily addresses authoring tasks across domains such as PPT, Web, Excel,
Blender, CAD, UE5, and audio production. It distills skills from tutorial videos, repositories, articles,
documentation, and reference artifacts. Its library provides retrievable and composable authoring
techniques, code patterns, and visual references to help agents create new artifacts, with downstream
evaluation primarily measuring artifact quality.
ScienceCUA aims to improve the ability of models and agents to operate scientific software.
Starting from supplied PDF/HTML software documentation, it discovers supported operational
tasks, derives task-level procedures, and organizes shared knowledge such as commands, syntax, and
parameter constraints. These forms of knowledge are represented as Skills and References, respectively,
to support agents in completing user tasks in deployed software environments. Downstream evaluation
primarily measures task success.
Thus, although both approaches investigate resource-to-skill construction, they differ in how
resources are used, how knowledge is organized, and what downstream evaluation emphasizes.
O.2
Limitations in Adapting the Released Implementation
At the implementation level, the relevant public interfaces of Resource2Skill do not directly provide
the document-level knowledge-construction process required for our collections of PDF/HTML
software documentation. Although the paper describes a construction operator that can gener-
ate multiple candidate skills from a single resource, the two interfaces directly relevant to our
documentation inputs have the following limitations in the public code we inspected.
1. StaticArtifactConnector does not directly support PDF manual parsing. Its di-
rectory mode filters files using domain-specific extension lists, covering .xlsx, .html/.htm,
.pptx, .blend, and selected audio and project formats, but excluding PDF. Consequently, the
KAlgebra and Celestia PDF manuals used in our experiments cannot be directly processed
through this mode. Its catalogue mode constructs candidates from supplied JSON fields, in-
cluding descriptions and applicability; it does not itself parse the referenced manuals, discover
knowledge units, or generate operational knowledge. StaticArtifactConnector implementation.
2. ArticleConnector uses individual supplied pages as candidate-generation units. It
accepts a URL list, fetches each page, and produces at most one CandidateSkill per URL.
Its optional model call primarily extracts a title, applicability, tags, and a short summary.
The interface does not implement recursive documentation crawling, cross-page evidence
aggregation, or the discovery of multiple procedural knowledge units within a page. Supplying
a documentation homepage or a list of page URLs therefore does not directly provide a
complete workflow for constructing operational knowledge from an entire documentation
collection. ArticleConnector implementation.
Adapting these interfaces to our setting would require additional components for PDF parsing,
HTML documentation discovery and collection, knowledge-unit decomposition, cross-page content
organization, and procedural-content generation, before packaging the results as CandidateSkill
56


records. Resource2Skill’s subsequent candidate processing and Skill Wiki construction remain
reusable. However, the added components would directly determine the content, granularity, and
coverage of the resulting library—properties central to the evaluation of resource-to-skill construction.
Such an adaptation would therefore extend beyond input-format conversion and introduce a
knowledge-extraction method designed by us. Its downstream performance would make the respective
contributions of Resource2Skill and the added extraction procedure difficult to distinguish. Given
these differences in knowledge objectives and the adaptation requirements of the released implemen-
tation, we did not include Resource2Skill as an original-pipeline baseline alongside VisualSkill and
SkillFoundry under the same evaluation setting.
