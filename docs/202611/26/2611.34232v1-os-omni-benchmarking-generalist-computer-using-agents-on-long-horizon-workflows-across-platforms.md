## 摘要
计算机使用智能体日益被期望完成真实的用户目标，而非孤立的 GUI 操作。然而，现有基准通常将 Web、移动端或桌面环境相互隔离，导致尚不清楚单一通用智能体能否执行跨越多个操作系统和持久应用状态的长程工作流。我们提出 OS-Omni，一个实时跨平台基准与执行环境，用于评估 Windows、Ubuntu、macOS、iOS、Android 和 Web 环境中的计算机使用智能体。OS-Omni 以每批 300 个任务的版本化批次发布；本文聚焦首个版本 v1，其中每个平台包含 48 个任务，并包含 12 个将桌面与 Android 手机配对的跨平台工作流。OS-Omni 提供可复现的初始化、平台特定适配器、轨迹日志和可执行的最终状态评估器，并包含受控的服务后端应用，用于涉及账户、购物车、预算、日历、消息及其他持久状态的工作流。人类研究表明，OS-Omni 任务平均需要 67.54 个交互步骤，显著超过 OSWorld 参考的 15.0 步。在 v1 上，评估中最强的智能体 Claude Opus 5.5 达到 68.5% 的平均成功率，落后人类参考的 77.3% 8.8 个百分点；这一差距在不同平台上并不均衡，前沿模型在 Linux 上超过人类，但在 iOS 和 macOS 上落后人类超过 25 个百分点。这些结果表明，当前智能体距离平台鲁棒的长程计算机使用仍有很大差距，尤其是当成功需要持续的状态跟踪和持久的最终状态变更时。

## Abstract
Computer-using agents are increasingly expected to complete realistic user goals rather than isolated GUI actions. However, existing benchmarks typically isolate web, mobile, or desktop environments, leaving it unclear whether a single generalist agent can execute long-horizon workflows that span multiple operating systems and persistent application states. We introduce OS-Omni, a live cross-platform benchmark and execution environment for evaluating computer-using agents across Windows, Ubuntu, macOS, iOS, Android, and Web environments. OS-Omni is released in versioned waves of 300 tasks each; this paper focuses on the first release, v1, which contains 48 tasks per platform and 12 cross-platform workflows that pair a desktop with an Android phone. OS-Omni provides reproducible initialization, platform-specific adapters, trajectory logging, and executable final-state evaluators, and includes controlled service-backed applications for workflows involving account, cart, budget, calendar, message, and other persistent state. Human studies show that OS-Omni tasks require 67.54 interaction steps, substantially exceeding OSWorld references of 15.0 steps. On v1, the strongest evaluated agent, Claude Opus 5.5, reaches 68.5% average success, trailing the 77.3% human reference by 8.8 points; the gap is uneven across platforms, with frontier models exceeding humans on Linux but trailing them by more than 25 points on iOS and macOS. These results indicate that current agents remain far from platform-robust, long-horizon computer use, especially when success requires sustained state tracking and durable final-state changes.

## 1. 核心问题与研究动机

- **问题**：单一通用计算机使用智能体（CUA）能否在**异构操作系统之间**完成**长程、有状态、跨应用**的真实用户目标？
- **背景痛点**：
  - 现有基准把 **Web**（WebArena、VisualWebArena、WorkArena）、**移动端**（AndroidWorld）、**桌面端**（OSWorld、WindowsAgentArena、macOSWorld、OS-MAP、MMBench-GUI）割裂评测，各自的动作接口、任务风格、评分协议不同。
  - 因此“某平台高分”难以解释为**通用计算机使用能力**，更可能只是对某一平台约定的适配。
- **两层挑战的耦合**：
  - **跨平台**改变交互瓶颈（桌面对话框 vs 手机 picker wheel、模态表单、软键盘）。
  - **长程**改变记忆与协调负担（跨窗口保持部分更新记录、去重、顺序约束）。
  - **终态评估**改变“成功”的定义：界面看起来完成 ≠ 导出文件/内部格式/购物车/预算记录一致。
- **量化动机**：人类完成 OS-Omni 任务平均需 **67.54 步 / 200.97 秒**，约为 OSWorld 参考（15.0 步 / 111.94 秒）的 1.8 倍时长，说明任务本身显著更长、更复杂。

## 2. 方法论：OS-Omni 基准与执行环境

### 2.1 核心思想
- 把评测从“能否操作某个界面”转为“**能否跨平台完成用户目标并留下正确的持久状态**”。
- 采用**终态评估**而非轨迹相似度：`R(τ) = g(s_T)`，其中 `τ=(o₀,a₀,…,o_T)` 为交互轨迹，`s_T` 为最终环境状态，`g(·)` 为任务专属评估器。
- **版本化“活基准”**：以每波 300 任务的节奏发布（v1, v2, …），每版增加更多 mock 应用与更难任务，缓解任务饱和与训练数据泄漏。

### 2.2 任务定义与规格
- 每个任务包含：稳定 ID、目标平台、自然语言指令、可选初始化、评估逻辑、描述性属性（以 YAML 描述）。
- 回合终止条件：智能体输出 `DONE`/`FAIL`、达到步数或时间上限、或运行不可恢复。
- 单平台任务：`max_steps=300`，单步超时 180s；跨端工作流：300–650 步，单步 120s。

### 2.3 环境基础设施
- **共享编排层 + 平台专属适配器**（Windows / Ubuntu / macOS / Android / iOS / Web）。
- **可复现初始化**：Linux 回滚干净 VM 快照；Windows 恢复 golden VM 存储；macOS 克隆 Tart VM 基线；iOS 克隆模拟器；Android 经 ADB 重置应用与设备状态。随后写入任务专属数据并布置应用窗口。
- **跨端工作流采用单屏设计**：Ubuntu/Windows 桌面通过 **scrcpy** 显示伴生 Android 设备，智能体仅用鼠标键盘在同一交互面上操作两台设备并自行传输文件；**任何调用或输入 `adb`/`scrcpy` 命令的行为判为失败**。

### 2.4 观察空间
- 三种模式：**仅截图**（主实验设置）、仅可访问性树、截图+树组合。
- 截图默认桌面 1920×1080、移动端原生分辨率；支持改分辨率以防像素记忆。
- 可访问性树被归一化为统一节点 schema（id、类型、可见文本、选择器、enabled/focused 标志、包围盒），但仅作为诊断/消融通道，不作“特权 oracle”。
- 终端输出为可选辅助通道，不属主协议。

### 2.5 动作空间（两级设计）
- **基础层（平台无关语义）**：指针、键盘快捷键、文本输入、滚动、拖拽、触摸手势、`WAIT`、`DONE`/`FAIL`。
- **执行层（原生后端映射）**：桌面用 PyAutoGUI 沙箱 / Windows、macOS 运行时调用；Android 用 ADB；iOS 用 Appium/XCUITest。
- 两套对外接口：
  - **自由形式 PyAutoGUI 代码块**（token 省、与 OSWorld 基线可比）；沙箱仅允许 `pyautogui`、`time`、简单循环与 print，禁止 `os`/`subprocess`/`tkinter`、`pyautogui.screenshot()`、`locateCenterOnScreen`，防止绕过视觉操作。
  - **结构化动作 schema**（TAP / DOUBLE_TAP / LONG_PRESS / SWIPE / DRAG / SCROLL / TYPE_TEXT / KEYBOARD / HOTKEY / CLIPBOARD / ALERT / SYSTEM / LAUNCH_APP / WAIT / DONE / FAIL），适合 tool-calling、约束解码与 RL 训练；target 可为绝对像素、归一化坐标或 a11y 节点 ID。
- 每步要求模型先给**简短反思**，再给一个可执行动作块。

### 2.6 评估器设计
- 统一 `BaseEvaluator` 接口，返回 `PASS / FAIL / UNDETERMINED / ERROR` + 结构化 metadata。
- 三阶段流水线：**getter**（取回文件、应用数据库、profile、本地服务响应、模拟器容器、设备存储）→ **normalize**（解析为工作簿单元格、文档段落、日历事件、购物车条目、交易记录等结构化记录）→ **task-specific predicate**（比对 YAML 规格，输出具体 mismatch）。
- 支持“补充检查”（Windows 的 PowerShell/文件检查），以及**手动核验协议**处理确定性评估器无法覆盖的歧义情形。

### 2.7 任务标注流水线（五阶段）
1. 基于真实使用经验的**任务设计**（指令+初始化+评估器）；
2. **独立复核**（可行性、歧义、期望结果是否可判）；
3. **跨平台难度校准**（比较人类步数，修订差异过大的任务）；
4. **Oracle 执行验证**（跑通 oracle 轨迹，确认初始化器与评估器一致）；
5. **失败态测试与终稿修订**（验证错误解被正确拒绝）。
- 人力投入：30 名计算机方向研究生、约 2 个月、**约 2,400 人时标注 + 400 人时复核**。

### 2.8 受控应用（Open 系列，18 个）
- **跨平台消费类 9 个**：OpenNote、OpenShop、OpenTwitter、OpenBank、OpenDriver、OpenTrip、OpenFood、OpenNavigation、OpenPhotoEdit。
- **Web 端专业类 9 个**（运行于 Ubuntu VM 的浏览器）：OpenDoc、OpenSheet、OpenSlide、OpenMail、OpenFinance、OpenCode、OpenBlender、OpenWireshark、OpenZotero。
- 设计原则：**固定种子数据、确定性业务日期（如 OpenBank 以 2026-06-01 为“今天”）、持久可检查状态、业务事件记录（可检测重复提交）、跨端共享同一数据模型**。
- **v1 中 180/300 任务（60.0%）依赖 Open 系列**。

## 3. 实验设计

- **基准规模（v1）**：300 任务 = Windows / Ubuntu / macOS / iOS / Android / Web 各 **48** + **12** 个跨端工作流（6 组 Ubuntu+Android、6 组 Windows+Android）。
- **任务构成**：日常类 138（46.0%）、专业生产力 59（19.7%）、跨应用 53（17.7%）、Web 50（16.7%），细分 34 个二级类目。
- **评测模型（9 个）**：GPT-6-Astra、Claude Opus 5.5、Gemini 4 Argon、GLM-5.3-753B、Kimi K3、Qwen 3.8 Max、Qwen 3.8 27B、Qwen 3.8 9B、DeepSeek V4.1 Flash。
- **人类基线**：具备基本软件使用技能、此前未接触任务的人类被试，使用**与模型相同的初始化器与终态评估器**，记录步数与耗时。
- **默认执行配置**：仅截图观察、平台控制器动作、历史窗口 3 步、300 步上限、180s/步。
- **指标**：各平台成功率 + **Macro-Avg（7 列等权）** + **Micro-Avg（300 任务等权）**。
- **分析维度**：跨平台不均衡性、跨应用难度、跨端工作流难度、四类错误归因（视觉定位、语义理解、长程状态跟踪、持久化、时序/模态、输入语法、跨端传输、基准系统故障）、以及端点级错误案例（OpenBank 重复转账、OpenTrip 五次预订重复/遗漏、DeltaChat 消息顺序错误、Thunderbird 日历重复创建、OpenSlide 评论重复导致 300 步耗尽等）。
- **对比对象**：主要以**人类参考**与**模型之间**横向对比为主，并与 OSWorld（步数、耗时）及图 3 中的既有基准在平台覆盖、应用数量、跨平台/跨应用流程、受控应用维度上做定性比较。

**充分性与公平性评估**
- **优点**：人机使用同一初始化与同一评估器，比较口径较公平；oracle 验证 + 失败态测试提升了评估器可信度；报告规范（附录 D.5）要求区分“任务失败”与“基础设施失败”，并列出 invalid-run rate、超时率、成功任务平均步数等字段，方法学意识较强。
- **不足**：
  - **未报告重复运行次数、方差或置信区间**，单次采样下的 ±1 任务差异（尤其跨端 12 任务，每任务值 8.3 个百分点）难以支撑细粒度排名。
  - **跨端通道统计效力弱**（仅 12 条），作者自己也提示“应谨慎解读”。
  - **人类研究细节缺失**：被试人数、是否跨平台同一批人、学习效应控制、耗时统计的方差均未给出。
  - **模型侧超参未披露**（温度、最大输出、重试策略、不同厂商的推理预算），存在“实现调优不对等”的风险。
  - 指标敏感性明显：Macro-Avg 下 Claude Opus 5.5 领先，Micro-Avg 下 GPT-6-Astra 反超（67.0% vs 66.7%），说明结论对聚合方式敏感，文中虽作解释但未给出统计显著性检验。
