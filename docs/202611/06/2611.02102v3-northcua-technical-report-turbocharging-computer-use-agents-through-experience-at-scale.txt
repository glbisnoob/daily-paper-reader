Turbocharging Computer-Use Agents through Experience at Scale
NorthCUA Team, Shanghai Qiji Zhifeng Co., Ltd.
ABSTRACT
Scaling computer-use agents from individual actions to complex software work requires experi-
ence that connects decisions to complete outcomes. We present NorthCUA, an integrated system
for turbocharging computer-use agents through experience at scale. Its Experience Flywheel
supplies diverse executable tasks to the NorthCUA Harness, which sustains long interactions,
records decisions, and checks task outcomes. The Flywheel uses these records to curate veri-
fied trajectories. For unsolved tasks, recursive self-improvement evolves reusable skills and pre-
serves verified milestones so later attempts build on earlier progress. Staged Learning combines
this experience with grounding data from the Flywheel to develop GUI competence through
mid-training and long-horizon supervised fine-tuning. The policy then learns from fresh at-
tempts in the same Harness through joint desktop–web reinforcement learning, closing the loop
between experience production and policy improvement. The resulting Nano, Mini, and Pro
family achieves state-of-the-art results among open-source models across GUI grounding, desk-
top execution, and Web interaction under the reported evaluation settings (Figure 1). For more
responsive Web workflows, NorthCUA-Ultrafast pairs direct action selection with open-ended
generation on pre-RL Nano, offering a measured quality–latency tradeoff. Together, these ad-
vances establish NorthCUA as a high-performing model family and a reusable foundation for
agents that carry complex software work from intent to completion.

Introduction
Computer-use agents (CUAs) extend the capabilities of large language models from generating
responses to operating computers and automating software tasks (Zhang et al., 2025b, Wang
et al., 2025b). They can invoke software functions through application programming interfaces
(APIs) and command-line interfaces (CLIs). Graphical user interfaces (GUIs) extend this ac-
cess to functions that applications do not expose programmatically, providing a critical last mile
for software automation (Zhang et al., 2025a,c). Through GUI interaction, agents interpret the
screen and translate natural-language goals into mouse and keyboard actions. Advances in vi-
sual grounding and action generation have expanded the range of operations these agents can
perform (Qin et al., 2025, Wang et al., 2025c, Zhou et al., 2025). As agents combine these oper-
ations into longer workflows, earlier actions shape the software state on which later decisions
depend. Reliable completion requires agents to preserve intermediate progress and the user’s
constraints, adapt to changing interfaces, and recover from errors while keeping the overall goal
in view (Zhang et al., 2026, Lu et al., 2026).
Training agents to coordinate such workflows therefore requires experience that develops pre-
cise interface skills and connects successive decisions to complete task outcomes. Obtaining
this experience at scale begins with constructing varied tasks, each of which needs a request
grounded in available software and content, a usable initial environment, and a reliable way to
judge success (Ge et al., 2026, Zhou et al., 2026b). Once these tasks are available, collecting ex-
perience from them requires an agent framework that sustains long interactions and records de-
cisions and outcomes across desktop and web environments. The resulting demonstrations can
teach the policy how to complete workflows, but independent execution may lead it into states
absent from those demonstrations. Continued improvement therefore requires fresh interaction
and outcome feedback from the policy’s own attempts (Wang et al., 2025c, Jung et al., 2026, Lu
et al., 2026). Meeting these linked needs calls for co-designing how tasks are constructed, how
agents execute them, and how the resulting experience is used for learning.
We present NorthCUA, an integrated system for turbocharging computer-use agents through expe-
rience at scale. Our central idea is to co-design the production and use of experience, making
software interaction a continuing source of learning. We connect executable tasks to policy up-
dates through three components (Figure 2), focusing on GUI-based software operation. The
Experience Flywheel constructs executable tasks for the NorthCUA Harness to run and assess.
The recorded trajectories and outcome evidence guide curation, supplying Staged Learning
with demonstrations that complement the Flywheel’s separately constructed grounding exam-
ples. This mixture develops interface understanding and workflow completion. Shared exe-
cution and outcome interfaces also let the learner collect fresh attempts from the policy itself,
extending the same system from demonstration collection to continued policy improvement.
NorthCUA Harness: full-lifecycle infrastructure. We design the NorthCUA Harness as full-
lifecycle infrastructure that executes software tasks and turns the resulting attempts into in-
spectable experience for learning. This requires keeping the agent’s decisions connected to
its workspace and outcomes, from environment preparation through execution and evalua-
tion to record preservation. Within the shared runtime, visual context and task memory help
agents build on progress across long workflows (Zhang et al., 2026, 2025d).

Staged Learning: from experience to capability. A model’s ability to coordinate a long work-
flow builds on familiarity with the interfaces and operations it uses. Staged Learning follows
this progression, starting with Broad GUI mid-training on grounding examples and desktop and
web trajectories judged to complete their tasks (Wang et al., 2025c, Jung et al., 2026). The broad
trajectory corpus spans over four million GUI interaction steps across dozens of applications.
Building on this operational foundation, Verified long-horizon supervised fine-tuning (SFT) concen-
trates on carefully selected, complete workflows whose outcomes pass executable task verifiers
and whose intermediate results support later decisions. Independent execution can still lead the
policy into states absent from its demonstrations. Joint desktop–web agentic reinforcement learning
therefore lets one policy practice in both domains and learn from fresh successes and failures.
Task verifiers score these attempts, and group-relative policy optimization (GRPO, Shao et al.,
2024) uses their outcomes to update the policy (Section 5).
Shared task, execution, and assessment interfaces connect these learning stages to experience
collection (Figure 2). An updated policy can return to the same Harness, where its new attempts
are evaluated and can be curated into subsequent training experience. This return path lets
advances in model capability support further collection, giving NorthCUA a reusable foundation
for continued learning across desktop and web environments.
The resulting NorthCUA family comprises Nano (9B), Mini (35B), and Pro (397B), all built
on Qwen3.5 (Qwen Team, 2026a). We evaluate this family on six benchmarks spanning GUI
grounding, desktop execution, and Web interaction. The suite follows the agent from locat-
ing controls to completing long workflows and checking whether Web applications behave
as intended.
NorthCUA establishes state-of-the-art results among open-source models in all
three domains (Figure 1). With 397B parameters, Pro outperforms trillion-parameter Qwen3.8-
Max and Kimi-K3 on both grounding benchmarks, OSWorld-Verified, and WebArena-Verified
(Qwen Team, 2026c, Kimi Team, 2026). The 35B Mini also surpasses Kimi-K3 on OSWorld-
Verified and Qwen3.8-Max on WebArena-Verified. Stage comparisons show desktop and Web
gains across all three model sizes after long-horizon SFT and joint RL (Section 6).
Long workflows also accumulate the latency of successive model decisions. To reduce this cost,
NorthCUA-Ultrafast adapts pre-RL Nano with a Jev-inspired choice head, selecting finite actions
directly while retaining generation for open-ended outputs (Almeida, 2026). Its Head + LoRA
variant completes matched successful WebArena-Verified tasks 2.3× faster on average than full
generation (Section 6.8). We release all three models, the full NorthCUA Harness code, and this
technical report, providing an open foundation for developing agents that carry software work
from user intent to completed outcomes.

System Organization and Experience Lifecycle
End-to-end computer use. An end-to-end task combines a user request, an initial software en-
vironment, and conditions for judging completion. The environment provides the applications,
files, and website records needed for the request. The agent observes the current state, takes
an action, and uses the resulting feedback to decide what to do next. Later decisions can use
information and results from earlier steps. The request and completion conditions stay fixed
throughout the attempt, so the final files or software state can be checked against the original
goal (Zhou et al., 2024, Xie et al., 2024). Figure 3(b) illustrates the two interaction settings:
• Desktop agents observe desktop screenshots and operate applications through mouse and
keyboard actions, including clicking, typing, scrolling, and dragging. Tasks may span mul-
tiple applications and files.
• Web agents observe webpage screenshots and document object model (DOM) informa-
tion, and interact through browser tools for navigation, element-based or coordinate-based
actions, text input, and tab management.
Both settings follow the same observation, action, and feedback loop, using their respective desk-
top or browser interfaces. The acting policy uses these interfaces to perform the task. Prepara-
tion, annotation, and evaluation can use additional programmatic tools with separate permis-
sions.
2.2 System Organization and Experience Lifecycle
The experience loop in Figure 2 connects task construction to execution and learning. Its hand-
offs specify how an executable task becomes an assessed record and then a training sample.
The Experience Flywheel packages each executable task as a CaseSpec, a task specification con-
taining the request, input materials, environment configuration, and setup instructions, together
with requirements for assessing the result. For the invoice task in Figure 3(b), this means pro-
viding the workbook and spreadsheet application and specifying that the exported PDF should
highlight overdue invoices.
Using this specification, the NorthCUA Harness prepares the environment, uploads input files,
and runs setup and launch commands before starting the agent on the request. Observations,
actions, and feedback are recorded throughout the attempt so that its outcome can be assessed in
the context of the work that produced it. Task-specific checks, an evaluator, or both inspect the re-
sult against the declared requirements. For the invoice task, this means checking the saved PDF
and its highlighted contents. These outcome and execution-quality assessments give the Expe-
rience Flywheel the evidence needed to select demonstrations. Valid tasks that remain unsolved
can instead enter the hard-task collection branch, where skill-guided exploration or milestone-
guided search produces further attempts for the same assessment process (Section 4.3).
Staged Learning turns this collected experience into capability in three steps. Broad GUI mid-
training combines diverse task trajectories with the Flywheel’s separate screenshot–query–target
examples, building a foundation in interface understanding and software operation. Grounding
supervision is used only in this stage. Verified long-horizon SFT then focuses on high-quality,
complete workflows with checked outcomes, teaching the policy to carry information and inter-
mediate results across dependent steps. This prepares the model to learn further from its own
interaction.
For joint desktop–web agentic reinforcement learning, we first select tasks on which the SFT pol-
icy’s trial attempts have different outcomes. This focuses initial collection on tasks with useful

NorthCUA Harness: Full-Lifecycle Infrastructure for Computer Use
The NorthCUA Harness provides full-lifecycle infrastructure for executing desktop and web tasks
and turning each attempt into inspectable experience for learning. During execution, a persis-
tent workspace and retained task context let the agent build on earlier progress. We retain its
execution record and resulting artifacts for outcome assessment, keeping the original environ-
ment available when live checks need to inspect the state the agent produced. Resources are
released after the required inspection and record preservation are complete. By carrying each
attempt through assessment and preservation, this lifecycle keeps decisions, outputs, and judg-
ments connected to the same task attempt (Section 2).
Figure 4 organizes this lifecycle at two levels. Within one task attempt, the unified agent run-
time (01) supplies the shared interaction loop and platform tool interfaces. Long-horizon sup-
port (02) operates within this execution, keeping the next decision informed while retaining the
complete trajectory. After acting ends, a tool-using evaluator (03) checks the declared require-
ments using that trajectory and the live workspace. The Batch Rollout Service coordinates the
parallel task lifecycles shown below. Each isolated environment proceeds through preparation,
execution, and assessment. Centralized control and recording manage these attempts, keeping
each workspace available through inspection and output capture. This distinction separates the
mechanisms that make one attempt inspectable from the service that turns them into sustained
experience production. Online RL reuses the execution and outcome interfaces under training-
side lifecycle management (Section 5.3), extending the same foundation from standalone collec-
tion to policy learning.
3.1 Unified Execution Across Desktop and Web
Desktop and web agents follow the same basic loop: observe the software, choose an action, exe-
cute it, and use the feedback to continue. What differs is how each platform exposes its state and
controls. Building on shared-runtime approaches to computer use (Zhang et al., 2026, Yan et al.,
2025), we design Agent Kit to separate this common loop from platform-specific observation and
action tools. Long-horizon support and evaluation reuse this same execution foundation.

results then inform the next decision. Common runtime services manage progress, budgets,

CUA execution also involves several timescales. Application and browser sessions persist across
actions, a user request can require many decisions, and each decision produces feedback needed
by the next. We represent these lifetimes through three nested scopes:
• Session maintains the agent’s execution state and associated software resources, such as a
browser session, across a sequence of user requests.
• Round tracks the processing of one user request, including its multi-step execution, budget,
and termination status.
• Step records one policy decision and the resulting tool execution and feedback. Each step
can contain multiple tool calls.
These runtime scopes organize interaction, while the task attempt supplies the collection-level
identity used to associate actions, artifacts, and assessment. Each recorded action retains its
request and session context, supporting task-level inspection and collection recovery. Session
resources are managed within the broader environment lifecycle coordinated by the collection
or training system. Appendix H.1 gives the execution-scope details.

3.1.2 Tool Integration and Dispatch
Desktop input, browser interaction, and workspace inspection expose different operations,
whose implementations may run beside the agent or near a remotely hosted application. To
make these capabilities available to the shared decision loop, we use a common tool interface
that allows their implementations to evolve independently.
Tool definitions describe operations and their arguments, while dispatch connects each call to
its implementation and returns the result to the requesting step. The Agent Kit integrates local
functions and tools exposed through Model Context Protocol (MCP), whose standard tool de-
scriptions and invocation messages support capability discovery and execution (Model Context
Protocol, 2025). Both paths feed the same interaction history and recording services. Platform-
specific controls can therefore be added through tool bindings while reusing task progression
and feedback handling.
To reduce the repeated inference overhead of long GUI workflows, we allow the model to is-
sue multiple action calls in a single response. The runtime executes these calls serially in the
specified order, allowing actions that can be planned together to share one model invocation.
For computer use, tool feedback also needs to describe the state after an operation. Post-action
observation hooks attach fresh screenshots or page observations to state-changing tool results,
giving the next decision a current view of the interface. Section 3.2.1 develops this action-aware
feedback design. The same tool separation supports centralized agents operating remote de-
vices, whose collection lifecycle is described in Section 3.4.
3.1.3 Desktop and Web Instantiations
We build desktop and web agents on this runtime by supplying the observations, tools, and
execution context appropriate to each platform. Table 1 compares the two instances along these
interfaces:
• Desktop agent. The agent uses desktop screenshots to observe applications and mouse
and keyboard tools to click, type, scroll, and drag. Its platform adapter manages the active
application, foreground window, and input focus so that an action reaches the intended
control. This supports workflows across application windows and files, with screenshots,
action results, and output artifacts retained for later assessment. Appendix H.2.1 lists its
actions and parameter schemas. Appendix J.2 follows a recorded animation task in which
these same desktop actions open a terminal, enter scripts and return to the presentation
UI for playback checks.
• Web agent. The agent observes page screenshots together with DOM-derived information.
Browser tools support navigation, element-reference or coordinate-based actions, form en-
try, and tab operations. Its adapter maintains the active tab, page state, and element refer-
ences as navigation changes the interface. The resulting record includes page observations,
action results, and browser artifacts. Appendix H.2.2 specifies the corresponding browser
tools and argument constraints.
The adapters handle these platform differences, while both agents reuse model invocation, re-
quest progression, context management, and trajectory recording.

3.2 Sustaining Long-Horizon Interaction
Long-horizon execution is a central challenge in practical computer use. Real software work
can require many fine-grained GUI operations across applications, files, and intermediate ar-
tifacts, with later actions depending on earlier discoveries and decisions (Yuan et al., 2026).
Editing a document may still require a value read from a spreadsheet and an output require-
ment encountered much earlier. Meanwhile, repeated visual observations and tool feedback
enlarge the history supplied to each decision (Lu et al., 2026, Lv et al., 2026). Sustaining these
workflows requires controlling context growth while keeping current state, earlier progress, and
task-relevant knowledge available for continued action.
We separate the decision context presented to the model from the complete execution record retained
for inspection and learning. To keep later decisions informed within a limited context budget,
we design three complementary mechanisms: action-aware visual context for recent states and
operations, task-preserving compaction for earlier progress and remaining work, and structured
working memory for facts and decisions the agent chooses to retain. Figure 5 follows one invoice
workflow across these mechanisms. The visual window shows the steps leading to export, the
summary keeps export marked as pending, and an agent-written note carries the overdue total
into the report. Each view supplies information needed for continued action without replacing
the full execution record.

3.2.1 Action-Aware Visual Context
Repeated GUI interaction produces an image-heavy history whose size grows with the workflow
(Lu et al., 2026). Its visual content serves two related purposes: the current screen guides the
next action, and recent states help the agent interpret what it just did. The resulting screen
alone can leave the location of a preceding click or the path of a drag unclear, particularly after a
window or page changes. Visual context therefore needs to preserve both current state and the
spatial meaning of recent operations within a limited image budget.
We use a sliding window to provide a bounded visual history of up to k recent frames, includ-
ing the latest clean screenshot. Textual action and tool-result history survives image eviction,
retaining a longer account of the interaction until the text-history policy calls for compaction.
To keep the newest frame current, post-action observation hooks supply fresh post-action feed-
back alongside state-changing tool results. The next policy invocation receives this screenshot
directly, avoiding a dedicated model turn solely to request the resulting screen.

Text and key badges record operations that are less clear from a spatial marker alone. Figure 6

next decision. Replacing an earlier clean frame with an overlay changes the image history. The
training-segment rule in Section 5.3.3 preserves the input seen before that change.
This bounded visual history preserves both the spatial meaning of recent actions and the current
interface state. The textual record continues to accumulate across these visual windows, creating
the next context-management challenge.

budget. Context-management methods consolidate long histories to retain useful information

preserving compaction around three priorities. When older history needs to be summarized, we
preserve the immediate action–feedback context, retain task progress, and avoid carrying stale

• Protect current interactions. The task request, latest GUI observation, and latest few steps

• Summarize task progress. The summary organizes goals, constraints, supported facts,
decisions, completed and failed work, current state, open items, and artifact references
around task continuation. Desktop and web profiles instruct the summarizer to retain
semantic software state and observed effects while condensing routine navigation. For
example, an extracted spreadsheet value, its source file, and a pending export requirement
can therefore remain available after the navigation history is compressed. The instructions
also distinguish issued actions, observed effects, and unresolved completion claims: an
export command and an observed saved file represent different evidence about progress.
• Handle transient GUI locators. Coordinates and element references can become stale after
a page update or application switch. The summary-input projection filters these volatile
fields, and the summary instructions exclude old locators from current executable state.
The retained current observation remains available for grounding subsequent actions.
Later compaction updates the existing summary with newly eligible history, with source refer-
ences available for inspection. This gives continued work a compact account of its dependen-
cies while keeping the full execution record available for outcome assessment. Alongside this
budget-triggered consolidation, the agent can actively preserve important information as it is
discovered.
3.2.3 Structured Working Memory
During a long task, an agent encounters information with clear future value: a figure read from
another file, a requirement for the final deliverable, an unsuccessful approach, or a plan for
remaining work. Assistant messages can mention these details in the chronological history,
where their later visibility depends on history retention and summarization. Giving selected
information an explicit working-memory representation lets the agent decide what to retain
and revise during execution, following the broader principle of agent-controlled memory man-
agement (Packer et al., 2024).
To let the agent preserve useful information when it discovers it, we design a dedicated text-only
note tool. The agent can call this tool proactively to record a spreadsheet value before switching
to a document, or to preserve a correction while revising an unsuccessful approach. The right-
hand panel of Figure 5 shows this transfer: note N1 records the overdue total from the workbook
for later use in the report. Notes are stored independently of the history summary and can be
presented in subsequent decision contexts. This complements compaction: a summary consol-
idates accumulated work under budget pressure, while a note explicitly preserves information
the agent expects to use again.

3.3 Agentic Outcome Evaluation
Selecting GUI trajectories for learning requires accurate outcome judgments across a growing
variety of tasks. Dedicated verifiers become diﬀicult to write and validate when correctness
depends on content, presentation, or application-specific state (Rosset et al., 2026). We there-
fore use an adaptive evaluator that interprets the declared task requirements and gathers the
evidence needed to assess the work. Figure 7 shows how recorded work and active inspection
together support an evidence-linked assessment.
We build the evaluator as an agent-as-a-judge (Zhuge et al., 2025), reusing Agent Kit tools. Af-
ter the acting phase ends, it selectively retrieves saved records and artifacts and can inspect the
original workspace using authorized shell, GUI, and browser tools. It adapts its inspection to
each requirement and seeks further evidence when the available observations leave the outcome
unclear. This combines reusable inspection capabilities with task-specific judgment, extending
assessment to requirements that lack dedicated executable checks. Task-grounded rubrics guide
this process, and multidimensional reports connect the findings to experience selection and fail-
ure analysis. In Figure 7’s export example, the evaluator checks that the PDF exists and opens
it to compare its contents with the source. This artifact inspection supplies the evidence for its
final report. We require this report to associate each criterion-level judgment with its evidence,
uncertainty, and evaluator operations.

• Recorded evidence. Retrieval tools expose selected steps, screenshots, tool results, and

3.3.2 Task-Grounded, Multidimensional Rubrics
The value of a GUI trajectory depends on both its result and the behavior it demonstrates. Suc-
cessful attempts can contain unnecessary detours or unintended changes, while an attempt
blocked late by the environment can contain useful completed subtasks. Data curation there-
fore needs answers to two complementary questions: (i) which task requirements were fulfilled, to
establish what the trajectory accomplished, and (ii) how the agent performed the work, to assess
the behavior available for learning. We therefore design the rubric to combine task-grounded
acceptance criteria with multidimensional execution assessment (Rosset et al., 2026).
For task fulfillment, the request and declared acceptance conditions define the intended out-
come. The rubric expresses these obligations as specific, individually checkable questions. Ex-
port tasks may require the right contents, destination, and format. Explicitly required proce-
dures also form part of acceptance. Request-derived criteria are generated before scoring the tra-
jectory, with the original task requirements governing their interpretation. Assessing these obli-
gations individually identifies complete, partial, and unresolved fulfillment, including which
requested subtasks have supporting evidence.
For execution assessment, the report records process quality, eﬀiciency, side effects, and fail-
ure diagnosis alongside judgment uncertainty. These dimensions explain the path taken to the
result: repeated ineffective actions may reduce its value as a demonstration, while a success-
ful recovery can provide useful behavior to study. Failure diagnosis distinguishes agent errors
from environment blockers, and uncertainty identifies judgments that need further checking.
Findings are linked to the relevant requirements and recorded steps so that their scope can be
inspected. Table 2 summarizes the dimensions and their uses.
Together, the rubric and execution report describe both the result achieved and the behavior that
produced it. Their links to specific requirements and recorded steps make the judgments use-
ful for selecting complete demonstrations, reviewing local segments, and analyzing recurring
errors.

3.4 Reliable Batch Rollout at Scale
The preceding mechanisms turn one task attempt into assessed experience. Producing a large
training corpus requires many such attempts to run in parallel, each with its own software state.
Their preparation, GUI execution, evaluation, and recording take different amounts of time and
consume different resources (Xie et al., 2024, Yuan et al., 2026). Simply launching more agents
can therefore create a backlog at another stage, while an interruption after execution can leave
useful work without a complete record.
To support eﬀicient large-scale collection, we design a Batch Rollout Service that coordinates
the entire task lifecycle. Following the environment-lifecycle perspective also explored in Peng
et al. (2026), we combine centralized agent control with isolated workspaces, prepare upcom-
ing tasks alongside ongoing execution, and manage load and recovery through record delivery.
Figure 8 shows the two relationships behind this design. Panel (a) connects one controller to in-
dependent device workers. Panel (b) shows how their lifecycles overlap: the same-time marker
crosses evaluation, execution, and preparation in three different attempts. The service coordi-
nates this concurrent work so that completed attempts produce usable experience records.
3.4.1 Remote Execution with Centralized Agent Control
As collection grows, prompts, model settings, and agent logic continue to change. Placing that
logic inside every task environment would require updating those environments whenever the
agent changes. We therefore separate centralized agent control from device execution, as
shown in Figure 8(a):
• Centralized controller. One service manages multiple agent runners and their device
workers. It maintains prompts and agent configuration, assembles context, invokes the
model, and dispatches actions.
• Device worker. Each worker runs inside one task’s isolated sandbox. It executes tool calls
and captures observations from that environment. The worker starts with its sandbox and
ends when the sandbox is released.
The controller maintains a long-lived WebSocket connection to each worker, sending actions
and receiving observations over the same connection. Related distributed device orchestration
appears in Zhang et al. (2025d). Here, each runner communicates with the worker assigned to
its task, keeping the concurrent attempts separate.
This division lets us update compatible prompt and model configurations centrally for later
batches while reusing the same device-worker implementation and software templates. The
device layer remains focused on observation and tool execution, so routine agent changes do

3.4.3 Completion-Oriented Scheduling and Recovery
Preparation, execution, and evaluation progress at different rates. Independent admission can
leave prepared environments waiting for execution or completed attempts waiting for evalua-
tion. We coordinate admission with two controls. Stage-specific concurrency limits bound the
number of attempts admitted to each stage. Because resource demand can vary within these
limits, controller-pressure feedback slows new admissions when the shared controller remains
busy. The first control limits local demand, while the second responds to load across the con-
current attempts.
When a connection is lost or a downstream process fails, we first check whether the affected
attempt is still running or has completed. Completed execution records can support retries of
record-based evaluation or artifact processing, preserving the work already done. If the task
itself needs to be rerun, we start it in a fresh environment.
Before delivery, we check that the required trajectory, observations, and assessments are com-
plete and linked to the same attempt. Appendix H.3 gives the configuration and recovery details.

foundation to construct tasks and curate the resulting records for model training.

4.1 Single-Step UI Grounding
Single-step grounding takes a screenshot and a natural-language query, then predicts the loca-
tion of the requested control (Cheng et al., 2024). Each training example contains a screenshot,
a query that identifies a visible control such as a button or toolbar icon, and the control’s coor-
dinate in the original image. The main construction challenge is to write queries that identify
the same control across different visual states and ways of describing an operation, especially
in specialized applications (Lu et al., 2024, Li et al., 2025a).
We construct these examples through two complementary routes:
1. Broad visual and structural coverage. We use screenshot evidence and available interface
metadata to describe visible controls across diverse applications and states (Figure 9).
2. Documentation-grounded functional localization. We retrieve application knowledge
when a control’s appearance leaves its function unclear, then use the matched function to
generate queries (Figure 10).
The first route expands interface and language coverage. The second fills gaps that visual ev-
idence alone leaves unresolved. Both preserve the target’s original location and produce the
same screenshot–query–coordinate format, so their candidates can pass through shared quality
and coverage checks.
4.1.1 Broad Visual and Structural Coverage
To obtain broad grounding coverage, we first need screenshots of varied interfaces, then a way
to turn their visible controls into language targets. We use the three-step procedure in Figure 9.
Panel (a) collects interface states, including states encountered during agent work. Panel (b)
associates one visible control with its appearance and original location. This target record gives
the query generator in (c) a fixed referent: it can vary how the control is described while keeping
the location label unchanged.
To collect these states, we combine public UI datasets, web-collected GUI screenshots, and
screenshots from agent trajectories, including real Linux desktop interaction. Trajectories con-
tribute intermediate states such as open dialogs, expanded menus, and partially completed
forms. We then use OmniParser, a screen-parsing system that detects interactive regions and
describes icons, to obtain candidate control boxes and descriptions (Lu et al., 2024). Accessibil-
ity annotations, when available for the same state, add control names and roles. These sources
provide complementary evidence for identifying a target. Visual parsing supports screenshots
collected without accessibility metadata, while names and roles help connect visible controls to
the language used in requests.
For each target, we consolidate this evidence into one control record that keeps the crop and orig-
inal image position together with the available name, role, color, appearance, and surrounding
context (Zhang et al., 2026). For the calendar example in Figure 9(b), the record identifies the
blue Week tab between Day and Month, together with a point inside its clickable region. The full
screenshot preserves the neighboring controls needed to make a description specific.

• Correctness check. Geometry checks confirm that the point lies inside the annotated

4.2.1 Scaling Intents
Applications and working materials are readily available from software templates, public file
collections, and websites. However, these resources do not come with a varied set of natural
user requests grounded in their contents and capabilities. We design Scaling Intents to generate
such requests from the operations the software supports and the content already present. This
grounding gives the requested work concrete subjects and feasible actions, while variation in
goals and phrasing broadens the collection. We first describe desktop base tasks, then extend
the construction to dependent long-horizon workflows and web content.
Desktop base tasks. For a desktop base task, we need to connect a supported software opera-
tion to material on which it makes sense. Figure 13 illustrates the three steps used to generate
the request. We first choose an application and one of its supported functions. That choice es-
tablishes the requirements for selecting a compatible source file. The selected file’s content then
supplies the facts from which an LLM writes a grounded request. Once the request is defined,
we prepare its starting workspace and assessment to form the complete task shown in the lower
panel.

Select a function. We begin with E2B templates that provide installed applications and their

Match a file. To supply these inputs, we collect tens of thousands of files from public and open
resources and supplement them with agent-generated materials (Ge et al., 2026). We index

values or document text excerpts. With the function selected, we use its format and material re-

within the construction run, and the selected files’ summaries become inputs to request gener-

source file.
Write the request. We give an LLM the selected function and file summaries, together with
a persona describing the user’s role and motivation (Jung et al., 2026). The function fixes the
operation, and the summaries identify the concrete subjects, fields, and values to which it can be

expresses the need.

where the harness should place the selected files in the sandbox, which software template and
dependencies to use, and which application or document to open before the first action. In
the example, opening the workbook in Calc makes “the open spreadsheet” an unambiguous
reference. Tasks involving several files instead identify them by name or workspace-relative
path.

Plan the workflow. We encode recurring workflows as scenario blueprints, each defining a final
deliverable, candidate stages, their applications and materials, and their prerequisites. For the

preparing the same delivery package.
For each instance, target task length, application coverage, and desired interaction challenges
guide the choice of a blueprint and a compatible stage combination. We favor less-used scenarios
and components, then use seeded sampling among eligible combinations to vary the work. A
combination is retained when its prerequisites are present and every selected stage contributes,
through its dependencies, to the overall workflow goal. Operation variants further specify the
requested result, such as requiring the PDF’s text to remain searchable.
We represent the selected workflow as a directed acyclic graph (DAG), a planning abstraction
also used for cross-device orchestration in UFO3 (Zhang et al., 2025d). Here the graph speci-

approved content, and may require several GUI actions. Edges can express use of earlier infor-
mation or artifacts, or a required execution order. We retain the blueprint’s dependencies and,
when constructing longer workflows, add precedence between selected stages that use shared
facts.

update before PDF production, shown by the dashed C-to-D edge. This edge specifies workflow
order, while the updated record remains a separate deliverable with its own check.
Before preparing the materials, we check the assembled plan for cycles, missing prerequisites,
and inconsistent production or use of files. The checked plan associates each stage with its
application, required inputs, and expected output, so material preparation can follow the de-
pendencies of the workflow.
Ground the workflow in materials. The DAG specifies what each stage should accomplish, but
its nodes still need concrete information to operate on. We ground each node by selecting or gen-
erating the files and service records required by that subtask. Existing-file selection follows the
same principles as base-task selection, matching application support, file format, and content.
Long-horizon construction also considers whether the selected files belong to a shared project
or directory and whether their contents support the relationships between stages. File sum-
maries supply the names, values, and other details used to specify stage goals and acceptance
conditions.

them in the files or records the agent will inspect. The oﬀice sample follows this path in Fig-
ure 14(2). The approved document supplies a value that the final PDF should include, while
the older deck contains obsolete wording that the PDF should exclude. The business record
supplies the initial state for a reconciliation update. Each material therefore has a role in both
the work stage and its outcome condition. The example requires two results: the PDF and the
updated record.

4.2.2 Scaling Environments
Scaling Intents uses the workspaces already available to generate new requests. Sourced re-
quests offer a complementary resource: they describe useful work, but often omit the files, de-
pendencies, or application state needed to execute it. Reference websites and software issues
likewise describe interactions without necessarily providing an isolated environment for collec-
tion. We design Scaling Environments to build these missing execution conditions. For desktop
requests, this means preparing the files and applications assumed by the user. For Web tasks,
we collect open-source frontends and reconstruct workflows from public URLs to create local
environments that we can initialize and reuse. We also develop repository-based frontend test-
ing as a distinct web-agent application, where a runnable project lets browser interaction test a
candidate code repair.
Desktop environments. Forums contain user-reported software problems, while tutorials and
help resources describe practical workflows and their intended results (Wang et al., 2025b).
These sources provide goals grounded in software use, but their descriptions often assume at-
tachments or workspace state that the collector does not have. We collect tens of thousands of
such requests and task seeds from forums, wikiHow, and help resources. The construction prob-
lem is then to supply the inputs and startup conditions each seed assumes while preserving the
work it asks the agent to do.
We therefore design an environment-building agent, EnvAgent, to interpret each request and
prepare its input files and startup plan. Figure 15 illustrates three construction steps. The
agent first retrieves and reads candidate files to establish which requirements are already sup-
ported. Any missing inputs then guide file generation, using the retrieved material to keep
related records consistent. With the inputs available, the agent specifies the request and startup
plan and checks that they agree. A failed check returns the affected input or instruction for re-
vision before the package becomes a CaseSpec. The order-comparison example below shows
how the retrieved and generated materials contribute to the same task.
Prepare the input materials. EnvAgent uses the request and selected software template to iden-
tify the applications and inputs the task needs. Comparing orders and shipments, for example,
requires two tables that refer to the same orders, with a shared identifier through which their
records can be matched. A request restricted to a particular month also requires the correspond-
ing date information. We reuse the indexed file formats and content summaries from Scaling
Intents to locate candidates, using project and date information to find related tables. EnvAgent
then reads their records to confirm that the identifiers refer to the same orders and that the files
contain both shipped and outstanding orders for the comparison. If the retrieved materials meet
the input requirements, the agent proceeds to request and startup specification. Otherwise, the
unmet requirements guide generation.
Figure 15(2) shows an example of this step. Given a suitable order table but no matching ship-
ment table, EnvAgent uses file tools and reusable construction skills to create a shipment table
with matching identifiers and business context. The resulting input set gives the requested com-
parison concrete files to operate on.

Our URL-to-environment construction builds on WebAnything (Xie et al., 2026) and follows
the four steps in Figure 16. We first explore the reference to identify the required pages and
behavior. Those observations guide construction of a local interface connected to backing state.
Once it runs, browser tests check the interactions and return discrepancies for repair. We then
restore the intended starting data and package the checked site for task collection. These steps
turn an external example into an interactive environment with controlled initial conditions.
The builder begins at the reference URL and explores the workflows selected for reconstruction,
retrieving relevant pages and accessible frontend assets. For record editing, this covers the list
page, detail view, editing controls, and navigation between them. An existing request can fur-

and what each interaction should do.

actions also specify the backend behavior to reproduce. When the reference’s backing data or
implementation is unavailable, the builder creates a local schema, initial records, and update
logic for the observed workflow. In the record-editing example, the list and detail views refer

reconstructed controls to these state changes makes the workflow available for actual browser
interaction. If construction raises questions about a page or control, the builder returns to the
reference site for targeted inspection before continuing the implementation.

with the reference and the effects of its controls. For the illustrated check, it opens a record,
edits and saves it, and refreshes the page to inspect the stored value. An unreachable detail page
leads to a navigation repair, while a lost update leads to a correction of the backend state change.

Testing the task and its verifier. Each rewritten task undergoes two complementary checks

prepared state. Verifier probes examine whether the checker judges known outcomes as the
task requires. The lower part of Figure 19 keeps these two sources of evidence separate.
For the execution trial, we run a CUA from the declared initial state with the rewritten request.
Its interaction and resulting state reveal problems such as missing inputs, unreachable controls,
or instructions inconsistent with the workspace. These findings identify which setup or request
needs repair.
To test the verifier itself, we construct outcome probes whose expected verdicts follow from
the request and starting data, then compare those verdicts with the verifier’s outputs. In the
approval-and-export example, a complete result should pass, whereas an otherwise correct up-

changes to protected records, and allowed alternative outputs. A disagreement identifies a
checker rule to revise, even when the GUI task itself can be completed.

the revision, we rerun the affected tests against the same intended requirements before admit-

meaningful outcome assessment.

4.3 Recursive Self-Improvement for Hard-Task Collection
The routes in Section 4.2 supply executable tasks whose rollouts provide experience for learning.
During collection, however, we encounter long and diﬀicult tasks that remain unsolved within
the ordinary budget. Collecting demonstrations of sustained planning and recovery from these
tasks requires addressing two recurring obstacles. Repeated attempts can lose useful discov-
eries and repeat ineffective procedures. A late failure can also force a new attempt to rebuild
substantial earlier work.

We design two recursive self-improvement (RSI) pipelines for collecting experience from these
tasks. Each carries forward the information needed to address one of these obstacles.
• Knowledge accumulation. Skill-guided recursive exploration turns trial-and-error find-
ings into tested procedures that guide subsequent attempts (Figure 20).
• Progress accumulation. Milestone-guided trajectory search preserves completed work
and resumes exploration from the corresponding software state and agent context (Fig-

Both use feedback from earlier trials to shape later exploration (Zhu et al., 2026). They target
tasks that pass construction checks but remain unsuccessful in ordinary collection. The original
acceptance conditions stay fixed. We check the completed task before admitting an assisted tra-
jectory as a full-task demonstration. Milestone-guided collection can also retain verified subtask
traces from attempts that leave the full task unfinished.
4.3.1 Skill-Guided Recursive Exploration
Some GUI tasks require a procedure that the agent has not discovered. The diﬀiculty may be
an unfamiliar application command, a hidden prerequisite, or a sequence whose useful effect
becomes clear only after trying it and inspecting the result. Repeated attempts can make par-
tial discoveries, but those discoveries remain scattered across their histories unless the collector
carries them forward. We therefore need a way to turn trial-and-error experience into reusable
operating guidance.
We design a skill-guided loop with four stages, shown in Figure 20. Task-directed exploration
first produces observations about useful operations and unresolved obstacles. A skill creator
then reviews that experience and consolidates actionable findings into written guidance. A sep-
arate agent tests the candidate instructions before they are supplied to a new task attempt. That
attempt can use the validated procedure to make further progress, and its new discoveries feed
the next round of skill refinement. The loop accumulates tested knowledge across attempts
while retaining full-task verification for the final result.
Explore the task and identify obstacles. We use a computer-use agent to attempt the original
query in its prepared workspace. It inspects the relevant applications and files, tries controls,
and adjusts its action sequence as it observes their effects. An unsuccessful attempt can still
reveal an important prerequisite, an ineffective action to avoid, or a way to reach a previously
inaccessible state. Successful operations likewise show procedures worth retaining. We examine
these findings in the trajectory and result, using evaluator observations of the live state to help
identify the remaining obstacle (Section 3.3) (Shinn et al., 2023).
In the representative report workflow in Figure 20, exploration may reveal several export options.
One trial produces a PDF with all the required pages but represents their text as an image. The
searchability check then focuses further trials on which export settings preserve text. The initial
exploration has thus turned a broad completion goal into a specific procedural question that can
be tested in the application.
Consolidate a candidate skill. The skill creator reviews the accumulated trajectories and their
outcomes. When the useful procedure is still unclear, further exploration or focused practice
tests alternative operations. The creator turns the resulting findings into textual guidance that
states when the procedure applies, which actions to take, and how to check its intended effect

4.3.2 Milestone-Guided Trajectory Search
A long task can be diﬀicult to finish in a single attempt even when its individual stages are within
the agent’s reach. When a late failure ends an attempt, restarting from the initial state repeats
work already completed. This motivates a second RSI strategy in which collection focuses on
smaller, verifiable goals and retains the work that reaches them.
We design milestone-guided trajectory search to implement this strategy. We first decompose
the original task into dependent milestones and their checks. GUI attempts then work toward
one milestone at a time, saving the workspace and agent context when a check passes. Further
attempts restore that checkpoint to explore the next stage, following the principle of returning to
useful states for exploration (Ecoffet et al., 2021). After the final milestone, the original verifier
checks the complete result before the selected path becomes a full-task demonstration. Figure 21
illustrates how this process builds successful continuations on retained progress. It reduces the
work each trial needs to repeat while keeping acceptance tied to the original task. A construction
case in Section 4.3.3 follows this accumulation of progress from an empty Blender scene to a
complete collected trajectory (Figure 23).
Define milestones and their checks. We use a planning agent to read the user request and the
original verifier code, identify dependencies, and propose meaningful intermediate goals. Each
milestone pairs a subtask with a check on its observable result. The goal should represent useful
progress and leave a state from which later work can continue. Reviewing the pairs against the
original requirements ensures that local checks support the intended full task. This uses the
decomposition principle in Section 4.2.3, here to guide collection within one long task.
For the oﬀice workflow in Figure 21, the original goal includes updating a business record and
producing a searchable PDF. We organize it into three milestones: complete the record update
(M1), prepare the report (M2), and export the searchable PDF (M3). Their checks inspect the
corresponding records, document content, and output file. The executing agent receives the
permitted subtask guidance, while private verifier constants remain in the checking context.

5.2 Verified Long-Horizon SFT
Mid-training gives the policy broad experience operating software, including extended work-

final deliverable. We therefore continue from the mid-trained checkpoint with supervised fine-
tuning on selected long-horizon trajectories whose complete outcomes pass executable task ver-

and 310,000 GUI interaction steps.

work. In either route, a candidate enters this stage only after its final result passes the original
task verifier. Appendix D lists the source contributions that remain to be reported separately
from this aggregate cohort.

5.3 Joint Desktop–Web Agentic Reinforcement Learning
Mid-training and long-horizon SFT provide a policy that can recognize interfaces and follow
demonstrated workflows. To develop its ability further, we let it learn from autonomous interac-
tion. Its own choices determine which states it encounters, and task outcomes provide feedback
on whether those choices accomplish the user’s goal. We use agentic reinforcement learning to
connect this fresh experience to policy improvement (Qi et al., 2025, Lai et al., 2026).
We train a single policy jointly on desktop and web tasks. The shared runtime in the NorthCUA
Harness already expresses both as repeated observation, reasoning, and tool-based action, mak-
ing it natural to learn from them through one training loop. Platform-specific observations and
tools retain the differences needed to operate each interface. Task-specific verifiers then provide
outcome feedback for the work performed in either domain.
Figure 24 follows an attempt from task preparation to a policy update. The Task and Environ-
ment Manager selects executable cases and prepares their isolated workspaces and verifiers, giv-

attempts have been recorded and scored, the Experience Adapter pairs the model calls with their
task outcomes to construct training samples. These task-grouped samples let the Policy Learner
compare alternative attempts with GRPO and update the shared policy (Shao et al., 2024, Zhu
et al., 2025). Returning the new weights to the workers closes the loop, so subsequent interaction
uses the updated model. The following subsections explain how we select useful tasks, obtain
comparable feedback, and preserve executed decisions as that feedback enters learning.
5.3.1 Selecting Tasks with Outcome Variation
GRPO obtains its task-level learning signal by comparing the rewards of multiple attempts at
the same task. An attempt’s relative outcome determines its advantage within that group. If
all valid attempts receive the same terminal reward, their terminal group-relative advantages
are zero. Since GUI rollouts are costly, we first identify tasks on which the SFT policy produces
different outcomes, so initial collection can provide informative comparisons.

5.3.3 Preserving Executed Decisions for Learning
The rollout procedure provides complete attempts and their outcomes, but the learner must
also preserve the conditions under which each decision was made. Our harness maintains a
sliding window of recent screenshots and can compact earlier history. As a task proceeds, an
image may leave the window or a summary may replace earlier messages. Using only the final
history to train every response would therefore change the evidence available to some decisions.
Preserving the sampled input is also a central concern in harnessed agentic RL (He et al., 2026).
To accommodate this context management, we design the Experience Adapter around two
preservation rules. First, each response is learned with its recorded decision-time input, start-
ing a new training segment when the history no longer extends consistently. Second, those
segments retain the reward attribution and learning weight of their original complete attempt.
This matters because frequent context changes can split one attempt into more segments than
another. Figure 25 illustrates input preservation in panel (a) and attempt-level comparison and
aggregation in panel (b). Together, the two rules let the harness manage long histories without
turning a representation change into a different learning problem.
Preserve decision-time inputs. Training associates each response with the context that pro-
duced it. To preserve this association through context changes, we capture each model call’s in-
put, delivered response, generation log-probabilities, and behavior-policy version. The adapter
joins consecutive calls only when their text and ordered image histories form a confirmed pre-
fix extension under the same version. Image identity includes its content digest, so replacing
a clean frame with the historical action overlay from Section 3.2.1 also breaks this prefix. The
adapter starts a new segment from the captured input whenever images are replaced or evicted,
a summary rewrites history, or the behavior version changes.

5.3.4 Continuous Rollout and Policy Updates
Training from long GUI rollouts is costly even after the samples are correctly constructed. Over-
lapping screenshot windows repeat visual preprocessing and carry large tensors to the learner.
Meanwhile, task durations vary, so waiting for every active task before updating the policy can
delay the next learning cycle. We address these two costs separately: visual-delivery mecha-
nisms reduce redundant input preparation and transfer, while asynchronous coordination lets
policy updates proceed without restarting ongoing tasks.
Deliver visual experience eﬀiciently. Adjacent decision windows often contain unchanged
screenshots. Processing every window from scratch repeats work on those images. For a sup-
ported per-image processor, the Experience Adapter therefore reuses the preprocessing tensors
of unchanged images within an attempt and processes only new images. It reconstructs the
requested image order under the same processor settings. Changed images or settings require
fresh processing. The reuse saves CPU preprocessing while retaining every image in the model
input. The neural visual encoder still processes the complete visual input.
Large image tensors also add delivery cost after preprocessing. The object-store path supports
lossless tensor compression, retaining a compressed payload only when it is smaller. The learner
decodes the microbatch it is about to consume, recovering the same values, shape, and type.
Bounded CPU workers prepare samples, and group admission counts completed work await-
ing delivery so that preparation does not create an unaccounted queue. These mechanisms
target redundant processing and payload transfer while preserving the sample’s contents. Ap-
pendix E.4 describes the implemented reuse and transport paths, their configuration, and the
checks used to assess sample equivalence and delivery cost.
Coordinate policy updates asynchronously. In asynchronous mode, completed groups can
supply the learner while other workspaces remain active. To publish an update, the system
pauses new model calls, waits for calls already in progress, commits the new weights, and
resumes calls. Ongoing tasks keep their workspace and completed work, so later decisions can
use the updated policy.

6.2 GUI Grounding Results
NorthCUA achieves state-of-the-art grounding results among the systems compared in Table 6,
with Pro reaching 93.3% on SSP and 91.0% on OSWorld-G. The two benchmarks test comple-
mentary requirements, from locating small controls in dense professional interfaces to follow-
ing functional and spatial instructions. We report the final long-horizon SFT checkpoints, using
direct SSP inference and the Refined OSWorld-G instructions described in Section 6.1.
Claude Opus 5.5 is the strongest reference on both benchmarks in this comparison, scoring 88.1%
on SSP and 89.9% on OSWorld-G in our evaluation. Pro exceeds these scores by 5.2 and 1.1
percentage points, respectively. On SSP, Pro also leads Qwen3.8-Max’s reported 84.5% by 8.8
points. On OSWorld-G, it exceeds Nex-N2.5-Pro’s reported 87.4% by 3.6 points.
The smaller tiers retain much of this capability.
Mini reaches 92.4% on SSP and 87.9% on
OSWorld-G with 35B total and 3B active language-model parameters. Its SSP score is within
one percentage point of Pro. Nano reaches 72.9% and 83.0% with 9B parameters, with SSP accu-
racy close to GUI-Owl-1.5-32B-Instruct’s reported 72.9%. To understand what these aggregate
scores capture, we next separate geometric precision, control semantics, and target availability.
Broad coverage and fine localization. Mini and Pro both exceed 90% SSP accuracy in all six
application groups. Pro reaches 95.0% in CAD and 94.5% in scientific software. This broad
coverage also includes controls with little room for a coordinate error. To measure that diﬀiculty
directly, we pair the three models’ predictions on all 1,581 examples and group targets by size,
measured as the smaller of the target box’s width and height in the original screenshot (Table 7).
A target in the smallest group is less than 16 pixels wide or tall. On these narrow targets, accuracy
rises from Nano’s 53.4% to Mini’s 85.2% and Pro’s 92.1%. Pro’s 6.8-point gain over Mini is larger
than its 1.2-point gain on targets at least 32 pixels wide and tall. Its stronger aggregate result
therefore also extends to the smallest target regions in this breakdown.
Interpreting specialized controls. A small target must also be matched to the user’s intended
function. Pro reaches 90.2% on SSP’s icon targets, followed by Mini at 88.6% and Nano at 55.0%.
The difference persists within the most populous size band of 16–< 32 pixels, where Pro and
Mini both locate 89.0% of the 418 icon targets and Nano locates 53.1%. Their corresponding
text-target scores are closer at 94.6%, 94.1%, and 84.6%, respectively. Even after this coarse size
grouping, the gap between Nano and the larger models remains greater for icon targets than for
text targets.
This distinction helps explain why our data construction addresses both target geometry and
control meaning. The broad route retains the image coordinates, while documentation supplies
functional descriptions for specialized controls.
Figure 26 illustrates this construction with the Legato Slide control in Ample Bass P, a virtual
instrument hosted in FL Studio. Its articulation buttons encode different playing techniques
through small symbols, so the icon alone gives little indication of the requested function.
The construction record links this control to the manual’s Legato Slide description (Ample
Sound, n.d.) and generates the instruction Activate the Legato Slide articulation, retaining the
original target location.

6.8 NorthCUA-Ultrafast
Long computer-use tasks accumulate the latency of many successive model decisions. Some
decisions require open-ended content, but others reduce to choosing an operation and a control
already present on the page. Predicting these finite choices directly could remove the decoding
cost of routine actions. Jev provides a relevant interface for this purpose by answering structured
choice questions without generating their answers token by token (Almeida, 2026). We adapt
this idea to NorthCUA-Nano through NorthCUA-Ultrafast, which combines a choice head for finite
decisions with the original model’s generation path for open-ended outputs.
Figure 32 illustrates the resulting division of work. The classifier receives the task and recorded
interaction history, including page observations, screenshots, and action overlays. Candidate
controls are bound to the latest valid page observation for execution. One backbone forward
pass supplies the features used to score the operation and its applicable targets. A selected click,
hover, or checkbox change can then be converted directly into a tool call.

8
Limitations and Responsible Use
Generalization and coverage. NorthCUA operates across diverse applications, while unfamil-
iar software and changing interface conventions remain challenging. Documentation-guided
grounding expands the functional knowledge available during data construction, and skill- and
milestone-guided collection revisit workflows that ordinary attempts leave unfinished. Extend-
ing this coverage to new software and maintaining reliable execution as applications evolve
remain important directions for the experience pipeline.
Feedback and optimization. Executable verifiers and live-workspace inspection tie learning
feedback to the work actually produced. Feedback quality depends on predicate coverage and
the calibration of model judgments for open-ended content (Zheng et al., 2023). Controlled
verifier probes and evidence-linked judgments help check both. Long workflows also concen-
trate many decisions into a terminal outcome. More informative intermediate feedback could
improve credit assignment and help agents reach correct results with fewer unnecessary actions.
Responsible deployment. Isolated workspaces, explicit tool profiles, and retained execution
records provide controls for deployment. Operating real software also requires authorized
access, least-privilege credentials, and confirmation for consequential actions. External pages
and documents can carry indirect prompt injections (Debenedetti et al., 2024), motivating ad-
versarial testing appropriate to each application. Released materials should undergo licensing,
privacy, and credential review alongside the operational checks.
9
Conclusion
We presented NorthCUA, an integrated system for developing computer-use agents through ex-
perience at scale. By connecting the NorthCUA Harness, Experience Flywheel, and Staged Learn-
ing through shared tasks and outcome checks, the system supports learning from both verified
demonstrations and fresh policy interaction. Improved policies can return to the same infras-
tructure to collect further experience. Recursive self-improvement extends collection to diﬀicult
workflows by preserving useful procedures and verified milestones, allowing later attempts to
build on earlier progress.
Across six benchmarks, the Nano, Mini, and Pro family achieves state-of-the-art results among
open-source models in GUI grounding, desktop execution, and Web interaction. At 397B pa-
rameters, Pro outperforms the trillion-parameter general-purpose baselines on both grounding
benchmarks, OSWorld-Verified, and WebArena-Verified. Stage comparisons further show im-
provements in desktop and Web execution across all three model sizes following long-horizon
SFT and joint RL. Alongside these gains in task completion, NorthCUA-Ultrafast explores a com-
plementary route to faster decision-making.

Runtime and Admission Protocols
This appendix defines the runtime choices needed to interpret an interaction record, including
the observations presented to the policy, the tools available to each role, environment ownership,
and demonstration selection. The learning-side segment and update rules are consolidated in
Appendix E.5.
H.1 Runtime Configuration
A context profile determines which retained interactions enter each model call. The sliding vi-
sual profile counts the latest clean frame within its image budget and keeps textual action/result
records after image eviction. Other profiles replay visual history within a compaction epoch.
Text windows, image budgets, and semantic compaction are separate settings. The generic con-
text manager defaults to off. Shadow mode records decisions without applying them, and en-
force mode applies its configured policy.
Historical overlays mark issued actions on pre-action images, while the latest clean frame shows
the currently observed state. Text-only tools, including notes, do not add visual frames. A later
application change can require waiting or a fresh observation. After a timeout or failed refresh,
state inspection precedes retry. Web element references belong to the observed page state, and
failed refreshes invalidate affected aliases.
Compaction retains a structured account of the goal, constraints, supported facts, completed
work, failures, current state, open items, and artifact references. Summaries and notes carry their
temporal provenance and remain distinguishable from observations. The summary prompt,
protected recent interactions, trigger/target budgets, and failure policy determine the result-
ing input. Note categories are fact, correction, precaution, constraint, decision, and checkpoint.
Compatibility names map mistake to correction and plan/other to checkpoint. The exposed
schema, replacement behavior, and prompt budget control which notes remain visible.
Execution scopes and tool interfaces. A session binds the agent to its environment and re-
sources. A round tracks one request and execution budget, and a step records one policy-
decision and action-execution iteration. A step can contain several tool calls, so model deci-
sions, tool calls, and GUI interactions are different counts. The dispatcher validates declared
arguments before invoking local handlers or connected MCP tools and returns results to the
requesting step. Appendix H.2 specifies the model-facing interfaces. Runtime probes use a sep-
arate permission profile from actor tools.
Evaluator profiles and attribution. Evaluation binds a task and rubric to an evidence source, in-
spection permissions, budget, and report schema. The rubric-generation template requests three
to seven criteria. The Agent Kit desktop entry path can use a request-level fallback, while the
web profile supplies eight fixed criteria. The selected profile determines which criteria, weights,
applicability rules, and reward conversion apply. Report-format validation checks the report’s
structure.
Artifact tools inspect retained records. Live tools additionally require authorization and a dis-
patcher bound to the evaluated workspace. Artifact-only replay has no live device access. Read-
only probes are preferred. Shell inspection uses an allowlist, and state-changing GUI or browser

inspection requires explicit permission. The workspace remains reserved through required live
checks.
Actor credit depends on the state before evaluator intervention. Terminal evidence and evalua-
tor actions are therefore recorded separately. Inspection checks the submitted artifact or page
state. A potentially mutating check needs a procedure that preserves the original state, such as
a prepared evaluation copy. When that basis cannot be preserved, assessment uses retained evi-

terminal status.

I.4 Web Repair Evaluation Protocol
The recorded case in Figure 18 illustrates browser feedback and code repair. A controlled re-
pair comparison additionally fixes the issue set, starting patch, Coding Agent, test generator,
adjudicator, budgets, and protected acceptance conditions. Role-specific information remains
separate even when roles share model weights.
Each assigned issue begins with the nominated defect reproduced. Before a new condition or
patch is tested, browser storage, account/backend data, service-worker state, and external fix-
tures are restored. Intentional stateful test dependencies remain explicit. Reports bind the build,
reset state, test item, and attempt. Only evidence-supported product discrepancies justify a re-
pair.
Acceptance uses the common assigned issue set as its denominator, retaining tester noncom-
pletion. Infrastructure-invalid attempts follow the same bounded rerun rule, and unresolved
issues remain in the results. Final acceptance runs the submitted patch from a protected clean
state outside the repair loop, with its outputs withheld from further revision.
